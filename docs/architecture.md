# Internal Architecture

## System Overview

The Slack Channel Router is a two-way bridge between Slack and Claude Code sessions via Socket Mode + MCP HTTP (StreamableHTTP). The server loads the persona configuration (`config.json`) and holds one Slack connection per persona: a Socket Mode client plus a Web API client, built from that persona's own credentials file by the connection manager (`src/persona-connections.ts`). Each Claude Code session connects to its own MCP Server instance and is matched to one persona by its working directory.

## Module Map

```
cli.ts                          CLI entry point — start/stop/clean_restart subcommands. Reads the same configuration file the server loads (`resolveServerConfigPath`, state directory from `resolveServerStateDir`) through the persona loader `loadPersonaConfig`, and reads no Slack token (b.av2 SR-8.7, SR-10.2). `start` checks only that the config file exists, spawns the daemon and waits for its startup outcome (see [start command](#start-command)). `stop --stop-bots` and clean_restart share a `teardownBots(personas, exit_timeout)` closure that runs one pause/status/kill teardown per persona of the config (SR-11 Event 12), addressing each persona's instance directly as `cscb_<key>` (`personaInstanceId`); log lines name the persona as its JSON-quoted name with its key (`renderPersonaRef`). All file, spawn, clock and agent-director access goes through the injectable `CliDeps`.
└── server.ts                   Main entry point — HTTP server, per-persona Slack connection wiring. Embeds the SR-5.1 startup gate, SR-3.2 template install, the b.av2 SR-6.3 start sweep (`reconcileOrphans`, handed the persona config), SR-2.1 poller. At import it only computes the state paths (`resolveServerStateDir` / `resolveServerConfigPath`), loads `access.json` when `SLACK_ACCESS_MODE=static`, builds its injected-dependency objects and registers the SIGTERM/SIGINT handlers: it builds no Slack client, reads no token and creates no directory (b.av2 SR-3.1, SR-13.1). `main()` creates the state and inbox directories, installs E2's `unhandledRejection` handler (`createUnhandledRejectionHandler`, once), then loads the persona config through `loadStartPersonaConfig` (`config.ts`); a missing, unreadable, pre-persona or invalid file is fatal. Right after the load it installs `trustPatchPersona` (`trust-bootstrap.ts`) as the session manager's pre-launch trust patcher, before the template install, the Slack connections, `Bun.serve` and restart init, so no launch path runs unpatched, and hands the persona config to the persona-keyed consumers: the template install, the start sweep, the trust, JSONL-safeguard and Stop-hook start passes (startup steps 4a-bis, 4a-quater and 4a-ter), the start bring-up, restart (guards, backoff, cap, relaunch), the health-check work list, outage state, the per-persona notifier and the cron dispatcher. It builds one connection manager (`createPersonaConnectionManager`) whose event handler is the event router (`persona-event-router.ts`) and whose status listener (`composePersonaStatusListeners`) both flushes a persona's held notices when it comes up (`createPersonaUpFlushListener`) and tells the bring-up controller about every status change; the manager is closed on shutdown with `stopAll()`. Over the manager it builds the bring-up controller (`createPersonaBringUpController`, `persona-bringup-controller.ts`), whose launch after a successful retry is `spawnForPersona(persona, appliedConfig, false)`; shutdown cancels its retries with `cancelAll()`. Over the manager and the controller it builds the relaunch gate (`createPersonaRelaunchGate`, `canRelaunch`) and hands it to restart (`RestartDeps.canRestart`), the restart launch (`launchSession`) and the health-check work list (`buildPersonaWorkList`), so none of them touches a persona that is not up. At module scope it builds one up predicate (`isPersonaUp`, `createPersonaUpPredicate` over the manager view and the controller's `isUp`; false for every persona until `main()` builds the controller) and hands that same function to MCP session admission (`decideSessionAdmission` in `handleInitialized`), the permission poller (`PollerDeps.isPersonaUp`) and `/interject`, so every serving path reads one "is this persona up" state (b.av2 SR-6.4); `server.ts` holds no up-check logic of its own. The controller's `onLeftUp` is `createNotUpSessionDropper` over `dropPersonaSessionAndKeepAlive` (`dropPersonaSession` plus stopping the session's SSE keep-alive), so a persona that stops being up loses its registered MCP session and nothing else (see Session Lifecycle, Disconnection). Restart's delay (`getRestartDelay`) reads `session_restart_delay` only from the loaded persona config. `clientFor(key)` (`createPersonaClientLookup`) returns the persona's long-lived Web client from the manager while it is serving, and the bot-identity lookup (`createPersonaIdentityLookup`) its bot user and bot ID; both answer nothing before `main()` builds the manager. The same `clientFor` and the applied-persona lookup (`getAppliedPersona`) go to the notifier, the MCP tools, the permission poller, the event router's click path and the archive's per-persona name resolver. It builds the one persona-routing instance (`persona-routing.ts`) over `clientFor`, the persona config, the identity lookup, the per-persona archive writer and `getAccess()`. The kill, liveness and reconnect adapters address a session as `cscb_<key>`; the kill adapter (`_buildKillSessionAdapter`) skips the kill while `isLaunchInFlight(key)` (see Auto-Restart step 4). The `/interject` route only wires the handler: it calls `handleInterject` (`interject.ts`) with the caller's address, the applied persona config, `isPersonaUp` and `getSessionByPersona`; the handler logic lives in that module. `isHttpVerbose()` (b.3k6) gates the per-request `/mcp` access line behind `CSCB_HTTP_VERBOSE` (truthy: 1/true/yes/on) — off by default, checked per request.

The persona loader (b.av2 SR-1) is the only loader; the pre-persona keys appear only in the conversion-error check (`PRE_PERSONA_KEYS`). `main()` calls `loadStartPersonaConfig(path, home?)`, which wraps `loadPersonaConfig` and turns a read failure (`PersonaConfigReadError`) into one message naming the path and saying the file does not exist or cannot be read and the server requires it to start; the conversion error and every other load error pass through unchanged. Also exports `credentialsFilesToProtect(appliedPersonas, configPath, home?)` (b.av2 SR-5.2), which lists every applied persona's `credentials_file` plus every `personas[i].credentials_file` named by the config file currently on disk (read tolerantly and not validated; an unreadable or unparseable file adds nothing; never throws) for `assertSendable` to refuse.
    ├── persona-identity.ts     b.av2 SR-2.1 / SR-2.2 persona key rule and every identifier derived from the key. Key rule: a name of 1–40 chars drawn only from `a-z0-9_` is its own key; any other name is lower-cased, each run of other characters becomes one `_`, leading/trailing `_` are trimmed, the stem is truncated to 40 chars, and `_` plus the first 8 hex digits of the SHA-256 of the original name is appended (an empty stem leaves the 8 hex digits alone; max key length 49). Spawns carry the derived identifiers, and restart, the health check, outage state, server notices, the MCP session registry, the permission relay and inbound delivery (`persona-routing.ts`) are keyed by persona key.
    ├── persona-diagnostics.ts  b.av2 SR-10.3 persona diagnostic class labels and the broken-persona log line. Holds the closed label set as a type plus constants: `persona-start`, `persona-credentials-missing`, `persona-credentials-unreadable`, `persona-credentials-invalid`, `persona-credentials-refused`, `persona-slack-unreachable`, `persona-connection-lost`, `persona-connection-restored`, `persona-directory-missing`, `persona-directory-unusable`, `unclaimed-channel`, `persona-dm-dropped`; later Epics extend it. `unclaimed-channel` and the interim `persona-dm-dropped` are logged by the inbound pipeline (`persona-routing.ts`); see Data Flow, Inbound. `persona-connection-lost` is logged once when a connection that was up drops without the server closing it, and `persona-connection-restored` once when it is open again; failed reopen attempts in between log nothing, and a credentials error on reopen logs one `persona-credentials-refused` line instead of the restored line (the latch is `persona-slack-episodes.ts`). `formatPersonaDiagnostic` builds one `[slack]` line from the class, the entry position `personas[<i>]`, the persona as its JSON-quoted name with the key beside it (`renderPersonaRef` from `persona-identity.ts`), the JSON-quoted path when there is one, and the cause, with every control character and U+2028/U+2029 escaped so the line is always one line. `personaCheckFailure` wraps that line into the failure result both checks below return, and emits it exactly once only when a logger is injected. Pure (b.av2 SR-13.1): no file-system, environment or console access, nothing at import. The lines never go to `startup-errors.log`. In the running server they are emitted by the bring-up controller (`persona-bringup-controller.ts`: the `persona-start` line, the credentials and working-directory check lines and the directory cleared line), by the connection manager and by `persona-routing.ts`. The bring-up lines are listed under Logging, Persona bring-up lines.
    ├── persona-credentials.ts  b.av2 SR-1.4 persona credentials-file reader, step 1 of the SR-6.1 bring-up. The file has a fixed shape: a JSON object with exactly two string keys, `bot_token` (prefix `xoxb-`) and `app_token` (prefix `xapp-`); each value has at least one character after its prefix and contains no whitespace or control character. `checkPersonaCredentials` finds it locally valid when it exists, is readable, parses and has that shape, and its real path is no other applied persona's credentials file. Checks run in this order: a real-path collision (`resolveRealPath`, lexical fallback) with another applied persona's credentials file makes the persona credentials-broken as `persona-credentials-invalid`, naming the other persona, and is checked first so the other persona's tokens are never read; a missing path (ENOENT/ENOTDIR) is `persona-credentials-missing`; the path is then opened once, read-only and non-blocking (following symlinks), so opening a FIFO never waits for a writer, and the type check and the read both go through that one descriptor, so the file checked is the file read; anything but a regular file (a directory, FIFO, socket or device) is `persona-credentials-unreadable` and is never read, so a FIFO cannot block the read and a device cannot feed it for ever; the descriptor is always closed, and a close failure is ignored; permission denied or any other open, stat or read error is also `persona-credentials-unreadable`; content that is not JSON, not an object, lacks a key, has a non-string or wrongly prefixed value, a value with nothing after its prefix, a value containing whitespace or a control character, or any extra key is `persona-credentials-invalid`, with every problem listed. Causes name a bad token by its key and rule only; a parse failure is described generically and extra keys are counted, not named. Success returns a `PersonaSlackTokens` value that redacts itself when JSON-serialised, string-converted or inspected. All file access goes through an injectable seam (`openFile`, `fstatFile`, `readFileFd`, `closeFile`, `realpath`), with the real file system as the default; the names differ from the working-directory check's `stat` and `access` so an override of one in the combined bring-up seam never reaches the other. Nothing runs at import, and it reads no environment variable, writes nothing and checks no file mode. It is the server's only token source: step 1 of each persona's start bring-up (`checkPersonaLocalSteps` in `persona-start.ts`, run by the bring-up controller), which hands the tokens to the connection manager. It is read once per persona at start; bring-up retries reuse that read.
    ├── persona-bringup.ts      b.av2 SR-6.1 steps 1 and 2 as pure checks. `checkPersonaWorkingDirectory` (step 2) requires the working directory to exist, be a directory (after following symlinks), be readable and searchable, and have a real path that is no other applied persona's working directory. A missing path is `persona-directory-missing`; anything else, including a real-path collision (named with the other persona), is `persona-directory-unusable`. It reads no credentials file, so a dry-run bring-up can call it alone. `checkPersonaLocalBringUp` always runs both the credentials check and the directory check before returning, so when both fail both causes are reported: it returns both outcomes plus the failure list (credentials first) and, with an injected logger, emits each failure line exactly once. It reuses `persona-credentials.ts`'s real-path collision and errno helpers rather than duplicating them. No Slack or agent-director call, no environment access, no writes, no timers, nothing at import; file access goes through an injectable seam (stat, access, realpath), and the combined check's seam also covers the credentials check's descriptor-based open, stat, read and close. The server runs them as steps 1 and 2 of each persona's start bring-up (`checkPersonaLocalSteps` in `persona-start.ts`, called by the bring-up controller): the combined check normally, the directory check alone in dry run. The controller also calls `checkPersonaWorkingDirectory` alone for each directory re-check.
    ├── persona-slack-validation.ts  b.av2 SR-3.2 classifier for a persona's Slack token validation: `auth.test` checks `bot_token`, opening Socket Mode checks `app_token`. Three outcome classes: up, Slack-unreachable (retried for ever with backoff) and credentials-broken. `botIdentityFromAuthTest` returns up only when `auth.test` gave both the bot user ID and the bot ID (SR-3.1); a result lacking either is Slack-unreachable. `classifySlackValidationError(error, check)` maps a thrown or rejected value to one of the two failure outcomes. Slack-unreachable (`persona-slack-unreachable`) covers a network, DNS or request-timeout error, a non-200 HTTP status (429 included), a rate-limited error, a `start()` whose WebSocket phase was abandoned after 10 s (the `SlackStartTimeoutError` marker, SR-3.3), no WebSocket URL, a socket closed before `hello`, any other Socket Mode error, any unrecognised value, and a `PlatformError` of `internal_error`, `fatal_error`, `service_unavailable`, `request_timeout` or `ratelimited`. A `PlatformError` whose Slack error code is missing, empty or not a short lower-case identifier is also Slack-unreachable (reason `unknown`): the library builds such errors itself from a 200 answer that isn't JSON, such as a proxy page. Only a `PlatformError` carrying a well-formed Slack error code outside those five is credentials-broken (`persona-credentials-refused`), carrying the key and the Slack error code. The "no WebSocket URL" reason applies only to the library's plain, code-less error from the Socket Mode open; any other code-less failure is reported as an unrecognised failure (reason `unknown`, still Slack-unreachable). An unreachable outcome carries a reason kind, plus the HTTP status, the transient Slack error code or `retryAfter` where they apply. Library errors are recognised by their `code` field, never by `instanceof`, so stub errors classify the same way. The classifier never throws. Waits come from `persona-retry-schedule.ts` (5 s doubling to 300 s, no cap, never shorter than `retryAfter`) and log lines from `persona-slack-episodes.ts`. Pure and injectable (SR-13.1): no timers, clock, Slack client, I/O or environment access, nothing at module scope. The connection manager (`persona-connections.ts`) calls it for every attempt.
    ├── persona-retry-schedule.ts  b.av2 SR-3.2 backoff for the Slack-unreachable class. `createPersonaRetrySchedule` returns one independent schedule per persona and retry purpose; it holds only its own failure count. `nextDelayMs(retryAfterSeconds?)` records a failure and returns the next wait in milliseconds: 5 s doubling to a 300 s ceiling (5, 10, 20 … 300 s), with no attempt cap. When a `retryAfter` is given the wait is never shorter than it, clamped only at the largest delay a JavaScript timer honours (about 24.8 days). `reset()` returns to 5 s once the cause clears. The arithmetic is `backoff.ts`'s stateless `doublingBackoffDelay`; the session-restart counters (keyed by persona key), 900 s ceiling and 5-failure cap are not used. Returns waits only: no timers or clock, so the caller schedules through its injected timers (SR-13.1). The connection manager (`persona-connections.ts`) keeps one per persona for bring-up retries and Socket Mode reopens, and the bring-up controller (`persona-bringup-controller.ts`) one per persona for working-directory re-checks; later Epics (destination retries) consume it too.
    ├── persona-slack-episodes.ts  b.av2 SR-10.3 cause-start / cause-clear latch for Slack validation log lines, so `persona-slack-unreachable` is logged when the cause starts and when it clears, not on every attempt. `createSlackEpisodeTracker` takes one persona (name, key, entry position, credentials-file path, optional logger) and `record(outcome)` returns the lines it produced. An episode is a run of outcomes of one class. When an episode starts it emits one line (`persona-slack-unreachable`, or `persona-credentials-refused` naming the key, check and Slack error code). When it ends, because the persona comes up or the class changes, it emits one cleared line with the same class label and a cause starting `cleared: `. A change of reason within Slack-unreachable stays in the same episode. A third episode kind, connection lost, opens when a connection that was up drops: it emits one `persona-connection-lost` line, absorbs every Slack-unreachable reopen outcome without a line, and closes with one `persona-connection-restored` line when the persona is up again; a refusal during it ends it silently and emits the `persona-credentials-refused` line in place of the restored line. Lines are built by `formatPersonaDiagnostic` from the outcome's own fields; with an injected logger each is emitted exactly once. No module-scope state or timers, so two personas' trackers are independent. The connection manager (`persona-connections.ts`) drives it, one tracker per persona, and is the only emitter of these lines for its personas.
    ├── persona-slack-clients.ts  b.av2 SR-3.3 / SR-13.1 Slack client factory and option sets for persona connections. Three client kinds, each built through the injectable `PersonaSlackClientFactory`: the long-lived Socket Mode client (app token); a short-lived validation Web API client used only for `auth.test` (bot token); and the long-lived Web API client every posting path uses (bot token), including `reply` uploads and `download_attachment`. Settings, in prose: library auto-reconnect is off on the Socket Mode client. The Socket Mode client's own Web API calls and the validation client make no retries, time out after 10 s and reject rate-limited calls instead of waiting. The long-lived Web API client times out each attempt after 30 s and keeps the library's default retry policy (ten retries with randomised backoff over about 30 minutes) and its rate-limit waiting. None of the three attaches the original request to its errors. Why: the library defaults reconnect and retry on their own (the socket client retries opening up to 100 times), set no request timeout, and attach the raw request error, Authorization header included, to request errors. Each option builder returns a fresh object, so no option object is shared between clients or personas. `PRODUCTION_SLACK_CLIENT_FACTORY` is the only place a token is handed to a Slack library, and it passes the token and options through unchanged. Also holds the 10 s `start()` bound and the 10 s / 30 s request-timeout constants. Nothing is constructed, read or logged at import.
    ├── persona-connection-errors.ts  b.av2 SR-3.3 / SR-10.3 token-safe description of thrown values and the process-level `unhandledRejection` handler. `describeThrownValue` renders any thrown or rejected value as one line holding only the constructor name (or the value's type for a non-`Error`), the `code` when it is a short identifier (letters, digits, `_`, `$`; a Slack token contains `-` and can never pass), and up to 10 stack frame lines after the message has been cut out of the stack. It never reads the message, `original`, headers, request config or `data`, never serialises the value and never throws. `describeSlackCallFailure` builds the tail of a failed-Slack-call log line: ` (reason=<reason>)` when the error carries a Slack platform error code that is a safe identifier (`slackPlatformReason`), then `: ` and the `describeThrownValue` description; the permission poller and click handler use it for every Slack-call failure line. `createUnhandledRejectionHandler(log)` returns a listener that logs one `[slack] unhandled rejection (process keeps running): …` line built with the describer and returns: it never throws (a throwing logger is swallowed), rethrows or exits, so one persona's stray rejection cannot take the process down. The module never installs it; `server.ts` installs it once with `process.on`, at the top of `main()`, before any persona connects. Pure: no module-scope state, no environment access, nothing at import.
    ├── persona-connections.ts  b.av2 SR-3.1 (module part) / SR-3.2 / SR-3.3 / SR-3.4 / SR-10.3 / SR-13.1 supervised per-persona Slack connection manager. Per persona, `createPersonaConnectionManager` validates, then connects: a short-lived validation client runs `auth.test` and is discarded, then one long-lived Web API client and one long-lived Socket Mode client are built. The three client kinds and their settings are in the `persona-slack-clients.ts` entry. A persona is up only once `auth.test` returned both the bot user ID and the bot ID and the socket's `start()` resolved. The manager bounds a bring-up's `auth.test` at 10 s on its injected clock (`SLACK_AUTH_TEST_TIMEOUT_MS`), because the validation client's own request timeout starts only once the connection is made and so does not cover a DNS or TCP-connect stall; on expiry the call is abandoned and the attempt is Slack-unreachable (`SlackAuthTestTimeoutError`, reason `timeout`). Each `start()` bounds its WebSocket phase at 10 s; one that never settles is abandoned and counts as Slack-unreachable, not broken. Slack-unreachable is retried with the `persona-retry-schedule.ts` backoff; a refusal leaves the persona credentials-broken. Reopen: when an up persona's socket drops and the manager didn't close it, the first reopen attempt is immediate and later ones use the same backoff; a credentials error on reopen leaves the persona disconnected and credentials-broken. Every event reaches the handler tagged with its persona's key, and a handler throw affects no other event or persona. All state lives in one entry per persona: no lock, queue or timer spans two personas, and no handling path reads another persona's connection. Dry run (SR-3.4) calls no factory method, needs no credentials and makes no Slack call: each persona is up at once with a distinct placeholder identity derived from its key (`dryRunPersonaIdentity`: `U000DRY_<key>` / `B000DRY_<key>`), and no Web API client exists. The Slack client factory, clock and timers are injected, as `createCronScheduler` takes its clock; nothing is created, read or scheduled at import. `server.ts` constructs one manager in `main()` with the event router as `onEvent`, the dry-run flag and a status listener composed of the up-flush listener and the bring-up controller's `onConnectionStatus` (reached through the module-scope `bringUps` holder, because the controller is built over the manager and so after it; the holder is set before anything connects), and each persona is brought up through the bring-up controller (`persona-bringup-controller.ts`) at start. Shutdown closes every connection with `stopAll()`.
    ├── persona-notifier.ts     b.av2 SR-7.1 / SR-7.2 per-persona server notices. `createPersonaNotifier({ getPersona, clientFor, isDryRun, log })` returns `notify(key, text, options?)` and `flush(key)`; neither throws or rejects. A notice goes only to the persona's destination (its `permission_prompts` channel), posted through the persona's own Web client from `clientFor(key)` as one top-level message with only channel and text, so it appears under the persona's identity. The notifier prefixes every body with `Persona "<name>" (key=<key>): `, so callers pass the key and the body only. Routing, in order: an unknown key logs one line and drops the notice; dry run logs the persona reference and the notice's first line, with no Slack call; a `dm` destination is logged with the full text, not posted and not held (DM notices arrive in E7); a channel destination whose persona has no serving client (`clientFor` returns undefined: not up yet, not brought up, or broken) is held in that persona's own queue in raised order; otherwise it is posted. A queue holds at most `MAX_HELD_NOTICES_PER_PERSONA` (20) notices, because a broken or retrying persona can go without a client for a long time: past the bound each new notice drops the oldest held one, which is logged (`[slack] persona-notifier: more than 20 notices held for <ref> — oldest held notice dropped, not posted: <first line>`) and never posted. `flush(key)` posts that persona's held notices in raised order once its client is validated and never touches another persona's queue; a notice raised for a validated persona that still has held notices posts after them. A failed post logs one token-safe line (`describeThrownValue`) and calls the notice's `onPostFailure` callback; there is no retry. Also exports `resolvePersonaDestination` (a persona's destination from `permission_prompts`: a channel with its ID, or `dm`), `formatPersonaNotice` (both also used by the permission poller for its prompts and stuck-prompt warning, which need the post's outcome and so do not go through `notify`), `firstNoticeLine` and `notifySafely` (calls an injected notify sink so that a throw or rejection goes to an error callback). Status → outcome: 200 `delivered`, 503 `no-session` (decision 1 — NO retry, no queue, no scheduleRestart), 404 `unknown-persona`, else/network error `http-error`. ## Data Flow
```

### Inbound (Slack → Claude Code)

Inbound delivery lives in `src/persona-routing.ts`. Each persona has its own Socket Mode connection (`src/persona-connections.ts`), and each connection's events reach the event router (`src/persona-event-router.ts`) tagged with that persona's key; `server.ts` only wires the router to the routing instance. The steps below run in code order, once per receiving persona P.

1. Slack message arrives on P's own connection (`message` or `app_mention` event). The event router logs `[slack] RAW <event> event persona=<P's key>: <first 300 chars of the event JSON>` and calls `receive(event, ack, <P's key>)`: P is the only receiver. Two personas in one channel each receive the event on their own connection, and each runs its own pipeline.
2. **Intake.** `receive` acks the event first; an ack failure is logged and handling continues. Then, for the receiving persona P (the intake also accepts a key list, each run concurrently), the archive is written and P's pipeline runs. The archive write is unconditional and comes before dedupe and any decision; it is keyed by (channel, ts), so a message received by several personas, or received twice by one, is stored once (see `src/message-archive.ts`). Each persona's run is isolated: a throw is logged as `[slack] persona-routing: error handling event for persona <ref>` with a `describeSlackCallFailure` tail and never stops another persona's run.
3. **Dedupe** (b.av2 SR-4.1). P's own dedupe store (`src/inbound-dedupe.ts`) records the event's (channel, ts). A key P first saw less than 10 minutes ago (`INBOUND_DEDUPE_RETENTION_MS`) is a duplicate and stops here: no decision, dispatch, reaction, recovery, post or log line. This collapses the `message` / `app_mention` pair Slack sends for a channel @mention and any Slack redelivery (for example after a reconnect). The window runs from the first sighting; a duplicate does not extend it. Expired keys are pruned lazily on each new record, with no timer. An event missing its channel or ts is not keyed and carries on as new. The routing instance keeps one store per persona key, created on first use, so it survives a reopen of P's connection; the stores are in memory only and are empty after a server restart.
4. **Decision** (`decideDelivery` in `src/delivery-decision.ts`, pure; see its Module Map entry). A key that is no applied persona first logs `[slack] persona-routing: no applied persona with key=<key> — event not delivered to it`. The decision runs against P in b.av2 SR-4.2 order:
   1. A subtype other than `file_share`, `bot_message`, `thread_broadcast` or `me_message`, or no channel, is dropped. An event with neither `user` nor `bot_id` is dropped as `no-author`.
   2. P's own messages (author `user` = P's bot user ID, or the event's `bot_id` = P's bot ID) are dropped. This self-exclusion is the only author filter: posts by people, bots, integrations, webhooks and other personas are delivered by the rules below, and nothing counts, throttles or arbitrates exchanges between personas.
   3. DMs (`channel_type` `im`) are dropped and log one interim `persona-dm-dropped` line naming the conversation, whatever `dm.enabled` says (E6 delivers DMs).
   4. A channel P is not configured into is not delivered. When no applied persona lists the channel, one `unclaimed-channel` line names the channel and P; when another applied persona lists it, nothing is logged.
   5. A `delivery: all` channel delivers.
   6. A `delivery: mentions` channel delivers when the text contains P's user mention (`<@P>` or `<@P|label>`) or `<!here>` / `<!channel>` (with or without a label); `<!everyone>` and user-group mentions do not count.

   A delivered message carries `via`, how it reached P; the first match wins: `dm`, `mention`, `broadcast`, `receive_all_shared` (a `delivery: all` channel that at least one other applied persona also receives with `delivery: all`), `receive_all`. No channel event produces `dm`; E6 does.

   The two classed lines are built by `formatPersonaDiagnostic`, e.g. `[slack] unclaimed-channel: personas[<i>] "<name>" (key=<key>): message in channel <C…> not delivered: no applied persona lists this channel` and `[slack] persona-dm-dropped: personas[<i>] "<name>" (key=<key>): direct message in conversation <D…> dropped: DMs are not delivered yet, whatever dm.enabled says`. The other drop reasons log `[slack] persona "<name>" (key=<key>) dropped message from channel=<C…> user=<U…>: <reason>`, with `bot_id=<B…>` in place of `user=` for an author without `user`. No drop line carries message text.
5. **Session lookup.** P's session is looked up with `getSessionByPersona(P's key)`. With no registered, connected session the message is dropped (`[slack] No live session for persona <ref> chat_id=<C…> — dropping message`) and the b.kvq no-session branch runs (step 8).
6. **Ack reaction.** The author's name is resolved through P's client; an author without `user` (a webhook or `bot_message`) is labelled from the event itself (`username`, else `bot_profile.name`, else its bot ID) with no Slack call. If `ackReaction` is set in `access.json`, the reaction is added through P's client and `trackAck(channelId, messageTs)` records it for later removal; with no client for P (dry run, or P not serving) it is skipped.
7. **Stream check.** The dispatch line `[slack] Dispatching to persona <ref> chat_id=<C…> cwd="…" mcpSessionId=… hasGetStream=… connected=… text="<first 80 chars>"` is logged. If the session has lost its `_GET_stream` (`hasSessionStream(key)` false), `notification()` would vanish silently, so it is not sent: `[slack] DROP: no _GET_stream for persona <ref> chat_id=<C…> …` is logged and the b.9cj streamless branch runs (step 8).
8. **Lost message** (b.kvq / b.9cj). The message is never delivered or replayed. `decideLostMessageRecovery(key, session_restart_delay)` applies the shared guards, keyed by P: a restart already pending or active → says the session is restarting; auto-restart disabled (`session_restart_delay: 0`) → says it will not self-recover and an operator must restart the server; P at the failure cap → the same, naming the restart-failure limit; otherwise it calls `scheduleRestart(key, cwd, undefined, { humanTrigger: true })` (P's `working_directory` in the no-session branch, the session's `cwd` in the streamless branch) and says the session is starting (no-session) or restarting (streamless). The reply is posted to the source conversation through P's client; a failed post is logged and not thrown, and with no client for P one line is logged and nothing is posted.
9. **Delivery.** P's session's MCP Server sends `notifications/claude/channel` to its Claude Code client, with P's own mention token (`<@P>` or `<@P|label>`) stripped from the text; other mentions and broadcasts stay. Only P's session receives it. The meta, rendered by the harness as attributes of the `<channel>` tag, is `chat_id` (the source conversation), `message_id`, `user` (the author label from step 6), the author's `user_id` (or, for an author without `user`, its `bot_id`; never both), `ts`, `via` from step 4, `thread_ts` when present, and `attachment_count` / `attachments` when the message has files.

Injected messages (`/interject` and cron, which posts through `/interject`) do not come through this pipeline. Their meta is unchanged, `user` and `ts` only, with no `via`; see [POST /interject](#post-interject).

### Outbound (Claude Code → Slack)

1. Claude Code calls MCP tools (`reply`, `react`, `edit_message`, etc.)
2. The tool handler resolves the calling persona at call time from the session's registered persona key (`SessionToolDeps.getPersona`). A session not yet matched to a persona, or whose key is no applied persona, gets a tool error.
3. `checkPersonaTarget()` checks the tool's target (`chat_id`, or `channel` for `fetch_messages`) against the persona's configured channels. Anything else is refused with a tool error naming the persona and the target, before the dry-run branch and with no Slack call. `reply` also runs `assertSendable()` on every file before any Slack call, and again on each file right before its upload so a file swapped in between is still caught; a refused file is a tool error.
4. The tool resolves the persona's own Web client at call time (`SessionToolDeps.clientFor`: the connection manager's long-lived client for that persona while it is serving; see `persona-start.ts`) and makes the Slack call with it, `reply` uploads (`filesUploadV2`) included, with no username or icon override. `download_attachment` authorises file fetches with that client's bot token, sent only to `https://files.slack.com` URLs. It refuses external (non-Slack-hosted) files and never follows a redirect off that origin with the header. A Slack call failure is logged token-safely and returned as a tool error naming the persona. A missing client or token is also a tool error.
5. After the first chunk posts, if `message_id` was provided and `consumeAck(channelId, messageTs)` finds a tracked entry, the ack reaction is removed via `reactions.remove`

### Slack Reply Guard (Stop hook)

`stop-hooks/slack-reply-guard.sh` runs in every bot session whose config dir the bootstrap patched (startup step 4a-ter). It reads the transcript once with a single `jq` pass and fails open (exit 0) on any error, missing input, or missing `jq`.

1. **Retry pass-through.** `stop_hook_active=true` exits 0 immediately, so the reminder fires at most once per turn.
2. **Trigger run.** A real user entry has `type=="user"`, is not `isSidechain` or `isCompactSummary`, and has at least one text block. The run is every real user entry after the nearest non-sidechain assistant entry preceding the latest real user entry. Claude Code can write queued channel messages as consecutive user entries, so the run can hold several. Tool-result-only entries, sidechain entries, and compaction summaries neither join nor end the run.
3. **Envelope.** Only an opening `<channel …>` tag at the very start of an entry's text (after optional whitespace) is an envelope; a tag later in the text is quoted body and is ignored. The envelope is Slack iff its `source` starts with `slack`. Attributes are read by name.
4. **Injected check.** A Slack envelope is injected if `user` starts with `cscb-cron:` or `ts` is present and does not match `^[0-9]+\.[0-9]{6}$`. Slack event timestamps always have six fractional digits; `/interject` stamps `String(Date.now() / 1000)`, which has at most three. The `/interject` `user` is a caller-supplied label, so `ts` shape is the identifying signal. An envelope with no `ts` counts as real Slack. No real Slack envelope in the run → exit 0.
5. **Reply check.** An assistant `tool_use` named `mcp__slack-channel-router__reply` anywhere after the earliest real Slack entry in the run → exit 0. Because the whole run is checked, an injected message queued right after a human's Slack message does not hide it.
6. **Reminder.** Otherwise exit 2 with a declinable reminder on stderr naming the provenance from the `chat_id` of the last real Slack envelope in the run: an ID starting with `D` gets the direct-message wording (`conversation <chat_id>`), any other Slack-shaped ID gets the channel wording (`channel <chat_id>`), and a missing or non-`^[A-Z0-9]+$` `chat_id` gets the channel wording without the parenthetical. README.md shows the direct-message and channel texts.

The envelope is rendered by the Claude Code harness from the MCP notification's `meta`, so the tag name and the attribute names (`chat_id`, `message_id`, `user`, `user_id`, `bot_id`, `ts`, `via`, `thread_ts`) are a harness-owned contract. Delivered Slack messages now carry `via`, but the guard doesn't read it: its injected check is unchanged until E10. The injected check also couples the guard to two CSCB-side formats: the `cscb-cron:` sender prefix (`src/crontable.ts`) and the `/interject` `ts` form (`src/interject.ts`). Injected envelopes carry no `chat_id`. Changing `/interject` to emit a six-decimal `ts` would make every non-cron `/interject` turn trigger the reminder.

### Permission Relay (SR-2)

Driven by polling against the agent-director Client + Block Kit click → `decide()`. The previous HTTP long-poll + hook script architecture has been deleted. Per-row Slack prompts: N concurrent `tool_use` blocks in one Claude Code assistant response produce N Slack messages, each independently allow/deny-able.

#### Wire surface (paired AD release)

CSCB consumes four AD verbs:

- `client.list({ state: ['check_permission'], label: ['service=cscb'] })` — returns spawn rows in the permission state.
- `client.get({ claude_instance_id })` — returns the row plus a plural `permission_requests` projection. Each element carries `request_token`, `request_id`, `tool_name`, `tool_input`, `requested_at`. The array may be empty (spawn has no open prompts). `null` / `undefined` in the slot is non-conforming.
- `client.decide({ claude_instance_id, decision, request_token })` — JSON snake `request_token`, CLI `--request-token`. Always required; absence yields `ErrInvalidFlags`. The wrapper `decideWithToken` in `agent-director-client.ts` is the single decide-wire serializer (SR-7.2).
- `client.getPermission({ request_token })` — single-row read, no state filter. Returns full PermissionRequestInfo plus `decision`, `decision_reason`, and `decided_at`. Not-found surfaces as `ErrPermissionRequestNotFound` (matched via `isErrPermissionRequestNotFound`).

#### In-memory state (SR-1)

`livePermissions: Map<string, LivePermission>` keyed on a composite `(claude_instance_id, request_token)` encoded by `makeCompositeKey` (null-byte separator — neither component can contain `\x00`). One entry per outstanding Slack prompt. `LivePermission` carries `claudeInstanceId`, `requestToken`, `personaKey` (the persona whose client posted the prompt; closing updates go through it), `channelId` (the channel the prompt was posted to), `messageTs`, `requestId` (log-only — never used for routing, keying, action-id encoding, or decide-wire payload per SR-1.4), and a `handled` flag. Lifecycle helpers `getLivePermission(cid, token)`, `markHandled(cid, token)`, and `dropPermission(cid, token)` all operate on the composite key. The tick is the sole owner of `dropPermission`; the click handler may only call `markHandled` (SR-1.2).

#### Per-tick flow (SR-2)

1. `list()` → spawns currently in `check_permission`.
2. For each spawn, resolve the persona from the row's `persona` label through the applied persona set (`PollerDeps.getPersona`, read every tick; b.av2 SR-7.1). The `channel` label is never read. A row with no `persona` label logs `[slack] permission-poller: spawn <id> has no persona label — skipping`, and one naming no applied persona logs `[slack] permission-poller: spawn <id> names no applied persona (persona=<key>) — skipping`; either is skipped this tick with no `get`. A spawn naming a persona that is no longer applied is treated like a non-conforming spawn (step 3): its live entries are exempt from the closing sweep and its wedge state is kept, since its requests may still be open in agent-director. A spawn with no `persona` label gets no such exemption. A spawn whose persona is applied but not up (`PollerDeps.isPersonaUp`, the server's shared up predicate; b.av2 SR-6.4) is skipped with no `get`: nothing is posted under any identity, its instance keeps running, and its wedge detector gets no tick. Its live entries are exempt from the closing sweep and its wedge state is kept, whether or not its spawn is listed this tick, because its requests are still open in agent-director. On the first tick after the persona is up its rows are read again: a prompt opened while it was down posts then, and a tracked prompt that closed meanwhile gets its verdict through step 5. The skip emits no trail event and no `cscb.poller.row_decision`. It logs once when it starts, `[slack] permission-poller: persona "<name>" (key=<key>) is not up — skipping its rows and holding its tracked prompts until it is up`, and once when it ends, `[slack] permission-poller: persona "<name>" (key=<key>) is up again — polling its rows again` (or `[slack] permission-poller: persona=<key> is no longer applied — no longer skipping its rows` when the persona left the applied set). Then `get()` returns the plural `permission_requests` projection, inside `withOutageDetection` keyed by the persona key.
3. Non-conforming response (`permission_requests` is `null` or `undefined`): log + skip processing for that spawn this tick. The spawn's existing live entries are excluded from the closure sweep below (no state mutation — SR-2.1). A spawn naming a persona that is no longer applied (step 2) gets the same exemption.
4. For each row in `permission_requests`, compute the composite key. If not in `livePermissions`, route it to the persona's destination (`resolvePersonaDestination` from `persona-notifier.ts`, the same rule the notifier uses):
   - **Channel destination:** emit the `post_attempted` row decision, post one `chat.postMessage` per row (no coalescing — SR-2.2) through the persona's own client (`PollerDeps.clientFor(key)`, the connection manager's long-lived client for that persona) to the destination channel, and insert one map entry.
   - **`dm` destination (until E7):** no Slack call, no `post_attempted`, no map entry. Logged once per open request: `[slack] permission-poller: "<name>" (key=<key>) has permission_prompts set to DM, and permission prompts by DM are not supported yet — prompt for <id> (tool=<tool>, request_token=<token>) logged instead of posted`.
   - **Client unavailable** (`clientFor` returns undefined; a persona that is not up is already skipped in step 2, so this is a guard for a persona whose connection stops serving between the two checks): no Slack call, no `post_attempted`, no map entry, so a later tick retries. Logged once per open request: `[slack] permission-poller: no Slack client for "<name>" (key=<key>) — prompt for <id> (request_token=<token>) not posted; retrying on a later tick`.

   The once-per-request record of an unposted prompt is forgotten when the prompt posts or the request is no longer observed (a spawn skipped this tick keeps its records); a changed reason logs again. If the composite key is already in `livePermissions`: no-op (duplicate-tick safe). An empty projection produces no posting activity but does not exclude the spawn's live entries from closure reconciliation. An empty projection also feeds the wedge detector (below).
5. **Set-diff closure reconciliation (SR-2.4):** `tokens_in_livePermissions − tokens_seen_this_tick = newly_closed_tokens` (with non-conforming spawns' entries protected per step 3, and a not-up persona's entries held per step 2). For each newly-closed token, call `getPermission(request_token)` inside `withOutageDetection` keyed by `entry.personaKey`. On success, render the verdict (below) via one `chat.update` against `entry.channelId` + `entry.messageTs` through the client of the persona that posted it (`clientFor(entry.personaKey)`), then drop the entry. When that client is unavailable, no update is made, `[slack] permission-poller: no Slack client for "<name>" (key=<key>) — closure update for <id> token=<token> (verdict=<tag>) skipped` is logged (`persona=<key>` in place of the name and key when the persona is no longer applied), and the entry is still dropped (agent-director has already closed the request). On `ErrPermissionRequestNotFound`: render generic deny, drop, do not retry. On transient error: leave the entry alive — the next tick retries.

#### Verdict rendering (SR-5)

The closure `chat.update` produces four visually-distinct surfaces driven by `decision` + `decision_reason`:

| `decision` | `decision_reason` | Rendering |
|---|---|---|
| `allow` | `null` | `*Permission* — Allowed` |
| `deny` | `'operator'` | `*Permission* — Denied by operator` |
| `deny` | `'timeout'` | `⏱ *Permission* — Timed out` |
| `deny` | `'find_missing'` | `🪦 *Permission* — Session ended` |
| anything else | anything else | `*Permission* — Denied (closed)` (fail-closed, log) |

`ErrPermissionRequestNotFound` collapses to the same generic-deny rendering (fail-closed log + drop, no retry). `decision_reason` is read verbatim from AD; CSCB does not derive, override, or infer it (SR-5.1). Unknown enum values do not crash the poller (SR-5.2). The `chat.update` targets only the closed row's `messageTs`; sibling rows are never touched in response to one row's closure (SR-5.3).

#### Click handler (SR-4)

`handlePermissionClick` decodes `(decision, claude_instance_id, request_token)` from the action_id and calls `decideWithToken(client, { claude_instance_id, decision, request_token })` unconditionally — this is the click's only AD interaction (SR-4.3). No `get` refetch, no "already decided" branch.

The click resolves through the receiving persona (b.av2 SR-7.1): `ClickDeps.receivingPersonaKey` looked up with `getPersona`. The click arrives on the owning persona's connection through its `interactive` event, and the event router (`src/persona-event-router.ts`) passes that connection's persona key, so a click that reaches another persona's connection is refused below. Parsing comes first: an action_id that does not parse returns `false` before any persona is resolved. After the `cscb.click_handler.invoked` event:

- A receiving persona that cannot be resolved is logged and the click is bypassed (no decide, no update): `[slack] permission-click-handler: cannot resolve the receiving persona (receiving key=<key>, claude_instance_id=<id>, action_id=<action_id>, request_token=<token>) — logging and bypassing this click. This is a CSCB bug — investigate.`
- A click whose instance ID is not the receiving persona's `cscb_<key>` fails closed — neither decided nor updated, so the request stays open until agent-director times it out: `[slack] permission-click-handler: click for <id> received for "<name>" (key=<key>) (instance cscb_<key>) — not deciding (request_token=<token>)`.
- Otherwise `decideWithToken` runs inside `withOutageDetection` keyed by the persona key, so click-path outage state is per persona, and every `chat.update` below (verdict and relay-fallen-back repaint) goes through that persona's client (`ClickDeps.clientFor`) to the channel and `ts` recorded on the live entry. When the client is unavailable, no update is made and `markHandled` is not called; one line is logged, `[slack] permission-click: no Slack client for "<name>" (key=<key>) — update for <id> (request_token=<token>, verdict=<tag>) skipped; the next poller tick reconciles the rendering`.

Decide outcomes:

- `ErrAlreadyDecided` → swallowed silently. The next tick's reconciliation (SR-2.4) owns the visible Slack state.
- `ErrRelayFallenBack` (b.qi1) → logged loudly, prompt message repainted, no session-level action. See the note below.
- `ErrInvalidFlags` / `ErrAmbiguousRequest` → logged once, no retry, no operator-visible signal.
- Unknown error types → logged, no retry.

On a successful decide *and* a live entry present, the handler renders one `chat.update` against just that row's `messageTs` (SR-4.5) carrying text byte-identical to the poller's SR-2.4 verdict surface — `*Permission* — Allowed` for allow, `*Permission* — Denied by operator` for deny — then calls `markHandled`. Matching the verdict text exactly means there is no visible flicker when the next tick's reconciliation lands on the same message. A stale click (no entry in `livePermissions`) still fires the decide call with the decoded token — AD is the source of truth and returns idempotent results — but produces no `chat.update` from the click path; the next tick's verdict rendering handles the message.

**b.qi1 `ErrRelayFallenBack` — loud surfacing, no session-level action.** agent-director 0.10.0 raises this from `decide` when the request's relay window has elapsed: Claude Code already gave up on the relay and re-asked at its own tmux pane, so AD refuses to record a verdict nothing will read. It is a *decide-path* error, not a spawn error — the spawn ladder in [Server-Managed Startup](#server-managed-startup-sr-11-event-1) cannot see it, and `handlePermissionClick` is its only reachable call site. The spawn itself is alive and healthy; only that one prompt can no longer be answered from Slack. The handler therefore logs a `[slack]`-prefixed line, emits `cscb.ad_decide.attempted{result_class:"ErrRelayFallenBack"}`, and — when a live entry is still present — renders one `chat.update` over that row's `messageTs` reading `*Permission* — relay window elapsed; answer this prompt at the session's tmux pane`, stripping the now-inert buttons, tagged `click_handler_relay_fallen_back`.

No delete, no respawn, no retry. Re-deciding fails identically (the window is already closed), and a respawn would destroy a healthy session over one un-relayed prompt while plausibly falling back again — the re-fallback loop the b.jgf delete+fresh policy would have walked into here. `markHandled` is deliberately **not** called: this is not a verdict and the AD request row stays open, so a later poller closure (timeout, `find_missing`, or the answer given at the pane) must remain free to render over the same message.

The Slack user id is intentionally NOT surfaced in the rendered text. An earlier draft of this design rendered "Allowed by <user>" / "Denied by <user>" as immediate operator feedback, but the SR-2.4 reconciler overwrites the message one tick later with the user-less verdict surface, producing visible flicker for the operator who clicked. The simpler, flicker-free design renders the verdict text on both the click path and the reconciliation path.

#### Wedge detector (b.fae F4)

A spawn can wedge permanently in `check_permission` with an **empty** `permission_requests` array: the underlying incident is a permission decision that AD recorded but could not deliver (the relay hook was killed before AD's poll deadline), leaving Claude Code blocked on a native TUI prompt with no open AD row and no hook that will ever fire again to advance state. To the poller this is a valid conforming response with zero rows, so before b.fae it was a silent no-op every tick — no log, no Slack message, no trail event ("the bot appears dead").

The detector counts consecutive ticks a spawn is observed in `check_permission` with an empty projection. The trip threshold is derived from the poll interval — `wedgeTripTicks(intervalMs) = max(5, ceil(90000 / intervalMs))`, roughly 90 s of wall-clock — because a genuine wedge takes minutes to develop while a normal decided-then-closing spawn passes through the empty state only briefly. The counter is reset **only on a positive observation** that the spawn is not wedged — open rows present, its state changed, or it's confirmed gone via `ErrSpawnNotFound`. A spawn skipped in a tick because of a transient `get` error or a non-conforming response does **not** have its counter reset, so a single flaky AD connection can't silently defer a genuine wedge alarm. A spawn whose persona is not up (b.av2 SR-6.4) is neither counted nor reset: its state is held, listed or not, until the persona is up.

On trip it logs `[slack] permission-poller: spawn <id> for "<name>" (key=<key>) wedged in check_permission with zero open rows for <n> ticks (~<s>s) — sending one-shot warning` and sends a **one-shot** warning to the persona's destination (b.av2 SR-7.2). The warning text names the persona: `Persona "<name>" (key=<key>): ⚠️ This persona appears blocked on a native Claude Code permission prompt …` (built with the notifier's `formatPersonaNotice`). For a channel destination it is one top-level message posted through the persona's client, and each post emits the `cscb.poller.wedge_detected` trail event. For a `dm` destination (until E7) the full text is logged instead (`[slack] permission-poller: "<name>" (key=<key>) has permission_prompts set to DM, and the stuck-prompt warning by DM is not supported yet — warning for <id> logged instead of posted: <text>`), with no Slack call and no trail event, and the episode counts as warned. A persona whose client is unavailable counts as a failed post, with no Slack call and no trail event (`[slack] permission-poller: no Slack client for "<name>" (key=<key>) — stuck-prompt warning for <id> not posted; retrying on a later tick`). Warning delivery is **fail-safe**: the `warningFired` latch is set **only after a successful `chat.postMessage`** (or the DM log line). If the post fails, the trail event still records the attempt (`ok:false`), `server.log` gets `[slack] permission-poller: wedge warning postMessage failed for "<name>" (key=<key>) (<id>)[ (reason=<reason>)]: <description>` (the tail is built by `describeSlackCallFailure`, below), and the poller retries the post on later ticks — throttled to one attempt per `wedgeWarnRetryTicks(intervalMs)` (~30 s of wall-clock, `WEDGE_WARN_RETRY_WALL_CLOCK_MS`) so a Slack outage can't storm the API at the poll interval — until one succeeds, after which the latch sets and the episode posts nothing further. The warning tells the operator to inspect the native prompt with `agent-director read-pane --claude-instance-id <id>` then kill and respawn the session; it explicitly does **not** offer `send-keys`, which AD's relay guard (`pkg/api/sendkeys.go`) hard-rejects while `relay_mode=on && state=check_permission`. The detector re-arms per spawn the moment it leaves the wedged condition (an open row appears, or the spawn disappears from the tick), so a later genuine wedge warns again. State is in-memory (`wedgeStates` map) and resets on daemon restart.

#### Action ID encoding (SR-3)

Block Kit buttons emit `action_id` strings of the shape `perm_(allow|deny)_<claude_instance_id>_<request_token>`, where `<request_token>` is a UUIDv4. The anchored decoder regex uses the UUIDv4 character class (`[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}`) as an outer-structure anchor — it disambiguates the rightmost boundary of the middle (underscore-bearing) `claude_instance_id` capture so embedded underscores in `cscb_<key>` remain safe. `<key>` is the persona key. CSCB does NOT validate the token's bytes; the regex shape only fixes the parse boundary (SR-1.3 + SR-3.1). The `request_id` field is no longer part of the action_id payload and is retained on `LivePermission` for logging only (SR-1.4).

#### Version pin (SR-6)

AD's library-side `Client.create()` reads `dist/version-floor.json` (`.min_binary_version`) and is the sole enforcement point for the runtime floor. The system-installed AD binary is probed by `resolveSystemBinary()`, compared against the declared minimum, and rejected via `ErrSystemInstallTooOld` (which the startup gate `instanceof`-matches → `ad-system-install-too-old` class label). CSCB's `package.json` caret on `agent-director` only governs npm resolution of AD's TypeScript shim; it does NOT participate in the runtime floor decision. The startup gate (`runStartupGate` in `src/agent-director-startup.ts`) is the sole compatibility boundary — no runtime code path degrades to the prior singular-projection or coalesced-prompt behavior on version mismatch (SR-6.2). The three new typed-error class labels are `ad-system-install-not-found`, `ad-system-install-too-old`, and `ad-system-install-unreachable`; see [Startup errors](../README.md#startup-errors).

Operators have an alternate diagnostic entry point via `bun run install-check` (`scripts/install-check.ts`). The script calls `runInstallCheck()` from `src/install-check.ts` — the same shared module the Epic-3 install-cscb skill consumes — and emits a single block on success or a class-labelled stderr block on failure. Beyond the three typed errors, the shared module surfaces `ad-version-floor-unreadable` when the AD package's `dist/version-floor.json` is missing, malformed, or lacks `.min_binary_version` (a packaging defect; remediation is to reinstall `agent-director` from npm, and the manual-skill-install block is intentionally NOT appended on this class).

#### API surface probe (SR-6.1)

A passing `Client.create()` proves only that the system-installed `agent-director` binary meets AD's declared `min_binary_version`. It does NOT prove the published npm package's TS shim is in sync with that binary — agent-director's `0.6.0` release shipped a stale shim whose `Client` dropped `getPermission`, whose `buildDecide()` dropped `--request-token`, and whose error catalog omitted three err_names CSCB branches on. Each defect fails silently at runtime (clicks resolve against the wrong row, error-envelope branches miss because the shim's `errorFromEnvelope` fallback constructs a base `AgentDirectorError` with `.errName` copied verbatim from the input rather than raising), so the gate runs three short-circuit probes after `Client.create()` resolves and before the same-user stat. The probes are dependency-injected via `StartupGateDeps` so tests can drive each failure path directly; the production defaults live alongside in `src/agent-director-startup.ts`.

| Probe | Default check | Failure `classLabel` |
|---|---|---|
| `probeGetPermission` | `typeof client.getPermission === 'function'` | `ad-shim-missing-get-permission` |
| `probeErrorCatalog` | Reads the resolved `agent-director` dist file and confirms each of `ErrInvalidFlags`, `ErrPermissionRequestNotFound`, `ErrAmbiguousRequest` appears as a word-boundary identifier in the bundled JS — same static-file approach as `probeDecideArgv` (a behavioral `errorFromEnvelope` round-trip cannot detect catalog drift because the shim's unknown-name fallback constructs a base `AgentDirectorError` with `.errName` copied verbatim from the input) | `ad-shim-catalog-incomplete` |
| `probeDecideArgv` | `import.meta.resolve('agent-director')` → `readFileSync` of the dist entry → string-contains `--request-token` (no subprocess, no state-DB write) | `ad-shim-decide-drops-token` |

On any probe failure, the gate closes the Client, records the operator-readable message to `startup-errors.log`, and exits non-zero — the same shape as the SR-6 version-pin failure. The remediation in every case is the same: reinstall a matching `agent-director` and confirm the resolved package actually carries the missing surface.

#### What this replaces

Three pre-Epic-4 mechanisms have been retired:

- The four-case per-spawn reconciliation matrix (and its sibling-stomping `updateNoLongerActive()` helper that edited a prior row's Slack message in response to another row's arrival) is gone. Sibling rows are now first-class state from the moment they appear in the plural projection.
- The click handler's prior get-then-stale-rerender branch (a refetch + "already decided" `chat.update` issued without calling decide) is gone. `decideWithToken` is the click's only AD interaction.
- The single-prompt coalescing of multiple concurrent `tool_use` blocks is gone. N parallel tool_uses → N Slack prompts.

AskUserQuestion is denied at the agent-director template (SR-3.1's `deny: ['AskUserQuestion']`) — the tool is unavailable to every CSCB-spawned bot and the prior `/ask` HTTP route + hook script have been removed.

The template also carries a narrow `allow` list (b.fae) pre-authorizing bot reads of their own persistent-memory directories. The rules are **derived per config** by `deriveMemoryReadAllowRules(personaConfig, home?)` rather than hardcoded. Each applied persona contributes its effective `claude_config_dir` (its own, else the top-level one, already resolved on the persona) — the directory `session-manager.ts` `buildSpawnParams` exports as `CLAUDE_CONFIG_DIR` at spawn. A persona with none uses Claude Code's default `<home>/.claude` (`resolveClaudeConfigDir`, home read at call time), and a config with no personas still gets the default-dir rule. The distinct dirs are de-duplicated and sorted, and one rule is emitted per dir:

```
Read(//<abs-config-dir>/projects/*/memory/**)
```

So a deployment whose personas use `~/.claude-infhub` and `~/.claude` yields those two rules, but a single-config or default-only deployment yields just one. Memory-note reads always require confirmation in Claude Code; without this rule they round-trip to a human as a native TUI permission prompt (the prompt class that wedged the relay in b.fae). **The scope is deliberately limited to `projects/*/memory/**` and must not be widened to the config-dir root** — that root holds live credentials (`settings.json` `ANTHROPIC_API_KEY`, `.claude.json` OAuth/token content), so a root-level allow would silently pre-authorize reads of billing credentials. The `//` prefix is Claude Code's absolute-path-from-filesystem-root anchor for Read rules.

### Scheduled Prompts (cscb_cron)

The server fires scheduled prompts from a crontable into personas once per minute. The flow crosses four modules — crontable → scheduler tick → dispatcher → the server's own `/interject` → cron log — and is driven entirely by `src/cron-scheduler.ts`'s single minute-aligned timer (decision 8; no per-job timers exist).

Managed sessions learn the crontable path via the `CSCB_CRONTABLE_PATH` export documented in the [Environment Variables](#environment-variables) section.

#### Wiring and startup

The scheduler is constructed and started in `main()` (`server.ts`) **after** `Bun.serve()` is listening, because it is its own `/interject` client — it must POST to a live listener. This is the opposite placement from `startPermissionPoller`, which starts before `Bun.serve`. It is wired on every start, dry run included: the configuration file is required, so there is no path that runs without it. The dispatcher is handed the server's ACTUAL bound port (`httpServer.port`, covering port-`0` configs), the config-resolved `cron_log_path` and `cron_table_path`, and a `resolveTarget` over the applied persona config (`resolvePersonaTarget(personaConfig, target)?.key`). Any construction or `start()` failure is non-fatal — the server keeps serving without a scheduler; `shutdown()` calls `cronScheduler.stop()` alongside `stopHealthCheck`/`stopPermissionPoller`.

`start()` runs, in order: (1) the crontable bootstrap — `ensureCrontableExists`, which this `start()` is the SOLE caller of; a missing crontable is created with the template header and an info line, and the scheduler proceeds with zero schedules; (2) the initial read + parse of the table through the same shared load path the tick's reload step uses, each parse error becoming one `parse-error` outcome line (identity/target `-`); (3) exactly one `scheduler started, N schedules loaded` info line — the PD-4 outage-window marker, since there is no catch-up, this line is the only bound on a missed-fire window; (4) arming the tick. `start()` is failure-isolated and never throws out to the server.

#### The tick (reload → match → dispatch)

The timer is a self-re-arming `setTimeout` chain aligned to the top of each minute (not `setInterval`), so ticks are serialized — a pass never overlaps the next, which is the property the hot-reload depends on: the in-memory table is swapped between whole passes, never mid-pass. Each pass, in decision-8 loop order: (1) re-load the crontable if it changed (see [Hot-reload](#hot-reload) below) — this step never dispatches and never re-arms the timer; (2) stamp the current wall-clock minute and skip the whole pass unless it is strictly after the last-ticked minute — the **monotonic guard**, so a backwards clock jump cannot re-fire already-fired minutes (matches Vixie cron), and, because it sits *after* the reload, also the protection against a double-fire across a reload — a minute already processed is never processed again, whichever generation of the table is in memory; (3) match every in-memory schedule against that minute in **server-local time** via croner (DST is croner's, D-Q3); (4) per match, consult the at-most-once `Map<schedule instance, epoch minute>` — keyed on the compiled-schedule instance (identity), NOT raw line text, so two identical operator lines are two distinct schedules that EACH fire (plain cron semantics, PD-6); only the SAME loaded schedule reappearing twice in one pass is skipped and logged as a loud `SCHEDULER BUG` info line, otherwise the instance is recorded and the match collected; (5) prune map entries older than the current minute. All matches for the minute are handed, in crontable line order, to the dispatcher.

**No catch-up (PD-4):** a tick fires only the minute observed at its start; if a pass overruns the next minute top, that minute is simply skipped — specified behavior, not a bug. A minute with no matches does nothing and logs nothing. The `(schedule instance, minute)` at-most-once assertion is a **logged bug signal**, not the dispatch mechanism — the minute-aligned single pass already makes a double-fire structurally impossible; because the key is the compiled-schedule instance rather than raw line text, two identical operator lines are distinct schedules that each fire (PD-6) and never trip the assertion — only the same loaded schedule firing twice in one pass does. The `SCHEDULER BUG` line is an info line kind, deliberately NOT an outcome class, so it never pollutes the `grep http-error` network-failure triage view. It is likewise not the cross-reload double-fire protection — that is the monotonic guard's job. There is NO rate cap, backlog cap, busy-detection, session-state check, or queue-depth throttle anywhere in the tick (owner gate answers 1-2).

#### Hot-reload

The crontable **file**, not the in-memory copy, is the runtime source of truth. Step (1) of each tick stats the crontable and compares `(mtimeMs, size)` for *inequality* against the last successful load — not ordering, so a backwards `touch` still reloads. Unchanged means no read, no log, no work. Changed means re-read, re-parse, re-compile, and swap the array; the swap only ever replaces the whole table, and it never dispatches and never touches the timer chain.

There is deliberately **no `fs.watch`, no watcher, and no dirty flag.** A swap can only take effect at a tick anyway, and a single-file watch drops the atomic-save rename that is the mandated write pattern, so a per-tick stat is both sufficient and cheaper to reason about. A successful tick reload writes one `crontable reloaded, N schedules` info line; `start()`'s initial load deliberately emits no such line (it has its own `scheduler started` marker).

Parse errors are logged **once per reload, not once per tick**, because the recorded stat is updated on every successful read — including a read whose content has bad lines — so an unchanged broken file stays quiet. A mid-write read needs no special handling: the parser is PD-6-tolerant, so healthy lines survive and keep firing, and the completed write is a further stat change the next tick picks up.

**Deleted file (D-Q1).** ENOENT drops to **zero schedules immediately** — nothing stale ever fires behind a deleted crontable — forgets the recorded stat, and emits a latched `crontable vanished … — 0 schedules until it is restored` warn-kind line. The warn kind is what distinguishes this from the first-install info line. The *next* pass attempts the re-create through `cron-bootstrap.ts`: an exclusive create, so if a human or a bot restored the file with content first, the bootstrap reports `already-exists` and that content loads intact; otherwise the empty template header is created (zero schedules) and logged with re-creation wording distinct from the first-install line. A persistent re-create failure stays silent — the vanish warn already latched the condition, and it must not repeat once a minute.

**Other stat/read failures.** Any non-ENOENT errno (EACCES, EIO, …) **keeps the currently loaded schedules firing** and emits one latched warn naming the cause and the schedule count. Because a failed load never updates the recorded stat, recovery (a `chmod`, say) is picked up by the next tick's inequality check, which clears the latch and logs the normal reload line.

#### The fire path (dispatcher → /interject → cron log)

For each match the dispatcher (`src/cron-dispatch.ts`) resolves the prompt path and reads the prompt FRESH at fire time (never cached — an edited prompt takes effect next fire), resolves the written targets to persona keys and deduplicates them, applies the D-Q5 pre-checks (skip, never truncate), and POSTs `{persona, message, sender}` (`persona` = the resolved key, or the target as written when it names no persona) to `http://127.0.0.1:<port>/interject`. `sender` is the schedule identity `cscb-cron:<prompt-file-basename-without-extension>` (D-Q4) — without it `/interject` defaults `senderLabel` to `interject` and a cron fire is indistinguishable from peer-bot traffic. HTTP status maps to outcome class: 200 → `delivered`, 503 → `no-session` (decision 1 — NO retry, no queue, no `scheduleRestart`; this includes a persona that is not up, which `/interject` answers 503 even while its instance runs, b.av2 SR-6.4), 404 → `unknown-persona`, any other status or a network failure → `http-error`. Every outcome plus one per-fire summary (`delivered`/`failed` counts) is appended to the cron log. A line with no persona list (all-bots) is matched but logged `fanout-deferred` and NOT dispatched — no read, no POST — with a `delivered=0 failed=0` summary; fan-out is not yet enabled.

**Same-minute matches deliver independently.** Each matched schedule is delivered on its own — its own freshly-read prompt, its own `/interject` POST with `sender` = its schedule identity, and its own outcome line and per-fire summary. When several crontable lines match the same minute for the same persona, each one arrives as its own message; they are not combined.

The cron-log outcome classes are defined once in [cron.log](#cronlog-cron_log_path) — the taxonomy there is authoritative; this subsection does not restate the class names.

**Bind constraint.** The scheduler POSTs to `127.0.0.1`, so a `bind` on a single non-loopback interface leaves no loopback listener and every fire fails connection-refused → `http-error`. `bind` must include loopback (the default `127.0.0.1`, or `0.0.0.0`) for scheduled fires to work. This is log-visible and accepted; no loopback detection is added.

## Session Lifecycle

### Connection

1. Claude Code sends POST to `/mcp` (no session ID) → `initPendingSession()` creates a pending session
2. MCP handshake completes → `server.oninitialized` fires → `handleInitialized()` waits for the session's SSE stream, then calls `roots/list`. An SSE stream that never opens, a failed `roots/list` and an empty roots list each disconnect the pending session through `closePendingSession` (`registry.ts`): the pending entry is removed, its SSE keep-alive stopped and its transport closed.
3. The first root's directory (tilde-expanded, made absolute) is matched by real path against the applied personas' working directories, and admitted only while that persona is up (`decideSessionAdmission` in `registry.ts`, over `matchPersonaByRootsPath` and the server's shared up predicate; b.av2 SR-6.3, SR-6.4). On a match to exactly one persona that is up, the pending session is promoted in place to the registered session for that persona key, with the real path as its `cwd`; a newer session for the same persona replaces the older one (logged as `Session replaced existing connection for persona …`). With no matching persona or an ambiguous match, the pending session is disconnected through `closePendingSession`, as in step 2.
   - **Persona not up (b.av2 SR-6.4).** When the matched persona is `broken` or `retrying`, or its Slack connection is not serving, the session is refused the same way (`closePendingSession`: removed from the pending map, its keep-alive stopped and its transport closed); it is never promoted or mapped, and a session already registered for that persona is left as it is. The instance sees its MCP connection close; nothing is done to the instance or its agent-director row. One line is logged per refused attempt, so each new connection attempt the instance makes while the persona is down logs again (the line is not rate-limited), with no token and no diagnostic class label: `[slack] Session refused: persona "<name>" (key=<key>) is not up (<reason>) — not registered; its instance is kept and may register once the persona is up`, where `<reason>` is `describePersonaNotUp`'s `<outcome>: <first cause>`, or `its bring-up has not run` / `its Slack connection is not serving`. A missing working directory still matches its own persona through `resolveRealPath`'s lexical fallback, so its instance is refused here rather than logged as unmatched. The instance registers once the persona is up: the launch that follows its bring-up (the start pass, or the launch after a retry) goes through the collision ladder, whose `waiting` and `working` branches send `/mcp reconnect` to the running instance, and whose `ended`/`missing` branches resume the row (Server-Managed Startup step 5). An instance the ladder leaves alone (`pending`, `check_permission`, `ask_user`) is picked up by the health check's alive-but-not-connected path, which reconnects it through restart.
   - **Every server start.** Admission reads the same predicate at start, so an instance that survived the previous server process is refused until its persona's bring-up finishes, healthy personas included: `its bring-up has not run` before the controller has started that persona, `its Slack connection is not serving` while its bring-up is in progress. Once the persona is `up`, the instance registers through the same two routes: the start pass's launch reaches its row through the ladder, which reconnects a `waiting` or `working` row, and a row in `pending`, `check_permission` or `ask_user` is reconnected by the health check.
4. Session receives the messages its persona's pipeline (`persona-routing.ts`) delivers from the persona's configured channels
5. A keep-alive timer is started (`startSseKeepAlive`) that writes SSE comment frames (`:ping\n\n`) every ~30 s to prevent idle connection drops from proxies or load balancers

### Server-Managed Startup (SR-11 Event 1)

Called from `main()` in `server.ts`. Before step 1, `main()` creates the state and inbox directories (nothing is created at import) and installs E2's `unhandledRejection` handler (`createUnhandledRejectionHandler`, once, before any persona connects), so one persona's stray rejection is logged token-safely as `[slack] unhandled rejection (process keeps running): …` and never takes the process down.

In `main()` the steps run in this order: 1, 2, 2a, 3, then the message-archive setup, outage state and notifier installation, the connection manager, step 7, `Bun.serve` with the PID file and the cron scheduler, `initRestart`, then 4, 4a-bis, 4a-quater, 4a-ter, 5 and 8. Step 6 is not a point in the sequence: it happens whenever a persona comes up. The steps:

1. **SR-5.1 startup gate** — `runAgentDirectorStartupGate()` awaits `createClient(opts)` (production injects `Client.create`), which runs AD's library-side discovery + floor enforcement against `dist/version-floor.json`. The opts carry `logger: makeFilteredAdLogger(console)` (b.brv) so the Client's per-poll `SubprocessClient: <verb> ok` success dumps are dropped from `server.log` unless `CSCB_AD_VERBOSE` is set — see [Logging](#logging). On success the gate installs the constructed Client into the singleton via `setClient(client)` so subsequent `getClient()` call sites resolve to it, and the success-arm `adVersion` is read from `client.binaryVersion`. The construct-step catch ladder `instanceof`-matches `ErrBunVersionTooOld` (→ `ad-bun-version-too-old`), `ErrSystemInstallNotFound` (→ `ad-system-install-not-found`), `ErrSystemInstallTooOld` (→ `ad-system-install-too-old`, message names detected + required versions), and `ErrSystemInstallUnreachable` (→ `ad-system-install-unreachable`, message surfaces AD's `err.reason` verbatim); the three `ad-system-install-*` branches append the `install-skill-pointer.ts` manual-skill-install instructions block to their `recordStartupError` output. CSCB no longer performs a post-Client floor check — AD owns it. Then runs the SR-6.1 API surface probes (`getPermission` presence, error-catalog round-trip, `--request-token` in the dist) and stats `~/.agent-director/state.db` against `geteuid()`. Failure writes to `startup-errors.log` and exits non-zero.
2. **PID conflict check** — existing `checkPidConflict(PID_FILE)` invariant. CSCB enforces one instance per host.
2a. **Configuration load (b.av2 SR-1.7, SR-8.7)** — `loadStartPersonaConfig(CONFIG_PATH)` reads `config.json` from the state directory (see Configuration, config.json). A missing, unreadable, pre-persona (the conversion error) or otherwise invalid file logs `[slack] Fatal: configuration error — <message>` and exits 1 here, before any port is bound, the PID file is written, a Slack connection opens or anything is spawned. There is no fallback. On success `main()` installs `trustPatchPersona` as the session manager's pre-launch trust patcher (`setPreLaunchTrustPatcher`), ahead of the Slack connections, `Bun.serve` and `initRestart`, so no launch path runs unpatched, and logs `[slack] Loaded persona config: <N> persona(s)`. `bind` and `port` come from the loaded config.
3. **SR-3.2 template refresh** — `installSlackChannelBotTemplate(personaConfig)` builds the SR-3.1 `MakeTemplateParams` and calls `client.makeTemplate({ ..., overwrite: true })`. Atomic replacement is the library's responsibility (sibling-tempfile + `rename(2)`). Fatal on rejection. It runs right after step 2a, over the loaded persona config.
4. **b.av2 SR-6.3 start sweep** — `reconcileOrphans(personaConfig)`, run before the trust patch and any spawn. `client.list({ label: ['service=cscb'] })` enumerates every CSCB spawn, and each row is judged by its `persona` label against the applied personas. A row is killed + deleted when any of these holds, checked in this order:
    - it has no `persona` label (`no persona label`) — this includes every row spawned by a build that predates persona labels, so the first start of this build replaces those bots with fresh spawns (their transcripts stay on disk, unresumed);
    - its `persona` label names a persona absent from the applied set (`absent persona`);
    - its instance ID is not that persona's `cscb_<key>` (`wrong instance ID`);
    - its `cwd` differs from that persona's working directory by real path (`wrong cwd`, via `compareRowToPersona`).

    Every other row is kept for step 5. **Unresolvable working directory (b.av2 SR-6.4).** When the persona's working directory has no real path (missing, not searchable, a dangling symlink) and the row's `cwd` has no real path either or equals the configured `working_directory` lexically (`compareRowToPersona`'s `cwdCheckDeferred`), the `cwd` condition cannot be evaluated and is deferred: the row is kept (the other three conditions still apply), with one line per persona, `[slack] reconcileOrphans: persona "<name>" (key=<key>) working_directory="<path>" cannot be resolved to a real path — keeping its rows; the cwd check is deferred to its launch`. Such a persona is not up (`retrying`, or `broken` when its credentials also fail; step 5), so its instance keeps running, unserved (Connection step 3, Permission Relay, `/interject`), and its row waits for the launch that follows the directory's return, where the ladder's `cwd` guard runs against the real path. A row whose `cwd` resolves to an existing directory elsewhere is swept as `wrong cwd` even while the working directory is missing, so a persona can't adopt another persona's directory; its launch then spawns fresh. A row whose `cwd` differs by real path from a resolvable working directory is swept as before. A `channel` label left on a row by an older spawn plays no part. Each removed row logs `[slack] reconcileOrphans: sweeping row (<reason>) persona=<persona> instanceId=<id> state=<state> — killing and deleting`, with ` cwd=<row cwd>` before the dash for `wrong cwd`; `<persona>` is `"<name>" (key=<key>)` for an applied persona, the raw label value for an absent one, and `<no persona label>` otherwise. A failed kill still attempts the delete. Kill and delete failures record `orphan-cleanup` (`kill failed for orphan instanceId=<id> persona=<persona>: <ErrName>`, likewise `delete failed …`) and a list failure records `orphan-cleanup-list-failed`; none blocks startup. Dry run skips the sweep and logs `[slack] dry-run: skipping orphan reconciliation`.
4a-bis. **b.uhv / b.k54 trust-bootstrap** — `trustBootstrap(personaConfig)` (from `src/trust-bootstrap.ts`) runs over the applied personas: for each persona's working directory it patches the `.claude.json` in the persona's effective `claude_config_dir` (its own, else the top-level one) so the Claude Code trust-folder dialog never appears at launch. Each persona is patched once, however many channels it lists. It reads `<dir>/.claude.json` and ensures `projects[<working_directory>].hasTrustDialogAccepted` and `projects[<working_directory>].hasCompletedProjectOnboarding` are both `true`. Idempotent: when both flags are already `true` the file is not rewritten (verifiable via unchanged `mtime`). Writes are atomic (`.tmp` + `renameSync`), and the read-modify-write is fully synchronous, so two personas sharing one config dir cannot lose each other's update. Soft-skip behavior: a persona with no configured `claude_config_dir` logs `[slack] trust-bootstrap: "<name>" (key=<key>) has no claude_config_dir — skipping` and continues without recording an error (Claude uses its own default; there is nothing to patch). A missing or unreadable `.claude.json` logs an info line and calls `recordStartupError('trust-bootstrap-config-missing', '"<name>" (key=<key>): cannot read <path>')` — the file is never auto-created. Malformed JSON records `trust-bootstrap-config-parse`, and any unexpected per-persona failure records `trust-bootstrap` (`unexpected error for "<name>" (key=<key>) cwd=<dir>`). The function never throws to the caller, so one bad persona cannot block the rest. Runs in both real and dry-run modes — it's a config-file patch, not a session operation. The call site is in `main()` right after step 4 (`reconcileOrphans`), before any spawn fires.

    - **Per-launch patch (b.av2 SR-6.2).** The same patch also runs before every launch: `trustPatchPersona(persona)`, installed as the pre-launch trust patcher, runs at the top of every ladder run — fresh spawn, resume or restart (see step 5 and Auto-Restart step 5). At launch time a patch failure is logged only, as `[slack] trust-bootstrap: pre-launch patch failed [<class>] <detail> — <cause>` with the same class names, and never adds a `startup-errors.log` entry; a missing `.claude.json` therefore logs two lines (the info line and the failure line). The start pass records failures as described above.
4a-quater. **b.zak JSONL-persistence safeguard** — `runJsonlPersistenceSafeguard(personaConfig, notify)` (from `src/jsonl-persistence-check.ts`), run over the applied personas. Call site: `main()` in `server.ts`, immediately after step 4a-bis (`trustBootstrap`) and before step 4a-ter (`stopHookBootstrap`) — critically, **before** step 5's resume path, which silently `delete+fresh`-spawns a memory-less bot when `resume` throws `ErrJsonlMissing`. Detection/reporting only: it never changes resume behavior, never throws, and never blocks startup (wrapped in its own `try/catch` at the call site as well). Every warning is a persona notice: the server passes the per-persona notifier's `notify`, which posts to the affected persona's destination, names the persona, and only logs in dry run. Sibling scope: the lost / never-created / inconclusive classification inside the resume path itself is **b.wrb / b.fwu**, not this module. Two layers:

    - **Layer 1 — non-persistent storage.** `checkJsonlPersistence` resolves the deduped set of the personas' effective `<claude_config_dir>/projects` roots (a persona with no configured dir uses `<home>/.claude`; with no personas at all, the home default root is checked) and classifies each root's mount fstype by longest-prefix match over `/proc/self/mountinfo` (string-prefix, not a stat — a not-yet-created dir classifies by its parent mount). A root on `tmpfs`/`ramfs` → `recordStartupError('jsonl-non-persistent', …)` plus one notice through the notifier to each affected persona's destination — those whose effective JSONL root is the flagged root, not every persona (resume is structurally impossible for those personas on this host). An undeterminable fstype (unreadable/unparseable/unresolvable) → `recordStartupError('jsonl-persistence-check-warning', …)`, no notice.
    - **Layer 2 — per-persona transcript loss.** For each applied persona it fetches the persona's AD row (through `withOutageDetection`, the sanctioned CSCB→AD entry point). A row the collision ladder will spawn fresh instead of resuming — its `cwd` differs from the persona's working directory by real path, or its `config_dir` label is missing or mismatched (`compareRowToPersona`, the same check as step 5's guards) — is not checked: one log line naming the persona, the mismatch (the row's `cwd` against the working directory, or the missing or changed `config_dir` label) and that the transcript was not checked because the collision ladder will spawn fresh, with no record and no notice. Otherwise, when the row carries a `claude_session_id`, it stats the AD-recorded `jsonl_path` **and** a config-dir-aware fallback path composed the same way agent-director composes it (`resolveJsonlPath`, under the persona's effective config dir). Outcomes: persisted exists → healthy, silent. Persisted stale/missing but fallback exists → `recordStartupError('jsonl-transcript-stale-path', …)` + a notice through the notifier to that persona's destination (history is on disk but AD 0.8.0's resume only stats the persisted path, so it would throw `ErrJsonlMissing` and wipe the persona's memory). Both missing → the `message_archive_db` archive (when configured) is consulted for evidence under the b.av2 SR-7.4 rule (`personaArchiveEvidenceScope`): only messages in the persona's `delivery: all` channels since `started_at` count, in one query over all of them. A persona with no `delivery: all` channel counts 0 without the archive being opened (even when none is configured), and since every persona has a channel or DMs on, that persona always takes (once `started_at` parses) the unattributable-zero path below. A count ≥1 → `recordStartupError('jsonl-transcript-lost', …)` + a notice to that persona's destination saying its conversation memory has been lost (conversation provably happened, transcript is gone). A zero count for a persona with any `delivery: mentions` channel or DMs on is not evidence of idleness, because the archive cannot attribute messages from `mentions` channels or DMs to a persona: one quiet log line saying the archive evidence is inconclusive (`UNATTRIBUTABLE_ZERO_REASON`), no record and no notice. The archive check is read-only: a missing archive DB file yields no evidence (it is never created here). Both missing with no archive evidence → a single quiet log line only: a persona idle since spawn has no transcript yet because Claude creates the `.jsonl` lazily on first message — normal, not an error, and must not alarm every boot. Log lines name the persona as `"<name>" (key=<key>)`. Per-persona AD/get errors (including `ErrSpawnNotFound`) are logged and skipped; the sweep never aborts.
4a-ter. **b.osj stop-hook bootstrap** — `stopHookBootstrap(personaConfig)` (from `src/stop-hook-bootstrap.ts`) patches `<claude_config_dir>/settings.json` for every applied persona's effective config dir to install (or remove) the CSCB-managed Slack Reply Guard Stop hook. Call site: `main()` in `server.ts`, immediately after step 4a-quater (`runJsonlPersistenceSafeguard`) and before step 5 (`startupSessionManager`) — before any spawn fires. Runs in both real and dry-run modes (config-file patch, not a session operation). Never throws to the caller; per-dir failures are caught and recorded via `recordStartupError`. Behavior:

    - **Grouping / aggregation (SR-3.5).** The applied personas are grouped by the real path of their effective `claude_config_dir` (the persona's own, else the top-level one), resolved with `resolveRealPath` (lexical fallback), so personas reaching one dir through a symlink share one group and its `settings.json` is patched once, at the first contributing persona's configured path. For each dir the aggregate `anyEnabled` flag is the OR of each persona's effective `stop_hook_bootstrap` (its own, else the top-level one) across all personas resolving to it. Diagnostics name the contributing personas as `personas="<name>" (key=<key>), …`. `anyEnabled=true` → ensure the managed entry; `anyEnabled=false` → remove it (and prune emptied groups).
    - **Managed-entry shape.** Own group `{"hooks":[{"type":"command","command":"<abs>"}]}`, no `matcher` field (Stop is not tool-scoped). Recognition rule: any Stop-hook `command` string containing the substring `slack-reply-guard.sh` is CSCB-managed.
    - **Canonical command resolution.** `resolveManagedCommand()` resolves the script path relative to the installed package (same idiom as `src/install-skill-pointer.ts`), correct under both published-package layout and repo checkout. Stale on-disk commands from a prior install path are treated as managed and rewritten to the canonical path (self-heal).
    - **Idempotent write decision.** `scanStopGroups` returns `hasSingleCanonicalGroup=true` only when there is exactly one Stop group whose sole hook entry has `type=='command'`, `command==canonicalCmd`, no `matcher`, and no extra keys. In that state the write is skipped entirely. Any drift — stale command, duplicates, extra keys, extra hooks in the managed group — triggers a strip-all-managed + append-canonical rewrite via `.tmp` + `renameSync` (trust-bootstrap precedent).
    - **Create-missing.** ENOENT on the target `settings.json` for an enabled dir → the file is created with just the managed group.
    - **Malformed JSON soft-fail.** Non-ENOENT read errors, unparseable JSON, and non-object top levels all call `recordStartupError` with a class label of `stop-hook-bootstrap-settings-read` / `stop-hook-bootstrap-settings-parse` / `stop-hook-bootstrap-settings-shape` and leave the file untouched — never a clobber.
    - **Personal-config-dir refusal (SR-3.11).** `isForbiddenHomeClaudeDir` resolves both the candidate dir and `homedir()/.claude` through `resolveRealPath` from `src/config.ts` (`realpathSync`, with a lexical `resolve()` fallback whenever realpath fails), so symlinked personal dirs cannot slip past a string compare. On a match the dir is skipped and `recordStartupError('stop-hook-bootstrap-refuse-home', …)` is recorded.
    - **Skip conditions.** Personas with no effective `claude_config_dir` are logged (`[slack] stop-hook-bootstrap: "<name>" (key=<key>) has no claude_config_dir — skipping`) and skipped. Empty or whitespace-only dirs are treated as absent (guards against `resolve("")` landing in the process cwd). A dir that fails `statSync` (or is not a directory) is skipped; the ensure path records `stop-hook-bootstrap-dir-missing` / `stop-hook-bootstrap-not-a-dir`, the remove path is silent.
    - **jq presence check.** A one-time `command -v jq` probe at boot: if `jq` is absent the entry is **still installed** (the hook fails open at hook time when `jq` is missing) but a `stop-hook-bootstrap-jq-missing` startup error is recorded so operators see the warning.
    - **Duplicate collapse and removal (SR-3.7, SR-3.8).** When rewriting an enabled dir, every managed `{type, command}` object across every Stop group is stripped before the canonical group is appended, so pre-existing duplicates collapse to one. Removal for a fully-disabled dir strips every managed object and prunes any group left with an empty `hooks` array.
    - **Never-throws contract.** A top-level `try/catch` around the whole entry point plus per-dir `try/catch` blocks record `stop-hook-bootstrap` / `stop-hook-bootstrap-dir` classes on unexpected failure. Other dirs continue processing. Timing note (SR-3.15): on-disk state is refreshed every boot, but Claude Code only reads the hook config at claude-process start — a live session that survives a CSCB restart via reconnect keeps its running process and picks the new entry up only on next fresh spawn or resume.
5. **Per-persona bring-up and launch (b.av2 SR-6.1)** — `startupSessionManager(personaConfig, { bringUp: personaBringUps })` runs after the start-wide passes (step 4 sweep, 4a-bis trust patch, 4a-quater JSONL safeguard, 4a-ter Stop-hook bootstrap). `personaBringUps` is the bring-up controller (`createPersonaBringUpController` in `src/persona-bringup-controller.ts`), built in `main()` right after the connection manager. It brings each persona up once, so a persona listed in several channels is brought up and spawned exactly once. Steps 1–3 run for every persona at once (the controller's `bringUp`), so no persona's Slack connection waits behind another persona's launch. Only step 4 goes through the launch pool: at most `concurrency` launches (default 3) run at a time, taken first in, first out in the order the personas become ready. A persona that is not `up` takes no launch slot. Per persona, in order:
   - **`persona-start` line** — one line per applied persona as its bring-up starts, naming the persona, its entry and its key (see Logging, Persona bring-up lines).
   - **Steps 1 and 2: local credentials check** (`checkPersonaCredentials`) **and working-directory check** (`checkPersonaWorkingDirectory`), both evaluated before either stops the bring-up, so both causes are logged (`persona-credentials-*`, `persona-directory-*` lines). Dry run skips the credentials check and reads no credentials file.
   - **Step 3: Slack validation and connection** — the connection manager's `bringUp(persona, tokens)`: `auth.test` on a short-lived validation client, then the long-lived Web API and Socket Mode clients (see the `persona-connections.ts` entry for the client options, the 10 s bounds on `auth.test` and `start()`, backoff and reopen). The manager logs every Slack outcome itself (`persona-slack-unreachable`, `persona-credentials-refused`). In dry run the persona is up at once with its placeholder identity.
   - **Step 4: launch** — only when the persona's outcome is `up`: `spawnForPersona` (SR-1.4 collision-then-act dispatcher), below. The connection is therefore up before the instance is launched.

   **Outcomes (b.av2 SR-6.1, SR-6.4).** Every bring-up ends with one outcome, which the controller keeps per persona:

   | Cause | Class | Outcome |
   |---|---|---|
   | None: steps 1–3 passed | — | `up` |
   | Credentials file missing, unreadable or invalid (step 1) | `persona-credentials-missing` / `-unreadable` / `-invalid` | `broken` |
   | Slack refused a token (step 3, at bring-up or on a reopen) | `persona-credentials-refused` | `broken` |
   | Slack unreachable (step 3) | `persona-slack-unreachable` | `retrying` |
   | Working directory missing or unusable (step 2) | `persona-directory-missing` / `-unusable` | `retrying` |

   A persona with both a credentials cause and a directory cause is `broken`. Its directory is still re-checked, and its start and cleared lines are logged, but it goes no further while the credentials cause holds; it comes up only once both clear. A credentials-broken persona is not retried. Recovery through a confirmed credentials change isn't built yet (E13), so today it stays down until the server restarts.

   A persona that isn't `up` is not launched by the start, records no startup error, raises no notice and is not counted as a failed spawn. The lines above say why. Its agent-director row and any instance still running from before are kept (b.av2 SR-6.4): nothing kills them for the persona being down, but the server does not serve the instance. Its MCP registration is refused (Connection step 3), the permission poller skips its rows (Permission Relay, Per-tick flow) and `/interject` answers 503 (Endpoint Inventory). When the persona comes up, its launch reaches the row through the collision ladder below, so the history is kept. Personas are brought up independently, so one persona's failure stops neither the others nor the server.

   **Retries run on per-persona timers, outside `startupSessionManager`.** The start pass returns once every persona has an outcome and every `up` persona's launch has settled; it never waits on a retry, and a retrying persona never delays another. Two kinds of retry exist, both on the SR-3.2 backoff (5 s doubling to a 300 s ceiling, no cap, `persona-retry-schedule.ts`), and neither touches the restart failure counter or cap (`backoff.ts`):

   - **Slack-unreachable** — the connection manager retries on its own per-persona timer with the tokens it was handed.
   - **Directory-broken** — the controller opens no Slack connection and re-checks the directory (`checkPersonaWorkingDirectory`) on the persona's own timer. Once the directory is usable the bring-up continues with no restart and no confirmation: Slack validation and connection, then the launch. If Slack is then unreachable, the persona becomes Slack-unreachable `retrying`.

   A retry uses the credentials content read at the persona's original bring-up; the controller holds those tokens and never re-reads the file. An edit to the file made meanwhile is ignored by the retry. Once confirmed changes exist (E11), such an edit becomes a pending change, and a confirmed change replaces the original read.

   **Launch after a retry.** A persona that reaches `up` through a retry is launched from its own retry path, not by the health check: when a directory retry's Slack step leaves the persona's outcome `up` (the manager's status is `up`, `lost` or `retrying` in the `reopen` phase, since a blip right after the connection came up does not undo it), or when the manager reports `up` right after `retrying` its bring-up (the controller's `onConnectionStatus`). The launch runs once per persona through `spawnForPersona(persona, applied, false)`, so it shares the one-launch-in-flight guard that restarts use and a launch failure takes the runtime spawn-failure path. An `up` after `lost` or a reopen launches nothing, since the instance is already running.

   **Never posted to Slack (b.av2 SR-7.2, part).** Bring-up failures are logged to the server log only, at start and on every later retry, and never to `startup-errors.log`. No notice is posted or held for a later flush under any identity.

AD's per-row, evidence-based sweep (requires agent-director ≥ 0.8.0, plan b.93m t1.93m.hp: degraded-mode guard removed) transitions the dead row to `missing`, so the subsequent `resume` succeeds and restores the pre-reboot transcript (provided the row passes the `config_dir` guard, which runs after this sweep). Skipped when `resume_enabled=false`. A `findMissing` error → fall through to `resume` anyway (which then kill+delete+fresh-spawns, today's behavior). The `ended`/`missing` collision branch above does NOT set the flag (row already terminal).

A genuinely-dead row reconciles to `missing`, so the **first** status poll hits the ended/missing branch and returns `'dead-session'` in seconds; a genuinely-alive long-turn row is untouched by the evidence-based sweep and keeps the existing polling behavior (long-turn guard preserved). On any `findMissing` error, the sweep is logged and skipped and the poll loop proceeds unchanged (today's behavior). This prefers AD's `findMissing` verb over a CSCB-side tmux probe, mirroring `resumeOrFreshSpawn`'s `reconcileMissingFirst` branch (docs/engineering-guide.md, "Avoiding Duplicated Effort").
     - **b.ecw terminal verdicts key on the claude PROCESS, not the raw tmux session.** Once b.93m Part E landed (AD ≥ 0.8.0: degraded-mode guard removed, `findMissing` verdicts per-row and evidence-based), the two dead-session branches in `waitForWaitingAndReconnect` decide off AD's process-level verdict rather than a raw `tmux has-session` probe. AD probes the *claude process*; CSCB's `_hasTmuxSession` probes the *tmux session* — a lingering tmux shell with a dead claude process would flip the two, so each branch documents which object it keys on:
       - **ended/missing branch (in-loop):** keys on the process. `ended` means `SessionEnd` fired (process exited); `missing`, after the up-front sweep, is an evidence-based verdict that the process is provably gone. Returns `'dead-session'` directly — **no tmux probe**. A dead process in a live tmux shell is still a dead bot; routing it to `resumeOrFreshSpawn` lets b.vub's `selfHealTmuxCollisionAndRespawn` reap the orphan tmux shell on `ErrTmuxSessionCreate`. (The former tmux-alive → `'ok'` behavior deferred a dead channel to the health-check for minutes.)
       - **timeout branch:** keys on the process via a **fresh** `reconcileMissingSweep` (the 10s memo has long expired at the 10-minute deadline) + one `status` call. `ended`/`missing` → `'dead-session'`; any live state (working/waiting/ask_user/check_permission/pending) → `'ok'` (a process mid-long-turn is not an error — the b.rmy/b.3ce long-turn guard, now keyed on the process). The raw tmux probe survives here **only as a fallback**: on `ErrSpawnNotFound` (AD row gone, nothing to consult) or any other `status` error, fall back to `_hasTmuxSession` (alive → `'ok'`, gone → `'dead-session'`) so an AD outage can't manufacture a false `'dead-session'` — the b.rmy invariant.
       - **ErrSpawnNotFound branch (in-loop):** keys on the tmux session by design (b.c3o) — no AD row exists, so there is nothing to reconcile or consult; only a direct probe of the deterministic session name is available. Unchanged.
     - **b.m4r shared memoized sweep — `reconcileMissingSweep`.** Three sweep callers go through one shared `reconcileMissingSweep` helper rather than calling `client.findMissing({})` inline: this `working`-row up-front sweep, `resumeOrFreshSpawn`'s `reconcileMissingFirst`, and the tick/restart escalate-dead path (via the exported `sweepDeadTmuxChannel` wrapper, which prepends its unconditional operator log then delegates here — `reconcileMissingSweep` itself stays module-private). Because `findMissing({})` is a whole-store, idempotent sweep, a fleet restart — `startupSessionManager` runs once per persona at `concurrency=3`, and every `working`-row collision plus each dead-path `reconcileMissingFirst` would otherwise fire its own whole-store sweep — is collapsed by single-flight (concurrent callers share one in-flight sweep promise) plus a 10s TTL memo (a caller arriving just after the last successful sweep reuses that result). This sheds the redundant N-sweep amplification without changing recovery behavior; failures are never memoized, so the next caller after an error re-sweeps. The post-reboot fleet-wide case (b.nk5 — `/tmp` wiped, every channel dead-tmux at once) is served correctly: one in-flight-shared sweep reconciles the whole store for every simultaneously-escalating channel. The 10s memo TTL is harmless against the ~120s health-check tick cadence: a memoized-stale answer on the escalate-dead path costs at most **one** extra tick, because the following tick's escalate-dead sweeps again well past the TTL. (The `reconcileMissingFirst`/`working`-row callers are startup-clustered within one boot rather than tick-spaced, so they benefit from the memo directly.)

       - **Path + provenance logging.** AD's `ErrJsonlMissing` description enumerates every transcript candidate it stat'd as `<source> <path> (<stat error>)`, joined by `"; "` — a capability AD's bug `b.1ba` delivered, introduced in agent-director v0.10.0. When the description carries that enumeration, `parseJsonlMissingCandidates` parses it and logs the candidates verbatim, labelled *paths+sources reported by agent-director*. The parsed source tokens are `persisted` (AD's recorded `jsonl_path`), `fallback` (its `CLAUDE_CONFIG_DIR`-aware recomputed path), and `history` (an archived `session_history` entry). When the description does **not** match that shape — a pre-0.10.0 AD, or any AD whose message wording differs — the parse yields nothing and CSCB reconstructs the candidates locally instead: the persisted `jsonl_path` column plus a `CLAUDE_CONFIG_DIR`-aware fallback via `resolveJsonlPath` and the persona's effective `claude_config_dir` (its own, else the top-level one), labelled explicitly *locally computed* so a reader never mistakes a CSCB-side reconstruction for what AD actually stat'd. The parse keys off those literal source tokens, not any version string, so it degrades cleanly in both directions.
       - **lost / never-created / inconclusive classification (b.fwu).** Using b.zak's read-only `makeDefaultArchiveCount` / `rfc3339ToEpochSeconds` helpers over `message_archive_db`, bounded by `started_at`, and the b.av2 SR-7.4 scope from `personaArchiveEvidenceScope` (the same helper step 4a-quater's Layer 2 uses), `diagnoseJsonlMissing` counts archived messages only in the persona's `delivery: all` channels since `started_at` and returns one of `'lost' | 'never-created' | 'inconclusive'`:
         - **lost** — archive shows ≥1 message since spawn in the persona's `delivery: all` channels, real conversation history destroyed. Made operator-visible via `recordStartupError('jsonl-transcript-lost-on-resume', …)` (startup only) **and** a notice through the notifier to the persona's destination ("my conversation memory has been lost and I was started fresh").
         - **never-created** — strictly evidence-based: the archive was actually consulted and returned 0 messages since spawn, and that zero is attributable — the persona has no `delivery: mentions` channel and DMs off, so its `delivery: all` channels carry all of its traffic. The transcript was never written (Claude creates the `.jsonl` lazily on first message; expected and lossless). One quiet log line only.
         - **inconclusive (b.fwu)** — "no evidence either way": the AD row fetch failed, `started_at` was absent or unparseable, the count was 0 but the persona has a `delivery: mentions` channel or DMs on (b.av2 SR-7.4: the archive cannot attribute messages from `mentions` channels or DMs to a persona, so the zero proves nothing — `UNATTRIBUTABLE_ZERO_REASON`; a persona with no `delivery: all` channel counts 0 without the archive being consulted, so once `started_at` parses it always gets this reason, even when `message_archive_db` is not configured), `message_archive_db` is not configured, or the archive read failed. Previously these fell through to a reassuring `never-created`/console-only `unknown`, silently downgrading a possible real loss. Now each emits `recordStartupError('jsonl-diagnosis-inconclusive', …)` carrying the reason (row-fetch failed / started_at absent or unparseable / zero count not attributable / archive unconfigured / archive read failed) **and** a notice through the notifier to the persona's destination, worded as *uncertainty* ("on restart I was started fresh; I could not determine whether my prior conversation history was preserved") — deliberately distinct from the `lost` wording, since a false "your history was destroyed" is its own harm. When `message_archive_db` is unconfigured the operator message states diagnosis is impossible because no message archive is configured, with a hint to enable it.

         All three outcomes still take the same delete+fresh recovery (policy unchanged). `lost` and `never-created` surface as the `fresh-after-amnesia` action; **inconclusive** surfaces as the new `'fresh-after-inconclusive-amnesia'` action (see the honest-summary note below). This is distinct from b.zak's `jsonl-transcript-lost` class (which fires *pre-resume* to warn of an impending wipe); `jsonl-transcript-lost-on-resume` records a wipe that just happened on the row resume tried and failed.
     - **b.jgf `ErrJsonlNeverWritten` — the ceremony-free branch.** agent-director 0.10.0 split the old "resume cannot open a transcript" condition into two typed errors, and CSCB branches on both. `ErrJsonlMissing` means a transcript path was recorded but is not there now: history *may* have existed and been destroyed, and that ambiguity is exactly what the b.wrb / b.fwu diagnosis above exists to resolve. `ErrJsonlNeverWritten` asserts the opposite — the session produced no transcript at all — which proves there is nothing to lose, so the fresh spawn is lossless by construction. It therefore shares the delete+fresh recovery but none of the ceremony: `diagnoseJsonlMissing` and the `fresh-after-*` actions are gated on `instanceof ErrJsonlMissing`, so this branch emits one informational log line, raises **no** persona notice, records no startup-error class, and returns plain `spawned` — the same shape as the `ErrSpawnNotFound` branch. Returning a successful action is the load-bearing part: `restart.ts` treats `failed` as retryable, so before b.jgf this error fell to the generic failure tail and the channel retried the one operation that could never succeed, on a doubling backoff, posting a spawn-failure message each pass. This branch is also the resume-path counterpart of the b.zak Layer 2 policy in step 4a-quater: a channel that has been idle since spawn has no transcript yet because Claude creates the `.jsonl` lazily on first message — normal, not an error, and it must not alarm.

   - **b.wrb / b.fwu honest startup summary.** `startupSessionManager` tallies each persona's `SpawnPersonaResult['action']` into a per-outcome breakdown and prints `startupSessionManager: complete — N persona(s): N resumed, N fresh-spawned, N fresh-after-amnesia, N fresh-after-inconclusive-amnesia, N reconnected, N no-op, N failed, N not brought up`. `fresh-after-amnesia` (a fresh spawn replacing a resume where the archive gave a definite lost/never-created verdict) and `fresh-after-inconclusive-amnesia` (b.fwu — the same recovery but the diagnosis was inconclusive, so it is *unknown* whether history was preserved) are counted and reported separately; each has its own loud, grep-friendly follow-up line when its count is `> 0`, pointing at the per-persona `ErrJsonlMissing diagnostic` lines. A b.jgf `ErrJsonlNeverWritten` recovery counts as an ordinary `fresh-spawned`, not as either amnesia bucket: no history existed, so counting it as memory loss would overstate the damage. The fresh spawns of the b.av2 SR-6.2 `cwd` and `config_dir` guards also count as `fresh-spawned` (action `spawned`); they add no action or summary line of their own, and their per-persona log lines above say why the row was replaced. A launch that joined an in-flight one returns that launch's action.
6. **Held notices flush per persona (b.av2 SR-7.2)** — the connection manager's status listener (`createPersonaUpFlushListener`) calls the notifier's `flush(key)` each time a persona reports `up`: after its bring-up in step 5 and after every reopen. Only that persona's queue is posted, in raised order, through its own client; other personas' queues are untouched. A notice is held while its persona has no client (`clientFor` answers only for a serving persona), so notices raised before a persona comes up, such as start-pass notices from steps 4a-quater and 5, post once it is up. A persona that is never brought up keeps its held notices, at most 20: past that the oldest is dropped with a log line and never posted (see the `persona-notifier.ts` entry). No bring-up failure is ever among them (step 5). Dry run holds nothing: its notices are logged when raised.
7. **SR-2.1 poller start** — outside dry run, `main()` calls `resetAllToHealthy` with the applied persona keys (a clean outage slate before any persona is brought up) and then `startPermissionPoller({ getClient, clientFor, getPersona: getAppliedPersona, isPersonaUp, intervalMs: personaConfig.agent_director_poll_interval_ms })`. This runs right after the connection manager and the bring-up controller are built, before `Bun.serve` and step 4. The poller waits for no persona: it skips the rows of a persona that is not up (`isPersonaUp`, the shared up predicate) and reads them again on the first tick after it is up; `clientFor` is the same per-persona lookup the notifier uses. Single-threaded interval loop; skipped-tick WARN at 5+ consecutive skips. Dry run logs `[slack] Running in dry-run mode — Slack disabled` instead and starts no poller.
8. **Health-check poller** — `startHealthCheck()` begins backstop liveness checks via `client.status(...)`, over the personas that are up (see Health-Check Poller). It starts once the step 5 pass returns, so it can be running while a retrying persona is still retrying. A persona joins the tick only once it is up, which is when its own retry launches it. A restart the tick schedules meanwhile runs after the restart delay, and its kill and launch defer to a launch still in flight (Auto-Restart steps 4 and 5).

CSCB does NOT maintain its own `sessions.json` registry. agent-director owns Claude session-id state internally, surfaced via `client.resume(...)` and the SR-11 state machine.

### Disconnection

1. Transport closes → `onsessionclosed` fires
2. A pending session is simply removed. A registered session is removed with `unregisterByMcpSessionId()`, which returns its persona key; a stale close of a session already replaced by a newer one returns nothing and leaves the newer session registered
3. `restartDisconnectedPersona(key, via)` resolves the key to its applied persona and calls `scheduleRestart(key, persona.working_directory)`; a key that is no applied persona is logged and not restarted. The SSE-abort path of a `GET /mcp` stream does the same

**Session drop when a persona stops being up (b.av2 SR-6.3, SR-6.4).** A session is registered only while its persona is up. When a running persona's outcome changes from `up` to `broken` or `retrying` (today a refused reopen, `persona-credentials-refused`), the bring-up controller calls its `onLeftUp` listener once, which the server sets to `createNotUpSessionDropper`. It stops the session's SSE keep-alive and calls `dropPersonaSession(key)`, which removes the persona's MCP session-ID mappings and registry entry before closing the transport, so the close finds no session and steps 2–3 schedule no restart. When a session was registered it logs `[slack] persona "<name>" (key=<key>): MCP session dropped — the persona is not up (<outcome>: <cause>); its instance and agent-director row are kept`. Nothing else happens: no restart, kill or delete, no agent-director call, nothing posted to Slack. A lost Slack connection being reopened (`lost`, or `retrying` in the `reopen` phase) keeps the persona `up` and drops nothing. While the persona is down, any new connection from the instance is refused (Connection, step 3). A credentials-broken persona recovers only through a server restart today, and the instance registers again through that start's launch.

### Auto-Restart

Restart guards, backoff, the cap latch and every restart dependency are keyed by persona key (b.av2 SR-6.3), and restart log lines name it as `persona=<key>`, e.g. `[slack] Scheduling restart for persona=<key> in <n>s (backoff)`.

Auto-restart only acts on a persona that is up. It is separate from bring-up retries (Server-Managed Startup step 5), which have their own per-persona timers on the SR-3.2 backoff with no cap and never touch this module's counter, backoff or cap. In particular, a directory that is missing at bring-up is a bring-up retry. A persona that is running and whose directory later disappears stays on this path: the health check raises `cwd-unreachable` for it (b.av2 SR-11), and its relaunches follow the backoff and cap below.

After `scheduleRestart(key, cwd)` is called:

1. **Delay check** — if `session_restart_delay` is 0, restart is skipped immediately. The delay comes only from the loaded persona config (`getRestartDelay`).

   **Shutdown check** — next, during graceful shutdown no timer is armed and the relaunch gate is not asked: `[slack] Skipping restart — server is shutting down (persona=<key>)`. Shutdown cancels every bring-up, so no persona is up, and stopping the HTTP server aborts every MCP stream, which lands here; asking the gate would log healthy personas as not relaunched. The timer callback repeats this check first when it fires.

   **Up check (b.av2 SR-6.4)** — next, `RestartDeps.canRestart(key)` (the relaunch gate, see step 5) is asked. A persona that is not up (its bring-up is broken or retrying, or its Slack connection is not serving) gets no timer: `[slack] Not scheduling restart for persona=<key> — the persona is not up (its bring-up has not succeeded, or its Slack connection is not serving)`. The timer callback asks again right after its shutdown check, before the liveness check, and once more right after the liveness check returns, before any reconnect or kill (the probe is an async agent-director call, and the persona may stop being up while it runs). A persona that stopped being up by either check (for example, Slack refused its token on a reopen) logs `[slack] Skipping restart for persona=<key> — the persona is no longer up; its instance is left as it is`. Nothing further is probed, reconnected, killed or launched, and no success or failure is recorded, so a not-up persona's instance and agent-director row are left alone. `launchSession` asks the gate once more (step 5).
2. **Backoff timer** — a `setTimeout` fires after `nextBackoffDelay(key, session_restart_delay)` seconds: `min(base * 2^preFailureCount, 900)`, so the delay doubles on each consecutive failure from the `session_restart_delay` base up to a 900 s (15 min) ceiling (`src/backoff.ts`, SR-25). `scheduleRestart` accepts `opts.humanTrigger`; when set, the computed delay is clamped **down** to `HUMAN_TRIGGER_DELAY_CEILING = 5` s (never raised) so a person typing in the channel isn't told to wait out a 900 s backoff. The clamp only shortens the wait — it does not reset the failure counter and does not bypass the re-entrancy guard, so each attempt still counts toward normal backoff/cap accounting. The `scheduleRestart` path itself does not consult the cap — it is cap-exempt (the cap only gates the health-check tick and the inbound message triggers, which check `isAtCap` themselves before firing, see below). Two triggers reach this path from inbound messages, both in `src/persona-routing.ts` and both keyed by the receiving persona: the b.9cj streamless branch, for a session that is *registered* for the persona yet lacks a `_GET_stream` (it calls `scheduleRestart(key, session.cwd, undefined, { humanTrigger: true })`; it does not call `notification()`, since the SDK's `send()` would evaporate silently with the stream gone), and the b.kvq no-session branch, for a persona with **no** registered, connected session (the "No live session for persona … — dropping message" line; it calls `scheduleRestart(key, persona.working_directory, undefined, { humanTrigger: true })`). Both go through `decideLostMessageRecovery(key, session_restart_delay)`, so the restart fires only when no restart is already pending or active, auto-restart is enabled and the persona is under the failure cap; either way the sender gets a per-case reply in the source conversation, posted through the persona's client. Guards and restart are keyed by the receiving persona's key, so there is no owner resolution and a recovery never spawns a second instance. At the cap the inbound path does **not** bypass the cap; only a server restart clears the in-process counter and revives a capped persona. In all cases the dropped message itself is lost — recovery starts a session but never delivers or replays that message.
3. **Liveness check** — `isSessionAlive(key)` calls `client.status({claude_instance_id})` and returns true when the state is in `AGENT_DIRECTOR_LIVE_STATES`; `ErrSpawnNotFound` → dead. When alive, `restart.ts` skips the reconnect as "already reconnected" only when the session is connected **AND** its standalone GET SSE stream is present (`RestartDeps.hasSessionStream`, b.9cj); a connected-but-streamless session (`connected === true` but the SDK dropped `_GET_stream`) cannot receive messages, so it is *not* waved through — it proceeds to recovery. If alive and not skipped, `reconnectSession()` first probes AD state and, when the row is `working`, returns `'transient'` without poking the pane — deferring the `/mcp reconnect` send-keys to a later tick so a mid-long-turn session is not corrupted (b.9a7 hazard 2, preserving the b.rmy invariant: a `working` row is never declared dead, only left alone; on a status error it falls through to the reconnect attempt rather than manufacture a false defer). Otherwise `reconnectMcp(key)` runs — main returns `'ok'` | `'failed'` | `'dead-session'` (from a `/mcp reconnect slack-channel-router` send-keys with retry), adapter-mapped to `'success'` | `'transient'` | `'escalate-dead'`. A `'success'` reconnect calls `recordSuccess` (resetting the failure count and cap latch); the non-success branches do **not** `recordFailure`. On `'escalate-dead'` / `'transient'` (including the `working` defer) `restart.ts` does not re-enter `scheduleRestart`; instead the **next health-check tick** re-observes the persona and, if it is still not deliverable (alive-but-disconnected or connected-but-streamless) or has since gone dead, calls `scheduleRestart` again, so a failed/deferred reconnect is retried on a bounded cadence. For the dead-tmux `escalate-dead` case CSCB recovers itself internally: the `_buildReconnectSessionAdapter` mapping awaits `sweepDeadTmuxChannel(key, verdict)` (`src/session-manager.ts`) before returning the verdict. That wrapper emits an operator-visible log line (`[slack] escalate-dead: persona=… verdict=… — tmux session provably dead, triggering internal findMissing reconciliation …`) then runs the memoized `reconcileMissingSweep` (b.m4r), which reconciles the frozen `working` row to `missing`; the next tick then observes `alive === false` and takes the normal kill+relaunch branch. The external `~/startup/find-missing-loop.sh` is now belt-and-braces only — recovery no longer depends on it, and removing it stays a separate operator decision. Not counting here keeps the failure count tied to actual launch attempts (the single counting site, SR-25.1) rather than a non-launch reconnect site — the sweep records neither success nor failure.
4. **Kill zombie** — `client.kill({claude_instance_id})` is best-effort; `ErrSpawnNotFound` is ignored. The kill adapter (`_buildKillSessionAdapter` in `src/server.ts`) first asks `isLaunchInFlight(key)`: when a launch for the persona is already running, it logs `[slack] killSession (restart adapter): launch already in flight for persona=<key> — not killing` and returns without killing. Mid-ladder the row can read dead, so a kill here would take down the process the running launch is bringing up; the relaunch in step 5 joins that launch instead (b.av2 SR-6.6).
5. **Relaunch** — `launchSession(key, personaConfig, { canLaunch: canRelaunch })` looks up the persona with that key (`false` when there is none), then asks the relaunch gate (`createPersonaRelaunchGate` in `src/persona-start.ts`), and otherwise collapses `spawnForPersona`'s richer outcome to a boolean — the single counting site (SR-25.1). Resume vs fresh is decided by the SR-1.4 collision-then-act dispatch (no separate `sessionId` arg from CSCB — agent-director owns resume state), the same persona-keyed ladder as startup, so the b.av2 SR-6.2 `cwd` and `config_dir` guards apply to runtime relaunches too. A relaunch runs only the launch: it never repeats the start bring-up's credentials, working-directory or Slack steps (Server-Managed Startup step 5): a row in another directory is replaced, and a row whose `config_dir` label is missing or differs is spawned fresh rather than resumed. Like every launch, the relaunch is preceded by the trust patch for the persona's working directory in its effective config dir (the pre-launch patcher at the top of the ladder; see startup step 4a-bis), and a patch failure there is logged only. The relaunch goes through `spawnForPersona`'s one-in-flight-launch-per-persona rule (b.av2 SR-6.3), so a relaunch that overlaps a still-running launch for the same persona (the start pass or another trigger) joins it and receives its outcome. `restart.ts` counts each `launchSession` result it receives, so overlapping restarts that join one failed launch count that failure once per caller. A joined launch's failure record and notice follow the mode (startup or runtime) of the launch that actually ran, not of the caller that joined it. On a `true` outcome, `recordSuccess` resets the counter and cap latch; on `false`, `recordFailure` increments it.

   **Relaunch gate.** The gate (`createPersonaRelaunchGate`, over the connection manager and the bring-up controller) answers true only while the persona's Slack connection is serving and its bring-up outcome is `up`. Besides step 1's up check, `launchSession` asks it, which covers a change during the kill. When that check answers false, `launchSession` returns `'skipped'` without spawning or running the trust patch, and `restart.ts` records neither success nor failure, so the counter, backoff and cap latch stay as they were and no cap notice is raised. The gate's own log lines are in the `persona-start.ts` entry of the Module Map. Once the persona is up again it is eligible, and its next restart counts normally.
6. **Cap latch** — after the 5th consecutive failure (`RESTART_FAILURE_CAP = 5`, exported from `src/restart.ts`), `shouldNotifyCap(key, …)` fires once per episode and `onCapReached(key)` calls the session manager's `notifyRestartCapReached(key)`, which raises a synthetic `ErrSpawnCapReached` spawn-failure notice through the per-persona notifier to the persona's destination, with the remediation "restart the server to retry — automatic restarts are suspended for this persona"; **no** further timer is scheduled. A capped persona has no registered session; an inbound Slack message hits the no-session branch in `src/persona-routing.ts`, whose `decideLostMessageRecovery` detects the cap (`isAtCap(key, RESTART_FAILURE_CAP)`) and does **not** fire a restart — firing one would only burn a spawn attempt against a persona that cannot come up. The sender is told the channel will not self-recover. Only a **server restart** clears the in-process counter (lost on restart by design) and gives the persona a fresh attempt.

### Health-Check Poller

A periodic backstop that runs alongside the reactive disconnect path. It catches three failure modes that the reactive `onsessionclosed` path misses: (a) sessions that die without triggering a close event (e.g., an externally-killed tmux session); (b) sessions that are alive but MCP-disconnected — an AD live-state row (`waiting` etc.) whose MCP transport is gone, `isSessionAlive === true` yet unreachable; and (c) connected-but-streamless sessions (b.9cj) — `isSessionAlive === true` and `isSessionConnected === true` in the registry, but the SDK has silently dropped the `_GET_stream` map entry, so messages cannot reach the bot. Without (c) an idle streamless session would stay broken forever, invisible to the reactive path. The tick recovers all three.

On each tick:

1. **Persona iteration** — for each persona key / working-directory pair from `HealthCheckDeps.getPersonas()` (production: `buildPersonaWorkList(personaConfig, canRelaunch)`, one entry per applied persona however many channels it lists, rebuilt every tick). The relaunch gate leaves out every persona that is not up: its bring-up is `broken` or `retrying`, or its Slack connection is not serving (never brought up, connecting, retrying its bring-up, broken or stopped). Such a persona is absent from the whole tick: no `cwd-unreachable` update, no reconnect and no relaunch, including a persona that was launched and whose connection later broke or stopped. A directory-broken persona's directory is therefore watched only by its bring-up retry, never by this tick. It rejoins the tick once it is up. The gate's one line per persona per state is described under Auto-Restart step 5. Every guard call, the disconnected streak and the `cwd-unreachable` outage flag are keyed by persona key (b.av2 SR-6.3); log lines name it as `persona=<key>`, e.g. `[slack] health-check: persona=<key> is at cap — skipping tick (SR-25.3/25.4)`:
   - **Skip if restart pending/active** — `isRestartPendingOrActive(key)` returns true; a relaunch is already in flight.
   - **Skip if at failure cap** — `isAtCap(key, RESTART_FAILURE_CAP)` (injected as `HealthCheckDeps.isAtCap`) returns true; a persona at the consecutive-failure cap is skipped this tick (SR-25.3/25.4), including the alive-but-disconnected reconnect path — a capped persona gets no tick-driven reconnect. The inbound drop branch likewise detects the cap and declines to fire a restart, so a **server restart** is the only path back — it clears the in-process counter and gives the persona a fresh attempt.
   - **Working-directory check** — `statRoute(cwd)` on the persona's working directory clears `cwd-unreachable` for the persona when it exists and raises it otherwise.
   - **Liveness check** — `isSessionAlive(key)` calls `client.status({claude_instance_id})`; the state is checked against `AGENT_DIRECTOR_LIVE_STATES`. `isSessionConnected(key)` (b.9a7, wraps the same registry-`connected` adapter used by restart.ts) reports whether the MCP session is currently connected. `hasSessionStream(key)` (b.9cj, wraps the shared `getSessionByPersona` → `hasGetStreamKey(transport)` probe wired into both `HealthCheckDeps` and `RestartDeps`) reports whether the standalone `_GET_stream` is present.
2. **Dead session** — if the liveness check fails, `scheduleRestart(key, cwd)` is called, delegating to the same restart path used by `onsessionclosed`.
3. **Alive but not deliverable** — if `isSessionAlive` is true but the session is either not connected (`!isSessionConnected`, b.9a7) **or** connected-but-streamless (`!hasSessionStream`, b.9cj), the tick tracks a per-persona consecutive-failing streak and calls `scheduleRestart(key, cwd)` only once the streak reaches **two consecutive ticks**. Both cases land in this branch and share the one streak/debounce, which suppresses the freshly-launched false positive: a booting session that connects (and re-opens its stream) between ticks is never poked. Observing the persona as fully healthy — alive, connected, AND stream present — (or dead) resets/consumes the streak. A tick that skips the persona clears it too: a restart pending or active, the cap, or the relaunch gate leaving it out of the tick's work list (not up), so a persona that comes back up starts a fresh count. `_resetHealthCheckState` clears the whole map. `restart.ts` then reconnects an alive-but-disconnected row (deferring a `working` row per Auto-Restart step 3), recovers a streamless one, or relaunches a dead one. This gives time-bounded recovery on the `health_check_interval` (default 120 s) even for idle personas that receive no inbound traffic.

The interval is controlled by `health_check_interval` in `config.json`. If the value is `0`, `startHealthCheck()` returns immediately and no interval is created. `stopHealthCheck()` clears the interval during graceful shutdown, before `cancelAllRestartTimers()` runs.

**Ordering invariant**: `startHealthCheck()` is called only after `startupSessionManager()` returns, which is once every persona has a bring-up outcome and every `up` persona's start launch has settled. Moving it earlier in the startup sequence would risk the poller racing with in-progress start launches. Bring-up retries that finish later don't delay it; their launches go through `spawnForPersona`'s one-launch-in-flight guard, which a restart the tick triggers also respects.

### start command

`start` (CLI subcommand) has one prerequisite: the configuration file the server loads (`resolveServerConfigPath()`) must exist, else it prints `missing prerequisite: config.json not found at <path>` and exits 1. It reads no Slack token and checks no token environment variable (b.av2 SR-10.2): each persona's tokens are in its credentials file, which only the server reads. The file's contents are not checked here; the server validates them at start and `start` reports that failure (below). It then **self-daemonizes**: the parent process spawns a detached background child, waits for its startup outcome and exits, leaving the child running as the server. Detection of parent vs. child is via the `_CLI_DAEMON_CHILD` env marker.

The parent spawn (`CliDeps.spawnDaemon`) uses `detached: true` (child becomes its own session leader via `setsid`), `stdio: ['ignore', logFd, logFd]` (stdin from `/dev/null`, stdout/stderr to `STATE_DIR/server.log` — no inherited pipes), and `child.unref()`. This isolates the server from the launcher's session and process group, so killing the launching shell's group does not kill the server. The child re-execs `start` with the marker set, redirects logging to `server.log`, and calls `startServer()`.

**Early-failure report (b.av2 SR-1.7, SR-8.7).** Before the spawn the parent records `server.log`'s size. It then polls every `DAEMON_STARTUP_POLL_MS` (100 ms) for up to `DAEMON_STARTUP_WAIT_MS` (30 s), long enough for the startup gate, the config load and the template refresh that precede the PID file:

- The daemon exits, or cannot be launched: `[slack] Server failed to start (exit code N | killed by <signal> | could not be launched: …). From <log>:` followed by the last `DAEMON_FAILURE_LOG_LINES` (20) non-empty lines this run appended to `server.log` (read from the start if the log shrank, i.e. rotated), or `…; it wrote nothing to <log>`; exit 1. These lines carry the server's own fatal reason, such as the `[slack] Fatal: configuration error — …` line with the conversion error for a pre-persona file, or the PID-conflict error when a server is already running. Server log lines never carry a token.
- `STATE_DIR/server.pid` names the child's PID (the server writes it once it is listening, after the config load): `[slack] Server starting in background (PID n)`, exit 0.
- The wait expires: `[slack] Server is still starting in the background (PID n) after 30s — its log is <path>`, exit 0. The daemon is never signalled.

The clock, sleep and log reads (`now`, `sleep`, `fileSize`, `readFileFrom`) are `CliDeps` seams, as are the log-file operations: `openLogAppend` / `closeFd` open and close the parent's `server.log` descriptor, and `initLogging` performs the child's redirect (and `clean_restart`'s).

**Marker-leak guard (b.acn)**: the `_CLI_DAEMON_CHILD` marker alone is untrusted, because it can leak from an operator wrapper script (e.g. `start-all.sh` / `cscb-up`) into the launching environment. If leaked, the parent daemonize branch would be skipped and the server would run in-place inside the launcher's session — dying when that process group is killed. A genuine daemon child is always a session leader, so `start` requires the marker **and** session-leadership to trust it. `isSessionLeader()` reads the session id (field 4 after `comm`) from `/proc/self/stat` on Linux and compares it to the pid; it fails open (treats the process as a leader) where `/proc` is unavailable, preserving prior behavior on non-Linux platforms. A set-but-not-leader marker is treated as a leak: it is deleted and `start` falls through to the parent path to re-detach properly.

### stop command

`stop` (CLI subcommand) sends SIGTERM to the running server via the PID file at `STATE_DIR/server.pid`. If the process does not exit within `stop_timeout` seconds (default 30 s, configurable in `config.json`; read with the persona loader, and 30 s when the file cannot be loaded, a pre-persona file included), a SIGKILL is sent. A brief 2 s confirmation poll follows the SIGKILL. Stale PID files (process no longer running) are silently removed. A non-zero exit from this phase causes `stop` to exit 1.

Plain `stop` leaves the managed bots running (they are meant to survive server restarts — see [Graceful Shutdown](#graceful-shutdown-sr-11-event-11)). The **`--stop-bots`** flag (b.4dk) additionally exits the bots gracefully, mirroring `clean_restart`'s order: the server daemon is stopped **first**, then the shared `teardownBots` closure runs over the config's persona set (the same per-persona pause/poll/kill sequence on `cscb_<key>` as `clean_restart`, minus the restart phase). A config with no personas tears down nothing.

Stopping the server first prevents its `onsessionclosed`/`scheduleRestart` handler (`initPendingSession` in `src/server.ts`) from respawning a just-exited bot mid-teardown — the respawn would delete the bot's `ended` row and history before SIGTERM lands. `directorPause` is an agent-director client subprocess that needs no live CSCB daemon (SessionEnd hooks are wired by agent-director into the spawned claude process and call the AD binary), so teardown works fine after the server is down.

Before teardown runs, `stop --stop-bots` initializes the agent-director Client singleton via the non-exiting startup gate (`initClient` in `CliDeps`, b.qwo) — the same init the `clean_restart` algorithm covers in step 3 below (see there for the b.qps / `incident-2026-09-18-clean_restart.md` root cause). An AD-unreachable initialization or teardown failure is a **loud** `exit(1)`, not a swallowed skip; a config-load failure, a pre-persona file included, is best-effort (logged, teardown skipped, but the server stop still succeeds, since the server is already down). A pause-timeout kill escalation does NOT guarantee an `ended` row — that residual case is recovered later by the dead-session `findMissing`→`resume` path.

### clean_restart (SR-11 Event 12)

`clean_restart` (CLI subcommand) stops the server daemon first, then concurrently pauses every managed Claude Code spawn via agent-director, then starts a fresh server. The stop-first ordering prevents the health-check poller and auto-restart logic from interfering with the teardown. It logs to `STATE_DIR/clean_restart.log` via `initLogging()`; its four fatal lines (`failed to load config:` in step 1, `agent-director initialization failed:` in step 3, `bot teardown failed — aborting restart:` in step 6, `start failed with exit code N` in step 8) are also written to the terminal's stderr, through the `console.error` captured before the redirect, so an operator sees why it exited without opening the log. If the redirect fails, every line stays on the terminal and a fatal line appears once. `CliDeps` exposes injectable `directorStatus`, `directorPause`, and `directorKill` adapters (production builds them with the exported `createDirectorOps(getClient)`, which calls `getClient().status/pause/kill` on each operation and maps only `ErrSpawnNotFound` to "no row") plus an optional `initClient` (b.qwo) that installs the AD Client singleton before any per-persona work — tests that pre-install a stub via `setClientForTests` omit it. Each adapter takes the persona's instance ID, `cscb_<key>` (`personaInstanceId`); no label lookup is involved. The per-persona teardown (steps 4–5 below, `teardownPersona`) runs for every persona at once inside a shared `teardownBots(personas, exit_timeout)` closure reused by `stop --stop-bots` (b.4dk). Teardown log lines name the persona as its JSON-quoted name with its key, e.g. `[slack] teardownBots: no spawn row for persona "Ops Bot" (key=ops_bot_5e2526f3) — skipping`.

Algorithm:

1. **Init logging + load config** — `initLogging()` redirects output to `clean_restart.log`. `loadConfig(resolveConfigPath())` (production: `loadPersonaConfig` on the server's config path) provides the persona set and `exit_timeout`. Config load failure is fatal, a pre-persona file included (the loader's conversion error).
2. **Stop server daemon** — shells out to `claude-slack-channel-bots stop`, which sends SIGTERM and escalates to SIGKILL after `stop_timeout`.
3. **Init agent-director client** (b.qwo) — this short-lived CLI process does not run the server startup gate, so `getClient()` would otherwise throw. `initClient` (`CliDeps`) installs the Client singleton via the non-exiting `runStartupGate` variant. A gate failure is a distinct loud `exit(1)` — the restart never proceeds to teardown or `start` on top of bots it could not reach. Skipping this init was the b.qps / `incident-2026-09-18-clean_restart.md` root cause: the throw was swallowed and every bot reported a bogus "no spawn row — skipping".
4. **Per-persona precheck** — `directorStatus(cscb_<key>)` returns `null` only when the row is genuinely absent (`ErrSpawnNotFound` from `client.status`); "no spawn row — skipping" is printed only in that case. Terminal states (`ended`, `missing`) → skip; otherwise proceed. Any error reaching agent-director (connection refused, uninitialized client, binary unreachable) **propagates** — it is no longer collapsed into a `null`/"no row". Such rejections surface after the parallel loop as a loud aggregate error (see step 6).
5. **Pause + poll** — `directorPause(cscb_<key>)` is called; if it rejects, escalate immediately to `directorKill(cscb_<key>)`. After a successful pause, `directorStatus(cscb_<key>)` is polled with exponential backoff (100 ms start, capped at 2 s, total budget `exit_timeout`). The first poll observing `null` / `ended` / `missing` is treated as clean exit. If the budget is exhausted, `directorKill(cscb_<key>)` force-terminates the spawn. On both the escalation and timeout kill paths the kill's outcome decides the persona's fate (b.dnt): a kill failure other than the benign already-gone race (`ErrSpawnNotFound`) is itself a teardown failure surfaced as a rejection in step 6. Teardown is **kill-but-never-delete**: rows are paused/killed but never deleted, preserving each row's `claude_session_id` so the next start can resume with context.
6. **Loud AD-unreachable failure** (b.qwo, b.dnt) — after the parallel loop, any settled rejection (an agent-director connectivity error raised by a precheck in step 4, a poll-loop `directorStatus` in step 5, or (b.dnt) an escalation- or timeout-path `directorKill` that failed with anything other than the benign already-gone race, never a normal terminal-row skip and never an `ErrSpawnNotFound` already-gone kill, both of which resolve quietly) is logged and re-thrown as an aggregate error (`teardown incomplete for N persona(s); other personas may already have been paused or killed; rows are never deleted, safe to retry`). `clean_restart` catches it and `exit(1)`, aborting the restart **before** starting a new server. A silent no-op teardown is thus impossible.
7. **Start new server daemon** — shells out to `claude-slack-channel-bots start`. Reached only if teardown completed without an AD-unreachable failure.
8. **Exit** — a non-zero exit code from `start` is propagated and the process exits with that code, logged as `[slack] clean_restart: start failed with exit code N`. Because `start` now waits for the daemon's startup outcome, a server that fails early (for example on a config error) makes this exit 1; the reason is in `server.log`, not `clean_restart.log`.

Per-persona polling cadence (100 ms → 2 s cap, `exit_timeout` total) is unrelated to the SR-2.1 permission poller's `agent_director_poll_interval_ms`.

### Graceful Shutdown (SR-11 Event 11)

On `SIGTERM` or `SIGINT`, the shutdown handler:
1. Flips the `shuttingDown` flag (idempotent guard).
2. Calls `stopPermissionPoller()` to stop the SR-2.1 tick.
3. Calls `stopHealthCheck()`, stops the cron scheduler, then `cancelAllRestartTimers()`, the bring-up controller's `cancelAll()` (every pending directory re-check; a re-check already running does nothing more, and no launch after a retry starts) and `stopAllKeepAliveTimers()`. The manager's Slack retries stop with `stopAll()` in step 5.
4. Stops the HTTP server, drains pending + active MCP transports. Each aborted stream reaches `scheduleRestart`, which arms no timer during shutdown (Auto-Restart step 1, shutdown check).
5. Closes every persona's Slack connection through the connection manager (`stopAll()`), logging `[slack] Disconnecting persona Slack connections`.
6. Calls `closeClient()` inside a try/catch to release the agent-director Client handle. The library's `close()` is idempotent and never throws; the catch is belt-and-suspenders.
7. Removes the PID file.

The bots themselves are NOT killed or paused on shutdown — same as the prior behavior and consistent with SR-11 Event 11.

## Configuration

### config.json (`SLACK_STATE_DIR`/config.json, default ~/.claude/channels/slack/config.json)

The server's configuration is the persona config described in the next section: a `personas` array plus the server-wide settings below. `main()` reads it once at start, from `config.json` in the state directory (`resolveServerConfigPath()`), through `loadStartPersonaConfig` (b.av2 SR-1.7, SR-8.7). The file is required and there is no fallback of any kind: no environment variable supplies the bind address, port or anything else. Any load failure stops the start with one line, `[slack] Fatal: configuration error — <message>`, and exit code 1, before any port is bound, the PID file is written, a Slack connection opens or anything is spawned:

- a missing file: `The configuration file "<absolute path>" does not exist. The server requires the configuration file to start.` (`cannot be read`, with the errno code in parentheses when there is one, in place of `does not exist` for any other read failure);
- a pre-persona file (top-level `routes`, `default_route` or `default_dm_session`): the loader's conversion message, unchanged (see Pre-persona rejection below);
- any other parse or validation failure: the loader's error, unchanged.

The CLI (`start`, `stop`, `clean_restart`) reads the same path with `loadPersonaConfig`; see the command sections under Session Lifecycle.

Server-wide settings (the persona entry keys are in the next section):
- `bind` — HTTP server bind address (default: 127.0.0.1)
- `port` — HTTP server port (default: 3100)
- `session_restart_delay` — seconds before auto-restarting dead sessions (default: 60, 0 = disabled)
- `health_check_interval` — seconds between health-check polls (default: 120, 0 = disabled)
- `exit_timeout` — seconds `clean_restart` and `stop --stop-bots` wait for a Claude session to exit cleanly before force-killing it (default: 120)
- `stop_timeout` — seconds the `stop` command waits after SIGTERM before escalating to SIGKILL (default: 30)
- `mcp_config_path` — path to MCP config file for Claude launch (default: ~/.claude/slack-mcp.json)
- `append_system_prompt_file` — optional path to a file appended to every managed session's system prompt via `--append-system-prompt-file`; missing file silently skipped
- `system_prompt_mode` — controls whether `append_system_prompt_file` is applied (default: `"append"`; valid: `append`, `none`). `"append"` passes `--append-system-prompt-file` to Claude when launching sessions; `"none"` skips the flag entirely so only `CLAUDE.md` is used
- `cozempic_prescription` — cozempic cleaning intensity used before `--resume` launches (default: `"standard"`; valid: `gentle`, `standard`, `aggressive`); has no effect if cozempic is not installed
- `message_archive_db` — optional path to the SQLite message archive (`src/message-archive.ts`); absent means no archive
- `agent_director_poll_interval_ms` — permission-poller interval in milliseconds (default: 1000; 200 to 3 600 000). The old `claude_director_poll_interval_ms` name is rejected with a rename message
- `claude_config_dir` — optional path to a Claude on-disk config directory used for managed sessions; when set, launches carry `CLAUDE_CONFIG_DIR` so the persona authenticates against a specific account. `~` is expanded and the path is resolved to absolute. A persona's own `claude_config_dir` overrides this top-level value. When neither is set, Claude's own default applies.
- `resume_enabled` — boolean (default: `true`). When `false`, the session manager skips `--resume` entirely and always performs a fresh launch, even when a stored session ID exists. Use this to work around versions of Claude Code that crash on `--resume` (e.g. the v2.1.120 "sandbox required but unavailable" regression). Affects both startup (Server-Managed Startup step 5) and auto-restart (Auto-Restart step 5).
- `stop_hook_bootstrap` — boolean (default: `true`). Controls whether step 4a-ter `stopHookBootstrap` installs the CSCB-managed Slack Reply Guard Stop hook into `<effective_claude_config_dir>/settings.json`. The top-level value defaults to `true` when absent; a non-boolean is rejected at either scope. A persona's own `stop_hook_bootstrap` overrides the top-level value, and the resolved values feed the per-dir aggregation in step 4a-ter — a per-persona opt-out only fully disables the guard for a bot when its persona owns a dedicated `claude_config_dir`.
- `cron_table_path` — optional path to the cscb_cron crontable file (default: `<config dir>/crontab`, where `<config dir>` is the directory of the loaded config file). Anything that is not a non-empty string is rejected; `~` is expanded and the path is resolved to absolute, yielding a required string on the resolved config. Boot-fixed: only the crontable's contents hot-reload at runtime; its location never does.
- `cron_log_path` — optional path to the cscb_cron log file (default: `<config dir>/cron.log`). Same non-empty-string validation, tilde expansion, required-resolved-string, and boot-fixed notes as `cron_table_path`.
- `cron_log_max_bytes` — optional positive integer (>= 1); no default. Any value that is not a positive integer is rejected when set. When absent, log pruning is disabled — this bullet states the contract only; the prune mechanics ship in a later Epic.

The path keys are pointers only: schedules never live in `config.json` — the crontable file is the single source of truth.

### Persona config

The persona loader in `src/config.ts` (`resolvePersonaConfig`, `loadPersonaConfig`, and the start wrapper `loadStartPersonaConfig`) accepts the persona shape of b.av2 SR-1. It is the only configuration shape; the server and the CLI both load it.

**Entry points and purity (b.av2 SR-13.1).** `resolvePersonaConfig(raw, configDir, home)` parses, defaults and validates an already-parsed value. It never opens, reads, creates or writes a file and never requires a path to exist; the only file-system access is resolving the real paths of persona working directories and credentials files for the cross-persona rules below. `loadPersonaConfig(path, home?)` reads the file once and delegates to it; it never writes, renames or converts the file. Nothing runs at import.

**Top level.** A required `personas` array, which may be empty, plus the server-wide settings. The server-wide settings are the ones listed in the `config.json` section above, with the meaning, default and validation given there, including path resolution for the top-level path keys. Unknown top-level keys are rejected by name, and the renamed poll-interval key `claude_director_poll_interval_ms` gets a rename message naming `agent_director_poll_interval_ms`. Three keys are new to this shape. They are validated only; E9 wires them.

| Key | Type | Default | Meaning |
|---|---|---|---|
| `ack_reaction` | non-empty string | absent | Emoji name of the acknowledgement reaction. Absent means no acknowledgement. |
| `reply_chunk_limit` | positive integer | `4000` | Largest reply chunk, in characters. |
| `reply_chunk_mode` | `length` or `newline` | `newline` | How a long reply is split. |

**Persona entry.** Each element of `personas` is an object with these keys:

| Key | Type | Default | Meaning |
|---|---|---|---|
| `name` | non-empty string, required | — | Persona identity. No format rule; the persona key is derived from it by `src/persona-identity.ts`. |
| `credentials_file` | path, required | — | The persona's credentials file. |
| `working_directory` | path, required | — | The instance's working directory. |
| `channels` | array of channel entries | none | Channels the persona is in. The same channel ID may not appear twice in one persona. |
| `dm.enabled` | boolean | `false` | The DMs switch. |
| `dm.contact` | Slack user ID | absent | The user who receives prompts and notices when `permission_prompts` is `dm`. |
| `permission_prompts` | `dm` or a channel ID, required | — | Where permission prompts and notices go. |
| `claude_config_dir` | path | top-level `claude_config_dir` | Claude config dir for the persona. Absent at both levels means Claude's own default. |
| `stop_hook_bootstrap` | boolean | top-level `stop_hook_bootstrap` | Per-persona Stop-hook bootstrap flag. |

**Channel entry.** Both keys are required: `id`, a Slack channel ID matching `^[CG][A-Z0-9]+$`, and `delivery`, either `all` (every message) or `mentions` (only messages that mention the persona or hold `<!here>` / `<!channel>`, with or without a label; `<!everyone>` and user-group mentions do not count). `dm.contact` must match `^[UW][A-Z0-9]+$`, and a channel ID in `permission_prompts` uses the channel ID format.

**Path rule.** Persona paths (`credentials_file`, `working_directory`, per-persona `claude_config_dir`) must be absolute, exactly `~`, or start with `~/`. The tilde is expanded under the home directory passed in (the OS home when not given) and the result is made absolute. Relative paths are rejected.

**Unknown keys.** An unknown key in a persona entry, its `dm` object or a channel entry is rejected, naming the persona and the key. A token-like key such as `bot_token` is rejected the same way: credentials live only in the credentials file.

**Per-entry rejections.** On top of the type and format rules above, a persona entry is rejected when:

- `permission_prompts` is missing
- it has zero channels and DMs off (`dm.enabled` not `true`), so it can receive no messages
- `permission_prompts` names a channel the persona isn't in
- `permission_prompts` is `dm` but `dm.contact` is missing or DMs are off (both are named when both are wrong)

**Cross-persona rejections (b.av2 SR-1.5).** Once every entry has parsed, the loader rejects:

- a duplicate name or key. Each persona's name and key are compared, by exact string, with every other persona's name and key, so a name equal to another persona's derived key is a duplicate too. The error names the duplicated name or key.
- a shared `working_directory`, then a shared `credentials_file`. Each is compared by `resolveRealPath` (real path, with a lexical `path.resolve` fallback when realpath fails for any reason), so a symlink to another persona's path, or `~/x` against its absolute form, is a duplicate. Only the same setting is compared: one persona's working directory against another's credentials file is not a collision. The error names the setting and the expanded path; when the two expanded paths differ (only a symlink can cause this), it shows both and the real path they share.

Each error names both personas, each as its array position plus the `src/persona-identity.ts` rendering. Personas are scanned in array order and the first colliding persona is reported against the earliest persona it collides with.

One persona listed in several channels loads: the rule is one working directory per persona, not one per channel.

**Pre-persona rejection (b.av2 SR-1.7).** If the top level has `routes` (in any shape), `default_route` or `default_dm_session`, the loader stops with the conversion message before any other check. The message names the key and says the configuration must be rewritten by hand as personas. The file is never written and nothing is auto-converted. The CLI uses the same loader: such a file stops the server's start, makes `clean_restart` exit 1 before stopping anything, and makes `stop` fall back to its default `stop_timeout` (with `--stop-bots`, bot teardown is skipped).

**Check order and errors.** The loader checks, in order: the value is an object, the pre-persona keys, unknown top-level keys, `personas` is present and an array, the server-wide settings, each persona entry in array order, the name/key rule, then the shared-path rule (`working_directory` before `credentials_file`). It reports the first violation only, so a per-entry error anywhere wins over any cross-persona one. Entry errors name the entry's position and, once `name` is valid, the persona as its JSON-quoted name with its key (the `src/persona-identity.ts` renderer), plus the setting. Errors don't echo rejected values: they may repeat only the persona name and IDs that already passed their format rule (e.g. a `permission_prompts` channel ID that isn't in the persona's channels, or a duplicated channel ID). The shared-path errors are the deliberate exception: they show the expanded, absolute paths, which have already passed the path rule. A malformed-JSON error omits the parser's detail, which could quote file content.

**Not checked at load time.** The loader doesn't read the credentials file and doesn't check that any directory or file exists. Those are bring-up checks: the credentials-file check is in `src/persona-credentials.ts` and the working-directory check is in `src/persona-bringup.ts` (see the Module Map); neither checks `claude_config_dir`. The server runs them at start, for each persona, as steps 1 and 2 of its bring-up (`checkPersonaLocalSteps` in `src/persona-start.ts`, run by the bring-up controller; see Server-Managed Startup step 5). A credentials failure leaves that persona `broken`; a working-directory failure leaves it `retrying`, and its directory is re-checked until usable.

### agent-director state.db (~/.agent-director/state.db)

Persistent CSCB-spawn registry — owned by agent-director, not CSCB. CSCB reads this transitively via `client.list/status/get/resume(...)`. Same-user invariant verified at SR-5.1 startup gate.

### startup-errors.log (~/.claude/channels/slack/startup-errors.log)

Append-only log of fatal startup errors written by `recordStartupError` (`src/startup-errors.ts`). One timestamped line per entry; includes the agent-director `errName` when surfacing typed library errors. Rotation is operator-owned via `docs/logrotate-startup-errors.conf`.

### cron.log (`cron_log_path`)

Append-only plain-text log of every cscb_cron fire outcome, written by `src/cron-log.ts`. Location is the config-resolved `cron_log_path` (default `<config dir>/cron.log`); boot-fixed — the path never hot-reloads. Deliberately plain text, not JSONL, so `grep no-session cron.log` yields human-triageable lines.

Each outcome entry is one physical line of five space-delimited fields: `<ISO-8601 UTC ms timestamp> <identity|-> <target|-> <outcome> <detail>`. The `detail` field leads with key=value tokens (`prompt=`, `status=`, `errno=`, `line=`) then free text. Every value is newline-escaped, so one record is always exactly one physical line. UTC matches server.log so an outage window can be cross-correlated.

The `outcome` field is one of nine classes:

| Outcome | Meaning |
|---|---|
| `delivered` | prompt delivered to the target persona |
| `no-session` | `/interject` answered 503: the target persona is not up (broken or retrying), or has no live connected session — dropped |
| `unknown-persona` | no persona in the applied config has that name or key |
| `prompt-missing` | prompt file did not exist at fire time |
| `prompt-unreadable` | prompt file existed but could not be read |
| `prompt-oversize` | prompt file exceeded the size ceiling |
| `parse-error` | the crontable line could not be parsed |
| `http-error` | localhost POST hit an unexpected HTTP status or a network failure (503→`no-session`, 404→`unknown-persona` are classed separately) |
| `fanout-deferred` | all-bots fire skipped — emitted by the cron dispatcher while fan-out remains deferred to E4; kept so old lines stay interpretable |

A per-fire summary line shares the five-field layout with `summary` in the outcome position (a line kind, not an outcome class): `<ts> <identity> - summary delivered=N failed=M`. An `info` line kind (same layout) carries informational markers, and a `warn` line kind carries operator-actionable conditions — the crontable vanishing or becoming unreadable — with `identity`/`target` defaulting to `-` because they are not fire-scoped. Both tokens are distinct from every outcome class, so `grep warn cron.log` matches exactly the warn lines and neither kind pollutes the outcome triage views.

Append-only: no rotation, no pruning, no read-back (pruning ships in a later Epic). The writer `mkdir`s the log's missing parent directory on first append — deliberately unlike `cron-bootstrap.ts`'s no-mkdir invariant, which is crontable-only (D-Q1), since the log is server-owned output. Write failures never break dispatch — a failed append logs one `[slack] cron-log` line, drops the fd, and self-heals on the next append. This module is a writer other code calls.

### permission-trail.jsonl (~/.claude/channels/slack/permission-trail.jsonl)

Append-only **JSON Lines** event store for the CSCB-side visibility trail of the AD↔CSCB tool-permission relay (SRD `t1.cdb.4g`). One JSON object per newline-terminated line. The file path honors `SLACK_STATE_DIR` — default `~/.claude/channels/slack/permission-trail.jsonl`. Owned by `src/permission-trail.ts`; every emit goes through `emitTrail()` (auto-stamps `ts`) or `emitTrailEvent()` (caller-supplied `ts`).

**Line schema** (enforced at the emitter — SR-V-1 / SR-V-4.5):

| Field | Type | When present | Notes |
|---|---|---|---|
| `ts` | string | always | RFC 3339 with ≥ ms precision (SR-V-4.3, SR-V-4.5). Substituted with a `[slack]` warning if missing/invalid. |
| `event` | string | always | Stable hierarchical identifier in the `cscb.*` namespace (e.g. `cscb.chat_post.attempted`, `cscb.click_handler.invoked`, `cscb.chat_update.attempted`, `cscb.decide.attempted`, `cscb.block_actions.received`). |
| `request_token` | string | when AD has minted one | AD-side UUID (SR-V-1.1). Absent for events emitted before token assignment (SR-V-1.2). |
| `claude_instance_id` | string | whenever known | Primary join key when `request_token` is absent (SR-V-1.2). |
| `channel` | string | events touching Slack | Slack channel id (SR-V-1.3). |
| `message_ts` | string | events touching Slack | Slack message `ts` of the prompt or closure (SR-V-1.3). |
| _per-event-class fields_ | any | event-class specific | Passed through verbatim — no truncation (SR-V-3). |

**Example line** (a `chat.postMessage` attempt emitted by the SR-2.1 poller):

```json
{"ts":"2026-06-04T20:39:58.123Z","event":"cscb.chat_post.attempted","claude_instance_id":"cscb_C0B1ZJJLJ9M","request_token":"6f3a1d2c-aaaa-bbbb-cccc-dddddddddddd","channel":"C0B1ZJJLJ9M","text":"*Permission* requested for `Bash`","blocks":[{"type":"section","text":{"type":"mrkdwn","text":"…"}},{"type":"actions","elements":[{"type":"button","action_id":"perm_allow_cscb_C0B1ZJJLJ9M_6f3a1d2c-aaaa-bbbb-cccc-dddddddddddd","text":{"type":"plain_text","text":"Allow"}},{"type":"button","action_id":"perm_deny_cscb_C0B1ZJJLJ9M_6f3a1d2c-aaaa-bbbb-cccc-dddddddddddd","text":{"type":"plain_text","text":"Deny"}}]}],"ok":true,"slack_ts":"1717536002.000100"}
```

**No-truncation guarantee.** The canonical trail line persists every field at full fidelity (SR-V-3.1) — the full `blocks` array including every `action_id`, the full `text`, the full Slack API response. The 300-character `[slack] RAW <event> event persona=<key>: …` summaries the event router (`src/persona-event-router.ts`) logs for each `message` / `app_mention` event, before handing it to `persona-routing.ts`, are a **separate human-readable log** kept truncated intentionally per SR-V-3.2; they do not replace the canonical store and the two coexist.

**`jq` smoke-check** — confirm the file is valid JSONL and pivot by correlation key:

```sh
# Every line parses as JSON
jq -c . ~/.claude/channels/slack/permission-trail.jsonl | head -3

# Every event for one request_token, in time order
jq -c 'select(.request_token=="6f3a1d2c-aaaa-bbbb-cccc-dddddddddddd")' \
  ~/.claude/channels/slack/permission-trail.jsonl

# Every event on a Slack channel within a time window (SR-V-5.2)
jq -c 'select(.channel=="C0B1ZJJLJ9M" and .ts>="2026-06-04T20:00:00Z" and .ts<="2026-06-04T21:00:00Z")' \
  ~/.claude/channels/slack/permission-trail.jsonl
```

**Federation.** AD emits a complementary JSONL log on its side (`t1.n4v.14`). The two logs join on `request_token` + `claude_instance_id` per SR-V-4. No shared store; the operator stitches the trail via `jq` or equivalent.

**Retention.** None. The file is append-only and the system does not self-protect against disk pressure (SR-V-5.5). Operators rotate / archive / delete out-of-band.

#### `cscb.poller.row_decision` (SR-V-2.3)

Emitted once per `permission_requests` row per tick (and once per `non_conforming_skipped` spawn per tick) from `src/permission-poller.ts`. Some rows emit no row decision: rows of a spawn skipped for its `persona` label (missing, or naming no applied persona), rows of a spawn whose persona is not up (b.av2 SR-6.4; no `get` is made, so there are no rows to decide), and new rows whose persona has a `dm` destination or no Slack client (logged instead; see [Per-tick flow](#per-tick-flow-sr-2)). The `action` field is one of six stable identifiers; the set is open to extension per SR-V-2.3 — new poller branches may add identifiers without an SRD edit.

| `action` | Meaning |
|---|---|
| `post_attempted` | New row seen this tick; `chat.postMessage` was issued for this `request_token`. |
| `already_tracked` | Row's composite key already in `livePermissions`; no-op this tick. |
| `reconciled_closed` | Row no longer in the tick's projection; `getPermission` returned a verdict; the closure `chat.update` is sent when the posting persona's client is available, otherwise skipped and logged. The entry is dropped either way. |
| `not_found_generic_deny` | `getPermission` threw `ErrPermissionRequestNotFound`; the generic-deny closure `chat.update` is sent when the posting persona's client is available, otherwise skipped and logged. The entry is dropped either way. |
| `non_conforming_skipped` | The spawn's `permission_requests` was `null`/`undefined`; the row was excluded from the closure sweep this tick. `request_token` is **absent** on this event per SR-V-1.1. |
| `transient_retry` | Transient error on `getPermission`; the entry was left alive for the next tick to retry. |

#### `cscb.chat_post.attempted` (SR-V-2.4)

Successes are trail-only; failures land in BOTH the trail (as `ok=false` with the Slack platform error class string) AND `server.log` via `logViaDeps`/`logDeps` (`b.emk` defense-in-depth). #### `cscb.poller.wedge_detected` (b.fae F4)

Emitted from `postWedgeWarning` in `src/permission-poller.ts` when the wedge detector trips — a spawn seen in `check_permission` with an empty `permission_requests` array for `wedgeTripTicks` consecutive ticks (~90 s). Exactly one **successful** (`ok=true`) event per wedge episode: the `warningFired` latch (set only after a successful post) suppresses further posts until the detector re-arms. A failed post emits an `ok=false` event without latching and the poller retries on a later tick (throttled ~30 s), so an episode with Slack trouble can log several `ok=false` events before the one `ok=true`. Only an actual Slack post emits the event: a `dm` destination (logged until E7) and an unavailable persona client emit none. The envelope shape mirrors `cscb.chat_post.attempted`: success is trail-only; failure lands in BOTH the trail (`ok=false`) AND `server.log` (`b.emk` convention).

Fields:
- `ts`, `event="cscb.poller.wedge_detected"`, `claude_instance_id`, `channel` (the persona's destination channel).
- `text` — the full one-shot warning message posted to the channel, prefixed with the persona reference (read-pane + kill/respawn remediation; send-keys explicitly not offered).
- `ok` — `true` on success, `false` on failure.
- On success: `slack_ts` — the Slack `ts` of the posted warning.
- On failure: `error` — the Slack platform error class string.

Emitted once per inbound `block_actions` action by the event router (`src/persona-event-router.ts`) when a persona's connection delivers an `interactive` event, regardless of whether the `action_id` decodes. This is the diagnostically critical surface for **"I clicked Allow and nothing happened"** — decode-failure cases are explicitly in scope. ### Removed pre-Epic-2 files

The previous tmux-direct architecture wrote `~/.claude/channels/slack/sessions.json` to persist tmux session names and discovered Claude session UUIDs. Both responsibilities have moved to agent-director — `sessions.json` and `sessions.json.last` no longer exist. Operators upgrading from a pre-Epic-2 install can safely delete the stale files; CSCB will not read them.

### server.pid (STATE_DIR/server.pid)

Written at startup with the server's process ID. Used by the CLI `stop` command to send SIGTERM (with SIGKILL escalation after `stop_timeout`) to a running server, and by startup to detect a conflicting already-running instance. Removed on graceful shutdown.

### Environment Variables

The server (`server.ts`) requires no environment variable and reads no Slack token from the environment: each persona's `bot_token` and `app_token` come only from its credentials file (`credentials_file`, see Persona config), and nothing supplies the bind address or port except `config.json`. The CLI reads no token either: `start` checks only that `config.json` exists (see [start command](#start-command)). `SLACK_BOT_TOKEN` and `SLACK_APP_TOKEN` are read by nothing; setting them has no effect.

Optional:

- `SLACK_STATE_DIR` — the state directory (made absolute; default `~/.claude/channels/slack`). `config.json`, `access.json`, the inbox, `server.pid`, the logs and the permission trail live under it. `resolveServerStateDir` reads it at call time; `server.ts` computes its paths once at import.
- `SLACK_DRY_RUN` — set to `1`, `true`, or `yes` to enable dry-run mode (`isDryRun()` in `tokens.ts`). No credentials file is read and no Slack call is made: each persona's bring-up runs only the working-directory check, then the connection manager marks it up with a distinct placeholder identity derived from its key (`U000DRY_<key>` / `B000DRY_<key>`), and builds no Slack client. Spawns, the start sweep and the permission poller are skipped. All MCP tool calls (`reply`, `react`, `edit_message`, `fetch_messages`, `download_attachment`) are stubbed — each returns a `[dry-run]` placeholder and logs the call to the server log — and persona notices are logged, not posted. The HTTP/MCP server still starts normally so Claude Code sessions can connect and exercise tool calls without a Slack workspace.

Optional CLAUDE_CONFIG_DIR (set at spawn time via SpawnParams.extra_env when configured per persona or top-level) is propagated by agent-director to the spawn's tmux session, enabling per-persona Claude account selection.

CSCB_PERSONA and CLAUDE_MANAGED_CHANNEL are set at spawn time via SpawnParams.extra_env for every managed session, both to the persona key, and are propagated by agent-director to the spawn's tmux session. An instance uses its `CSCB_PERSONA` key to target itself in crontable lines and in `/interject` requests.

CSCB_CRONTABLE_PATH is set at spawn time via SpawnParams.extra_env for every managed session — unconditionally, for every persona — and is propagated by agent-director to the spawn's tmux session. It carries the resolved tilde-expanded `cron_table_path` (the default `<config dir>/crontab` or the configured override) so bots can self-schedule by locating and appending to the crontable, the single source of truth for scheduled prompts (bots are first-class writers alongside the server).

### access.json (~/.claude/channels/slack/access.json)

The server still reads only `ackReaction` (the inbound ack emoji) and `textChunkLimit` / `chunkMode` (reply chunking). `dmPolicy`, `allowFrom`, `channels` and `pending` are no longer read and do not affect delivery. chmod 600. E9 removes the file.

## Logging

### Why console.error/console.log are overridden directly

Bun bypasses `process.stderr.write` overrides — the runtime writes directly to the file descriptor, so patching `process.stderr.write` has no effect. `src/logging.ts` works around this by replacing `console.error` and `console.log` themselves before any logging occurs.

### initLogging()

`initLogging(logFilePath)` in `src/logging.ts` opens the target file in append mode and replaces both `console.error` and `console.log` with wrapper functions that:

1. Format all arguments to a single string (JSON-serializing objects)
2. Prepend an ISO-8601 timestamp: `[2024-01-01T00:00:00.000Z] message`
3. Roll the file if it has grown past the threshold (see **Rotation** below)
4. Write the line synchronously via `writeSync` to the open file descriptor
5. Fall back to the original `console.error`/`console.log` if the write fails

The originals are captured at module load time so the fallback always refers to Bun's native output.

### Rotation (b.brv)

Rotation is built into `src/logging.ts` so it applies on every machine that runs CSCB — no per-host logrotate config. `maybeRotate()` runs before each write: it `fstat`s the active fd and, when the size crosses the threshold, closes the fd, shifts `<path>.N-1 → <path>.N` down to `<path>.1`, renames the active file to `<path>.1`, discards the oldest generation beyond `CSCB_LOG_KEEP`, and reopens a fresh active file. It is best-effort — any filesystem error is swallowed rather than thrown into the caller's hot path, and a failed reopen after rotation is recovered on a subsequent write rather than disabling file logging.

| Env var | Default | Effect |
|---|---|---|
| `CSCB_LOG_MAX_BYTES` | 10 MiB (`10485760`) | Rotate when the active file reaches N bytes. Values `<= 0` or non-numeric ignored. |
| `CSCB_LOG_KEEP` | 5 | Rotated generations retained. `0` = keep none (the active file is `rm`ed on rotation, i.e. truncate). Values `< 0` or non-numeric ignored. |

Rotated generations are **not** compressed. Applies to both `server.log` and `clean_restart.log` (any file passed to `initLogging`). This is distinct from `startup-errors.log`, whose rotation remains operator-owned via `docs/logrotate-startup-errors.conf`.

### agent-director logger filter (b.brv)

The agent-director `Client` is constructed with a `logger` in `src/agent-director-startup.ts`, and since `initLogging()` patches `console`, everything the Client logs lands in `server.log`. At info level the Client emits a per-poll `SubprocessClient: <verb> ok { … }` success dump for every `list`/`status`/`get`/`decide` call — with CSCB polling continuously, these dumps historically dominated the log (2 GB / 137 MB observed in b.brv). `makeFilteredAdLogger(console)` in `src/agent-director-logger.ts` wraps the console: it drops those routine `SubprocessClient: <verb> ok` records at `log`/`info` level while passing `warn`/`error` through unfiltered. Setting `CSCB_AD_VERBOSE` to a truthy value (`1`/`true`/`yes`/`on`) returns the base logger unwrapped, restoring the full chatter for debugging.

### HTTP request access line (b.3k6)

The `/mcp` endpoint's `fetch` handler in `src/server.ts` is hit on every MCP round-trip — client polls, notifications, tool-call responses, and each SSE stream open — so its one-line-per-request access log (`[slack] HTTP <method> <path> session=…`) is the highest-frequency routine success line left in `server.log` after b.brv silenced the `SubprocessClient` dumps. It shares their signal/noise profile: routine and continuous at steady state, useful only when debugging a specific transport/session-routing problem. It is gated behind `isHttpVerbose()`, which reads `CSCB_HTTP_VERBOSE` (truthy: `1`/`true`/`yes`/`on`, case-insensitive) — off by default. Unlike `CSCB_AD_VERBOSE`, the env var is checked per request rather than once at startup, so toggling it takes effect without a restart. Real events (session connect/disconnect, no matching persona, errors) are logged unconditionally elsewhere and are unaffected by this flag.

### Persona bring-up lines (b.av2 SR-10.3)

A persona's bring-up and its retries log to `server.log` only, with the `[slack]` prefix; none goes to `startup-errors.log` or to Slack. Diagnostic lines use `formatPersonaDiagnostic` (`persona-diagnostics.ts`): `[slack] <class>: personas[<i>] "<name>" (key=<key>)`, then ` path="<path>"` when the class has one, then `: <cause>`. The full class list is in the `persona-diagnostics.ts` entry of the Module Map. No line carries a token. The operator-facing catalogue of these classes, with each one's cause and fix, is the shipped debugging skill `skills/debug-slack-channel-bots/SKILL.md`.

| Line | When | Fields |
|---|---|---|
| `persona-start: … : bring-up starting` | Once per applied persona as its bring-up starts, before any of its outcome lines | entry, name, key |
| `persona-credentials-missing` / `-unreadable` / `-invalid` | Once, when step 1 fails | entry, name, key, credentials-file path, cause |
| `persona-directory-missing` / `-unusable` | Once, when step 2 fails and its retry starts; later failed re-checks log nothing, even if the class changes | entry, name, key, working directory, cause |
| Same directory class, cause `cleared: working directory is usable again; continuing the bring-up` | Once, when a re-check finds the directory usable; with a credentials cause still open the cause ends `the persona stays broken until its credentials are fixed and the server is restarted` instead | entry, name, key, working directory |
| `persona-slack-unreachable` / `persona-credentials-refused` | Logged by the connection manager once when the cause starts and once when it clears (cause `cleared: …`), not on every attempt | entry, name, key, credentials-file path, cause |
| `[slack] persona "<name>" (key=<key>): up after its bring-up retry (directory\|Slack) — launching` | Once, when a retry brings the persona up and the controller launches it | name, key, which retry |
| `[slack] persona "<name>" (key=<key>): launch after its bring-up retry failed: <error>` | That launch threw | name, key, error |

The restart and relaunch-gate lines for a persona that isn't up are under Session Lifecycle, Auto-Restart. The b.av2 SR-6.4 lines for a persona that isn't up but still has a running instance are with the path that logs them: `Session refused: …` (Session Lifecycle, Connection step 3), `MCP session dropped — …` (Session Lifecycle, Disconnection), `permission-poller: … is not up — …` and `… is up again — …` (Permission Relay, Per-tick flow step 2), `/interject: refused for persona …` (Endpoint Inventory), and the start sweep's and ladder's `cannot be resolved to a real path — keeping its row(s)` (Server-Managed Startup steps 4 and 5). None of them carries a token or a diagnostic class label.

### Log file locations

Both paths are rooted in `SLACK_STATE_DIR` (default: `~/.claude/channels/slack/`).

| Process | Log file |
|---------|----------|
| Server daemon (`server.ts`) | `STATE_DIR/server.log` |
| `clean_restart` subcommand | `STATE_DIR/clean_restart.log` |
| cscb_cron fire log (`cron-log.ts`) | `cron_log_path` (default `<config dir>/cron.log`) |

All three are opened in append mode — multiple restarts accumulate in the same file rather than overwriting it; only the first two are subject to the size-based rotation above.

## Endpoint Inventory

### POST /interject

Injects a message into one persona's live Claude session without going through Slack. Localhost-only. Handler: `handleInterject` in `src/interject.ts`, wired by `server.ts`.

**Request body** (JSON, max 32 KB)

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `persona` | string | yes | Target persona's name or key (exact, case-sensitive match) |
| `message` | string | yes | Message content to inject |
| `sender` | string | no | Display name; defaults to `"interject"` |

**Success response**

`200 OK` — `{ ok: true, persona: <name> }` (the persona's name, even when the request used its key)

**Status codes**

| Status | Condition | Body `error` |
|--------|-----------|--------------|
| 200 | Notification handed to the persona's session | — |
| 400 | Invalid JSON | `Invalid JSON` |
| 400 | Missing, empty or non-string `persona` (including a body with only the old `channel` field) | `Missing or invalid field: persona (string) required` |
| 400 | Missing, empty or non-string `message` | `Missing or invalid field: message (string) required` |
| 403 | Non-localhost origin | `Forbidden` |
| 404 | No applied persona has that name or key, or there is no persona config | `Persona not found in the applied config` |
| 405 | Non-POST method | `Method Not Allowed` |
| 413 | Body exceeds 32 KB | `Request body too large (max 32KB)` |
| 503 | The persona is in the applied config but not up (broken or retrying), even when its instance is running or its session is still registered; the body also carries `persona` (its name) | `Persona is not up` |
| 503 | The persona is up but has no registered, connected session | `No active session for this persona` |

**Behavior**

- Resolves `persona` against the applied persona config (`resolvePersonaTarget`); 404 if absent
- Asks the injected `isPersonaUp` (the server's shared up predicate, `createPersonaUpPredicate`; b.av2 SR-6.4) before any session lookup. A persona that is not up gets 503 and one line, `[slack] /interject: refused for persona "<name>" (key=<key>) — the persona is not up; nothing delivered`; nothing reaches its instance
- Calls `getSessionByPersona()` with the persona's key; 503 if none or not connected
- Logs `[slack] /interject: delivering to persona "<name>" (key=<key>) sender="<label>" message="<first 80 chars>"`
- Sends `notifications/claude/channel` to that session only, with `content: message` and `meta: { user, ts }` — no `chat_id`, `message_id` or `via`. `user` is the `sender` label; `ts` is `String(Date.now() / 1000)`, which has at most three fractional digits. The Slack Reply Guard relies on that shape to tell injected messages from Slack ones (see [Slack Reply Guard](#slack-reply-guard-stop-hook)).
- Does not await the notification: a later rejection is logged as `[slack] /interject: notification to persona … failed: …`
- Does not call the Slack API

## Security Model

- **Inbound delivery** (b.av2 SR-4.2): every inbound event goes through the receiving persona's pipeline (`src/persona-routing.ts`), whose delivery rules are in `src/delivery-decision.ts`. A persona receives only its configured channels, each by its `delivery` setting. Its own messages are dropped, and that is the only sender filter: there is no allowlist and no pairing. DMs are not delivered
- **Outbound scoping** (b.av2 SR-5.1): every MCP tool resolves the calling session's persona and its client at call time and may target only that persona's configured channels (`checkPersonaTarget`). A refused target returns a tool error naming the persona and the target, and no Slack call is made. The call posts as the persona, with no username or icon override
- **File exfiltration guard**: `assertSendable()` blocks uploading files from the state directory (outside `inbox/`) and every persona credentials file named by the applied or current configuration (`credentialsFilesToProtect`, rebuilt per call), compared by real path so a symlink to one is refused too. It never opens the file. `reply` checks every file up front and re-checks each one right before its upload
- **Attachment download token scope**: `download_attachment` sends the persona's bot token only to `https://files.slack.com` URLs. External (non-Slack-hosted) files are refused, and a redirect off that origin is never followed with the Authorization header, so the token cannot reach a third-party host
- **Localhost restriction**: `/interject` is the only localhost-restricted endpoint; it accepts requests only from 127.0.0.1/::1/::ffff:127.*
- **Session scope guard**: agent-director enforces session scope via `relay_mode='on'` at spawn time. Permission requests are routed through agent-director's internal relay machinery (SR-2.1 poller), which is scoped to the spawned session. Sessions not spawned by CSCB have no relay route and no `PermissionRequest` or `PreToolUse` hook entries in `settings.json` — the `.sh` hook files are not shipped.
- **Credentials-file secrecy**: each persona's credentials file is the server's only token source (b.av2 SR-1.4, SR-10.2). The persona credentials module (`src/persona-credentials.ts`) and the bring-up checks (`checkPersonaLocalSteps` in `src/persona-start.ts`, run by the bring-up controller) read it once per persona at start and hand the tokens to the connection manager; the controller holds them in the persona's entry for a later directory retry and never logs, returns or re-reads them; the server reads no token from the environment and holds none at module scope. That code reads no environment variable. The CLI reads no token at all: it neither checks token variables nor opens a credentials file. A credentials path that is not a regular file (a directory, FIFO, socket or device) is `persona-credentials-unreadable` and is never read: the file is opened non-blocking, so a FIFO cannot stall the open, and its type is checked through the same descriptor before any read. It never writes, copies, caches or persists a credentials file or any value from one. It does not check or change the file mode. A bad token is described only by its key and the rule it breaks, never by its value, so no diagnostic line or failure result carries a token, and the success value redacts itself if logged.
- **Slack validation outcome secrecy** (b.av2 SR-10.3): outcomes from `src/persona-slack-validation.ts` carry only the class, the token key, the check, and the Slack error code or reason kind (plus an HTTP status or `retryAfter` number). The log lines `src/persona-slack-episodes.ts` builds from them carry those fields plus the persona reference (entry position, name and key) and the credentials-file path. Neither ever carries the raw error object, its message, the request, a header or a token value. The connection manager (`src/persona-connections.ts`) uses them.
- **Persona Slack client error secrecy** (b.av2 SR-3.3): no persona Slack client (`src/persona-slack-clients.ts`) attaches the original request, and so the Authorization header, to its errors. The connection manager logs a thrown value only through `describeThrownValue` (constructor name, a short `code`, stack frames; never the message), and the exported `unhandledRejection` handler (`src/persona-connection-errors.ts`) logs the same way, so neither writes a token value. `server.ts` installs the handler once in `main()`; the event router, `connectPersonaSlack` and the bring-up controller also log thrown values only through `describeThrownValue`.
