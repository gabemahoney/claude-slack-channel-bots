# Internal Architecture

## System Overview

The Slack Channel Router is a two-way bridge between Slack and Claude Code sessions via Socket Mode + MCP HTTP (StreamableHTTP). Each Claude Code session connects to its own MCP Server instance and is matched to one persona by its working directory; under the transitional route→persona adapter each route is one persona.

## Module Map

```
    ├── config.ts               Routing configuration — load, validate, defaults, tilde expansion. SR-4.1 agent_director_poll_interval_ms field. SR-4.2 unknown-field rejection. Also holds the persona config loader (b.av2 SR-1), not yet called by the server; see "Persona config (loader only, not yet wired)" under Configuration.     ├── persona-identity.ts     b.av2 SR-2.1 / SR-2.2 persona key rule and every identifier derived from the key. Key rule: a name of 1–40 chars drawn only from `a-z0-9_` is its own key; any other name is lower-cased, each run of other characters becomes one `_`, leading/trailing `_` are trimmed, the stem is truncated to 40 chars, and `_` plus the first 8 hex digits of the SHA-256 of the original name is appended (an empty stem leaves the 8 hex digits alone; max key length 49). Derived from the key: instance ID `cscb_<key>` (keeps the `cscb_` anchor `permission-action-id.ts`'s regex relies on), tmux session name `slack_bot_<key>`, labels `service=cscb` / `persona=<key>` / `config_dir=<12 hex of SHA-256 of the effective claude_config_dir>` (`configDirLabelValue` resolves the dir lexically — tilde-expanded, made absolute, no symlink or existence check — and no configured dir means `~/.claude`; spawns don't call it directly but go through `session-manager.ts`'s `personaConfigDirLabelValue`, which real-paths the dir first so a symlink and its target get the same label), and spawn-environment values `CSCB_PERSONA` and `CLAUDE_MANAGED_CHANNEL` (both the key), `CSCB_CRONTABLE_PATH`, and `CLAUDE_CONFIG_DIR` only when a dir is configured. Persona references in logs and errors render as the JSON-quoted name with the key beside it, e.g. `"Ops Bot" (key=ops_bot_5e2526f3)`. Pure (b.av2 SR-13.1): the module does no I/O and runs nothing at import; the home directory can be passed in, and is looked up from the OS only at call time when not given; must not import `config.ts`. Also holds the one tilde rule (`expandTilde(path, home?)`: only exactly `~` or a leading `~/` expands). Its importers in `src/` are `config.ts` (both loaders use the tilde rule; the persona loader uses the key and the persona reference), `persona-diagnostics.ts` / `persona-credentials.ts` / `persona-connections.ts` / `persona-notifier.ts` / `trust-bootstrap.ts` / `stop-hook-bootstrap.ts` (the persona reference), `agent-director-template.ts` (the default config dir, `resolveClaudeConfigDir`), `session-manager.ts` (spawn parameters and persona references in spawn-path logs), `jsonl-persistence-check.ts` (the instance ID, the persona reference and the default config dir), and `server.ts` / `cli.ts` (the instance ID). Spawns carry the derived identifiers, and restart, the health check, outage state and server notices are keyed by persona key; the MCP session registry is keyed by persona key too; the rest of the runtime (the permission poller, inbound routing) is still keyed by route, as described elsewhere in this doc.
    ├── persona-diagnostics.ts  b.av2 SR-10.3 persona diagnostic class labels and the broken-persona log line. Holds the closed label set as a type plus constants: `persona-credentials-missing`, `persona-credentials-unreadable`, `persona-credentials-invalid`, `persona-credentials-refused`, `persona-slack-unreachable`, `persona-connection-lost`, `persona-connection-restored`, `persona-directory-missing`, `persona-directory-unusable`; later Epics extend it. `persona-connection-lost` is logged once when a connection that was up drops without the server closing it, and `persona-connection-restored` once when it is open again; failed reopen attempts in between log nothing, and a credentials error on reopen logs one `persona-credentials-refused` line instead of the restored line (the latch is `persona-slack-episodes.ts`). `formatPersonaDiagnostic` builds one `[slack]` line from the class, the entry position `personas[<i>]`, the persona as its JSON-quoted name with the key beside it (`renderPersonaRef` from `persona-identity.ts`), the JSON-quoted path when there is one, and the cause, with every control character and U+2028/U+2029 escaped so the line is always one line. `personaCheckFailure` wraps that line into the failure result both checks below return, and emits it exactly once only when a logger is injected. Pure (b.av2 SR-13.1): no file-system, environment or console access, nothing at import. The lines never go to `startup-errors.log`. The server doesn't call it yet; E3 wires it.
    ├── persona-credentials.ts  b.av2 SR-1.4 persona credentials-file reader, step 1 of the SR-6.1 bring-up. The file has a fixed shape: a JSON object with exactly two string keys, `bot_token` (prefix `xoxb-`) and `app_token` (prefix `xapp-`); each value has at least one character after its prefix and contains no whitespace or control character. `checkPersonaCredentials` finds it locally valid when it exists, is readable, parses and has that shape, and its real path is no other applied persona's credentials file. Checks run in this order: a real-path collision (`resolveRealPath`, lexical fallback) with another applied persona's credentials file makes the persona credentials-broken as `persona-credentials-invalid`, naming the other persona, and is checked first so the other persona's tokens are never read; a missing path (ENOENT/ENOTDIR) is `persona-credentials-missing`; a directory, permission denied or any other read error is `persona-credentials-unreadable`; content that is not JSON, not an object, lacks a key, has a non-string or wrongly prefixed value, a value with nothing after its prefix, a value containing whitespace or a control character, or any extra key is `persona-credentials-invalid`, with every problem listed. Causes name a bad token by its key and rule only; a parse failure is described generically and extra keys are counted, not named. Success returns a `PersonaSlackTokens` value that redacts itself when JSON-serialised, string-converted or inspected. All file access goes through an injectable seam (read, realpath), with the real file system as the default; nothing runs at import, and it reads no environment variable, writes nothing and checks no file mode. The server doesn't call it yet; E3 wires it, and `tokens.ts` stays the live token source until then.
    ├── persona-bringup.ts      b.av2 SR-6.1 steps 1 and 2 as pure checks. `checkPersonaWorkingDirectory` (step 2) requires the working directory to exist, be a directory (after following symlinks), be readable and searchable, and have a real path that is no other applied persona's working directory. A missing path is `persona-directory-missing`; anything else, including a real-path collision (named with the other persona), is `persona-directory-unusable`. It reads no credentials file, so a dry-run bring-up can call it alone. `checkPersonaLocalBringUp` always runs both the credentials check and the directory check before returning, so when both fail both causes are reported: it returns both outcomes plus the failure list (credentials first) and, with an injected logger, emits each failure line exactly once. It reuses `persona-credentials.ts`'s real-path collision and errno helpers rather than duplicating them. No Slack or agent-director call, no environment access, no writes, no timers, nothing at import; file access goes through an injectable seam (stat, access, realpath), and the combined check's seam also covers the credentials read. The server doesn't call it yet; E3 wires the procedure and E5 adds the broken/retrying outcome bookkeeping and directory-retry timers.
    ├── persona-slack-validation.ts  b.av2 SR-3.2 classifier for a persona's Slack token validation: `auth.test` checks `bot_token`, opening Socket Mode checks `app_token`. Three outcome classes: up, Slack-unreachable (retried for ever with backoff) and credentials-broken. `botIdentityFromAuthTest` returns up only when `auth.test` gave both the bot user ID and the bot ID (SR-3.1); a result lacking either is Slack-unreachable. `classifySlackValidationError(error, check)` maps a thrown or rejected value to one of the two failure outcomes. Slack-unreachable (`persona-slack-unreachable`) covers a network, DNS or request-timeout error, a non-200 HTTP status (429 included), a rate-limited error, a `start()` whose WebSocket phase was abandoned after 10 s (the `SlackStartTimeoutError` marker, SR-3.3), no WebSocket URL, a socket closed before `hello`, any other Socket Mode error, any unrecognised value, and a `PlatformError` of `internal_error`, `fatal_error`, `service_unavailable`, `request_timeout` or `ratelimited`. A `PlatformError` whose Slack error code is missing, empty or not a short lower-case identifier is also Slack-unreachable (reason `unknown`): the library builds such errors itself from a 200 answer that isn't JSON, such as a proxy page. Only a `PlatformError` carrying a well-formed Slack error code outside those five is credentials-broken (`persona-credentials-refused`), carrying the key and the Slack error code. The "no WebSocket URL" reason applies only to the library's plain, code-less error from the Socket Mode open; any other code-less failure is reported as an unrecognised failure (reason `unknown`, still Slack-unreachable). An unreachable outcome carries a reason kind, plus the HTTP status, the transient Slack error code or `retryAfter` where they apply. Library errors are recognised by their `code` field, never by `instanceof`, so stub errors classify the same way. The classifier never throws. Waits come from `persona-retry-schedule.ts` (5 s doubling to 300 s, no cap, never shorter than `retryAfter`) and log lines from `persona-slack-episodes.ts`. Pure and injectable (SR-13.1): no timers, clock, Slack client, I/O or environment access, nothing at module scope. The connection manager (`persona-connections.ts`) consumes it; the server doesn't use either until E3.
    ├── persona-retry-schedule.ts  b.av2 SR-3.2 backoff for the Slack-unreachable class. `createPersonaRetrySchedule` returns one independent schedule per persona and retry purpose; it holds only its own failure count. `nextDelayMs(retryAfterSeconds?)` records a failure and returns the next wait in milliseconds: 5 s doubling to a 300 s ceiling (5, 10, 20 … 300 s), with no attempt cap. When a `retryAfter` is given the wait is never shorter than it, clamped only at the largest delay a JavaScript timer honours (about 24.8 days). `reset()` returns to 5 s once the cause clears. The arithmetic is `backoff.ts`'s stateless `doublingBackoffDelay`; the session-restart counters (keyed by persona key), 900 s ceiling and 5-failure cap are not used. Returns waits only: no timers or clock, so the caller schedules through its injected timers (SR-13.1). The connection manager (`persona-connections.ts`) keeps one per persona for bring-up retries and Socket Mode reopens; later Epics (directory re-checks, destination retries) consume it too. The server doesn't yet.
    ├── persona-slack-episodes.ts  b.av2 SR-10.3 cause-start / cause-clear latch for Slack validation log lines, so `persona-slack-unreachable` is logged when the cause starts and when it clears, not on every attempt. `createSlackEpisodeTracker` takes one persona (name, key, entry position, credentials-file path, optional logger) and `record(outcome)` returns the lines it produced. An episode is a run of outcomes of one class. When an episode starts it emits one line (`persona-slack-unreachable`, or `persona-credentials-refused` naming the key, check and Slack error code). When it ends, because the persona comes up or the class changes, it emits one cleared line with the same class label and a cause starting `cleared: `. A change of reason within Slack-unreachable stays in the same episode. A third episode kind, connection lost, opens when a connection that was up drops: it emits one `persona-connection-lost` line, absorbs every Slack-unreachable reopen outcome without a line, and closes with one `persona-connection-restored` line when the persona is up again; a refusal during it ends it silently and emits the `persona-credentials-refused` line in place of the restored line. Lines are built by `formatPersonaDiagnostic` from the outcome's own fields; with an injected logger each is emitted exactly once. No module-scope state or timers, so two personas' trackers are independent. The connection manager (`persona-connections.ts`) drives it, one tracker per persona, and is the only emitter of these lines for its personas; the server doesn't use either until E3.
    ├── persona-slack-clients.ts  b.av2 SR-3.3 / SR-13.1 Slack client factory and option sets for persona connections. Three client kinds, each built through the injectable `PersonaSlackClientFactory`: the long-lived Socket Mode client (app token); a short-lived validation Web API client used only for `auth.test` (bot token); and the long-lived Web API client every posting path will use (bot token). Settings, in prose: library auto-reconnect is off on the Socket Mode client. The Socket Mode client's own Web API calls and the validation client make no retries, time out after 10 s and reject rate-limited calls instead of waiting. The long-lived Web API client times out each attempt after 30 s and keeps the library's default retry policy (ten retries with randomised backoff over about 30 minutes) and its rate-limit waiting, as the live server's client has today. None of the three attaches the original request to its errors. Why: the library defaults reconnect and retry on their own (the socket client retries opening up to 100 times), set no request timeout, and attach the raw request error, Authorization header included, to request errors. Each option builder returns a fresh object, so no option object is shared between clients or personas. `PRODUCTION_SLACK_CLIENT_FACTORY` is the only place a token is handed to a Slack library, and it passes the token and options through unchanged. Also holds the 10 s `start()` bound and the 10 s / 30 s request-timeout constants. Nothing is constructed, read or logged at import.
    ├── persona-connection-errors.ts  b.av2 SR-3.3 / SR-10.3 token-safe description of thrown values and the process-level `unhandledRejection` handler. `describeThrownValue` renders any thrown or rejected value as one line holding only the constructor name (or the value's type for a non-`Error`), the `code` when it is a short identifier (letters, digits, `_`, `$`; a Slack token contains `-` and can never pass), and up to 10 stack frame lines after the message has been cut out of the stack. It never reads the message, `original`, headers, request config or `data`, never serialises the value and never throws. `createUnhandledRejectionHandler(log)` returns a listener that logs one `[slack] unhandled rejection (process keeps running): …` line built with the describer and returns: it never throws (a throwing logger is swallowed), rethrows or exits, so one persona's stray rejection cannot take the process down. The module never installs it; E3 does. Pure: no module-scope state, no environment access, nothing at import.
    ├── persona-connections.ts  b.av2 SR-3.1 (module part) / SR-3.2 / SR-3.3 / SR-3.4 / SR-10.3 / SR-13.1 supervised per-persona Slack connection manager. Per persona, `createPersonaConnectionManager` validates, then connects: a short-lived validation client runs `auth.test` and is discarded, then one long-lived Web API client and one long-lived Socket Mode client are built. The three client kinds and their settings are in the `persona-slack-clients.ts` entry. A persona is up only once `auth.test` returned both the bot user ID and the bot ID and the socket's `start()` resolved. Each `start()` bounds its WebSocket phase at 10 s; one that never settles is abandoned and counts as Slack-unreachable, not broken. Slack-unreachable is retried with the `persona-retry-schedule.ts` backoff; a refusal leaves the persona credentials-broken. Reopen: when an up persona's socket drops and the manager didn't close it, the first reopen attempt is immediate and later ones use the same backoff; a credentials error on reopen leaves the persona disconnected and credentials-broken. Every event reaches the handler tagged with its persona's key, and a handler throw affects no other event or persona. All state lives in one entry per persona: no lock, queue or timer spans two personas, and no handling path reads another persona's connection. Dry run (SR-3.4) calls no factory method, needs no credentials and makes no Slack call: each persona is up at once with a distinct placeholder identity derived from its key. The process-level `unhandledRejection` handler is exported from `persona-connection-errors.ts` for E3 to install. The Slack client factory, clock and timers are injected, as `createCronScheduler` takes its clock; nothing is created, read or scheduled at import. Not yet wired: `server.ts` still uses its single module-scope clients from `tokens.ts` until E3 wires this module in.
    ├── persona-notifier.ts     b.av2 SR-7.1 / SR-7.2 per-persona server notices. `createPersonaNotifier({ getPersona, clientFor, isDryRun, log })` returns `notify(key, text, options?)` and `flush(key)`; neither throws or rejects. A notice goes only to the persona's destination (its `permission_prompts` channel), posted through the persona's own Web client from `clientFor(key)` as one top-level message with only channel and text, so it appears under the persona's identity. The notifier prefixes every body with `Persona "<name>" (key=<key>): `, so callers pass the key and the body only. Routing, in order: an unknown key logs one line and drops the notice; dry run logs the persona reference and the notice's first line, with no Slack call; a `dm` destination is logged with the full text, not posted and not held (DM notices arrive in E7); a channel destination whose client is not validated yet (`clientFor` returns undefined) is held in that persona's own queue in raised order; otherwise it is posted. `flush(key)` posts that persona's held notices in raised order once its client is validated and never touches another persona's queue; a notice raised for a validated persona that still has held notices posts after them. A failed post logs one token-safe line (`describeThrownValue`) and calls the notice's `onPostFailure` callback; there is no retry. Also exports `formatPersonaNotice`, `firstNoticeLine` and `notifySafely` (calls an injected notify sink so that a throw or rejection goes to an error callback). Pure (b.av2 SR-13.1): no module-scope state, no I/O of its own, nothing at import; each instance holds its own queues. `server.ts` builds one instance and installs it in outage state, the session manager and the JSONL safeguard.
```

## Data Flow

### Inbound (Slack → Claude Code)

1. Slack message arrives via Socket Mode (`message` or `app_mention` event). Both socket handlers call `handleMessage` and nothing deduplicates them, so a channel @mention (which Slack sends as both events) is dispatched to the bot twice with the same `ts`.
2. `gate()` checks access control (bot messages, subtypes, DM policy, allowlist)
3. If `ackReaction` is configured, the ack emoji is applied to the message and `trackAck(channelId, messageTs)` records the pending ack for later removal
4. Message is routed to the correct session via `getSessionByPersona()` (called with the channel ID, which is the persona key under the transitional route→persona adapter) or `getSessionByCwd()`. If the channel is configured (has a `routes` entry, or resolves via `default_route`) but its session is not registered, the message is dropped — it is never delivered to Claude or replayed — and the server posts a per-case reply back to the channel (b.kvq). If a restart is already pending/active it says the session is restarting; if under the failure cap and auto-restart is enabled it calls `scheduleRestart(..., { humanTrigger: true })` (fast human-clamped recovery) and says the session is starting; if at the cap or auto-restart is disabled (`session_restart_delay: 0`) it says the channel will not self-recover and an operator must restart the server. `default_route` does not apply for configured channels; it is only consulted for channels with no entry in `routes` at all.
5. Session's MCP Server sends `notifications/claude/channel` to the Claude Code client

### Outbound (Claude Code → Slack)

1. Claude Code calls MCP tools (`reply`, `react`, `edit_message`, etc.)
2. The tool handler resolves the calling persona at call time from the session's registered persona key (`SessionToolDeps.getPersona`). A session not yet matched to a persona, or whose key is no applied persona, gets a tool error.
3. `checkPersonaTarget()` checks the tool's target (`chat_id`, or `channel` for `fetch_messages`) against the persona's configured channels. Anything else is refused with a tool error naming the persona and the target, before the dry-run branch and with no Slack call. Under the route→persona adapter a persona's only channel is its route's channel, so replies to DMs and to channels reached through `default_route` are refused, and their ack reaction is never removed, until E3 Task 7 stops delivering those messages. `reply` also runs `assertSendable()` on every file before any Slack call, and again on each file right before its upload so a file swapped in between is still caught; a refused file is a tool error.
4. The tool resolves the persona's Web client at call time (`SessionToolDeps.clientFor`; until E3 Task 9 this is the single module-scope client for an applied persona once Slack is validated) and makes the Slack call with it, with no username or icon override. `download_attachment` authorises file fetches with that client's bot token, sent only to `https://files.slack.com` URLs. It refuses external (non-Slack-hosted) files and never follows a redirect off that origin with the header. A Slack call failure is logged token-safely and returned as a tool error naming the persona. A missing client or token is also a tool error.
5. After the first chunk posts, if `message_id` was provided and `consumeAck(channelId, messageTs)` finds a tracked entry, the ack reaction is removed via `reactions.remove`

### Slack Reply Guard (Stop hook)

`stop-hooks/slack-reply-guard.sh` runs in every bot session whose config dir the bootstrap patched (startup step 4a-ter). It reads the transcript once with a single `jq` pass and fails open (exit 0) on any error, missing input, or missing `jq`.

1. **Retry pass-through.** `stop_hook_active=true` exits 0 immediately, so the reminder fires at most once per turn.
2. **Trigger run.** A real user entry has `type=="user"`, is not `isSidechain` or `isCompactSummary`, and has at least one text block. The run is every real user entry after the nearest non-sidechain assistant entry preceding the latest real user entry. Claude Code can write queued channel messages as consecutive user entries, so the run can hold several. Tool-result-only entries, sidechain entries, and compaction summaries neither join nor end the run.
3. **Envelope.** Only an opening `<channel …>` tag at the very start of an entry's text (after optional whitespace) is an envelope; a tag later in the text is quoted body and is ignored. The envelope is Slack iff its `source` starts with `slack`. Attributes are read by name.
4. **Injected check.** A Slack envelope is injected if `user` starts with `cscb-cron:` or `ts` is present and does not match `^[0-9]+\.[0-9]{6}$`. Slack event timestamps always have six fractional digits; `/interject` stamps `String(Date.now() / 1000)`, which has at most three. The `/interject` `user` is a caller-supplied label, so `ts` shape is the identifying signal. An envelope with no `ts` counts as real Slack. No real Slack envelope in the run → exit 0.
5. **Reply check.** An assistant `tool_use` named `mcp__slack-channel-router__reply` anywhere after the earliest real Slack entry in the run → exit 0. Because the whole run is checked, an injected message queued right after a human's Slack message does not hide it.
6. **Reminder.** Otherwise exit 2 with a declinable reminder on stderr naming the provenance from the `chat_id` of the last real Slack envelope in the run: an ID starting with `D` gets the direct-message wording (`conversation <chat_id>`), any other Slack-shaped ID gets the channel wording (`channel <chat_id>`), and a missing or non-`^[A-Z0-9]+$` `chat_id` gets the channel wording without the parenthetical. README.md shows the direct-message and channel texts.

The envelope is rendered by the Claude Code harness from the MCP notification's `meta`, so the tag name and the `chat_id`/`user`/`ts` attribute names are a harness-owned contract. The injected check also couples the guard to two CSCB-side formats: the `cscb-cron:` sender prefix (`src/crontable.ts`) and the `/interject` `ts` form (`src/server.ts`). Changing `/interject` to emit a six-decimal `ts` would make every non-cron `/interject` turn trigger the reminder.

### Permission Relay (SR-2)

Driven by polling against the agent-director Client + Block Kit click → `decide()`. The previous HTTP long-poll + hook script architecture has been deleted. Per-row Slack prompts: N concurrent `tool_use` blocks in one Claude Code assistant response produce N Slack messages, each independently allow/deny-able.

#### Wire surface (paired AD release)

CSCB consumes four AD verbs:

- `client.list({ state: ['check_permission'], label: ['service=cscb'] })` — returns spawn rows in the permission state.
- `client.get({ claude_instance_id })` — returns the row plus a plural `permission_requests` projection. Each element carries `request_token`, `request_id`, `tool_name`, `tool_input`, `requested_at`. The array may be empty (spawn has no open prompts). `null` / `undefined` in the slot is non-conforming.
- `client.decide({ claude_instance_id, decision, request_token })` — JSON snake `request_token`, CLI `--request-token`. Always required; absence yields `ErrInvalidFlags`. The wrapper `decideWithToken` in `agent-director-client.ts` is the single decide-wire serializer (SR-7.2).
- `client.getPermission({ request_token })` — single-row read, no state filter. Returns full PermissionRequestInfo plus `decision`, `decision_reason`, and `decided_at`. Not-found surfaces as `ErrPermissionRequestNotFound` (matched via `isErrPermissionRequestNotFound`).

#### In-memory state (SR-1)

`livePermissions: Map<string, LivePermission>` keyed on a composite `(claude_instance_id, request_token)` encoded by `makeCompositeKey` (null-byte separator — neither component can contain `\x00`). One entry per outstanding Slack prompt. `LivePermission` carries `claudeInstanceId`, `requestToken`, `channelId`, `messageTs`, `requestId` (log-only — never used for routing, keying, action-id encoding, or decide-wire payload per SR-1.4), and a `handled` flag. Lifecycle helpers `getLivePermission(cid, token)`, `markHandled(cid, token)`, and `dropPermission(cid, token)` all operate on the composite key. The tick is the sole owner of `dropPermission`; the click handler may only call `markHandled` (SR-1.2).

#### Per-tick flow (SR-2)

1. `list()` → spawns currently in `check_permission`.
2. For each spawn, `get()` returns the plural `permission_requests` projection.
3. Non-conforming response (`permission_requests` is `null` or `undefined`): log + skip processing for that spawn this tick. The spawn's existing live entries are excluded from the closure sweep below (no state mutation — SR-2.1).
4. For each row in `permission_requests`, compute the composite key. If not in `livePermissions`: post one `chat.postMessage` per row (no coalescing — SR-2.2) and insert one map entry. If already present: no-op (duplicate-tick safe). An empty projection produces no posting activity but does not exclude the spawn's live entries from closure reconciliation. An empty projection also feeds the wedge detector (below).
5. **Set-diff closure reconciliation (SR-2.4):** `tokens_in_livePermissions − tokens_seen_this_tick = newly_closed_tokens` (with non-conforming spawns' entries protected per step 3). For each newly-closed token, call `getPermission(request_token)`. On success, render the verdict (below) via one `chat.update` against `entry.messageTs`, then drop the entry. On `ErrPermissionRequestNotFound`: render generic deny, drop, do not retry. On transient error: leave the entry alive — the next tick retries.

#### Verdict rendering (SR-5)

The closure `chat.update` produces four visually-distinct surfaces driven by `decision` + `decision_reason`:

| `decision` | `decision_reason` | Rendering |
|---|---|---|
| `allow` | `null` | `*Permission* — Allowed` |
| `deny` | `'operator'` | `*Permission* — Denied by operator` |
| `deny` | `'timeout'` | `⏱ *Permission* — Timed out` |
| `deny` | `'find_missing'` | `🪦 *Permission* — Session ended` |
| anything else | anything else | `*Permission* — Denied (closed)` (fail-closed, log) |

`ErrPermissionRequestNotFound` collapses to the same generic-deny rendering (fail-closed log + drop, no retry). `decision_reason` is read verbatim from AD; CSCB does not derive, override, or infer it (SR-5.1). Unknown enum values do not crash the poller (SR-5.2). The `chat.update` targets only the closed row's `messageTs`; sibling rows are never touched in response to one row's closure (SR-5.3).

#### Click handler (SR-4)

`handlePermissionClick` decodes `(decision, claude_instance_id, request_token)` from the action_id and calls `decideWithToken(client, { claude_instance_id, decision, request_token })` unconditionally — this is the click's only AD interaction (SR-4.3). No `get` refetch, no "already decided" branch.

- `ErrAlreadyDecided` → swallowed silently. The next tick's reconciliation (SR-2.4) owns the visible Slack state.
- `ErrRelayFallenBack` (b.qi1) → logged loudly, prompt message repainted, no session-level action. See the note below.
- `ErrInvalidFlags` / `ErrAmbiguousRequest` → logged once, no retry, no operator-visible signal.
- Unknown error types → logged, no retry.

On a successful decide *and* a live entry present, the handler renders one `chat.update` against just that row's `messageTs` (SR-4.5) carrying text byte-identical to the poller's SR-2.4 verdict surface — `*Permission* — Allowed` for allow, `*Permission* — Denied by operator` for deny — then calls `markHandled`. Matching the verdict text exactly means there is no visible flicker when the next tick's reconciliation lands on the same message. A stale click (no entry in `livePermissions`) still fires the decide call with the decoded token — AD is the source of truth and returns idempotent results — but produces no `chat.update` from the click path; the next tick's verdict rendering handles the message.

**b.qi1 `ErrRelayFallenBack` — loud surfacing, no session-level action.** agent-director 0.10.0 raises this from `decide` when the request's relay window has elapsed: Claude Code already gave up on the relay and re-asked at its own tmux pane, so AD refuses to record a verdict nothing will read. It is a *decide-path* error, not a spawn error — the spawn ladder in [Server-Managed Startup](#server-managed-startup-sr-11-event-1) cannot see it, and `handlePermissionClick` is its only reachable call site. The spawn itself is alive and healthy; only that one prompt can no longer be answered from Slack. The handler therefore logs a `[slack]`-prefixed line, emits `cscb.ad_decide.attempted{result_class:"ErrRelayFallenBack"}`, and — when a live entry is still present — renders one `chat.update` over that row's `messageTs` reading `*Permission* — relay window elapsed; answer this prompt at the session's tmux pane`, stripping the now-inert buttons, tagged `click_handler_relay_fallen_back`.

No delete, no respawn, no retry. Re-deciding fails identically (the window is already closed), and a respawn would destroy a healthy session over one un-relayed prompt while plausibly falling back again — the re-fallback loop the b.jgf delete+fresh policy would have walked into here. `markHandled` is deliberately **not** called: this is not a verdict and the AD request row stays open, so a later poller closure (timeout, `find_missing`, or the answer given at the pane) must remain free to render over the same message.

The Slack user id is intentionally NOT surfaced in the rendered text. An earlier draft of this design rendered "Allowed by <user>" / "Denied by <user>" as immediate operator feedback, but the SR-2.4 reconciler overwrites the message one tick later with the user-less verdict surface, producing visible flicker for the operator who clicked. The simpler, flicker-free design renders the verdict text on both the click path and the reconciliation path.

#### Wedge detector (b.fae F4)

A spawn can wedge permanently in `check_permission` with an **empty** `permission_requests` array: the underlying incident is a permission decision that AD recorded but could not deliver (the relay hook was killed before AD's poll deadline), leaving Claude Code blocked on a native TUI prompt with no open AD row and no hook that will ever fire again to advance state. To the poller this is a valid conforming response with zero rows, so before b.fae it was a silent no-op every tick — no log, no Slack message, no trail event ("the bot appears dead").

The detector counts consecutive ticks a spawn is observed in `check_permission` with an empty projection. The trip threshold is derived from the poll interval — `wedgeTripTicks(intervalMs) = max(5, ceil(90000 / intervalMs))`, roughly 90 s of wall-clock — because a genuine wedge takes minutes to develop while a normal decided-then-closing spawn passes through the empty state only briefly. The counter is reset **only on a positive observation** that the spawn is not wedged — open rows present, its state changed, or it's confirmed gone via `ErrSpawnNotFound`. A spawn skipped in a tick because of a transient `get` error or a non-conforming response does **not** have its counter reset, so a single flaky AD connection can't silently defer a genuine wedge alarm.

On trip it logs, emits the `cscb.poller.wedge_detected` trail event, and posts a **one-shot** top-level channel warning. Warning delivery is **fail-safe**: the `warningFired` latch is set **only after a successful `chat.postMessage`**. If the post fails, the trail event still records the attempt (`ok:false`) and the poller retries the post on later ticks — throttled to one attempt per `wedgeWarnRetryTicks(intervalMs)` (~30 s of wall-clock, `WEDGE_WARN_RETRY_WALL_CLOCK_MS`) so a Slack outage can't storm the API at the poll interval — until one succeeds, after which the latch sets and the episode posts nothing further. The warning tells the operator to inspect the native prompt with `agent-director read-pane --claude-instance-id <id>` then kill and respawn the session; it explicitly does **not** offer `send-keys`, which AD's relay guard (`pkg/api/sendkeys.go`) hard-rejects while `relay_mode=on && state=check_permission`. The detector re-arms per spawn the moment it leaves the wedged condition (an open row appears, or the spawn disappears from the tick), so a later genuine wedge warns again. State is in-memory (`wedgeStates` map) and resets on daemon restart.

#### Action ID encoding (SR-3)

Block Kit buttons emit `action_id` strings of the shape `perm_(allow|deny)_<claude_instance_id>_<request_token>`, where `<request_token>` is a UUIDv4. The anchored decoder regex uses the UUIDv4 character class (`[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}`) as an outer-structure anchor — it disambiguates the rightmost boundary of the middle (underscore-bearing) `claude_instance_id` capture so embedded underscores in `cscb_<key>` remain safe. CSCB does NOT validate the token's bytes; the regex shape only fixes the parse boundary (SR-1.3 + SR-3.1). The `request_id` field is no longer part of the action_id payload and is retained on `LivePermission` for logging only (SR-1.4).

#### Version pin (SR-6)

AD's library-side `Client.create()` reads `dist/version-floor.json` (`.min_binary_version`) and is the sole enforcement point for the runtime floor. The system-installed AD binary is probed by `resolveSystemBinary()`, compared against the declared minimum, and rejected via `ErrSystemInstallTooOld` (which the startup gate `instanceof`-matches → `ad-system-install-too-old` class label). CSCB's `package.json` caret on `agent-director` only governs npm resolution of AD's TypeScript shim; it does NOT participate in the runtime floor decision. The startup gate (`runStartupGate` in `src/agent-director-startup.ts`) is the sole compatibility boundary — no runtime code path degrades to the prior singular-projection or coalesced-prompt behavior on version mismatch (SR-6.2). The three new typed-error class labels are `ad-system-install-not-found`, `ad-system-install-too-old`, and `ad-system-install-unreachable`; see [Startup errors](../README.md#startup-errors).

Operators have an alternate diagnostic entry point via `bun run install-check` (`scripts/install-check.ts`). The script calls `runInstallCheck()` from `src/install-check.ts` — the same shared module the Epic-3 install-cscb skill consumes — and emits a single block on success or a class-labelled stderr block on failure. Beyond the three typed errors, the shared module surfaces `ad-version-floor-unreadable` when the AD package's `dist/version-floor.json` is missing, malformed, or lacks `.min_binary_version` (a packaging defect; remediation is to reinstall `agent-director` from npm, and the manual-skill-install block is intentionally NOT appended on this class).

#### API surface probe (SR-6.1)

A passing `Client.create()` proves only that the system-installed `agent-director` binary meets AD's declared `min_binary_version`. It does NOT prove the published npm package's TS shim is in sync with that binary — agent-director's `0.6.0` release shipped a stale shim whose `Client` dropped `getPermission`, whose `buildDecide()` dropped `--request-token`, and whose error catalog omitted three err_names CSCB branches on. Each defect fails silently at runtime (clicks resolve against the wrong row, error-envelope branches miss because the shim's `errorFromEnvelope` fallback constructs a base `AgentDirectorError` with `.errName` copied verbatim from the input rather than raising), so the gate runs three short-circuit probes after `Client.create()` resolves and before the same-user stat. The probes are dependency-injected via `StartupGateDeps` so tests can drive each failure path directly; the production defaults live alongside in `src/agent-director-startup.ts`.

| Probe | Default check | Failure `classLabel` |
|---|---|---|
| `probeGetPermission` | `typeof client.getPermission === 'function'` | `ad-shim-missing-get-permission` |
| `probeErrorCatalog` | Reads the resolved `agent-director` dist file and confirms each of `ErrInvalidFlags`, `ErrPermissionRequestNotFound`, `ErrAmbiguousRequest` appears as a word-boundary identifier in the bundled JS — same static-file approach as `probeDecideArgv` (a behavioral `errorFromEnvelope` round-trip cannot detect catalog drift because the shim's unknown-name fallback constructs a base `AgentDirectorError` with `.errName` copied verbatim from the input) | `ad-shim-catalog-incomplete` |
| `probeDecideArgv` | `import.meta.resolve('agent-director')` → `readFileSync` of the dist entry → string-contains `--request-token` (no subprocess, no state-DB write) | `ad-shim-decide-drops-token` |

On any probe failure, the gate closes the Client, records the operator-readable message to `startup-errors.log`, and exits non-zero — the same shape as the SR-6 version-pin failure. The remediation in every case is the same: reinstall a matching `agent-director` and confirm the resolved package actually carries the missing surface.

#### What this replaces

Three pre-Epic-4 mechanisms have been retired:

- The four-case per-spawn reconciliation matrix (and its sibling-stomping `updateNoLongerActive()` helper that edited a prior row's Slack message in response to another row's arrival) is gone. Sibling rows are now first-class state from the moment they appear in the plural projection.
- The click handler's prior get-then-stale-rerender branch (a refetch + "already decided" `chat.update` issued without calling decide) is gone. `decideWithToken` is the click's only AD interaction.
- The single-prompt coalescing of multiple concurrent `tool_use` blocks is gone. N parallel tool_uses → N Slack prompts.

AskUserQuestion is denied at the agent-director template (SR-3.1's `deny: ['AskUserQuestion']`) — the tool is unavailable to every CSCB-spawned bot and the prior `/ask` HTTP route + hook script have been removed.

The template also carries a narrow `allow` list (b.fae) pre-authorizing bot reads of their own persistent-memory directories. The rules are **derived per config** by `deriveMemoryReadAllowRules(personaConfig, home?)` rather than hardcoded. Each applied persona contributes its effective `claude_config_dir` (its own, else the top-level one, already resolved on the persona) — the directory `session-manager.ts` `buildSpawnParams` exports as `CLAUDE_CONFIG_DIR` at spawn. A persona with none uses Claude Code's default `<home>/.claude` (`resolveClaudeConfigDir`, home read at call time), and a config with no personas still gets the default-dir rule. The distinct dirs are de-duplicated and sorted, and one rule is emitted per dir:

```
Read(//<abs-config-dir>/projects/*/memory/**)
```

So a deployment whose personas use `~/.claude-infhub` and `~/.claude` yields those two rules, but a single-config or default-only deployment yields just one. Memory-note reads always require confirmation in Claude Code; without this rule they round-trip to a human as a native TUI permission prompt (the prompt class that wedged the relay in b.fae). **The scope is deliberately limited to `projects/*/memory/**` and must not be widened to the config-dir root** — that root holds live credentials (`settings.json` `ANTHROPIC_API_KEY`, `.claude.json` OAuth/token content), so a root-level allow would silently pre-authorize reads of billing credentials. The `//` prefix is Claude Code's absolute-path-from-filesystem-root anchor for Read rules.

### Scheduled Prompts (cscb_cron)

The server fires scheduled prompts from a crontable into bot channels once per minute. The flow crosses four modules — crontable → scheduler tick → dispatcher → the server's own `/interject` → cron log — and is driven entirely by `src/cron-scheduler.ts`'s single minute-aligned timer (decision 8; no per-job timers exist).

Managed sessions learn the crontable path via the `CSCB_CRONTABLE_PATH` export documented in the [Environment Variables](#environment-variables) section.

#### Wiring and startup

The scheduler is constructed and started in `main()` (`server.ts`) **after** `Bun.serve()` is listening, because it is its own `/interject` client — it must POST to a live listener. This is the opposite placement from `startPermissionPoller`, which starts before `Bun.serve`. Wiring is guarded on `routingConfig`: the env-var fallback path constructs nothing cron-related. The dispatcher is handed the server's ACTUAL bound port (`httpServer.port`, covering port-`0` configs), the config-resolved `cron_log_path` and `cron_table_path`. Any construction or `start()` failure is non-fatal — the server keeps serving without a scheduler; `shutdown()` calls `cronScheduler.stop()` alongside `stopHealthCheck`/`stopPermissionPoller`.

`start()` runs, in order: (1) the crontable bootstrap — `ensureCrontableExists`, which this `start()` is the SOLE caller of; a missing crontable is created with the template header and an info line, and the scheduler proceeds with zero schedules; (2) the initial read + parse of the table through the same shared load path the tick's reload step uses, each parse error becoming one `parse-error` outcome line (identity/channel `-`); (3) exactly one `scheduler started, N schedules loaded` info line — the PD-4 outage-window marker, since there is no catch-up, this line is the only bound on a missed-fire window; (4) arming the tick. `start()` is failure-isolated and never throws out to the server.

#### The tick (reload → match → dispatch)

The timer is a self-re-arming `setTimeout` chain aligned to the top of each minute (not `setInterval`), so ticks are serialized — a pass never overlaps the next, which is the property the hot-reload depends on: the in-memory table is swapped between whole passes, never mid-pass. Each pass, in decision-8 loop order: (1) re-load the crontable if it changed (see [Hot-reload](#hot-reload) below) — this step never dispatches and never re-arms the timer; (2) stamp the current wall-clock minute and skip the whole pass unless it is strictly after the last-ticked minute — the **monotonic guard**, so a backwards clock jump cannot re-fire already-fired minutes (matches Vixie cron), and, because it sits *after* the reload, also the protection against a double-fire across a reload — a minute already processed is never processed again, whichever generation of the table is in memory; (3) match every in-memory schedule against that minute in **server-local time** via croner (DST is croner's, D-Q3); (4) per match, consult the at-most-once `Map<schedule instance, epoch minute>` — keyed on the compiled-schedule instance (identity), NOT raw line text, so two identical operator lines are two distinct schedules that EACH fire (plain cron semantics, PD-6); only the SAME loaded schedule reappearing twice in one pass is skipped and logged as a loud `SCHEDULER BUG` info line, otherwise the instance is recorded and the match collected; (5) prune map entries older than the current minute. All matches for the minute are handed, in crontable line order, to the dispatcher.

**No catch-up (PD-4):** a tick fires only the minute observed at its start; if a pass overruns the next minute top, that minute is simply skipped — specified behavior, not a bug. A minute with no matches does nothing and logs nothing. The `(schedule instance, minute)` at-most-once assertion is a **logged bug signal**, not the dispatch mechanism — the minute-aligned single pass already makes a double-fire structurally impossible; because the key is the compiled-schedule instance rather than raw line text, two identical operator lines are distinct schedules that each fire (PD-6) and never trip the assertion — only the same loaded schedule firing twice in one pass does. The `SCHEDULER BUG` line is an info line kind, deliberately NOT an outcome class, so it never pollutes the `grep http-error` network-failure triage view. It is likewise not the cross-reload double-fire protection — that is the monotonic guard's job. There is NO rate cap, backlog cap, busy-detection, session-state check, or queue-depth throttle anywhere in the tick (owner gate answers 1-2).

#### Hot-reload

The crontable **file**, not the in-memory copy, is the runtime source of truth. Step (1) of each tick stats the crontable and compares `(mtimeMs, size)` for *inequality* against the last successful load — not ordering, so a backwards `touch` still reloads. Unchanged means no read, no log, no work. Changed means re-read, re-parse, re-compile, and swap the array; the swap only ever replaces the whole table, and it never dispatches and never touches the timer chain.

There is deliberately **no `fs.watch`, no watcher, and no dirty flag.** A swap can only take effect at a tick anyway, and a single-file watch drops the atomic-save rename that is the mandated write pattern, so a per-tick stat is both sufficient and cheaper to reason about. A successful tick reload writes one `crontable reloaded, N schedules` info line; `start()`'s initial load deliberately emits no such line (it has its own `scheduler started` marker).

Parse errors are logged **once per reload, not once per tick**, because the recorded stat is updated on every successful read — including a read whose content has bad lines — so an unchanged broken file stays quiet. A mid-write read needs no special handling: the parser is PD-6-tolerant, so healthy lines survive and keep firing, and the completed write is a further stat change the next tick picks up.

**Deleted file (D-Q1).** ENOENT drops to **zero schedules immediately** — nothing stale ever fires behind a deleted crontable — forgets the recorded stat, and emits a latched `crontable vanished … — 0 schedules until it is restored` warn-kind line. The warn kind is what distinguishes this from the first-install info line. The *next* pass attempts the re-create through `cron-bootstrap.ts`: an exclusive create, so if a human or a bot restored the file with content first, the bootstrap reports `already-exists` and that content loads intact; otherwise the empty template header is created (zero schedules) and logged with re-creation wording distinct from the first-install line. A persistent re-create failure stays silent — the vanish warn already latched the condition, and it must not repeat once a minute.

**Other stat/read failures.** Any non-ENOENT errno (EACCES, EIO, …) **keeps the currently loaded schedules firing** and emits one latched warn naming the cause and the schedule count. Because a failed load never updates the recorded stat, recovery (a `chmod`, say) is picked up by the next tick's inequality check, which clears the latch and logs the normal reload line.

#### The fire path (dispatcher → /interject → cron log)

For each match the dispatcher (`src/cron-dispatch.ts`) resolves the prompt path and reads the prompt FRESH at fire time (never cached — an edited prompt takes effect next fire), applies the D-Q5 pre-checks (skip, never truncate), and POSTs `{channel, message, sender}` to `http://127.0.0.1:<port>/interject`. `sender` is the schedule identity `cscb-cron:<prompt-file-basename-without-extension>` (D-Q4) — without it `/interject` defaults `senderLabel` to `interject` and a cron fire is indistinguishable from peer-bot traffic. HTTP status maps to outcome class: 200 → `delivered`, 503 → `no-session` (decision 1 — NO retry, no queue, no `scheduleRestart`), 404 → `unknown-channel`, any other status or a network failure → `http-error`. Every outcome plus one per-fire summary (`delivered`/`failed` counts) is appended to the cron log. A channel-less (all-bots) line is matched but logged `fanout-deferred` and NOT dispatched — no read, no POST — with a `delivered=0 failed=0` summary; fan-out is not yet enabled.

**Same-minute matches deliver independently.** Each matched schedule is delivered on its own — its own freshly-read prompt, its own `/interject` POST with `sender` = its schedule identity, and its own outcome line and per-fire summary. When several crontable lines match the same minute for the same channel, each one arrives as its own message; they are not combined.

The cron-log outcome classes are defined once in [cron.log](#cronlog-cron_log_path) — the taxonomy there is authoritative; this subsection does not restate the class names.

**Bind constraint.** The scheduler POSTs to `127.0.0.1`, so a `bind` on a single non-loopback interface leaves no loopback listener and every fire fails connection-refused → `http-error`. `bind` must include loopback (the default `127.0.0.1`, or `0.0.0.0`) for scheduled fires to work. This is log-visible and accepted; no loopback detection is added.

## Session Lifecycle

### Connection

1. Claude Code sends POST to `/mcp` (no session ID) → `initPendingSession()` creates a pending session
2. MCP handshake completes → `server.oninitialized` fires → `handleInitialized()` calls `roots/list`
3. The first root's directory (tilde-expanded, made absolute) is matched by real path against the applied personas' working directories (`matchPersonaByRootsPath`). On a match to exactly one persona the pending session is promoted in place to the registered session for that persona key, with the real path as its `cwd`; a newer session for the same persona replaces the older one (logged as `Session replaced existing connection for persona …`). With no persona config, no matching persona or an ambiguous match, the pending session is removed and its transport closed.
4. Session receives messages from its assigned Slack channel
5. A keep-alive timer is started (`startSseKeepAlive`) that writes SSE comment frames (`:ping\n\n`) every ~30 s to prevent idle connection drops from proxies or load balancers

### Server-Managed Startup (SR-11 Event 1)

Called from `main()` in `server.ts`. The order is:

1. **SR-5.1 startup gate** — `runAgentDirectorStartupGate()` awaits `createClient(opts)` (production injects `Client.create`), which runs AD's library-side discovery + floor enforcement against `dist/version-floor.json`. The opts carry `logger: makeFilteredAdLogger(console)` (b.brv) so the Client's per-poll `SubprocessClient: <verb> ok` success dumps are dropped from `server.log` unless `CSCB_AD_VERBOSE` is set — see [Logging](#logging). On success the gate installs the constructed Client into the singleton via `setClient(client)` so subsequent `getClient()` call sites resolve to it, and the success-arm `adVersion` is read from `client.binaryVersion`. The construct-step catch ladder `instanceof`-matches `ErrBunVersionTooOld` (→ `ad-bun-version-too-old`), `ErrSystemInstallNotFound` (→ `ad-system-install-not-found`), `ErrSystemInstallTooOld` (→ `ad-system-install-too-old`, message names detected + required versions), and `ErrSystemInstallUnreachable` (→ `ad-system-install-unreachable`, message surfaces AD's `err.reason` verbatim); the three `ad-system-install-*` branches append the `install-skill-pointer.ts` manual-skill-install instructions block to their `recordStartupError` output. CSCB no longer performs a post-Client floor check — AD owns it. Then runs the SR-6.1 API surface probes (`getPermission` presence, error-catalog round-trip, `--request-token` in the dist) and stats `~/.agent-director/state.db` against `geteuid()`. Failure writes to `startup-errors.log` and exits non-zero.
2. **PID conflict check** — existing `checkPidConflict(PID_FILE)` invariant. CSCB enforces one instance per host.
3. **SR-3.2 template refresh** — `installSlackChannelBotTemplate(personaConfig)` builds the SR-3.1 `MakeTemplateParams` and calls `client.makeTemplate({ ..., overwrite: true })`. Atomic replacement is the library's responsibility (sibling-tempfile + `rename(2)`). Fatal on rejection. It runs after the stand-in persona config is set; just before it, `main()` installs `trustPatchPersona` as the session manager's pre-launch trust patcher (`setPreLaunchTrustPatcher`), ahead of the Slack socket, `Bun.serve` and `initRestart`, so no launch path runs unpatched.
4. **b.av2 SR-6.3 start sweep** — `reconcileOrphans(personaConfig)`, run before the trust patch and any spawn. `client.list({ label: ['service=cscb'] })` enumerates every CSCB spawn, and each row is judged by its `persona` label against the applied personas. A row is killed + deleted when any of these holds, checked in this order:
    - it has no `persona` label (`no persona label`) — this includes every row spawned by a build that predates persona labels, so the first start of this build replaces those bots with fresh spawns (their transcripts stay on disk, unresumed);
    - its `persona` label names a persona absent from the applied set (`absent persona`);
    - its instance ID is not that persona's `cscb_<key>` (`wrong instance ID`);
    - its `cwd` differs from that persona's working directory by real path (`wrong cwd`, via `compareRowToPersona`).

    Every other row is kept for step 5. The sweep does not read the interim `channel` label; the permission poller and the CLI's `stop --stop-bots` lookup still do. Each removed row logs `[slack] reconcileOrphans: sweeping row (<reason>) persona=<persona> instanceId=<id> state=<state> — killing and deleting`, with ` cwd=<row cwd>` before the dash for `wrong cwd`; `<persona>` is `"<name>" (key=<key>)` for an applied persona, the raw label value for an absent one, and `<no persona label>` otherwise. A failed kill still attempts the delete. Kill and delete failures record `orphan-cleanup` (`kill failed for orphan instanceId=<id> persona=<persona>: <ErrName>`, likewise `delete failed …`) and a list failure records `orphan-cleanup-list-failed`; none blocks startup. Dry run skips the sweep and logs `[slack] dry-run: skipping orphan reconciliation`.
4a-bis. **b.uhv / b.k54 trust-bootstrap** — `trustBootstrap(personaConfig)` (from `src/trust-bootstrap.ts`) runs over the applied personas: for each persona's working directory it patches the `.claude.json` in the persona's effective `claude_config_dir` (its own, else the top-level one) so the Claude Code trust-folder dialog never appears at launch. Each persona is patched once, however many channels it lists. It reads `<dir>/.claude.json` and ensures `projects[<working_directory>].hasTrustDialogAccepted` and `projects[<working_directory>].hasCompletedProjectOnboarding` are both `true`. Idempotent: when both flags are already `true` the file is not rewritten (verifiable via unchanged `mtime`). Writes are atomic (`.tmp` + `renameSync`), and the read-modify-write is fully synchronous, so two personas sharing one config dir cannot lose each other's update. Soft-skip behavior: a persona with no configured `claude_config_dir` logs `[slack] trust-bootstrap: "<name>" (key=<key>) has no claude_config_dir — skipping` and continues without recording an error (Claude uses its own default; there is nothing to patch). A missing or unreadable `.claude.json` logs an info line and calls `recordStartupError('trust-bootstrap-config-missing', '"<name>" (key=<key>): cannot read <path>')` — the file is never auto-created. Malformed JSON records `trust-bootstrap-config-parse`, and any unexpected per-persona failure records `trust-bootstrap` (`unexpected error for "<name>" (key=<key>) cwd=<dir>`). The function never throws to the caller, so one bad persona cannot block the rest. Runs in both real and dry-run modes — it's a config-file patch, not a session operation. The call site is in `main()` right after step 4 (`reconcileOrphans`), before any spawn fires.

    - **Per-launch patch (b.av2 SR-6.2).** The same patch also runs before every launch: `trustPatchPersona(persona)`, installed as the pre-launch trust patcher, runs at the top of every ladder run — fresh spawn, resume or restart (see step 5 and Auto-Restart step 5). At launch time a patch failure is logged only, as `[slack] trust-bootstrap: pre-launch patch failed [<class>] <detail> — <cause>` with the same class names, and never adds a `startup-errors.log` entry; a missing `.claude.json` therefore logs two lines (the info line and the failure line). The start pass records failures as described above.
4a-quater. **b.zak JSONL-persistence safeguard** — `runJsonlPersistenceSafeguard(personaConfig, notify)` (from `src/jsonl-persistence-check.ts`), run over the applied personas. Call site: `main()` in `server.ts`, immediately after step 4a-bis (`trustBootstrap`) and before step 4a-ter (`stopHookBootstrap`) — critically, **before** step 5's resume path, which silently `delete+fresh`-spawns a memory-less bot when `resume` throws `ErrJsonlMissing`. Detection/reporting only: it never changes resume behavior, never throws, and never blocks startup (wrapped in its own `try/catch` at the call site as well). Every warning is a persona notice: the server passes the per-persona notifier's `notify`, which posts to the affected persona's destination, names the persona, and only logs in dry run. Sibling scope: the lost / never-created / inconclusive classification inside the resume path itself is **b.wrb / b.fwu**, not this module. Two layers:

    - **Layer 1 — non-persistent storage.** `checkJsonlPersistence` resolves the deduped set of the personas' effective `<claude_config_dir>/projects` roots (a persona with no configured dir uses `<home>/.claude`; with no personas at all, the home default root is checked) and classifies each root's mount fstype by longest-prefix match over `/proc/self/mountinfo` (string-prefix, not a stat — a not-yet-created dir classifies by its parent mount). A root on `tmpfs`/`ramfs` → `recordStartupError('jsonl-non-persistent', …)` plus one notice through the notifier to each affected persona's destination — those whose effective JSONL root is the flagged root, not every persona (resume is structurally impossible for those personas on this host). An undeterminable fstype (unreadable/unparseable/unresolvable) → `recordStartupError('jsonl-persistence-check-warning', …)`, no notice.
    - **Layer 2 — per-persona transcript loss.** For each applied persona it fetches the persona's AD row (through `withOutageDetection`, the sanctioned CSCB→AD entry point). A row the collision ladder will spawn fresh instead of resuming — its `cwd` differs from the persona's working directory by real path, or its `config_dir` label is missing or mismatched (`compareRowToPersona`, the same check as step 5's guards) — is not checked: one log line naming the persona, the mismatch (the row's `cwd` against the working directory, or the missing or changed `config_dir` label) and that the transcript was not checked because the collision ladder will spawn fresh, with no record and no notice. Otherwise, when the row carries a `claude_session_id`, it stats the AD-recorded `jsonl_path` **and** a config-dir-aware fallback path composed the same way agent-director composes it (`resolveJsonlPath`, under the persona's effective config dir). Outcomes: persisted exists → healthy, silent. Persisted stale/missing but fallback exists → `recordStartupError('jsonl-transcript-stale-path', …)` + a notice through the notifier to that persona's destination (history is on disk but AD 0.8.0's resume only stats the persisted path, so it would throw `ErrJsonlMissing` and wipe the persona's memory). Both missing → the `message_archive_db` archive (when configured) is consulted for evidence under the b.av2 SR-7.4 rule (`personaArchiveEvidenceScope`): only messages in the persona's `delivery: all` channels since `started_at` count, in one query over all of them. A persona with no `delivery: all` channel counts 0 without the archive being opened (even when none is configured), and since every persona has a channel or DMs on, that persona always takes (once `started_at` parses) the unattributable-zero path below. A count ≥1 → `recordStartupError('jsonl-transcript-lost', …)` + a notice to that persona's destination saying its conversation memory has been lost (conversation provably happened, transcript is gone). A zero count for a persona with any `delivery: mentions` channel or DMs on is not evidence of idleness, because the archive cannot attribute messages from `mentions` channels or DMs to a persona: one quiet log line saying the archive evidence is inconclusive (`UNATTRIBUTABLE_ZERO_REASON`), no record and no notice. The archive check is read-only: a missing archive DB file yields no evidence (it is never created here). Both missing with no archive evidence → a single quiet log line only: a persona idle since spawn has no transcript yet because Claude creates the `.jsonl` lazily on first message — normal, not an error, and must not alarm every boot. Log lines name the persona as `"<name>" (key=<key>)`. Per-persona AD/get errors (including `ErrSpawnNotFound`) are logged and skipped; the sweep never aborts.
4a-ter. **b.osj stop-hook bootstrap** — `stopHookBootstrap(personaConfig)` (from `src/stop-hook-bootstrap.ts`) patches `<claude_config_dir>/settings.json` for every applied persona's effective config dir to install (or remove) the CSCB-managed Slack Reply Guard Stop hook. Call site: `main()` in `server.ts`, immediately after step 4a-quater (`runJsonlPersistenceSafeguard`) and before step 5 (`startupSessionManager`) — before any spawn fires. Runs in both real and dry-run modes (config-file patch, not a session operation). Never throws to the caller; per-dir failures are caught and recorded via `recordStartupError`. Behavior:

    - **Grouping / aggregation (SR-3.5).** The applied personas are grouped by the real path of their effective `claude_config_dir` (the persona's own, else the top-level one), resolved with `resolveRealPath` (lexical fallback), so personas reaching one dir through a symlink share one group and its `settings.json` is patched once, at the first contributing persona's configured path. For each dir the aggregate `anyEnabled` flag is the OR of each persona's effective `stop_hook_bootstrap` (its own, else the top-level one) across all personas resolving to it. Diagnostics name the contributing personas as `personas="<name>" (key=<key>), …`. `anyEnabled=true` → ensure the managed entry; `anyEnabled=false` → remove it (and prune emptied groups).
    - **Managed-entry shape.** Own group `{"hooks":[{"type":"command","command":"<abs>"}]}`, no `matcher` field (Stop is not tool-scoped). Recognition rule: any Stop-hook `command` string containing the substring `slack-reply-guard.sh` is CSCB-managed.
    - **Canonical command resolution.** `resolveManagedCommand()` resolves the script path relative to the installed package (same idiom as `src/install-skill-pointer.ts`), correct under both published-package layout and repo checkout. Stale on-disk commands from a prior install path are treated as managed and rewritten to the canonical path (self-heal).
    - **Idempotent write decision.** `scanStopGroups` returns `hasSingleCanonicalGroup=true` only when there is exactly one Stop group whose sole hook entry has `type=='command'`, `command==canonicalCmd`, no `matcher`, and no extra keys. In that state the write is skipped entirely. Any drift — stale command, duplicates, extra keys, extra hooks in the managed group — triggers a strip-all-managed + append-canonical rewrite via `.tmp` + `renameSync` (trust-bootstrap precedent).
    - **Create-missing.** ENOENT on the target `settings.json` for an enabled dir → the file is created with just the managed group.
    - **Malformed JSON soft-fail.** Non-ENOENT read errors, unparseable JSON, and non-object top levels all call `recordStartupError` with a class label of `stop-hook-bootstrap-settings-read` / `stop-hook-bootstrap-settings-parse` / `stop-hook-bootstrap-settings-shape` and leave the file untouched — never a clobber.
    - **Personal-config-dir refusal (SR-3.11).** `isForbiddenHomeClaudeDir` resolves both the candidate dir and `homedir()/.claude` through `resolveRealPath` from `src/config.ts` (`realpathSync`, with a lexical `resolve()` fallback whenever realpath fails), so symlinked personal dirs cannot slip past a string compare. On a match the dir is skipped and `recordStartupError('stop-hook-bootstrap-refuse-home', …)` is recorded.
    - **Skip conditions.** Personas with no effective `claude_config_dir` are logged (`[slack] stop-hook-bootstrap: "<name>" (key=<key>) has no claude_config_dir — skipping`) and skipped. Empty or whitespace-only dirs are treated as absent (guards against `resolve("")` landing in the process cwd). A dir that fails `statSync` (or is not a directory) is skipped; the ensure path records `stop-hook-bootstrap-dir-missing` / `stop-hook-bootstrap-not-a-dir`, the remove path is silent.
    - **jq presence check.** A one-time `command -v jq` probe at boot: if `jq` is absent the entry is **still installed** (the hook fails open at hook time when `jq` is missing) but a `stop-hook-bootstrap-jq-missing` startup error is recorded so operators see the warning.
    - **Duplicate collapse and removal (SR-3.7, SR-3.8).** When rewriting an enabled dir, every managed `{type, command}` object across every Stop group is stripped before the canonical group is appended, so pre-existing duplicates collapse to one. Removal for a fully-disabled dir strips every managed object and prunes any group left with an empty `hooks` array.
    - **Never-throws contract.** A top-level `try/catch` around the whole entry point plus per-dir `try/catch` blocks record `stop-hook-bootstrap` / `stop-hook-bootstrap-dir` classes on unexpected failure. Other dirs continue processing. Timing note (SR-3.15): on-disk state is refreshed every boot, but Claude Code only reads the hook config at claude-process start — a live session that survives a CSCB restart via reconnect keeps its running process and picks the new entry up only on next fresh spawn or resume.
5. **Per-persona reconcile** — `startupSessionManager(personaConfig, { concurrency: 3 })` iterates the personas concurrently and calls `spawnForPersona` (SR-1.4 collision-then-act dispatcher) once per persona, so a persona listed in several channels is spawned exactly once. Until the persona loader switch the persona set comes from the transitional `route-persona-adapter.ts`: each route becomes a stand-in persona keyed by its channel ID, with one `delivery: all` channel (that channel), permission prompts to that channel and DMs off. Spawn-path log lines name the persona JSON-quoted with the key beside it, e.g. `spawnForPersona: spawned "C0123" (key=C0123) …`; under dry run each persona logs `dry-run: skipping spawn for "<name>" (key=<key>) cwd=<dir>` and nothing is spawned.
   - **Trust patch before every launch (b.av2 SR-6.2).** Each ladder run first calls the installed pre-launch trust patcher (`trustPatchPersona`, see step 4a-bis) for the persona's working directory in its effective config dir — once, before the first spawn or resume the ladder can make, so it covers fresh spawns, resumes and the replacement spawns below. It never runs under dry run and never for a call that joins an in-flight launch. A throw is logged as `[slack] spawnForPersona: pre-launch trust patch failed for "<name>" (key=<key>) — launching anyway: <error>` and the ladder continues.
   - Attempt `client.spawn(SR-1.1 params)`, built from `persona-identity.ts` (b.av2 SR-2.2):
     - `template: 'slack-channel-bot'`, `relay_mode: 'on'`, `cwd` = the persona's working directory.
     - `claude_instance_id: cscb_<key>`, `tmux_session_name: slack_bot_<key>`.
     - `label: ['service=cscb', 'persona=<key>', 'config_dir=<12 hex>', 'channel=<key>']`. The `config_dir` value hashes the real path of the persona's effective `claude_config_dir` (`personaConfigDirLabelValue`; no configured dir means `~/.claude`). The trailing `channel=<key>` label is transitional: the permission poller and the CLI's `stop --stop-bots` lookup still read it, and it goes once they read the `persona` label. The start sweep (step 4) and the ladder read the `persona`, `config_dir` and `cwd` fields, never `channel`.
     - `extra_env`: `CSCB_PERSONA=<key>`, `CLAUDE_MANAGED_CHANNEL=<key>`, `CSCB_CRONTABLE_PATH` on every spawn (the resolved tilde-expanded `cron_table_path`: the default `<config dir>/crontab` or the configured override), and `CLAUDE_CONFIG_DIR` only when a `claude_config_dir` is configured (passed as configured, not real-pathed).
   - **Never two live instances (b.av2 SR-6.3).** The instance ID is fixed at `cscb_<key>`, so agent-director refuses a second spawn for a persona that already has a row (`ErrInstanceIdCollision`), and the ladder below decides what happens to that row. Within the process, `spawnForPersona` allows one in-flight launch per persona key: a second call for a key whose launch is still running — from the start pass, a restart or a human-triggered restart — logs `[slack] spawnForPersona: launch already in flight for "<name>" (key=<key>) — joining it` and returns that launch's result instead of starting a second ladder. The entry is cleared when the launch settles, whatever its outcome; different keys never wait on each other. Dry run returns before the check.
   - On `ErrInstanceIdCollision`, call `client.get({claude_instance_id})` and keep the whole row. **`cwd` guard (b.av2 SR-6.2)** first, before any state branch and so before any `findMissing` sweep or reconnect: a row whose `cwd` differs from the persona's working directory by real path (`compareRowToPersona`; a symlink to the directory matches, a row with no `cwd` never does) is never resumed, reconnected or waited on, whatever its state and `resume_enabled`. It logs `[slack] spawnForPersona: "<name>" (key=<key>) row cwd=<row cwd> differs from working_directory=<dir> (state=<state>) — replacing the row: kill+delete+fresh`, then `replaceWithFreshSpawn` kills it (best effort), deletes it and spawns fresh (outcome `spawned`). A row that also fails the `config_dir` check below is handled here. At start the sweep (step 4) has already removed such rows, so this guard mostly catches runtime relaunches. Otherwise branch on state per the [SR-11 substitution table](#sr-11-substitution-table):
     - **`config_dir` guard before any resume (b.av2 SR-6.2).** `resumeOrFreshSpawn` compares the row's `config_dir` label (from the collision `get` above) with `personaConfigDirLabelValue` of the persona's current effective `claude_config_dir`, through `compareRowToPersona`. It runs after the `resume_enabled=false` branch and after the `reconcileMissingFirst` sweep (b.4dk), immediately before `client.resume(...)`, so it covers both the `ended`/`missing` resume and the dead-session resume. A missing or different label means no resume: agent-director's resume carries only the instance ID and would bring the session back under its old `CLAUDE_CONFIG_DIR`. The row is deleted (killed first on the dead-session paths, whose row may still be live) and spawned fresh through `replaceWithFreshSpawn`, outcome `spawned`. The old history stays in the old config dir; no transcript was lost, so neither `diagnoseJsonlMissing` nor an amnesia action runs. Log: `[slack] spawnForPersona: "<name>" (key=<key>) config_dir label missing (label absent, now=<hex> for claude_config_dir=<dir>) — not resuming; spawning fresh`, or `config_dir label changed (was=<old hex>, now=<new hex> for claude_config_dir=<dir>)` with the same tail; `<dir>` is `<default>` when none is configured. The fresh spawn then logs `[slack] spawnForPersona: fresh-spawned (after delete) for "<name>" (key=<key>)` (`after kill+delete` on the dead-session paths and for the `cwd` guard).
     - `ended` / `missing` + `resume_enabled` → `config_dir` guard above, then `client.resume(...)`; `ErrNoSessionId` / `ErrJsonlMissing` / `ErrJsonlNeverWritten` → `client.delete(...)` + fresh `client.spawn(...)`; `ErrSpawnNotFound` (row vanished between the dead-session verdict and resume — operator delete, expire, race) → fresh `client.spawn(...)` directly with no delete (the row is already gone), action `spawned`. On `ErrJsonlMissing` specifically, `diagnoseJsonlMissing` runs **before** the delete (see the b.wrb / b.fwu note below) — the delete+fresh policy itself is unchanged — and the resulting fresh spawn returns action `fresh-after-amnesia` (definite lost/never-created verdict) or `fresh-after-inconclusive-amnesia` (b.fwu — diagnosis inconclusive) rather than `spawned`, so the startup summary never counts a memory-loss recovery as an ordinary clean spawn. `ErrNoSessionId` and `ErrJsonlNeverWritten` take the same delete+fresh recovery but skip the diagnosis entirely and return plain `spawned` (b.jgf — see the note below).
     - `ended` / `missing` + `resume_enabled=false` → `client.kill(...)` + `client.delete(...)` + fresh `client.spawn(...)` through `replaceWithFreshSpawn` (never reaches the `config_dir` guard); an `ErrTmuxSessionCreate` on that spawn takes the b.vub self-heal like the other fresh-spawn paths.
     - `waiting` → `reconnectMcp(key)` sends `/mcp reconnect slack-channel-router` via `client.sendKeys(...)`. If that reconnect finds the tmux session dead (`'dead-session'` verdict), fall through to `resumeOrFreshSpawn(..., { reconcileMissingFirst: true })` — see the note below.
     - `working` → `waitForWaitingAndReconnect(...)` runs an up-front `findMissing({})` sweep via the shared `reconcileMissingSweep` helper (b.m4r — see note below), then polls `client.status(...)` until `waiting`, then sendKeys; a `'dead-session'` verdict likewise falls through to `resumeOrFreshSpawn(..., { reconcileMissingFirst: true })`.
     - **b.4dk dead-session recovery — `reconcileMissingFirst`.** After a reboot/pod-resume a `waiting`/`working` row is frozen live-state but its tmux session is gone. AD's `resume` verb only accepts a terminal (`ended`/`missing`) row, so on such a row it throws `ErrSpawnNotResumable` and the defensive branch (line above) kill+delete+fresh-spawns — losing all history. When `reconcileMissingFirst` is set (only the two dead-session callers set it), `resumeOrFreshSpawn` runs a `findMissing({})` sweep via the shared `reconcileMissingSweep` helper before `resume`. AD's per-row, evidence-based sweep (requires agent-director ≥ 0.8.0, plan b.93m t1.93m.hp: degraded-mode guard removed) transitions the dead row to `missing`, so the subsequent `resume` succeeds and restores the pre-reboot transcript (provided the row passes the `config_dir` guard, which runs after this sweep). Skipped when `resume_enabled=false`. A `findMissing` error → fall through to `resume` anyway (which then kill+delete+fresh-spawns, today's behavior). The `ended`/`missing` collision branch above does NOT set the flag (row already terminal).
     - **b.m4r `working`-row stall — up-front `findMissing` sweep.** A bot killed mid-turn (e.g. its tmux session dies) never fires `SessionEnd`, so its AD row freezes at `working`. Without a reconcile, `waitForWaitingAndReconnect`'s poll loop spins on `status` for the full `WAIT_FOR_WAITING_TIMEOUT_MS` window (10 min) before the timeout verdict finally returns `'dead-session'` — the channel stays down that whole time. `waitForWaitingAndReconnect` therefore runs AD's per-row, evidence-based `findMissing({})` sweep before entering the poll loop (requires agent-director ≥ 0.8.0, same b.93m t1.93m.hp capability as the `reconcileMissingFirst` path). A genuinely-dead row reconciles to `missing`, so the **first** status poll hits the ended/missing branch and returns `'dead-session'` in seconds; a genuinely-alive long-turn row is untouched by the evidence-based sweep and keeps the existing polling behavior (long-turn guard preserved). On any `findMissing` error, the sweep is logged and skipped and the poll loop proceeds unchanged (today's behavior). This prefers AD's `findMissing` verb over a CSCB-side tmux probe, mirroring `resumeOrFreshSpawn`'s `reconcileMissingFirst` branch (docs/engineering-guide.md, "Avoiding Duplicated Effort").
     - **b.ecw terminal verdicts key on the claude PROCESS, not the raw tmux session.** Once b.93m Part E landed (AD ≥ 0.8.0: degraded-mode guard removed, `findMissing` verdicts per-row and evidence-based), the two dead-session branches in `waitForWaitingAndReconnect` decide off AD's process-level verdict rather than a raw `tmux has-session` probe. AD probes the *claude process*; CSCB's `_hasTmuxSession` probes the *tmux session* — a lingering tmux shell with a dead claude process would flip the two, so each branch documents which object it keys on:
       - **ended/missing branch (in-loop):** keys on the process. `ended` means `SessionEnd` fired (process exited); `missing`, after the up-front sweep, is an evidence-based verdict that the process is provably gone. Returns `'dead-session'` directly — **no tmux probe**. A dead process in a live tmux shell is still a dead bot; routing it to `resumeOrFreshSpawn` lets b.vub's `selfHealTmuxCollisionAndRespawn` reap the orphan tmux shell on `ErrTmuxSessionCreate`. (The former tmux-alive → `'ok'` behavior deferred a dead channel to the health-check for minutes.)
       - **timeout branch:** keys on the process via a **fresh** `reconcileMissingSweep` (the 10s memo has long expired at the 10-minute deadline) + one `status` call. `ended`/`missing` → `'dead-session'`; any live state (working/waiting/ask_user/check_permission/pending) → `'ok'` (a process mid-long-turn is not an error — the b.rmy/b.3ce long-turn guard, now keyed on the process). The raw tmux probe survives here **only as a fallback**: on `ErrSpawnNotFound` (AD row gone, nothing to consult) or any other `status` error, fall back to `_hasTmuxSession` (alive → `'ok'`, gone → `'dead-session'`) so an AD outage can't manufacture a false `'dead-session'` — the b.rmy invariant.
       - **ErrSpawnNotFound branch (in-loop):** keys on the tmux session by design (b.c3o) — no AD row exists, so there is nothing to reconcile or consult; only a direct probe of the deterministic session name is available. Unchanged.
     - **b.m4r shared memoized sweep — `reconcileMissingSweep`.** Three sweep callers go through one shared `reconcileMissingSweep` helper rather than calling `client.findMissing({})` inline: this `working`-row up-front sweep, `resumeOrFreshSpawn`'s `reconcileMissingFirst`, and the tick/restart escalate-dead path (via the exported `sweepDeadTmuxChannel` wrapper, which prepends its unconditional operator log then delegates here — `reconcileMissingSweep` itself stays module-private). Because `findMissing({})` is a whole-store, idempotent sweep, a fleet restart — `startupSessionManager` runs once per persona at `concurrency=3`, and every `working`-row collision plus each dead-path `reconcileMissingFirst` would otherwise fire its own whole-store sweep — is collapsed by single-flight (concurrent callers share one in-flight sweep promise) plus a 10s TTL memo (a caller arriving just after the last successful sweep reuses that result). This sheds the redundant N-sweep amplification without changing recovery behavior; failures are never memoized, so the next caller after an error re-sweeps. The post-reboot fleet-wide case (b.nk5 — `/tmp` wiped, every channel dead-tmux at once) is served correctly: one in-flight-shared sweep reconciles the whole store for every simultaneously-escalating channel. The 10s memo TTL is harmless against the ~120s health-check tick cadence: a memoized-stale answer on the escalate-dead path costs at most **one** extra tick, because the following tick's escalate-dead sweeps again well past the TTL. (The `reconcileMissingFirst`/`working`-row callers are startup-clustered within one boot rather than tick-spaced, so they benefit from the memo directly.)
     - `pending` / `check_permission` / `ask_user` → no-op (poller picks it up).
     - **b.wrb `ErrJsonlMissing` diagnostic — legible amnesia, unchanged policy.** When resume throws `ErrJsonlMissing` the delete+fresh recovery is unchanged, but `diagnoseJsonlMissing` runs first (before `tryDelete`, while the doomed row's `jsonl_path` / `claude_session_id` / `cwd` / `started_at` are still readable) to make the loss legible. It is a sibling of the b.zak safeguard (step 4a-quater), which runs *before* the resume path; this one runs *inside* it, on the row resume actually failed to open. Never throws. Two things happen:
       - **Path + provenance logging.** AD's `ErrJsonlMissing` description enumerates every transcript candidate it stat'd as `<source> <path> (<stat error>)`, joined by `"; "` — a capability AD's bug `b.1ba` delivered, introduced in agent-director v0.10.0. When the description carries that enumeration, `parseJsonlMissingCandidates` parses it and logs the candidates verbatim, labelled *paths+sources reported by agent-director*. The parsed source tokens are `persisted` (AD's recorded `jsonl_path`), `fallback` (its `CLAUDE_CONFIG_DIR`-aware recomputed path), and `history` (an archived `session_history` entry). When the description does **not** match that shape — a pre-0.10.0 AD, or any AD whose message wording differs — the parse yields nothing and CSCB reconstructs the candidates locally instead: the persisted `jsonl_path` column plus a `CLAUDE_CONFIG_DIR`-aware fallback via `resolveJsonlPath` and the persona's effective `claude_config_dir` (its own, else the top-level one), labelled explicitly *locally computed* so a reader never mistakes a CSCB-side reconstruction for what AD actually stat'd. The parse keys off those literal source tokens, not any version string, so it degrades cleanly in both directions.
       - **lost / never-created / inconclusive classification (b.fwu).** Using b.zak's read-only `makeDefaultArchiveCount` / `rfc3339ToEpochSeconds` helpers over `message_archive_db`, bounded by `started_at`, and the b.av2 SR-7.4 scope from `personaArchiveEvidenceScope` (the same helper step 4a-quater's Layer 2 uses), `diagnoseJsonlMissing` counts archived messages only in the persona's `delivery: all` channels since `started_at` and returns one of `'lost' | 'never-created' | 'inconclusive'`:
         - **lost** — archive shows ≥1 message since spawn in the persona's `delivery: all` channels, real conversation history destroyed. Made operator-visible via `recordStartupError('jsonl-transcript-lost-on-resume', …)` (startup only) **and** a notice through the notifier to the persona's destination ("my conversation memory has been lost and I was started fresh").
         - **never-created** — strictly evidence-based: the archive was actually consulted and returned 0 messages since spawn, and that zero is attributable — the persona has no `delivery: mentions` channel and DMs off, so its `delivery: all` channels carry all of its traffic. The transcript was never written (Claude creates the `.jsonl` lazily on first message; expected and lossless). One quiet log line only.
         - **inconclusive (b.fwu)** — "no evidence either way": the AD row fetch failed, `started_at` was absent or unparseable, the count was 0 but the persona has a `delivery: mentions` channel or DMs on (b.av2 SR-7.4: the archive cannot attribute messages from `mentions` channels or DMs to a persona, so the zero proves nothing — `UNATTRIBUTABLE_ZERO_REASON`; a persona with no `delivery: all` channel counts 0 without the archive being consulted, so once `started_at` parses it always gets this reason, even when `message_archive_db` is not configured), `message_archive_db` is not configured, or the archive read failed. Previously these fell through to a reassuring `never-created`/console-only `unknown`, silently downgrading a possible real loss. Now each emits `recordStartupError('jsonl-diagnosis-inconclusive', …)` carrying the reason (row-fetch failed / started_at absent or unparseable / zero count not attributable / archive unconfigured / archive read failed) **and** a notice through the notifier to the persona's destination, worded as *uncertainty* ("on restart I was started fresh; I could not determine whether my prior conversation history was preserved") — deliberately distinct from the `lost` wording, since a false "your history was destroyed" is its own harm. When `message_archive_db` is unconfigured the operator message states diagnosis is impossible because no message archive is configured, with a hint to enable it.

         All three outcomes still take the same delete+fresh recovery (policy unchanged). `lost` and `never-created` surface as the `fresh-after-amnesia` action; **inconclusive** surfaces as the new `'fresh-after-inconclusive-amnesia'` action (see the honest-summary note below). This is distinct from b.zak's `jsonl-transcript-lost` class (which fires *pre-resume* to warn of an impending wipe); `jsonl-transcript-lost-on-resume` records a wipe that just happened on the row resume tried and failed.
     - **b.jgf `ErrJsonlNeverWritten` — the ceremony-free branch.** agent-director 0.10.0 split the old "resume cannot open a transcript" condition into two typed errors, and CSCB branches on both. `ErrJsonlMissing` means a transcript path was recorded but is not there now: history *may* have existed and been destroyed, and that ambiguity is exactly what the b.wrb / b.fwu diagnosis above exists to resolve. `ErrJsonlNeverWritten` asserts the opposite — the session produced no transcript at all — which proves there is nothing to lose, so the fresh spawn is lossless by construction. It therefore shares the delete+fresh recovery but none of the ceremony: `diagnoseJsonlMissing` and the `fresh-after-*` actions are gated on `instanceof ErrJsonlMissing`, so this branch emits one informational log line, raises **no** persona notice, records no startup-error class, and returns plain `spawned` — the same shape as the `ErrSpawnNotFound` branch. Returning a successful action is the load-bearing part: `restart.ts` treats `failed` as retryable, so before b.jgf this error fell to the generic failure tail and the channel retried the one operation that could never succeed, on a doubling backoff, posting a spawn-failure message each pass. This branch is also the resume-path counterpart of the b.zak Layer 2 policy in step 4a-quater: a channel that has been idle since spawn has no transcript yet because Claude creates the `.jsonl` lazily on first message — normal, not an error, and it must not alarm.
   - `ErrSpawnNotFound` race after collision → single retry-spawn.
   - Other errors → `notifySpawnFailure(key, error)` raises a spawn-failure notice through the per-persona notifier to the persona's destination. A notice raised while the persona's client is not yet validated is held in that persona's queue; in dry run it is only logged.
   - **Scope of this ladder.** It classifies only errors raised by the spawn/resume verbs (`spawn`, `get`, `resume`, `delete`, `kill`, `sendKeys`, `status`) — it is not a catalog of every AD error class CSCB handles. Decide-path errors are classified at their own call site: the only CSCB caller of AD's `decide` verb is `handlePermissionClick`, so `ErrAlreadyDecided`, `ErrInvalidFlags`, `ErrAmbiguousRequest`, and b.qi1's `ErrRelayFallenBack` are branched on there (see [Click handler (SR-4)](#click-handler-sr-4)) and never reach this ladder or its generic tail.
   - **Pre-session dialog approval (b.uhv / b.k54 / b.vub — defense-in-depth).** `approvePreSessionDialogs(key, …)` runs after every fresh spawn (9 sites across `runPersonaLadder`, `resumeOrFreshSpawn` and `replaceWithFreshSpawn`, including the `ErrTmuxSessionCreate` self-heal respawns) and after every successful `resume`, because a resumed bot faces the same dev-channels dialog. One loop handles both known dialogs; `PRE_SESSION_DIALOG_NEEDLES` holds their option labels, `TRUST_DIALOG_NEEDLE` (`'Yes, I trust this folder'`) and `DEV_CHANNELS_DIALOG_NEEDLE` (`'I am using this for local development'`), both verified against Claude Code 2.1.120. Each dialog pre-selects its accept option, so a single Enter accepts it.
     - Every `DIALOG_POLL_INTERVAL_MS` (500 ms) it asks `client.status` for the `cscb_<key>` row and returns as soon as the row reaches a live state (`waiting`, `working`, `ask_user`, `check_permission`). `ErrSpawnNotFound` also returns.
     - A `pending` row is read through `client.readPane({ n_lines: 40, allow_pending: true })`. When any needle is on screen it sends Enter through `client.sendKeys({ text: '', allow_pending: true })`. Enter is never sent without a visible needle, so no stray Enter reaches a live prompt.
     - A resumed row stays `ended`/`missing` while the dialog blocks `SessionStart`, and AD refuses to read or type into such a row. For those states the loop reads the pane with raw `tmux capture-pane` on the persona's `slack_bot_<key>` session and sends Enter with raw `tmux send-keys`.
     - An `ended`/`missing` row with no needle for `DIALOG_DEAD_GRACE_POLLS` (20) polls in a row counts as a dead spawn: `recordStartupError('dev-channels-approve-spawn-died', …)` at startup, then return. A needle resets the count.
     - At the `DIALOG_READY_TIMEOUT_MS` cap (5 min) it records `dev-channels-approve-not-ready` at startup and raises a spawn-failure notice for the persona.
     - A fresh spawn that shows no dialog reaches a live state on its own and the approver returns quietly. The trust patch (step 4a-bis, repeated before every launch) is the primary fix for the trust dialog, so the expected path is that it ran for this launch and no trust dialog appears; this loop covers unprovisioned cwds, clobbered trust state and dialog changes in later Claude Code releases.
   - **b.wrb / b.fwu honest startup summary.** `startupSessionManager` tallies each persona's `SpawnPersonaResult['action']` into a per-outcome breakdown and prints `startupSessionManager: complete — N persona(s): N resumed, N fresh-spawned, N fresh-after-amnesia, N fresh-after-inconclusive-amnesia, N reconnected, N no-op, N failed`. `fresh-after-amnesia` (a fresh spawn replacing a resume where the archive gave a definite lost/never-created verdict) and `fresh-after-inconclusive-amnesia` (b.fwu — the same recovery but the diagnosis was inconclusive, so it is *unknown* whether history was preserved) are counted and reported separately; each has its own loud, grep-friendly follow-up line when its count is `> 0`, pointing at the per-persona `ErrJsonlMissing diagnostic` lines. The returned `StartupSessionManagerResult` carries the same breakdown (`resumed` / `freshSpawned` / `freshAfterAmnesia` / `freshAfterInconclusiveAmnesia` / `reconnected` / `noop`) alongside the retained `succeeded` (any non-failed action) and `failed` totals, plus `perPersona` (each persona's key and action). A b.jgf `ErrJsonlNeverWritten` recovery counts as an ordinary `fresh-spawned`, not as either amnesia bucket: no history existed, so counting it as memory loss would overstate the damage. The fresh spawns of the b.av2 SR-6.2 `cwd` and `config_dir` guards also count as `fresh-spawned` (action `spawned`); they add no action or summary line of their own, and their per-persona log lines above say why the row was replaced. A launch that joined an in-flight one returns that launch's action.
6. **Slack auth + Socket Mode connect** — `web.auth.test()` resolves the bot user; `socket.start()` opens the WebSocket.
7. **SR-2.1 poller start** — `startPermissionPoller({ getClient, web, intervalMs: routingConfig.agent_director_poll_interval_ms })`. Single-threaded interval loop; skipped-tick WARN at 5+ consecutive skips.
8. **Flush held persona notices** — in `main()` this runs right after `socket.start()`, the `resetAllToHealthy` call with the applied persona keys and the poller start. The server marks Slack validated, which makes the transitional `clientFor` return the Web client for every applied persona, then calls the notifier's `flush(key)` once per applied persona without awaiting it. Each persona's notices raised before that point post in raised order to its destination; notices raised afterwards post at once. In `main()` this step also runs before steps 4 and 5 (the start sweep, the JSONL safeguard and `startupSessionManager`), so safeguard and startup spawn-failure notices post at once; only notices raised before Socket Mode connects are held. Dry run never marks Slack validated: its notices are logged when raised and none are held.
9. **Health-check poller** — `startHealthCheck()` begins backstop liveness checks via `client.status(...)`.

CSCB does NOT maintain its own `sessions.json` registry. agent-director owns Claude session-id state internally, surfaced via `client.resume(...)` and the SR-11 state machine.

### Disconnection

1. Transport closes → `onsessionclosed` fires
2. A pending session is simply removed. A registered session is removed with `unregisterByMcpSessionId()`, which returns its persona key; a stale close of a session already replaced by a newer one returns nothing and leaves the newer session registered
3. `restartDisconnectedPersona(key, via)` resolves the key to its applied persona and calls `scheduleRestart(key, persona.working_directory)`; a key that is no applied persona is logged and not restarted. The SSE-abort path of a `GET /mcp` stream does the same

### Auto-Restart

Restart guards, backoff, the cap latch and every restart dependency are keyed by persona key (b.av2 SR-6.3; the channel ID under the transitional route→persona adapter), and restart log lines name it as `persona=<key>`, e.g. `[slack] Scheduling restart for persona=<key> in <n>s (backoff)`.

After `scheduleRestart(key, cwd)` is called:

1. **Delay check** — if `session_restart_delay` is 0, restart is skipped immediately.
2. **Backoff timer** — a `setTimeout` fires after `nextBackoffDelay(key, session_restart_delay)` seconds: `min(base * 2^preFailureCount, 900)`, so the delay doubles on each consecutive failure from the `session_restart_delay` base up to a 900 s (15 min) ceiling (`src/backoff.ts`, SR-25). `scheduleRestart` accepts `opts.humanTrigger`; when set, the computed delay is clamped **down** to `HUMAN_TRIGGER_DELAY_CEILING = 5` s (never raised) so a person typing in the channel isn't told to wait out a 900 s backoff. The clamp only shortens the wait — it does not reset the failure counter and does not bypass the re-entrancy guard, so each attempt still counts toward normal backoff/cap accounting. The `scheduleRestart` path itself does not consult the cap — it is cap-exempt (the cap only gates the health-check tick and the inbound message triggers, which check `backoffIsAtCap` themselves before firing, see below). Two triggers reach this path from inbound messages: a session that is *registered* for the channel yet lacks a `_GET_stream` (the streamless branch of `handleMessage`, whose `humanTrigger` `scheduleRestart(ownerChannelId, targetSession.cwd, undefined, { humanTrigger: true })` fires only when the route is live-but-streamless, under the cap, auto-restart-enabled, and not already restarting — b.9cj: this branch no longer calls `notification()` afterward, since the SDK's `send()` would evaporate silently with the stream gone; it returns after triggering recovery and posts the sender an honest per-case reply, matching the b.kvq drop-branch reply shape), and — as of b.kvq — a configured channel with **no** registered session (the "No live session … — dropping message" drop branch in `handleMessage`, its `humanTrigger` `scheduleRestart`), which likewise fires unless a restart is already pending/active, auto-restart is disabled (`session_restart_delay: 0`), or the route is at the failure cap. Both branches key every guard and the `scheduleRestart` call on the **owning** channel (`ownerChannelId` — for a direct route that is the inbound channel; for a `default_route` channel or DM it is the direct route whose `cwd === default_route`, resolved via `targetSession.personaKey` in the streamless branch — the owning channel ID under the transitional route→persona adapter), so a `default_route` channel's recovery never spawns a duplicate instance under the inbound channelId. At the cap the inbound path does **not** bypass the cap; only a server restart clears the in-process counter and revives a capped route. In all cases the dropped message itself is lost — recovery starts a session but never delivers or replays that message.
3. **Liveness check** — `isSessionAlive(key)` calls `client.status({claude_instance_id})` and returns true when the state is in `AGENT_DIRECTOR_LIVE_STATES`; `ErrSpawnNotFound` → dead. When alive, `restart.ts` skips the reconnect as "already reconnected" only when the session is connected **AND** its standalone GET SSE stream is present (`RestartDeps.hasSessionStream`, b.9cj); a connected-but-streamless session (`connected === true` but the SDK dropped `_GET_stream`) cannot receive messages, so it is *not* waved through — it proceeds to recovery. If alive and not skipped, `reconnectSession()` first probes AD state and, when the row is `working`, returns `'transient'` without poking the pane — deferring the `/mcp reconnect` send-keys to a later tick so a mid-long-turn session is not corrupted (b.9a7 hazard 2, preserving the b.rmy invariant: a `working` row is never declared dead, only left alone; on a status error it falls through to the reconnect attempt rather than manufacture a false defer). Otherwise `reconnectMcp(key)` runs — main returns `'ok'` | `'failed'` | `'dead-session'` (from a `/mcp reconnect slack-channel-router` send-keys with retry), adapter-mapped to `'success'` | `'transient'` | `'escalate-dead'`. A `'success'` reconnect calls `recordSuccess` (resetting the failure count and cap latch); the non-success branches do **not** `recordFailure`. On `'escalate-dead'` / `'transient'` (including the `working` defer) `restart.ts` does not re-enter `scheduleRestart`; instead the **next health-check tick** re-observes the persona and, if it is still not deliverable (alive-but-disconnected or connected-but-streamless) or has since gone dead, calls `scheduleRestart` again, so a failed/deferred reconnect is retried on a bounded cadence. For the dead-tmux `escalate-dead` case CSCB recovers itself internally: the `_buildReconnectSessionAdapter` mapping awaits `sweepDeadTmuxChannel(key, verdict)` (`src/session-manager.ts`) before returning the verdict. That wrapper emits an operator-visible log line (`[slack] escalate-dead: persona=… verdict=… — tmux session provably dead, triggering internal findMissing reconciliation …`) then runs the memoized `reconcileMissingSweep` (b.m4r), which reconciles the frozen `working` row to `missing`; the next tick then observes `alive === false` and takes the normal kill+relaunch branch. The external `~/startup/find-missing-loop.sh` is now belt-and-braces only — recovery no longer depends on it, and removing it stays a separate operator decision. Not counting here keeps the failure count tied to actual launch attempts (the single counting site, SR-25.1) rather than a non-launch reconnect site — the sweep records neither success nor failure.
4. **Kill zombie** — `client.kill({claude_instance_id})` is best-effort; `ErrSpawnNotFound` is ignored. The kill adapter (`_buildKillSessionAdapter` in `src/server.ts`) first asks `isLaunchInFlight(key)`: when a launch for the persona is already running, it logs `[slack] killSession (restart adapter): launch already in flight for persona=<key> — not killing` and returns without killing. Mid-ladder the row can read dead, so a kill here would take down the process the running launch is bringing up; the relaunch in step 5 joins that launch instead (b.av2 SR-6.6).
5. **Relaunch** — `launchSession(key, personaConfig)` looks up the persona with that key (the channel ID under the transitional adapter; `false` when there is none) and collapses `spawnForPersona`'s richer outcome to a boolean — the single counting site (SR-25.1). Resume vs fresh is decided by the SR-1.4 collision-then-act dispatch (no separate `sessionId` arg from CSCB — agent-director owns resume state), the same persona-keyed ladder as startup, so the b.av2 SR-6.2 `cwd` and `config_dir` guards apply to runtime relaunches too: a row in another directory is replaced, and a row whose `config_dir` label is missing or differs is spawned fresh rather than resumed. Like every launch, the relaunch is preceded by the trust patch for the persona's working directory in its effective config dir (the pre-launch patcher at the top of the ladder; see startup step 4a-bis), and a patch failure there is logged only. The relaunch goes through `spawnForPersona`'s one-in-flight-launch-per-persona rule (b.av2 SR-6.3), so a relaunch that overlaps a still-running launch for the same persona (the start pass or another trigger) joins it and receives its outcome. `restart.ts` counts each `launchSession` result it receives, so overlapping restarts that join one failed launch count that failure once per caller. A joined launch's failure record and notice follow the mode (startup or runtime) of the launch that actually ran, not of the caller that joined it. On a `true` outcome, `recordSuccess` resets the counter and cap latch; on `false`, `recordFailure` increments it.
6. **Cap latch** — after the 5th consecutive failure (`RESTART_FAILURE_CAP = 5`, exported from `src/restart.ts`), `shouldNotifyCap(key, …)` fires once per episode and `onCapReached(key)` calls the session manager's `notifyRestartCapReached(key)`, which raises a synthetic `ErrSpawnCapReached` spawn-failure notice through the per-persona notifier to the persona's destination, with the remediation "restart the server to retry — automatic restarts are suspended for this persona"; **no** further timer is scheduled. A capped channel has no registered session; an inbound Slack message hits the drop branch, which detects the cap (`backoffIsAtCap`) and does **not** fire a restart — firing one would only burn a spawn attempt against a route that cannot come up. The sender is told the channel will not self-recover. Only a **server restart** clears the in-process counter (lost on restart by design) and gives the persona a fresh attempt.

### Health-Check Poller

A periodic backstop that runs alongside the reactive disconnect path. It catches three failure modes that the reactive `onsessionclosed` path misses: (a) sessions that die without triggering a close event (e.g., an externally-killed tmux session); (b) sessions that are alive but MCP-disconnected — an AD live-state row (`waiting` etc.) whose MCP transport is gone, `isSessionAlive === true` yet unreachable; and (c) connected-but-streamless sessions (b.9cj) — `isSessionAlive === true` and `isSessionConnected === true` in the registry, but the SDK has silently dropped the `_GET_stream` map entry, so messages cannot reach the bot. Without (c) an idle streamless session would stay broken forever, invisible to the reactive path. The tick recovers all three.

On each tick:

1. **Persona iteration** — for each persona key / working-directory pair from `HealthCheckDeps.getPersonas()` (production: `buildPersonaWorkList(personaConfig)`, one entry per applied persona however many channels it lists). Every guard call, the disconnected streak and the `cwd-unreachable` outage flag are keyed by persona key (b.av2 SR-6.3); log lines name it as `persona=<key>`, e.g. `[slack] health-check: persona=<key> is at cap — skipping tick (SR-25.3/25.4)`:
   - **Skip if restart pending/active** — `isRestartPendingOrActive(key)` returns true; a relaunch is already in flight.
   - **Skip if at failure cap** — `isAtCap(key, RESTART_FAILURE_CAP)` (injected as `HealthCheckDeps.isAtCap`) returns true; a persona at the consecutive-failure cap is skipped this tick (SR-25.3/25.4), including the alive-but-disconnected reconnect path — a capped persona gets no tick-driven reconnect. The inbound drop branch likewise detects the cap and declines to fire a restart, so a **server restart** is the only path back — it clears the in-process counter and gives the persona a fresh attempt.
   - **Working-directory check** — `statRoute(cwd)` on the persona's working directory clears `cwd-unreachable` for the persona when it exists and raises it otherwise.
   - **Liveness check** — `isSessionAlive(key)` calls `client.status({claude_instance_id})`; the state is checked against `AGENT_DIRECTOR_LIVE_STATES`. `isSessionConnected(key)` (b.9a7, wraps the same registry-`connected` adapter used by restart.ts) reports whether the MCP session is currently connected. `hasSessionStream(key)` (b.9cj, wraps the shared `getSessionByPersona` → `hasGetStreamKey(transport)` probe wired into both `HealthCheckDeps` and `RestartDeps`) reports whether the standalone `_GET_stream` is present.
2. **Dead session** — if the liveness check fails, `scheduleRestart(key, cwd)` is called, delegating to the same restart path used by `onsessionclosed`.
3. **Alive but not deliverable** — if `isSessionAlive` is true but the session is either not connected (`!isSessionConnected`, b.9a7) **or** connected-but-streamless (`!hasSessionStream`, b.9cj), the tick tracks a per-persona consecutive-failing streak and calls `scheduleRestart(key, cwd)` only once the streak reaches **two consecutive ticks**. Both cases land in this branch and share the one streak/debounce, which suppresses the freshly-launched false positive: a booting session that connects (and re-opens its stream) between ticks is never poked. Observing the persona as fully healthy — alive, connected, AND stream present — (or dead) resets/consumes the streak; `_resetHealthCheckState` clears the whole map. `restart.ts` then reconnects an alive-but-disconnected row (deferring a `working` row per Auto-Restart step 3), recovers a streamless one, or relaunches a dead one. This gives time-bounded recovery on the `health_check_interval` (default 120 s) even for idle personas that receive no inbound traffic.

The interval is controlled by `health_check_interval` in `config.json`. If the value is `0`, `startHealthCheck()` returns immediately and no interval is created. `stopHealthCheck()` clears the interval during graceful shutdown, before `cancelAllRestartTimers()` runs.

**Ordering invariant**: `startHealthCheck()` is called only after `startupSessionManager()` returns. Moving it earlier in the startup sequence would risk the poller racing with in-progress launches.

### start command

`start` (CLI subcommand) checks prerequisites (Slack tokens, `config.json`), then **self-daemonizes**: the parent process spawns a detached background child and exits, leaving the child running as the server. Detection of parent vs. child is via the `_CLI_DAEMON_CHILD` env marker.

The parent spawn uses `detached: true` (child becomes its own session leader via `setsid`), `stdio: ['ignore', logFd, logFd]` (stdin from `/dev/null`, stdout/stderr to `STATE_DIR/server.log` — no inherited pipes), and `child.unref()`. This isolates the server from the launcher's session and process group, so killing the launching shell's group does not kill the server. The child re-execs `start` with the marker set, redirects logging to `server.log`, and calls `startServer()`.

**Marker-leak guard (b.acn)**: the `_CLI_DAEMON_CHILD` marker alone is untrusted, because it can leak from an operator wrapper script (e.g. `start-all.sh` / `cscb-up`) into the launching environment. If leaked, the parent daemonize branch would be skipped and the server would run in-place inside the launcher's session — dying when that process group is killed. A genuine daemon child is always a session leader, so `start` requires the marker **and** session-leadership to trust it. `isSessionLeader()` reads the session id (field 4 after `comm`) from `/proc/self/stat` on Linux and compares it to the pid; it fails open (treats the process as a leader) where `/proc` is unavailable, preserving prior behavior on non-Linux platforms. A set-but-not-leader marker is treated as a leak: it is deleted and `start` falls through to the parent path to re-detach properly.

### stop command

`stop` (CLI subcommand) sends SIGTERM to the running server via the PID file at `STATE_DIR/server.pid`. If the process does not exit within `stop_timeout` seconds (default 30 s, configurable in `config.json`), a SIGKILL is sent. A brief 2 s confirmation poll follows the SIGKILL. Stale PID files (process no longer running) are silently removed. A non-zero exit from this phase causes `stop` to exit 1.

Plain `stop` leaves the managed bots running (they are meant to survive server restarts — see [Graceful Shutdown](#graceful-shutdown-sr-11-event-11)). The **`--stop-bots`** flag (b.4dk) additionally exits the bots gracefully, mirroring `clean_restart`'s order: the server daemon is stopped **first**, then the shared `teardownBots` closure runs (the same per-route pause/poll/kill sequence as `clean_restart`, minus the restart phase).

Stopping the server first prevents its `onsessionclosed`/`scheduleRestart` handler (`initPendingSession` in `src/server.ts`) from respawning a just-exited bot mid-teardown — the respawn would delete the bot's `ended` row and history before SIGTERM lands. `directorPause` is an agent-director client subprocess that needs no live CSCB daemon (SessionEnd hooks are wired by agent-director into the spawned claude process and call the AD binary), so teardown works fine after the server is down.

Before teardown runs, `stop --stop-bots` initializes the agent-director Client singleton via the non-exiting startup gate (`initClient` in `CliDeps`, b.qwo) — the same init the `clean_restart` algorithm covers in step 3 below (see there for the b.qps / `incident-2026-09-18-clean_restart.md` root cause). An AD-unreachable initialization or teardown failure is a **loud** `exit(1)`, not a swallowed skip; a config-load failure is best-effort (logged, teardown skipped, but the server stop still succeeds, since the server is already down). A pause-timeout kill escalation does NOT guarantee an `ended` row — that residual case is recovered later by the dead-session `findMissing`→`resume` path.

### clean_restart (SR-11 Event 12)

`clean_restart` (CLI subcommand) stops the server daemon first, then concurrently pauses every managed Claude Code spawn via agent-director, then starts a fresh server. The stop-first ordering prevents the health-check poller and auto-restart logic from interfering with the teardown. It logs to `STATE_DIR/clean_restart.log` via `initLogging()`. `CliDeps` exposes injectable `directorStatus`, `directorPause`, and `directorKill` adapters (the production implementations call `getClient().status/pause/kill`) plus an optional `initClient` (b.qwo) that installs the AD Client singleton before any per-channel work — tests that pre-install a stub via `setClientForTests` omit it. The per-route teardown (steps 4–5 below) lives in a shared `teardownBots(routes, exit_timeout)` closure reused by `stop --stop-bots` (b.4dk).

Algorithm:

1. **Init logging + load config** — `initLogging()` redirects output to `clean_restart.log`. `loadConfig()` provides the `routes` map and `exit_timeout`. Config load failure is fatal.
2. **Stop server daemon** — shells out to `claude-slack-channel-bots stop`, which sends SIGTERM and escalates to SIGKILL after `stop_timeout`.
3. **Init agent-director client** (b.qwo) — this short-lived CLI process does not run the server startup gate, so `getClient()` would otherwise throw. `initClient` (`CliDeps`) installs the Client singleton via the non-exiting `runStartupGate` variant. A gate failure is a distinct loud `exit(1)` — the restart never proceeds to teardown or `start` on top of bots it could not reach. Skipping this init was the b.qps / `incident-2026-09-18-clean_restart.md` root cause: the throw was swallowed and every route reported a bogus "no spawn row — skipping".
4. **Per-route precheck** — `directorStatus(channelId)` returns `null` only when the row is genuinely absent (empty label-list result); "no spawn row — skipping" is printed only in that case. Terminal states (`ended`, `missing`) → skip; otherwise proceed. Any error reaching agent-director (connection refused, uninitialized client, binary unreachable) **propagates** — it is no longer collapsed into a `null`/"no row". Such rejections surface after the parallel loop as a loud aggregate error (see step 6).
5. **Pause + poll** — `directorPause(channelId)` is called; if it rejects, escalate immediately to `directorKill(channelId)`. After a successful pause, `directorStatus(channelId)` is polled with exponential backoff (100 ms start, capped at 2 s, total budget `exit_timeout`). The first poll observing `null` / `ended` / `missing` is treated as clean exit. If the budget is exhausted, `directorKill(channelId)` force-terminates the spawn. On both the escalation and timeout kill paths the kill's outcome decides the channel's fate (b.dnt): a kill failure other than the benign already-gone race (`ErrSpawnNotFound`) is itself a teardown failure surfaced as a rejection in step 6. Teardown is **kill-but-never-delete**: rows are paused/killed but never deleted, preserving each row's `claude_session_id` so the next start can resume with context.
6. **Loud AD-unreachable failure** (b.qwo, b.dnt) — after the parallel loop, any settled rejection (an agent-director connectivity error raised by a precheck in step 4, a poll-loop `directorStatus` in step 5, or (b.dnt) an escalation- or timeout-path `directorKill` that failed with anything other than the benign already-gone race, never a normal terminal-row skip and never an `ErrSpawnNotFound` already-gone kill, both of which resolve quietly) is logged and re-thrown as an aggregate error. `clean_restart` catches it and `exit(1)`, aborting the restart **before** starting a new server. A silent no-op teardown is thus impossible.
7. **Start new server daemon** — shells out to `claude-slack-channel-bots start`. Reached only if teardown completed without an AD-unreachable failure.
8. **Exit** — a non-zero exit code from `start` is propagated and the process exits with that code.

Per-channel polling cadence (100 ms → 2 s cap, `exit_timeout` total) is unrelated to the SR-2.1 permission poller's `agent_director_poll_interval_ms`.

### Graceful Shutdown (SR-11 Event 11)

On `SIGTERM` or `SIGINT`, the shutdown handler:
1. Flips the `shuttingDown` flag (idempotent guard).
2. Calls `stopPermissionPoller()` to stop the SR-2.1 tick.
3. Calls `stopHealthCheck()`, `cancelAllRestartTimers()`, `stopAllKeepAliveTimers()`.
4. Stops the HTTP server, drains pending + active MCP transports.
5. Disconnects Socket Mode.
6. Calls `closeClient()` inside a try/catch to release the agent-director Client handle. The library's `close()` is idempotent and never throws; the catch is belt-and-suspenders.
7. Removes the PID file.

The bots themselves are NOT killed or paused on shutdown — same as the prior behavior and consistent with SR-11 Event 11.

## Configuration

### config.json (~/.claude/channels/slack/config.json)

Maps Slack channels to project directories. The server matches each MCP session's working directory to a route's `cwd` by real path (through the stand-in persona the adapter builds for that route; see Session Lifecycle, Connection).

Key fields:
- `routes` — `Record<channelId, { cwd: string }>` — the channel-to-directory mapping
- `bind` — HTTP server bind address (default: 127.0.0.1)
- `port` — HTTP server port (default: 3100)
- `default_route` — CWD for channels without explicit routes. `gate()` only admits such a channel if it has an `access.json` `channels` entry (`routeChannels` is built from `routes` keys alone), so an unlisted channel is dropped before routing
- `default_dm_session` — CWD for handling direct messages
- `session_restart_delay` — seconds before auto-restarting dead sessions (default: 60, 0 = disabled)
- `health_check_interval` — seconds between health-check polls (default: 120, 0 = disabled)
- `exit_timeout` — seconds `clean_restart` waits for a Claude session to exit cleanly before force-killing it (default: 120)
- `stop_timeout` — seconds the `stop` command waits after SIGTERM before escalating to SIGKILL (default: 30)
- `mcp_config_path` — path to MCP config file for Claude launch (default: ~/.claude/slack-mcp.json)
- `append_system_prompt_file` — optional path to a file appended to every managed session's system prompt via `--append-system-prompt-file`; missing file silently skipped
- `system_prompt_mode` — controls whether `append_system_prompt_file` is applied (default: `"append"`; valid: `append`, `none`). `"append"` passes `--append-system-prompt-file` to Claude when launching sessions; `"none"` skips the flag entirely so only `CLAUDE.md` is used
- `cozempic_prescription` — cozempic cleaning intensity used before `--resume` launches (default: `"standard"`; valid: `gentle`, `standard`, `aggressive`); has no effect if cozempic is not installed
- `claude_config_dir` — optional path to a Claude on-disk config directory used for managed sessions; when set, launches are prefixed with `CLAUDE_CONFIG_DIR='<resolved-path>'` so the route authenticates against a specific account. `~` is expanded and the path is resolved to absolute. Per-route `routes[id].claude_config_dir` overrides this top-level value. When neither is set, Claude's own default applies.
- `resume_enabled` — boolean (default: `true`). When `false`, the session manager skips `--resume` entirely and always performs a fresh launch, even when a stored session ID exists. Use this to work around versions of Claude Code that crash on `--resume` (e.g. the v2.1.120 "sandbox required but unavailable" regression). Affects both startup (step 4, **Resume** branch) and auto-restart (step 6).
- `stop_hook_bootstrap` — boolean (default: `true`). Controls whether step 4a-ter `stopHookBootstrap` installs the CSCB-managed Slack Reply Guard Stop hook into `<effective_claude_config_dir>/settings.json`. Registered in `KNOWN_TOP_LEVEL_KEYS` and `KNOWN_ROUTE_KEYS`; `applyDefaults` fills the top-level value to `true` when absent; `validateConfig` rejects a non-boolean at either scope. Per-route `routes[id].stop_hook_bootstrap` overrides the top-level value (`route.stop_hook_bootstrap ?? routingConfig.stop_hook_bootstrap`), and the resolved values feed the per-dir aggregation in step 4a-ter — a per-route opt-out only fully disables the guard for a bot when its route owns a dedicated `claude_config_dir`.
- `cron_table_path` — optional path to the cscb_cron crontable file (default: `<config dir>/crontab`, where `<config dir>` is the directory of the loaded config file). Registered in `KNOWN_TOP_LEVEL_KEYS`; `validateConfig` rejects anything that is not a non-empty string; `~` is expanded and the path is resolved to absolute, yielding a required string on the resolved config. Boot-fixed: only the crontable's contents hot-reload at runtime; its location never does.
- `cron_log_path` — optional path to the cscb_cron log file (default: `<config dir>/cron.log`). Same registration, non-empty-string validation, tilde expansion, required-resolved-string, and boot-fixed notes as `cron_table_path`.
- `cron_log_max_bytes` — optional positive integer (>= 1); no default. Registered in `KNOWN_TOP_LEVEL_KEYS`; `validateConfig` rejects any value that is not a positive integer when set. When absent, log pruning is disabled — this bullet states the contract only; the prune mechanics ship in a later Epic.

The path keys are pointers only: schedules never live in `config.json` — the crontable file is the single source of truth.

### Persona config (loader only, not yet wired)

The persona loader in `src/config.ts` (`resolvePersonaConfig`, `loadPersonaConfig`) accepts the persona shape of b.av2 SR-1. **The running server doesn't read this shape yet.** It still loads the route-keyed `config.json` above through `loadConfig`, and E3 switches it over. Everything else in this doc that talks about routes still describes runtime behaviour.

**Entry points and purity (b.av2 SR-13.1).** `resolvePersonaConfig(raw, configDir, home)` parses, defaults and validates an already-parsed value. It never opens, reads, creates or writes a file and never requires a path to exist; the only file-system access is resolving the real paths of persona working directories and credentials files for the cross-persona rules below. `loadPersonaConfig(path, home?)` reads the file once and delegates to it; it never writes, renames or converts the file. Nothing runs at import. Both loaders share the server-wide defaults, path resolution and validation helpers.

**Top level.** A required `personas` array, which may be empty, plus the server-wide settings. Every current top-level key except `routes`, `default_route` and `default_dm_session` keeps its meaning, default and validation from the `config.json` section above, including path resolution for the top-level path keys. Unknown top-level keys are rejected by name, and the renamed poll-interval key gets the same rename message as today. Three keys are new to this shape. They are validated only; E9 wires them.

| Key | Type | Default | Meaning |
|---|---|---|---|
| `ack_reaction` | non-empty string | absent | Emoji name of the acknowledgement reaction. Absent means no acknowledgement. |
| `reply_chunk_limit` | positive integer | `4000` | Largest reply chunk, in characters. |
| `reply_chunk_mode` | `length` or `newline` | `newline` | How a long reply is split. |

**Persona entry.** Each element of `personas` is an object with these keys:

| Key | Type | Default | Meaning |
|---|---|---|---|
| `name` | non-empty string, required | — | Persona identity. No format rule; the persona key is derived from it by `src/persona-identity.ts`. |
| `credentials_file` | path, required | — | The persona's credentials file. |
| `working_directory` | path, required | — | The instance's working directory. |
| `channels` | array of channel entries | none | Channels the persona is in. The same channel ID may not appear twice in one persona. |
| `dm.enabled` | boolean | `false` | The DMs switch. |
| `dm.contact` | Slack user ID | absent | The user who receives prompts and notices when `permission_prompts` is `dm`. |
| `permission_prompts` | `dm` or a channel ID, required | — | Where permission prompts and notices go. |
| `claude_config_dir` | path | top-level `claude_config_dir` | Claude config dir for the persona. Absent at both levels means Claude's own default. |
| `stop_hook_bootstrap` | boolean | top-level `stop_hook_bootstrap` | Per-persona Stop-hook bootstrap flag. |

**Channel entry.** Both keys are required: `id`, a Slack channel ID matching `^[CG][A-Z0-9]+$`, and `delivery`, either `all` (every message) or `mentions` (only messages that mention the persona). `dm.contact` must match `^[UW][A-Z0-9]+$`, and a channel ID in `permission_prompts` uses the channel ID format.

**Path rule.** Persona paths (`credentials_file`, `working_directory`, per-persona `claude_config_dir`) must be absolute, exactly `~`, or start with `~/`. The tilde is expanded under the home directory passed in (the OS home when not given) and the result is made absolute. Relative paths are rejected.

**Unknown keys.** An unknown key in a persona entry, its `dm` object or a channel entry is rejected, naming the persona and the key. A token-like key such as `bot_token` is rejected the same way: credentials live only in the credentials file.

**Per-entry rejections.** On top of the type and format rules above, a persona entry is rejected when:

- `permission_prompts` is missing
- it has zero channels and DMs off (`dm.enabled` not `true`), so it can receive no messages
- `permission_prompts` names a channel the persona isn't in
- `permission_prompts` is `dm` but `dm.contact` is missing or DMs are off (both are named when both are wrong)

**Cross-persona rejections (b.av2 SR-1.5).** Once every entry has parsed, the loader rejects:

- a duplicate name or key. Each persona's name and key are compared, by exact string, with every other persona's name and key, so a name equal to another persona's derived key is a duplicate too. The error names the duplicated name or key.
- a shared `working_directory`, then a shared `credentials_file`. Each is compared by `resolveRealPath` (real path, with a lexical `path.resolve` fallback when realpath fails for any reason), so a symlink to another persona's path, or `~/x` against its absolute form, is a duplicate. Only the same setting is compared: one persona's working directory against another's credentials file is not a collision. The error names the setting and the expanded path; when the two expanded paths differ (only a symlink can cause this), it shows both and the real path they share.

Each error names both personas, each as its array position plus the `src/persona-identity.ts` rendering. Personas are scanned in array order and the first colliding persona is reported against the earliest persona it collides with.

One persona listed in several channels loads: the rule is one working directory per persona, not one per channel. The per-channel duplicate-CWD rule of `loadConfig` applies only to the route-keyed `config.json` until E3.

**Pre-persona rejection (b.av2 SR-1.7).** If the top level has `routes` (in any shape), `default_route` or `default_dm_session`, the loader stops with the conversion message before any other check. The message names the key and says the configuration must be rewritten by hand as personas. The file is never written and nothing is auto-converted.

**Check order and errors.** The loader checks, in order: the value is an object, the pre-persona keys, unknown top-level keys, `personas` is present and an array, the server-wide settings, each persona entry in array order, the name/key rule, then the shared-path rule (`working_directory` before `credentials_file`). It reports the first violation only, so a per-entry error anywhere wins over any cross-persona one. Entry errors name the entry's position and, once `name` is valid, the persona as its JSON-quoted name with its key (the `src/persona-identity.ts` renderer), plus the setting. Errors don't echo rejected values: they may repeat only the persona name and IDs that already passed their format rule (e.g. a `permission_prompts` channel ID that isn't in the persona's channels, or a duplicated channel ID). The shared-path errors are the deliberate exception: they show the expanded, absolute paths, which have already passed the path rule. A malformed-JSON error omits the parser's detail, which could quote file content.

**Not checked at load time.** The loader doesn't read the credentials file and doesn't check that any directory or file exists. Those are bring-up checks: the credentials-file check is in `src/persona-credentials.ts` and the working-directory check is in `src/persona-bringup.ts` (see the Module Map); neither checks `claude_config_dir`. E3 wires the checks into the server and E5 adds retries.

### cron.log (`cron_log_path`)

Append-only plain-text log of every cscb_cron fire outcome, written by `src/cron-log.ts`. Location is the config-resolved `cron_log_path` (default `<config dir>/cron.log`); boot-fixed — the path never hot-reloads. Deliberately plain text, not JSONL, so `grep no-session cron.log` yields human-triageable lines.

Each outcome entry is one physical line of five space-delimited fields: `<ISO-8601 UTC ms timestamp> <identity|-> <channel|-> <outcome> <detail>`. The `detail` field leads with key=value tokens (`prompt=`, `status=`, `errno=`, `line=`) then free text. Every value is newline-escaped, so one record is always exactly one physical line. UTC matches server.log so an outage window can be cross-correlated.

The `outcome` field is one of nine classes:

| Outcome | Meaning |
|---|---|
| `delivered` | prompt delivered to the target channel |
| `no-session` | no live session for the target channel — dropped |
| `unknown-channel` | target is not a configured channel |
| `prompt-missing` | prompt file did not exist at fire time |
| `prompt-unreadable` | prompt file existed but could not be read |
| `prompt-oversize` | prompt file exceeded the size ceiling |
| `parse-error` | the crontable line could not be parsed |
| `http-error` | localhost POST hit an unexpected HTTP status or a network failure (503→`no-session`, 404→`unknown-channel` are classed separately) |
| `fanout-deferred` | all-bots fire skipped — emitted by the cron dispatcher while fan-out remains deferred to E4; kept so old lines stay interpretable |

A per-fire summary line shares the five-field layout with `summary` in the outcome position (a line kind, not an outcome class): `<ts> <identity> - summary delivered=N failed=M`. An `info` line kind (same layout) carries informational markers, and a `warn` line kind carries operator-actionable conditions — the crontable vanishing or becoming unreadable — with `identity`/`channel` defaulting to `-` because they are not fire-scoped. Both tokens are distinct from every outcome class, so `grep warn cron.log` matches exactly the warn lines and neither kind pollutes the outcome triage views.

Append-only: no rotation, no pruning, no read-back (pruning ships in a later Epic). The writer `mkdir`s the log's missing parent directory on first append — deliberately unlike `cron-bootstrap.ts`'s no-mkdir invariant, which is crontable-only (D-Q1), since the log is server-owned output. Write failures never break dispatch — a failed append logs one `[slack] cron-log` line, drops the fd, and self-heals on the next append. This module is a writer other code calls.

### permission-trail.jsonl (~/.claude/channels/slack/permission-trail.jsonl)

| Field | Type | When present | Notes |

| `event` | string | always | Stable hierarchical identifier in the `cscb.*` namespace (e.g. `cscb.chat_post.attempted`, `cscb.click_handler.invoked`, `cscb.chat_update.attempted`, `cscb.decide.attempted`, `cscb.block_actions.received`). |

**No-truncation guarantee.** The canonical trail line persists every field at full fidelity (SR-V-3.1) — the full `blocks` array including every `action_id`, the full `text`, the full Slack API response. The 300-character `console.error('[slack] RAW … event:', JSON.stringify(...).slice(0, 300))` summaries in the socket `message` / `app_mention` handlers (near `src/server.ts:804` / `:817`) are a **separate human-readable log** kept truncated intentionally per SR-V-3.2; they do not replace the canonical store and the two coexist.

#### `cscb.poller.row_decision` (SR-V-2.3)

#### `cscb.poller.wedge_detected` (b.fae F4)

Emitted from `postWedgeWarning` in `src/permission-poller.ts` when the wedge detector trips — a spawn seen in `check_permission` with an empty `permission_requests` array for `wedgeTripTicks` consecutive ticks (~90 s). Exactly one **successful** (`ok=true`) event per wedge episode: the `warningFired` latch (set only after a successful post) suppresses further posts until the detector re-arms. A failed post emits an `ok=false` event without latching and the poller retries on a later tick (throttled ~30 s), so an episode with Slack trouble can log several `ok=false` events before the one `ok=true`. The envelope shape mirrors `cscb.chat_post.attempted`: success is trail-only; failure lands in BOTH the trail (`ok=false`) AND `server.log` (`b.emk` convention).

Fields:
- `ts`, `event="cscb.poller.wedge_detected"`, `claude_instance_id`, `channel`.
- `text` — the full one-shot warning message posted to the channel (read-pane + kill/respawn remediation; send-keys explicitly not offered).
- `ok` — `true` on success, `false` on failure.
- On success: `slack_ts` — the Slack `ts` of the posted warning.
- On failure: `error` — the Slack platform error class string.

#### `cscb.block_action.received` (SR-V-2.9)

Emitted once per inbound `block_actions` action from the Socket Mode interactive handler in `src/server.ts`, regardless of whether the `action_id` decodes. This is the diagnostically critical surface for **"I clicked Allow and nothing happened"** — decode-failure cases are explicitly in scope. The classification helper lives in `src/permission-click-handler.ts` (`emitBlockActionReceived`) so the server stays a thin wiring layer.

Fields:
- **Always present**: `ts`, `event="cscb.block_action.received"`, `channel`, `message_ts`, `user`, `raw_action_id`.
- **On decode success**: `claude_instance_id`, `request_token`, `decision` (`"allow"` | `"deny"`). `parse_failure_reason` is omitted.
- **On decode failure**: `parse_failure_reason` (table below). Decoded fields are omitted.

**Parse-failure reason set** — open to extension per SR-V-2.9:

| `parse_failure_reason` | Meaning |
|---|---|
| `foreign_action_id` | `action_id` does not match the `perm_(allow|deny)_*` prefix — not a CSCB permission button at all. |
| `malformed_token` | `action_id` matches the `perm_(allow|deny)_*` prefix but `parsePermissionActionId` returns `null` (body broken). |

**Not a parse failure: `stale_prompt`.** A click on a closed prompt decodes fine — the `action_id` is still well-formed. Stale clicks surface as `cscb.click_handler.invoked{live_pending: false}` instead.

#### `cscb.click_handler.invoked` (SR-V-2.6)

Emitted from `handlePermissionClick` in `src/permission-click-handler.ts` for every parsed-as-permission click. Emitted exactly once per call, after `parsePermissionActionId` succeeds and before the AD `decide` call. Decode-failure clicks (foreign or malformed action_id) do NOT emit this event — they show up only as `cscb.block_action.received{parse_failure_reason}`.

Fields: `ts`, `event="cscb.click_handler.invoked"`, `claude_instance_id`, `request_token`, `decision`, `channel`, `message_ts`, `user`, `raw_action_id`, `live_pending` (boolean).

`live_pending` is the result of `getLivePermission(claude_instance_id, request_token) !== undefined` at handler entry. `true` means a `LivePermission` entry existed (happy path); `false` means the click decoded fine but the entry had already aged out or been dropped — the operator's "I clicked but the prompt was already closed" diagnostic.

**Example sequence** — happy-path Allow click:


#### `cscb.ad_decide.attempted` (SR-V-2.7 call-side)

Emitted from `handlePermissionClick` (`src/permission-click-handler.ts`) once per `decideWithToken` invocation, on success and on every error path. This is the CSCB-side half of SR-V-2.7; AD's complementary SR-A-2.4 emission lives in `t1.n4v.14`. The two halves join on `request_token` for after-the-fact debugging.

Fields:
- `ts`, `event="cscb.ad_decide.attempted"`, `claude_instance_id`, `request_token`, `decision` (submitted — `"allow"` | `"deny"`).
- `result_class` — one of the 6 values below.
- On `result_class="other"`: additionally `raw_error_message` (the original error's `.message` string, untruncated). For the named classes, `raw_error_message` is OMITTED.
- `submitted_decision_reason` — currently never sent on the wire from CSCB. Documented for future use per SR-V-2.7's "when present" rule.

**Response-class set** — match the AD error identifiers in `src/agent-director-errors.ts` so the trail's classification stays consistent with the rest of the codebase. Open to extension.

| `result_class` | Meaning |
|---|---|
| `ok` | `decideWithToken` returned without throwing. |
| `ErrAlreadyDecided` | The request was already closed (race with poller reconciliation or peer click). |
| `ErrInvalidFlags` | AD rejected the call shape — typically a missing required field. Should not happen under contract. |
| `ErrAmbiguousRequest` | AD couldn't uniquely identify the request — defense-in-depth backstop per SR-4.4. |
| `ErrRelayFallenBack` | b.qi1 — the request's relay window elapsed, so Claude re-asked at its own tmux pane and AD will not record the verdict. The click did not land; the session is unaffected. |
| `other` | Any other thrown value (non-AD error, transport, etc.). `raw_error_message` carries the original `.message`. |

**Example** — happy-path `ad_decide.attempted` after a click:

```json
{"ts":"2026-06-04T20:40:01.130Z","event":"cscb.ad_decide.attempted","claude_instance_id":"cscb_C0B1ZJJLJ9M","request_token":"6f3a1d2c-aaaa-bbbb-cccc-dddddddddddd","decision":"allow","result_class":"ok"}
```

**Operational logging.** The existing `[slack] permission-click: ErrInvalidFlags from decide for ...` / `ErrAmbiguousRequest` / `decide failed for ...` `console.error` lines stay alongside the trail event. They serve a different purpose — live stderr monitoring — and are intentionally not redundant with the canonical after-the-fact debugging surface.

### Environment Variables

Required at startup:

- `SLACK_BOT_TOKEN` — bot user OAuth token; must begin with `xoxb-`
- `SLACK_APP_TOKEN` — app-level token for Socket Mode; must begin with `xapp-`

Both values are read directly from the process environment. When `SLACK_DRY_RUN` is set (see below), `loadTokens()` returns dummy values (`xoxb-dry-run` / `xapp-dry-run`) and validation is skipped.

## Logging

### Why console.error/console.log are overridden directly

Bun bypasses `process.stderr.write` overrides — the runtime writes directly to the file descriptor, so patching `process.stderr.write` has no effect. `src/logging.ts` works around this by replacing `console.error` and `console.log` themselves before any logging occurs.

### initLogging()

`initLogging(logFilePath)` in `src/logging.ts` opens the target file in append mode and replaces both `console.error` and `console.log` with wrapper functions that:

1. Format all arguments to a single string (JSON-serializing objects)
2. Prepend an ISO-8601 timestamp: `[2024-01-01T00:00:00.000Z] message`
3. Roll the file if it has grown past the threshold (see **Rotation** below)
4. Write the line synchronously via `writeSync` to the open file descriptor
5. Fall back to the original `console.error`/`console.log` if the write fails

The originals are captured at module load time so the fallback always refers to Bun's native output.

### Rotation (b.brv)

Rotation is built into `src/logging.ts` so it applies on every machine that runs CSCB — no per-host logrotate config. `maybeRotate()` runs before each write: it `fstat`s the active fd and, when the size crosses the threshold, closes the fd, shifts `<path>.N-1 → <path>.N` down to `<path>.1`, renames the active file to `<path>.1`, discards the oldest generation beyond `CSCB_LOG_KEEP`, and reopens a fresh active file. It is best-effort — any filesystem error is swallowed rather than thrown into the caller's hot path, and a failed reopen after rotation is recovered on a subsequent write rather than disabling file logging.

| Env var | Default | Effect |
|---|---|---|
| `CSCB_LOG_MAX_BYTES` | 10 MiB (`10485760`) | Rotate when the active file reaches N bytes. Values `<= 0` or non-numeric ignored. |
| `CSCB_LOG_KEEP` | 5 | Rotated generations retained. `0` = keep none (the active file is `rm`ed on rotation, i.e. truncate). Values `< 0` or non-numeric ignored. |

Rotated generations are **not** compressed. Applies to both `server.log` and `clean_restart.log` (any file passed to `initLogging`). This is distinct from `startup-errors.log`, whose rotation remains operator-owned via `docs/logrotate-startup-errors.conf`.

### agent-director logger filter (b.brv)

The agent-director `Client` is constructed with a `logger` in `src/agent-director-startup.ts`, and since `initLogging()` patches `console`, everything the Client logs lands in `server.log`. At info level the Client emits a per-poll `SubprocessClient: <verb> ok { … }` success dump for every `list`/`status`/`get`/`decide` call — with CSCB polling continuously, these dumps historically dominated the log (2 GB / 137 MB observed in b.brv). `makeFilteredAdLogger(console)` in `src/agent-director-logger.ts` wraps the console: it drops those routine `SubprocessClient: <verb> ok` records at `log`/`info` level while passing `warn`/`error` through unfiltered. Setting `CSCB_AD_VERBOSE` to a truthy value (`1`/`true`/`yes`/`on`) returns the base logger unwrapped, restoring the full chatter for debugging.

### HTTP request access line (b.3k6)

The `/mcp` endpoint's `fetch` handler in `src/server.ts` is hit on every MCP round-trip — client polls, notifications, tool-call responses, and each SSE stream open — so its one-line-per-request access log (`[slack] HTTP <method> <path> session=…`) is the highest-frequency routine success line left in `server.log` after b.brv silenced the `SubprocessClient` dumps. It shares their signal/noise profile: routine and continuous at steady state, useful only when debugging a specific transport/session-routing problem. It is gated behind `isHttpVerbose()`, which reads `CSCB_HTTP_VERBOSE` (truthy: `1`/`true`/`yes`/`on`, case-insensitive) — off by default. Unlike `CSCB_AD_VERBOSE`, the env var is checked per request rather than once at startup, so toggling it takes effect without a restart. Real events (session connect/disconnect, route mismatch, errors) are logged unconditionally elsewhere and are unaffected by this flag.

### Log file locations

Both paths are rooted in `SLACK_STATE_DIR` (default: `~/.claude/channels/slack/`).

| Process | Log file |
|---------|----------|
| Server daemon (`server.ts`) | `STATE_DIR/server.log` |
| `clean_restart` subcommand | `STATE_DIR/clean_restart.log` |
| cscb_cron fire log (`cron-log.ts`) | `cron_log_path` (default `<config dir>/cron.log`) |

All three are opened in append mode — multiple restarts accumulate in the same file rather than overwriting it; only the first two are subject to the size-based rotation above.

## Endpoint Inventory

### POST /interject

Injects a message directly into an active Claude session without going through Slack. Localhost-only.

**Request body** (JSON, max 32 KB)

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `channel` | string | yes | Slack channel ID |
| `message` | string | yes | Message content to inject |
| `sender` | string | no | Display name; defaults to `"interject"` |

**Success response**

`200 OK` — `{ ok: true, channel, cwd }`

**Status codes**

| Status | Condition |
|--------|-----------|
| 200 | Notification delivered to session |
| 400 | Invalid JSON or missing required field (`channel`, `message`) |
| 403 | Non-localhost origin |
| 404 | Channel not found in `routingConfig.routes` |
| 405 | Non-POST method |
| 413 | Body exceeds 32 KB |
| 503 | No active session for the channel |

**Behavior**

- Looks up the channel in `routingConfig.routes`; 404 if absent
- Calls `getSessionByPersona()` with the channel ID (the persona key under the transitional route→persona adapter) to resolve the active session; 503 if none or not connected
- Sends `notifications/claude/channel` with `content: message` and `meta: { chat_id, message_id, user, ts }` — `user` is the `sender` label; `message_id` and `ts` are both `String(Date.now() / 1000)`, which has at most three fractional digits. The Slack Reply Guard relies on that shape to tell injected messages from Slack ones (see [Slack Reply Guard](#slack-reply-guard-stop-hook)).
- Does not call `gate()` or the Slack API

## Security Model

- **Gate layer**: All inbound messages pass through `gate()` — drops bot messages, enforces DM policy, validates allowlist
- **Outbound scoping** (b.av2 SR-5.1): every MCP tool resolves the calling session's persona and its client at call time and may target only that persona's configured channels (`checkPersonaTarget`). A refused target returns a tool error naming the persona and the target, and no Slack call is made. The call posts as the persona, with no username or icon override
- **File exfiltration guard**: `assertSendable()` blocks uploading files from the state directory (outside `inbox/`) and every persona credentials file named by the applied or current configuration (`credentialsFilesToProtect`, rebuilt per call), compared by real path so a symlink to one is refused too. It never opens the file. `reply` checks every file up front and re-checks each one right before its upload
- **Attachment download token scope**: `download_attachment` sends the persona's bot token only to `https://files.slack.com` URLs. External (non-Slack-hosted) files are refused, and a redirect off that origin is never followed with the Authorization header, so the token cannot reach a third-party host
- **Localhost restriction**: `/permission`, `/ask`, and `/interject` endpoints only accept requests from 127.0.0.1/::1/::ffff:127.*
- **Session scope guard**: agent-director enforces session scope via `relay_mode='on'` at spawn time. Permission requests are routed through agent-director's internal relay machinery (SR-2.1 poller), which is scoped to the spawned session. Sessions not spawned by CSCB have no relay route and no `PermissionRequest` or `PreToolUse` hook entries in `settings.json` — the `.sh` hook files are not shipped.
- **Credentials-file secrecy**: applies to the persona credentials module (`src/persona-credentials.ts`) and the bring-up checks that call it, which are not yet the live token source; the running server still loads tokens from the environment through `tokens.ts` until E3. That code never reads `SLACK_BOT_TOKEN` or `SLACK_APP_TOKEN` (or any environment variable). It never writes, copies, caches or persists a credentials file or any value from one. It does not check or change the file mode. A bad token is described only by its key and the rule it breaks, never by its value, so no diagnostic line or failure result carries a token, and the success value redacts itself if logged.
- **Slack validation outcome secrecy** (b.av2 SR-10.3): outcomes from `src/persona-slack-validation.ts` carry only the class, the token key, the check, and the Slack error code or reason kind (plus an HTTP status or `retryAfter` number). The log lines `src/persona-slack-episodes.ts` builds from them carry those fields plus the persona reference (entry position, name and key) and the credentials-file path. Neither ever carries the raw error object, its message, the request, a header or a token value. The connection manager (`src/persona-connections.ts`) uses them; E3 wires the manager into the server.
- **Persona Slack client error secrecy** (b.av2 SR-3.3): no persona Slack client (`src/persona-slack-clients.ts`) attaches the original request, and so the Authorization header, to its errors. The connection manager logs a thrown value only through `describeThrownValue` (constructor name, a short `code`, stack frames; never the message), and the exported `unhandledRejection` handler (`src/persona-connection-errors.ts`) logs the same way, so neither writes a token value. Not yet live; E3 wires the manager and installs the handler.
