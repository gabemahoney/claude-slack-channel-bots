# Engineering Best Practices

## Language and Runtime

- TypeScript with strict mode enabled
- Bun as the runtime and test runner
- ES2022 target, ESNext modules with bundler resolution
- Import .ts extensions explicitly (e.g., `import { foo } from './bar.ts'`)

## Module Organization

### Separation of Concerns

- **Pure logic** goes in dedicated modules (lib.ts, config.ts) — side-effect-free, importable by tests
- **Stateful registries** go in their own modules (registry.ts) — module-scoped Maps, exported CRUD functions, `_reset` functions for tests
- **Server wiring** stays in server.ts — building the connection manager and registering the per-persona event handler with it, HTTP routing, startup/shutdown, process lifecycle. Slack clients are created only by the connection manager through its injected `PersonaSlackClientFactory` (see Security), never at module scope and never in server.ts; server.ts reads a persona's client only through `clientFor(key)`. Importing server.ts must stay free of Slack clients, token reads and directory creation: that work belongs in `main()`
- **Per-persona start and event routing** live in importable, side-effect-free modules: the SR-6.1 bring-up steps (`checkPersonaLocalSteps` for steps 1–2, `connectPersonaSlack` for step 3) and the connection seams (`clientFor`, the identity lookup, the up-flush listener, the up predicate `createPersonaUpPredicate`, the relaunch gate) in `src/persona-start.ts`, the per-persona outcomes, retries, launch after a retry, leaving-up listener and not-up session dropper (`createNotUpSessionDropper`) in `src/persona-bringup-controller.ts`, and the handler every persona connection forwards its `message`, `app_mention` and `interactive` events to in `src/persona-event-router.ts`. Put new start steps or event handling there, with dependencies injected, not in server.ts
- **Inbound delivery** lives in `src/persona-routing.ts`, which is importable and side-effect-free, with every client and source injected through `createPersonaRouting`. The event router only logs the RAW line and hands the event to its `receive` with the receiving persona's key; put drop logging and lost-message handling (the recovery decision and raising the lost-message notice through the injected `notify`) in the module, not in the router or server.ts, so tests drive the real code. The lost-message state and notice text live in the pure `src/lost-message.ts` (`decideLostMessageState`, `buildLostMessageNotice`); change a state or its wording there. The delivery rules themselves, channel and DM alike, live only in the pure `src/delivery-decision.ts` (`decideDelivery`); add or change a rule there, not in the pipeline. Inbound dedupe (b.av2 SR-4.1) lives in the pure `src/inbound-dedupe.ts`: the routing keeps one store per persona key, built with its injected `dedupeClock`; the store counts and limits nothing, so don't add a rate or count check to it

### When to Extract

Extract to a new module when:
- A concern has its own types + state + functions (e.g., registry.ts owns session Maps)
- Tests need to import the logic without triggering server-side side effects (connecting sockets, starting listeners)
- The module is independently testable

Do NOT extract prematurely — a few related functions in server.ts are fine until they grow.

## Error Handling

- Use `try/catch` around external calls (Slack API, file I/O, agent-director library verbs). For agent-director rejections, get the class from the classifier in `src/ad-error-class.ts` (`classifyAdError`, or `classifyWithInvalidFlagsRecheck` at a site that gives `ErrInvalidFlags` no meaning); never write a new `instanceof` ladder or parse error strings to decide a class. A site that must tell one agent-director error name from another uses `hasAdErrorName(value, <name constant from src/agent-director-errors.ts>)` (`src/ad-error-class.ts`, never throws), never a new `instanceof` ladder. New or changed code imports agent-director error classes through `src/agent-director-errors.ts`, not from `agent-director` directly; some existing modules import from `agent-director` directly; move one over when you next change it. Until the Phase 1 client is adopted, never import or re-export a Phase-1-only export (`ErrTmuxKillFailed`, `ErrTmuxUnresponsive`, `ErrTmuxSessionConflict`): those errors are recognised by name, through the string constants in `src/agent-director-errors.ts`.
- A refusal at a launch or recovery call site (b.jg5 SRJ-105) is never destructive, never counted and never a spawn-failure notice. A refusal is an UNAVAILABLE outcome from any verb, `ErrTmuxKillFailed` included, an ENVIRONMENT answer (`ErrTmuxNotAvailable`) from any verb (b.jg5 SRJ-311), or a `status`, `get` or `list` error other than `ErrSpawnNotFound`, a CONFIG answer and an UNUSABLE_NAME answer. After one, the site deletes nothing, kills nothing to recover, launches and reuses nothing, never answers `dead-session`, records no failure and no `spawn-failed` startup-errors entry, and posts no spawn-failure notice. A read error is handled the same way, but it never starts the `tmux-unresponsive` condition. Decide it through the arming predicate, `unavailableRetryCauseFor(err, verb)` (`src/unavailable-retry.ts`), which classifies by name through `src/ad-error-class.ts` (the interim rule above), and never by a Phase-1-only export or a new `instanceof` check. In the collision ladder, handle it through the one helper, `refusalAt` (`src/session-manager.ts`). It logs one line and answers `failed`, and the site calls nothing more. A persona's `findMissing` sweep goes through it too (`sharedFindMissingSweep`, for the persona that started the sweep and each that joined it), and answers `FIND_MISSING_REFUSED`: the launch stops with the refused `failed`, and the restart path's reconnect adapter answers `transient`, so nothing is resumed, re-probed, killed or relaunched after it. At the restart path's kill, answer `KILL_SESSION_REFUSED` (`src/restart.ts`) so that the work launches nothing. `ErrSpawnNotFound` keeps each site's own meaning, and every other class keeps the site's own branch.
- Log errors to stderr with the `[slack]` prefix, as one line: `[slack] context: description: <describeThrownValue(err)>`. Never pass the error object itself, its raw message or `String(err)` (see the rules below)
- Non-critical failures (reaction add, message update) use empty catch blocks with `/* non-critical */` or `/* ignore */`
- Only start-wide failures exit the process with a clear message, with one runtime exception: the agent-director version re-check's stop (`src/ad-version-gate.ts`, b.jg5 SRJ-205) records one startup-errors entry and exits the running server non-zero through `shutdown()`. The start rules (b.av2 SR-8.7) decide which configuration failures those are, and each is logged before any port, PID file, Slack connection or spawn:
  - With no last-applied record, a missing, unreadable, pre-persona or invalid config file (`[slack] Fatal: configuration error — …`), or a record that can't be written (`reload-record-write-failed`).
  - With a record, only a record that can't be read or validated (`[slack] Fatal: last-applied record error — …`, naming the record and saying that deleting it makes the next start apply the config file). The config file's validity doesn't gate such a start. Never fall back from a bad record to the config file.
  - The other start-wide steps: the startup gate, a PID conflict, the persona client's build (a construct failure or a floor refusal of the client built with the start's `agent_director_call_timeout_ms`, b.jg5 SRJ-213), the boot template install. The server loads no token, so there is no token failure to exit on. The apply-time template refresh (step 5) is not start-wide and never exits (see Reload Detection Tick)
- A per-persona bring-up failure (credentials, working directory, Slack validation or connection) never exits the process: it is logged through the persona diagnostics below and isolated to that persona, which ends `broken` or `retrying` while the others and the server carry on (see Persona Bring-Up Retries). Don't add a `process.exit` or a thrown startup error on a per-persona path
- Persona diagnostic lines (b.av2 SR-10.3) go through `src/persona-diagnostics.ts`. Add a new class to its closed label set, build the line with `formatPersonaDiagnostic()` or `personaCheckFailure()`, and emit it only through an injected logger, never with a direct `console` call in a pure module. The cause is one line, names a bad token by its key and the rule it breaks, never by its value, and never quotes file contents
- Reload diagnostic classes (the last-applied record, the pending change) are a separate closed set, `RELOAD_DIAGNOSTIC_CLASSES` in `src/reload.ts`. Add a reload class there, not to `PERSONA_DIAGNOSTIC_CLASSES`: a reload line is about the server's configuration, not one persona's bring-up. Reload output goes to the server log only, never to Slack (b.av2 SR-7.2)
- On every Slack or agent-director path (persona connections, the permission poller and click handler, restart, the health check and its stat route, the outage state, the session manager, the JSONL check, the CLI's teardown and `stop --stop-bots`, reload), render a thrown or rejected value in a log line, a startup-error record or a notice only through `describeThrownValue()` in `src/persona-connection-errors.ts`, never the error object or its raw message: a Slack library error's request and headers can hold a token, and its message can quote a URL (the Socket Mode WebSocket `ticket=` URL) or a token (b.av2 SR-10.3). The description holds the constructor name, a `code` and, for a base `AgentDirectorError`, its `errName`, each only when it passes `isSafeIdentifier`, the message as `message="…"` and the stack frames. To log any other error text (an agent-director `errDescription`, a message you read yourself), pass it through `describeLogMessage()` (the same module: `redactSlackLogText`, one line, capped at 300 characters, JSON-quoted as `message="…"`) or at least `redactSlackLogText()` (`src/slack-log-redaction.ts`), never raw. The Slack validation classifier (`classifySlackValidationError`) does this for a Slack-unreachable outcome: its `message` field is `describeLogMessage` of the thrown value's message, which the `persona-slack-unreachable` start line prints after the cause. Keep error text out of every outcome's `cause`, which the bring-up state, start summaries and the not-up lines reuse. Where a line names an agent-director error by its `errName` directly, check it with `isSafeIdentifier` first and fall back to `describeThrownValue`; `describeAgentDirectorFailure` (`src/ad-error-class.ts`; the permission poller re-exports it) and the template refresh's `describeRefreshFailure` do both, rendering `<errName> message="<description>"`. The spawn-failure notice shows the checked label and the redacted description, capped at 300 characters. Pass `recordStartupError` a built string (`describeAgentDirectorFailure(err)` in its message, or a describer's output as its cause), never the error. Never pass a credentials file's read or parse error to a describer: its message can quote the file, so `persona-credentials.ts` words fixed causes instead. A failure CSCB builds itself, from token-free parts, may print its own message: the CLI's `describeCliFailure` does so for `StartupGateFailedError` and `TeardownIncompleteError` and describes anything else. For a failed Slack Web API call, end the log line with `describeSlackCallFailure()` from the same module, which adds the Slack platform reason when it is a safe identifier
- The deliberate exceptions, which print an error's own text, and why. Keep the list closed: `tests/secrecy-audit.test.ts` scans every log call under `src/` (console methods and `log`, `logFailure`, `logViaDeps`, `logDeps` (the click handler's log sink), `recordStartupError`, `fatal`) and fails on a caught error passed, interpolated or stringified, its message or stack read outside a safe describer call, an `errDescription` not through `redactSlackLogText` or an unchecked `errName`, unless the call is in its `RAW_ERROR_ALLOWED` list with a reason. Add a new safe describer to its `SAFE_DESCRIBERS`, and a new exception to the allow-list only with its reason:
  - the `[slack] Fatal:` catch-alls in `src/cli.ts` and `src/server.ts`: the only text an unexpected start failure has
  - the CLI's config-load lines (`stop --stop-bots`, `stop`, `clean_restart`, `credentials`): the loader's message is token-free and carries the deletion hint (a record's), and the CLI process reads no credentials file
  - the `clean_restart` `fatal(...)` lines for a failed initialization or teardown: in production they receive the CSCB-built `StartupGateFailedError` and `TeardownIncompleteError`
  - the boot template install's failure, recorded verbatim as the operator's diagnosis; and the startup gate's message, which may embed agent-director's description or a construct error and is the same text the server writes to `startup-errors.log`
  - paths that touch neither Slack nor agent-director: MCP roots and connect, the message archive's open, cron, permission trail and cron log writes, cozempic, the PID read, and the Stop-hook and trust patches' catch-alls (file system and JSON only)

## Configuration

- The config is the persona config at `config.json` in the state directory, but what runs is the last-applied record beside it, `config.json.last-applied` (b.av2 SR-8.1, SR-8.7). Saving `config.json` changes nothing that runs until a change is applied, and every start runs the record when it exists; the config file is validated, recorded and applied only at a start with no record. Nothing but the operator's confirmation (E12) applies a change: the detection tick (see [Reload Detection Tick](#reload-detection-tick)) only notices one and reports it in `config.json.pending` and the server log; a bring-up retry doesn't pick it up either. Detection makes no lifecycle call: only a confirmed apply does (step 2's teardowns and step 6's bring-ups). The start rules live in the reload controller in `src/reload.ts` (`createReloadController`, every dependency injected); put reload work there, not in server.ts. Code that needs the applied config reads it from the controller or from `personaConfig` in server.ts, never from `config.json` directly (the SR-5.2 file guard's current-file read, `protectedCredentialsFiles()`, is the one exception)
- The CLI takes every setting it uses (such as `stop_timeout`) and its persona set only through the shared record-first resolver, `readAppliedPersonaConfig` in `src/reload.ts`: the record when it exists, otherwise the config file. Don't read `config.json` in CLI code with the persona loader, and never write, rewrite or delete any SR-8.1 file (`config.json.pending`, `config.json.apply`, `config.json.last-applied`) from the CLI. Why: `stop --stop-bots` and `clean_restart` must act on the personas that run, not on an edit that was never applied
- Parse configuration JSON only through `parsePersonaConfigBytes` in `src/config.ts`, from the bytes that were read, so the bytes recorded or applied are the bytes that were checked. It reports malformed JSON by line and column (`src/json-position.ts`) and never echoes the parser's message or any file content: a token pasted into the file must never reach a log. Don't add a second `JSON.parse` of a config or record file. The one exception is `referencedCredentialsPaths` in `src/config.ts`, the one extraction of the credentials paths a config file names, used by the SR-5.2 file guard (`credentialsFilesToProtect`) and the reload detection tick's fingerprint. It must stay tolerant, so a file with an invalid edit still yields the credentials paths it names; it discards any parse error rather than reporting it, and returns only paths. Get referenced credentials paths from it; don't parse the config file for them anywhere else
- Read the config file and the last-applied record only through `readPersonaConfigBytes` in `src/config.ts`. It is stat-first, like the credentials check: open read-only and non-blocking, `fstat` the descriptor, and read only a regular file through it. Why: a FIFO at either path would otherwise hang the start or the CLI, and a device such as `/dev/zero` would never end. Tests reach it through its `PersonaConfigFs` seam
- The 64 KiB cap (`MAX_RELOAD_FILE_BYTES` in `src/config.ts`) lives in the two shared readers, `readPersonaConfigBytes` and `readCredentialsFile`, and covers every config, record, pending, apply and credentials read but one: a larger file is refused unread after its `fstat`, and the read itself asks for at most one byte over the limit and refuses more, so a file that grows after the stat is refused too. A new reader of any of these files uses those readers; never add a second read path or a second size check. Why: the start and the detection tick must judge the same file the same way (the same digest or unreadable marker), and an unbounded read of a huge file would stall the tick
- The one sanctioned exception is the SR-5.2 file-send guard: `credentialsFilesToProtect` reads `config.json` with `readPersonaConfigBytes(path, fs, { uncapped: true })`, which skips both size checks but keeps the stat-first open (a non-regular file is still refused). Why: it must see every credentials path the current file names, so a path named only in an oversized, unapplied `config.json` can't be uploaded. Pass `uncapped` nowhere else; a read whose bytes are recorded, applied, digested or compared must stay capped
- Resolve both locations only with `resolveServerStateDir()` / `resolveServerConfigPath()` in `src/config.ts` (state directory `~/.claude/channels/slack/`, overridable via `SLACK_STATE_DIR`); don't join the path by hand
- New config fields go into the persona config types, defaults and validation (the pre-persona keys exist only in `PRE_PERSONA_KEYS`, for the conversion error). Put each field where its scope says:
  - Server-wide keys: `ServerSettingsInput` (optional) and `ServerSettings` (resolved), a default in `applyServerDefaults()`, the key in `SHARED_TOP_LEVEL_KEYS`, and a rule in the shared validation helpers (`validateServerTimingsAndModes()` / `validateServerPollAndCron()`). A server-wide key that holds a path also goes in `SERVER_PATH_SETTINGS`, the one list of path-valued settings: `resolveServerPaths()` expands exactly these (its `satisfies` check fails the typecheck until the two agree), and the reload change plan compares exactly these by real path
  - Persona-only top-level keys: `PersonaConfigInput` and `PersonaConfig`, plus the key in `PERSONA_ONLY_SERVER_KEYS`
  - Persona-entry keys: `PersonaInput` and `Persona`, plus the key in `PERSONA_ENTRY_KEYS`; parse it in `parsePersonaEntry()`, the per-entry path `resolvePersonaConfig()` calls. `name`, `credentials_file`, `working_directory` and `permission_prompts` are required
  - A key missing from these key lists is rejected as unknown
  - Every new key also needs a reload effect: see "A new config field needs a reload effect" in [Reload Detection Tick](#reload-detection-tick)
  - Every new key is documented in README.md's persona reference ([Personas (config.json)](../README.md#personas-configjson)) in the same change: `tests/shipped-docs.test.ts` fails until its key tables list exactly the loader's keys (`PERSONA_TOP_LEVEL_KEYS`, `PERSONA_ENTRY_KEYS`, `PERSONA_DM_KEYS`, `CHANNEL_ENTRY_KEYS`), and it loads the README's complete example through the real loader, so a new required key goes into that example too. `docs/architecture.md` (Configuration) describes the loader's rules
  - Errors report the first violation only, render the persona with `renderPersonaRef()` from `src/persona-identity.ts`, and name the setting. Never echo a rejected value: an error may repeat only the persona name, IDs and paths that already passed their format rule
  - Never echo file text that could be a token, and that includes key names. Name an unknown key only when it is a plain setting name (`ECHOABLE_KEY_NAME_RE` in `src/config.ts`: letters and underscores, up to 48 characters); count the rest. Build every unknown-key error with `describeUnknownKeys`, which does both. Why: the running server's detection tick writes loader errors into `config.json.pending` and `server.log` every 5 s, so a token pasted as a key name would otherwise leak there (b.av2 SR-10.3)
- New "same path" checks compare configured paths through `resolveRealPath()` in `src/config.ts`: the real path, or the lexical `path.resolve` form when realpath fails. Tilde-expand the path first; tests inject the realpath function. Import it; don't write a second realpath-with-fallback helper, so these checks agree. One intentional exception stays as it is: the pure, lexical `configDirLabelValue` in `src/persona-identity.ts`. Spawns and any later `config_dir` label comparison use `personaConfigDirLabelValue` in `src/session-manager.ts`, which real-paths the dir through `resolveRealPathStrict()` before hashing; don't hash a `config_dir` label from `configDirLabelValue` directly. A `claude_config_dir` never falls back to its lexical path (bug b.g57): `resolveRealPathStrict` (`src/config.ts`) gives the real path, or, for a directory not created yet under a resolvable ancestor, the path it will have, and otherwise reports it unresolvable. An unresolvable directory has no label: `personaConfigDirLabelValue` throws `ConfigDirUnresolvableError`, and `compareRowToPersona` reports `configDirResolved: false` with no `configDirMatches` verdict, which a caller treats as "keep the row", never as a mismatch. A launch checks the directory first (`checkLaunchConfigDir`) and, when it can't be resolved, makes no agent-director call, keeps the row, hands the persona to the bring-up controller's hold (`setConfigDirUnresolvableHook`) and returns `deferred` (`'skipped'` to restart, no failure counted). A new consumer of the `claude_config_dir` resolves it the same way; never with `resolveRealPath`, whose lexical fallback would give a label no spawn can match. To compare an agent-director row with a persona (its `cwd` against the working directory, its `config_dir` label against the persona's current one), call `compareRowToPersona` in `src/session-manager.ts`, as the collision ladder and the start sweep do, and pass the same home the spawn labels use; don't compare `cwd` strings or labels inline. When a check must know that a path has no real path (rather than silently fall back to its lexical form), use `tryResolveRealPath()`, which `resolveRealPath()` delegates to; `compareRowToPersona` reports it for the working directory as `workingDirectoryResolved`, and reports `cwdCheckDeferred` when neither the working directory nor the row's `cwd` has a real path (or the row's `cwd` equals the configured path lexically). A caller that acts on `cwdMatches` must check `cwdCheckDeferred` first; a row whose `cwd` resolves to an existing directory elsewhere is not deferred and is still a mismatch (see Serve Only Personas That Are Up). The same goes for E1's `personaLabels` in `src/persona-identity.ts`: it hashes the dir lexically and nothing in `src/` calls it. Spawns build their labels in `src/session-manager.ts` with `personaConfigDirLabelValue`; don't use `personaLabels` for spawn labels
- File writes that a reader may see mid-write are atomic, and those whose loss across a crash matters are also durable. The helpers live in `src/atomic-write.ts`; use them, don't write another:
  - `durableWriteFileSync` (b.av2 SR-8.1): writes a uniquely named temp file beside the target, fsyncs it, renames it over the target, then fsyncs the directory. Use it for every server write of the reload files (`config.json.pending`, `config.json.apply`, `config.json.last-applied`) and for any new file whose loss or rollback after a crash or power cut would matter. It logs nothing and rethrows every failure: before the rename the target is untouched, the temp file is removed and the error is thrown as raised; a failure to open or fsync the directory comes after the rename and is thrown as `DurableWriteUnsyncedError` (`path`, `code`, `syncError`), since the new bytes are already in place. A failure to close the directory after a successful fsync is ignored. A caller that must know the write is durable (the start's record write) treats either as a failure, and tells them apart with `instanceof DurableWriteUnsyncedError` so its log line says what is on disk. Tests pass a `DurableWriteFs` to observe the call order or fail one call, since permission-based failures aren't reliable when tests run as root
  - `durableUnlinkSync`: the delete counterpart. It unlinks the file, then fsyncs the directory, and returns `false` when the file was already gone. Every server delete of a reload file (such as removing `config.json.pending` when nothing is pending) uses it; don't `unlinkSync` or `rmSync` a reload file. It logs nothing and rethrows every other failure. An unlink failure is thrown as raised and leaves the file in place, so the caller logs it and retries at its next pass. A failure to open or fsync the directory comes after the unlink and is thrown as `DurableUnlinkUnsyncedError` (`path`, `code`, `syncError`), the counterpart of `DurableWriteUnsyncedError`: the file is gone, but the removal may not survive a crash. Tell the two apart with `instanceof DurableUnlinkUnsyncedError` and treat that case as removed; there is nothing left to retry
  - `atomicWriteFileSync`: writes a fixed `<path>.tmp`, then renames it; no fsync. Keep it for the files that already use it (the Stop-hook `settings.json` edits and the reply-guard records in `src/stop-hook-bootstrap.ts` and `src/reply-guard-record.ts`), which the pre-launch pass rewrites at every start; don't use it for a reload file
- A file named after a persona key: check the key against `PERSONA_KEY_RE` from `src/persona-identity.ts` before building the path (as `src/reply-guard-record.ts` does). `PERSONA_KEY_IN_FORM_RE` only says whether a name is its own key and rejects hashed keys
- Keep persona keys prefix-free. The loader rejects a key that starts with another persona's key (`checkPrefixRelatedKeys` in `src/config.ts`, b.1ix follow-up), in record mode too, and its error suggests a new name from `suggestNonPrefixingName`. Why: agent-director 0.10.0's verbs (read-pane, send-keys, kill, the has-session inside resume) pass `slack_bot_<key>` to tmux bare, and tmux takes a session whose name starts with a bare target when none has it exactly, so with `dev` and `dev_2` they could act on the wrong persona's session. The rule is the guard for agent-director's calls; there is no check on its side. Build any new name derived from a key as fixed text around the whole key, the same for every persona (`personaInstanceId`, `personaTmuxSessionName`): two such names start one another only when their keys do, so the rule covers them. A derivation that shortens or transforms the key needs its own check. Test a new cross-persona rule with a prefix pair (`dev`, `dev_2`) and a pair that only shares a start (`dev_a`, `dev_b`)

## Code Quality

- **Remove dead code.** No commented-out blocks, unused exports/imports, or leftover debug `console.log`. Version control is the safety net — delete with confidence.
- **YAGNI.** Don't build abstractions for hypothetical future requirements. Three similar lines are better than a premature helper.
- **Match existing patterns.** If the codebase has a convention for something, follow it — don't introduce a second way of doing the same thing.
- **Keep functions readable.** Over ~50 lines or more than 3 levels of nesting: extract helpers.
- **Magic values.** Named constants over mystery numbers and strings (see Naming Conventions).
- **DRY.** Copying a block of code a second time means it's time for a shared function.

## Security

- Localhost-only endpoints: check `server.requestIP(req)` for `127.0.0.1`, `::1`, and `::ffff:127.*`
- Never put a token in `config.json` or hardcode a token or key in source. Tests use fake tokens only
- Slack tokens come only from the credentials file each persona names (`credentials_file`, read by `src/persona-credentials.ts` during its bring-up). Never read a Slack token from the environment, and never write, copy, cache, persist or log a credentials file or any value from one. The CLI reads no token; don't add a token prerequisite to `start`
- Don't check, warn about or change a credentials file's mode. Why: the file is the operator's, and its permissions are the operator's choice (b.av2 SR-1.4). The server never creates a credentials file; the operator does, by hand or with the setup wizard's operator-run credentials command, `claude-slack-channel-bots credentials <persona>` (`## Credentials command` in `skills/setup-slack-channel-bots/SKILL.md`), whose packaged script `scripts/write-credentials.sh` writes it with mode 0600 and is the only place that mode is guaranteed
- Shipped skills never ask for, accept or print a token value, and never display a credentials file's content: no `cat`, `head` or `jq .`. They may check that the file exists and its mode, and the debugging skill checks its JSON shape with `jq`, reporting key names and prefixes only. A token goes only into the credentials command, run in the operator's own terminal, never into the chat or a skill's Bash call. Keep the credentials behaviour in the packaged script, never in a skill's shell block or the CLI process: the CLI only finds the persona in `config.json` (as it stands, never the record) and runs the script with `bash` on the operator's terminal, so the tokens are read at the script's own no-echo prompts. Keep the tokens off every program's arguments and environment (they reach `curl` only on its standard input), and out of every output, and keep the script working under bash and zsh. Keep the wizard's line one short line (the persona, never a path, as its argument), so a copy from an 80-column terminal keeps it whole. A shipped script belongs in package.json `files`. `tests/credentials-command.test.ts` pins it (b.av2 SR-12)
- Read a credentials file only through `readCredentialsFile` in `src/persona-credentials.ts`, the one stat-first reader (it reads only a regular file, so a FIFO or a device can't hang the server, and refuses a file over the 64 KiB cap; see Configuration). The bring-up check and the reload detection tick both use it; never read a credentials file any other way
- Compare credentials content only by digest (`credentialsDigest`, a SHA-256 or a missing/unreadable marker), held in memory by the bring-up controller for the tick to compare with. ## Auto-Restart

When a managed session's MCP connection closes, `onsessionclosed` calls `scheduleRestart()` in `restart.ts` to schedule a delayed relaunch.

### Configuration

`session_restart_delay` in `config.json` sets the delay in seconds before attempting a relaunch. Default is 60. Set to 0 to disable auto-restart entirely — the server will log `Auto-restart disabled (delay=0)` and skip all scheduling for that disconnect. Delay 0 does not disable the UNAVAILABLE retry timer: its retries never read the delay (b.jg5 SRJ-303).

Delay 0 disables restarts, not a launch's own reconnect. The collision ladder still types `/mcp reconnect` into a `waiting` row, and into a `working` row once the positive-idle rule shows it stale (b.f2b, see [Health-Check Poller](#health-check-poller)), whatever the delay: that reconnect is part of the launch. Nothing else reconnects a persona under delay 0, so a persona left running but unreachable is reported, never left down silently (b.f2b). Two paths raise the not-connected notice (`notifyPersonaNotConnected` in `src/session-manager.ts`):

- **The launch wait.** `waitForWaitingAndReconnect` ends with the session alive but nothing typed (`not-reconnected`): the `auto-restart-disabled` notice (*Not connected*), `blocked-on-prompt` (*Waiting on a prompt*) when the row ended at `ask_user` or `check_permission` (`waitEndedNotice`), or `unproven-idle` (*Not connected*) when the timeout finds it `working`.
- **The health check.** A persona is alive but not deliverable on two consecutive ticks: the tick calls `scheduleRestart`, which only logs, then `notifyNotConnected(key, cause)` (`HealthCheckDeps.isAutoRestartDisabled`). `cause` words the `auto-restart-disabled` notice: *Not connected* for `disconnected`, *Not receiving messages* for `streamless` (connected, but its `_GET_stream` is gone).

At any delay, holding back from a `working` row is bounded too. Every time the launch wait or the restart path's reconnect adapter holds back from one, typing nothing because it can't prove the session idle, it calls `noteWorkingRowDeferral`. Once that run of deferrals has lasted `UNPROVEN_IDLE_NOTICE_AFTER_MS` (10 min) from its first, the `unproven-idle` notice is raised: *Not connected*, its session reads working but CSCB can't prove it's idle, so it won't type into it. At a non-zero delay nothing else escalates such a row, so without it a row whose idleness can never be proven (an unreadable transcript, a compaction summary, a screen that keeps changing) would be held back from for good, silently. The run ends (`endWorkingRowDeferral`) when the row reads another state, when a reconnect is typed, when a launch starts, and with the episode; a failed status call leaves it as it is. Never add a path that holds back from a `working` row without noting the deferral.

The notices share one latch per persona (`notConnectedNoticeRaised`), so at most one is posted per episode, whichever path raises it first. The episode ends, and the latch is cleared, when the persona's MCP session registers again (`handleInitialized` in `src/server.ts`), on a health-check tick that finds it alive, connected and with its stream (`HealthCheckDeps.endNotConnectedEpisode`), and at its teardown, all through `forgetNotConnectedEpisode`. A new path that reports a persona not connected goes through `notifyPersonaNotConnected`, never a notice of its own, so the operator never gets two notices for one episode. Never write a log line that says the health check will reconnect a persona without checking the delay: with 0 it won't. Each give-up line in `waitForWaitingAndReconnect` takes its tail from `reportWaitEndedDisconnected`, which words it for the delay in effect.

### Failure Limiting

Consecutive relaunch failures are tracked per persona, keyed by persona key (b.av2 SR-6.3), by `src/backoff.ts` — a pure, import-free module with no timers or I/O (see SR-25). The module exposes a simple counter API consumed one-way by restart/health-check/server wiring. `restart.ts` counts at a single site: the `launchSession` boolean outcome (SR-25.1). A successful launch — or a successful MCP reconnect on the alive-but-disconnected path — calls `recordSuccess`; the failing `launchSession` branch calls `recordFailure`. A launch whose ladder waited on a `working` row and ended with the session alive but nothing typed, or whose wait its teardown cancelled, returns the action `not-reconnected` (b.f2b). `launchSession` maps it to `true`, so it records a success; don't count it as a failure: the session runs, and the wait has logged what happens next. A `'skipped'` launch (the relaunch gate refused it because the persona is not up) calls neither, so a persona that cannot be launched never burns its failure budget or trips the cap. Most not-up personas never get that far, because `restart.ts` asks the same gate earlier (see [Not-up guard](#not-up-guard-bav2-sr-64)). Any new launch path that can decline to launch returns `'skipped'` rather than `false`. The reconnect path never calls `recordFailure`: an `'escalate-dead'` or `'transient'` reconnect does not re-enter `scheduleRestart`, so counting stays tied to actual launch attempts rather than a non-launch reconnect site. `'transient'` also covers the b.f2b deferrals: a `working` row whose pane shows a busy turn or a prompt, is blank or can't be read, whose idle pane comes with a transcript that doesn't end with a completed turn or can't be read, or whose idle evidence is still being gathered across attempts; an `ask_user` or `check_permission` row whose tmux session lives (or can't be probed), which is never typed into; a `waiting` row whose pane shows a running turn or a prompt; and a failed status call, after which nothing is typed blind. On `'escalate-dead'` restart.ts does not re-enter either, and the verdict is not a silent dead end. The `_buildReconnectSessionAdapter` mapping first awaits `sweepDeadTmuxChannelWithCause` (an operator log line worded by the verdict, plus the memoized `reconcileMissingSweep`, b.m4r), reconciling the dead-tmux row to `missing`. A refused sweep (b.jg5 SRJ-105) makes the adapter answer `'transient'` instead, so nothing is re-probed, killed or relaunched. (A prompt row whose deferrals have run for 10 min escalates only after its own sweep has read the row `ended` or `missing`, so it needs no second one, b.jdc.) restart.ts then probes liveness again (`reprobeDeadAfterEscalate`, b.d61): a row that now reads dead is killed and relaunched in the same restart run, with no wait for the next tick or the external `~/startup/find-missing-loop.sh` (now belt-and-braces). A row that still reads alive returns as a `'transient'` does. The sweep and the re-probe record neither success nor failure, and the relaunch counts at `launchSession` like any other, so SR-25.1 (counting only at `launchSession`) is unchanged. A returned reconnect is not a dead end (b.9a7): the periodic health-check tick is the retry driver, re-observing the persona each interval and calling `scheduleRestart` again while it is still alive-but-disconnected or once it goes dead, so a failed or deferred reconnect is retried on a bounded cadence.

#### Exponential backoff

Each successive failure doubles the restart delay, starting from `session_restart_delay` (default 60 s), capped at 900 s (15 minutes):

| Pre-failure count | Delay (base = 60 s) |
|---|---|
| 0 | 60 s |
| 1 | 120 s |
| 2 | 240 s |
| 3 | 480 s |
| 4 | 900 s |
| 5+ | 900 s |

Formula: `min(base * 2^preFailureCount, 900)`. `nextBackoffDelay(key, baseDelaySeconds)` returns this value for persona `key` using the count recorded before the current failure attempt.

The arithmetic is also exported statelessly as `doublingBackoffDelay(base, priorAttempts, ceiling)` for callers that keep their own attempt count; `nextBackoffDelay` delegates to it with the 900 s ceiling. The session-restart ladder above, its 5-failure cap and its counters are keyed by persona key.

Persona bring-up retries (b.av2 SR-3.2: Slack-unreachable and directory-broken) use a separate schedule in `src/persona-retry-schedule.ts`: 5 s doubling to 300 s, no attempt cap, and never shorter than Slack's `retryAfter`. Create one schedule per persona and retry purpose with `createPersonaRetrySchedule`. Don't use the session-restart counters for bring-up retries: both are per persona, but they count different failures and share no state. See [Persona Bring-Up Retries](#persona-bring-up-retries).

#### Cap at 5 consecutive failures

After 5 consecutive failures, `isAtCap(key, RESTART_FAILURE_CAP)` returns `true` (`RESTART_FAILURE_CAP = 5` is exported from `restart.ts` and referenced by `src/persona-routing.ts` and the health-check wiring in `server.ts` — no hardcoded literal). Capped personas are skipped by the health-check tick — the poller calls `isAtCap` before `scheduleRestart` and skips the persona when it is true.

A capped persona recovers **only via a server restart**. The in-process counter is lost on restart by design; startup reconcile then re-runs for every persona, giving each a fresh attempt.

Sending a message in the channel does **not** revive a capped persona. A persona capped by 5 consecutive `launchSession` failures has no registered session, so an inbound message it receives hits the no-session branch in `src/persona-routing.ts` (`[slack] No live session for persona <ref> chat_id=<C…> — dropping message`). As of b.kvq that branch *can* trigger a recovery `scheduleRestart`, but the shared guard `decideLostMessageState` (`src/lost-message.ts`, fed the persona's real restart state) checks `isAtCap(key, RESTART_FAILURE_CAP)` and, at the cap, answers `restart-limit-reached` and does **not** fire — the persona's destination gets a lost-message notice saying automatic restarts are suspended and the server must be restarted. The cap is therefore still honored on the inbound path; firing a restart would only burn a spawn attempt against a persona that cannot come up. Only a server restart clears the in-process counter and gives the persona a fresh attempt.

There are two message-triggered restart sites, both in `src/persona-routing.ts`, neither of which bypasses the cap for a capped-dead persona:

- The streamless trigger (b.9cj) fires for a session that is *registered* for the persona yet missing its `_GET_stream` (`hasSessionStream(key)` false). A capped-dead persona has no such registered session, so this never applies to it. The branch does **not** call `notification()` — with the stream gone the SDK's `send()` evaporates silently, so the message is provably undeliverable; it triggers recovery with `scheduleRestart(key, session.cwd, undefined, { humanTrigger: true })` and raises a lost-message notice at the persona's destination instead of staying silent. Recovery actually fires because `restart.ts` doesn't wave a connected-but-streamless session through as "already reconnected" (it skips only when connected AND `hasSessionStream`).
- The no-session trigger (b.kvq) fires for a persona with **no** registered, connected session, calling `scheduleRestart(key, persona.working_directory, undefined, { humanTrigger: true })`.

Both branches go through `handleLostMessage`, which asks `decideLostMessageState`, so `scheduleRestart` fires only in the `starting-now` state: the persona up, no restart pending or active, auto-restart enabled and the persona under the cap. Pass the routing the shared `isPersonaUp`; without it every persona counts as up. `humanTrigger` clamps the computed backoff delay **down** to `HUMAN_TRIGGER_DELAY_CEILING = 5` s (never up) but does not touch the failure counter or the re-entrancy guard, so the cap and backoff accounting are unchanged.

Key every guard and the `scheduleRestart` call on the receiving persona's key. The session is looked up by that key (`getSessionByPersona`), so the persona that received the message is always the one that owns the session: there is no owner resolution, and a recovery can never spawn a second instance on another persona's directory. Report the lost message with one notice through the routing's injected `notify` (the per-persona notifier's `notify`, wired in `server.ts`), never with a post of your own. The notifier prefixes the persona reference and takes the notice down the one notice path: the pre-validation hold while the persona has no validated client, its channel or `dm` destination (the DM opened when the notice is attempted), and the shared destination hold's retry and once-per-episode `persona-destination-failed` line when the destination refuses. Nothing else is posted in the source conversation (when the destination is that conversation, the notice is the one post there); see [Report Delivery Failures Only to the Persona's Destination](#report-delivery-failures-only-to-the-personas-destination). Await the notice inside `try`/`catch`: a failing `notify` logs one `[slack] persona-routing: lost-message notice for persona <ref> failed: …` line (built with `describeThrownValue`, no message text) and never throws out of dispatch.

Resolve the author label, read the session and probe the stream before anything else, then await the send. Nothing is awaited between the session read and the send (b.9cj). Only after the send has succeeded does the persona record its ack-tracker entry (keyed by its own key, the conversation and the ts) and add the `ack_reaction` through its own client (issued, not awaited; b.av2 SR-4.5). A lost message or a send that throws gets no entry and no reaction. Never key an ack entry, or consume one, without the persona key: the `reply` tool consumes and removes only the calling persona's own entry and reaction, and the persona teardown drops the persona's entries (`forgetPersonaAcks`).

The notice names the sender (the same `resolveAuthorLabel` label the meta uses, with `&`, `<` and `>` escaped so a bot `username` can't ping anyone) and the recovery state, and never the message text. The dropped message itself is always lost — recovery starts a session but never delivers or replays it. There are five recovery states (`LostMessageState`), decided in this order, first match wins:

1. **`not-up`** — the routing's injected `isPersonaUp` (the server's one `isPersonaUp`) answers false: the persona's bring-up is `retrying` or `broken`. A persona that is not up forwards no Slack event, so this is reached only in a race: the persona stops being up between receiving the message and the session lookup (for example a Web API call refused for its bot token), or the old half of a destructive modify receives a message after its bring-up state is cancelled and before its connection stops. No restart is fired: its own recovery launches it once it is up, and a restart would only reach the not-up guard. Checked first, so a not-up persona never reports a restart it won't get.
2. **`restarting`** — `isRestartPendingOrActive(key)`: a restart is already pending or running. No restart is fired, so no second launch is stacked.
3. **`auto-restart-disabled`** — `session_restart_delay: 0`. `scheduleRestart` would early-return, so it is not called; the notice says to restart the server.
4. **`restart-limit-reached`** — `isAtCap(key, RESTART_FAILURE_CAP)`. No restart is fired; the notice says automatic restarts are suspended and to restart the server.
5. **`starting-now`** — up, under the cap, auto-restart enabled, nothing pending: fires the human-clamped `scheduleRestart`. Both branches report this state.

#### SpawnCapReached notification (once per episode)

On the transition to 5 consecutive failures, the `launchSession`-failure branch calls `shouldNotifyCap(key, RESTART_FAILURE_CAP)`; on its single `true` return it invokes `deps.onCapReached(key)` and schedules **no** further timer. `onCapReached` calls the session manager's cap-notice function, `notifyRestartCapReached(key)`, which raises a distinct `SpawnCapReached` notice through the per-persona notifier (`src/persona-notifier.ts`). The notifier posts it to the persona's destination under the persona's identity, as one top-level message with no `thread_ts`, and prefixes it with the persona reference. Raise restart, spawn, outage and transcript notices through the notifier; never post them from `restart.ts`, `server.ts` or `session-manager.ts` directly. Subsequent failures in the same capped episode are silent. `shouldNotifyCap` implements this latch: it returns `true` on the first call at cap, then latches to `false` until the counter is reset.

#### Counter reset semantics

`recordSuccess(key)` resets the persona's consecutive-failure count and clears the cap-notified latch. It is called on any successful launch or successful MCP reconnect. Both state values reset together — a fresh episode starts from 0 failures with the cap-notification latch cleared.

#### State lifetime

The backoff state is in-process only — no persistence. A server restart resets all counters. This is intentional: the server re-runs startup reconcile on start, so each persona gets a clean shot at reconnection after a process restart.

#### Not-up guard (b.av2 SR-6.4)

A persona that is not up (its bring-up is broken or retrying, or its Slack connection is not serving) is never restarted: its instance and agent-director row are left alone and its failure count is unchanged. `RestartDeps.canRestart(key)` (the server passes the relaunch gate) is asked at `scheduleRestart` entry (after the delay=0 and shutdown checks), at the top of the timer callback before `isSessionAlive`, and again right after `isSessionAlive` returns, before `reconnectSession` or `killSession` (`skipIfNotUp`). After an `'escalate-dead'` reconnect, it is asked once more after the second `isSessionAlive` probe, before the kill (b.d61). `launchSession`'s own gate is the backstop for a flip during the kill; its `'skipped'` counts as neither success nor failure. The same gate refuses a key outside the applied set (a persona a confirmed change removed), so a restart armed before the removal kills and launches nothing (see Reload Detection Tick).

- **Check shutdown before the gate.** During shutdown every bring-up is cancelled, so the gate would answer false for every persona and log healthy ones as not relaunched. `scheduleRestart` returns on `isShuttingDown()` without asking it, and the timer callback checks shutdown first too.

- **Ask the gate after every await, before touching the instance.** The liveness probe is an async agent-director call, and the persona can stop being up while it runs. A new step that awaits before a reconnect, kill or launch gets its own `skipIfNotUp` check after the await.
- **A refusal records nothing.** Never call `recordFailure` or `recordSuccess` on a not-up skip; the persona's next restart after it comes up counts normally.

#### The UNAVAILABLE retry timer and the counter (b.jg5 SRJ-302, SRJ-303)

The retry timer (`src/unavailable-retry.ts`) never records to the failure counter or reads its backoff: it imports only the stateless `doublingBackoffDelay`. A launch agent-director refused comes back `'refused'` and records nothing, and a retry skipped because a launch is in flight, or because the persona reached the cap while the retry waited behind other restart work, makes no call, so a persona is never capped or given up for UNAVAILABLE alone. A refused kill in the restart work (`KILL_SESSION_REFUSED`) records nothing either: the work answers `'refused'` with no launch. `'refused'` rests on the trigger sink's answer: `arm` answers true only when the persona has a timer after the call, and a launch whose error armed nothing (the controller closed, or its first timer could not be set) is an ordinary counted `false`, so no failure goes uncounted without a timer to retry it. The one way a retry reaches the counter is through its own restart work: its launch's failure is counted at the single counting site (`launchSession`'s `false`) like any other, and its successful launch or reconnect calls `recordSuccess`. Keep it that way: a new retry step never calls `recordFailure` itself, a new refusal outcome returns an uncounted result such as `'refused'`, never `false`, and a new check in `runRestartRetry` that can skip the work goes inside its serialized work, where the state it reads is current. The `tmux-unresponsive` condition's *Not answering*, *Still not answering* and *Answering again* notices (b.jg5 SRJ-308, SRJ-309, SRJ-310) never count toward `RESTART_FAILURE_CAP`, and the alert caps nothing: it never touches the counter, the cap latch or the retry timer, so the retries continue after it.

#### The tmux-unresponsive condition is not an outage (b.jg5 SRJ-307, SRJ-310)

`tmux-unresponsive` is a per-persona condition held in `src/persona-episodes.ts` (`createTmuxUnresponsiveCondition`), never an `OutageClass` in `src/outage-state.ts`.

- **Only a tmux-touching UNAVAILABLE inside an attempt starts it.** The one start site is the reporting step, `reportAgentDirectorError`: inside a launch or recovery attempt for the persona, for a call `isTmuxTouchingCall` accepts, when the arming predicate answers the `unavailable` cause. `ErrTmuxKillFailed` (the `kill-failed` cause) never starts it, and neither does any error from `status`, `get`, `list` or `find-missing`. Don't add a second start site, and don't start it from a call outside an attempt.
- **Every wrapped call declares its verb.** `withOutageDetection` and `withSpawnDetection` take an `AdCall` (`src/ad-error-class.ts`) between the working directory and the function, and the function makes exactly that call. A `kill` declares whether the site kills a row it read in a live state (`adKillCall(rowReadLive)`); only such a kill is tmux-touching. Declare it from what the site read, never from the verb alone: a kill after a `dead` reading, or of a row the site did not read, declares `AD_CALL_KILL_ROW_NOT_READ_LIVE`. The one exception is the kill after a resume answers `ErrSpawnNotResumable`: it always declares `AD_CALL_KILL_ROW_READ_LIVE`, whatever the site read before, since agent-director has just said the row is non-terminal.
- **Only tmux clears `tmux-unavailable` (b.jg5 SRJ-311, SRJ-312).** The `tmux-unavailable` outage flag is cleared by a declared tmux-touching call (`isTmuxTouchingCall`: `spawn`, plain or reuse, `resume`, `read-pane`, `send-keys`, `pause`, a `kill` declared `AD_CALL_KILL_ROW_READ_LIVE`) that succeeded or threw a GONE error (the wrappers in `src/outage-state.ts`), or by a health tick or a retry that finds the persona's row live other than `pending`, its session connected and its stream present (the tick's healthy branch; the retry's `endTmuxUnresponsive` binding in `main()`). Nothing else clears it: a successful read (`status`, `get`, `list`, `find-missing`), `delete`, `get-permission`, `decide` or kill declared `AD_CALL_KILL_ROW_NOT_READ_LIVE` leaves it raised, and so does a `status` answering `ErrSpawnNotFound`. A new wrapped call site gets this for free by declaring its verb truthfully; never add a `clearOutageFlag(key, 'tmux-unavailable')` at a site of your own. `ad-unreachable` still clears on any successful call. Why: a read can succeed while tmux is still unusable. A clear reaches the retry timer's condition-end entry through the cleared-flag observer, so a false clear would stop the persona's retry timer and post a false all-clear.
- **ENVIRONMENT arms from any verb and is never counted (b.jg5 SRJ-311).** `ErrTmuxNotAvailable` from any verb, `kill` included, arms the persona's retry timer in any context (`reportAttemptError`), and at every launch and recovery site it is a refusal through `refusalAt` or the restart kill adapter: no kill, delete, launch, `dead-session`, spawn-failure notice or `spawn-failed` entry follows it. Don't give it an early `failed` branch of its own at a new site; let the arming predicate decide, and classify it by name through `src/ad-error-class.ts`, never with `instanceof`.
- **Raising or ending it touches no outage state.** No `setOutageFlag` / `clearOutageFlag`, no onset or all-clear notice, no bad-stretch history. Each end goes through the condition's `end`, which calls the retry timer's `conditionEnded` once; never call `conditionEnded` for it from anywhere else.
- **An end passes the row reading it has.** A tick or a retry passes the reading it made (`live`, or the live row state), a successful launch call (`isLaunchCall`: `spawn`, `resume`) passes `pending` (its row is `pending`, so SRJ-306 keeps the timer), and any other tmux-touching success or GONE passes none. Don't pass a reading the end did not make: the retry timer takes it as the latest row read. For an end deferred during a retry run, the run's own row wins unless the deferred reading is `pending` (`deferredReadingApplies`); keep that order when a new answer carries a row. An arm (either mode) later in the same run cancels that deferred end and its reading, since the condition started again; an end after that arm is deferred again and applied.

Why: a refusal from a call that touches the persona's session is about that persona, not an agent-director outage, and a read that times out says nothing about the session. Held as an outage flag, it would post a generic onset and all-clear, and it would hold back or join the all-clear of a real outage for the same persona.

### Persona Bring-Up Retries

A persona's bring-up ends `up`, `broken` or `retrying` (b.av2 SR-6.1). Slack-unreachable and directory-broken personas are retried; credentials-broken ones aren't. This is a second retry mechanism with different rules from auto-restart. It lives in `src/persona-bringup-controller.ts` (directory re-checks, the `claude_config_dir` hold, the launch after a retry) and `src/persona-connections.ts` (Slack retries). See docs/architecture.md, Server-Managed Startup step 5. A persona whose `claude_config_dir` is unresolvable (bug b.g57) is held `retrying` by the controller, like a directory-broken persona: checked right before its Slack step, it never connects; found later by a launch (`holdForConfigDir`), its Slack connection is closed and its MCP session dropped, with its instance and row kept. It is re-checked on its own schedule like a directory retry, then connects and launches; these rules apply to it too. A confirmed credentials change while it is held is taken as for any retrying persona: no connection opens until the directory resolves.

- **Never touch the restart counter or cap.** Bring-up retries use their own `createPersonaRetrySchedule` (5 s doubling to 300 s, no cap), never `backoff.ts`, `scheduleRestart` or `RESTART_FAILURE_CAP`. A missing directory is an operator fix that can take hours; a cap would leave the persona down after the fix, and counting it as a restart failure would cap a persona that never launched (AC 66).
- **Keep retries on per-persona timers, outside `startupSessionManager`'s pool.** The start pass must return once every persona has an outcome; never await a retry there or give a retrying persona a pool slot. One slow or broken persona must not delay a healthy one (AC 23, 24). The same holds for a launch: one whose ladder starts waiting for a `working` row (up to 10 minutes) tells the pass through `LaunchHooks.onWorkingRowWait`, and the pass parks it (`launchOrPark`): it frees the pool slot and goes on, while the launch stays in flight and logs its outcome when it settles (b.f2b).
- **No timer, lock, queue or promise chain spans two personas.** Keep all retry state in the persona's own entry, and schedule the next re-check only after the previous one finished. A shared structure lets one persona's stall block another.
- **Reuse the credentials read at the original bring-up.** A retry hands the manager the tokens held from the first read (or from the last confirmed credentials change); never re-read the file. An edit made meanwhile is detected as a pending change (see Reload Detection Tick in `docs/architecture.md`) for the operator to confirm (E12), not something a retry picks up silently (AC 66).
- **Launch from the retry, once.** A persona that reaches `up` through a retry is launched from its own retry path through `spawnForPersona`, so it shares the one-launch-in-flight guard with restarts. Don't wait for the health check: until the launch, an inbound message would take the lost-message path.
- **Keep the running-persona path separate.** A persona that is running and whose directory later disappears is not a bring-up retry: it keeps the restart backoff, cap and `cwd-unreachable` notice (b.av2 SR-11). Don't route it through the bring-up controller, and don't route a bring-up retry through restart.
- **Log, never post.** Broken-persona and retry failures go to the server log only, through the injected logger: never to Slack under any identity, never held for a later flush and never to `startup-errors.log`. A persona that isn't up has no validated identity to post as, and posting under another persona's identity would leak one persona's state into another's channel.
- **Log when a cause starts and when it clears, not on every attempt.** A retry that runs every 300 s for days would otherwise flood the log. A class change between attempts is the same episode and logs nothing.
- **No token value in any line.** Name the persona, its `personas[i]` entry, its key and the file path; describe a bad token only by its key and the rule it breaks.

### Serve Only Personas That Are Up

A persona that is not up (b.av2 SR-6.4: its bring-up is `broken` or `retrying`, or its Slack connection is not serving) may still have an agent-director row and a running instance. Keep the instance, but don't serve it until the persona is up. See docs/architecture.md, Session Lifecycle, Connection and Disconnection.

- **Check the persona is up before delivering work to its instance or relaying work from it.** Ask the one shared predicate, `createPersonaUpPredicate` in `src/persona-start.ts`, which `server.ts` builds once as `isPersonaUp` and injects. The current paths are MCP registration (`decideSessionAdmission` in `src/registry.ts`), the permission poller (`PollerDeps.isPersonaUp`), `/interject` (`InterjectDeps.isPersonaUp`, 503) and the lost-message recovery (`PersonaRoutingDeps.isPersonaUp`: a not-up persona gets the `not-up` notice and no restart). A new endpoint, tool or poller that serves an instance takes the same function as an injected dependency. Don't keep a second copy of the up state, and don't use "`clientFor` returned a client" as the check: `clientFor` answers on the connection status alone, not on the bring-up outcome. Why: work sent to or relayed from a persona whose Slack identity is down is lost, or posted under no identity or the wrong one (AC 23, 24).
- **Never kill or delete a not-up persona's row or instance for being not up.** Leave the row for the launch that follows its coming up, which reaches it through the collision ladder, so the conversation history survives the outage (AC 23, 24). In particular, when the `cwd` check can't be evaluated it is not a `cwd` mismatch: check `compareRowToPersona`'s `cwdCheckDeferred` before acting on `cwdMatches`. It is true only when the persona's working directory has no real path and the row's `cwd` has none either (absent, missing, a dangling symlink's old target) or equals the configured `working_directory` lexically. Only then does the start sweep keep the row and defer the check to the launch, and the ladder keep it and fail the launch. A row whose `cwd` resolves to an existing directory elsewhere is still replaced, even while the working directory is missing, and so is a row whose `cwd` differs by real path from a resolvable working directory (b.av2 SR-6.2, SR-6.3). Keep the deferral to the `cwd` guard: the ladder's `resume_enabled=false`, `config_dir`, `ErrNoSessionId` and `ErrJsonl*` paths replace the row whatever the directory's state. Why: a missing directory is a temporary operator fault, and the lexical fallback can't prove the row is elsewhere; but a row in an existing directory provably is, and keeping it would let a persona adopt another persona's directory.
- **When a persona stops being up, drop its MCP session and do nothing else.** The controller's `onLeftUp` fires once per change from `up` to `broken` or `retrying`; the server's listener (`createNotUpSessionDropper` over `dropPersonaSession`) removes the registry entry and session-ID mappings before closing the transport, so the close schedules no restart. No restart, kill, delete or Slack post. A Slack connection being reopened (`lost`, or `retrying` in the `reopen` phase) keeps the persona `up`, and so does a credentials reconnect (see Credentials Reconnects): don't drop on either. Why: the persona can't be served while down, but its instance and history must be there when it comes back (AC 23, 24).

### Credentials Reconnects

A confirmed change to a persona's credentials content at the same path reconnects only that persona (b.av2 SR-8.6 step 4). It is the one place a persona holds two Slack connections at once. The manager's side is `reconnectCredentials` in `src/persona-connections.ts`, the controller's `changeCredentials` in `src/persona-bringup-controller.ts`, and the lifecycle operation in `src/persona-lifecycle.ts`. See docs/architecture.md, Session Lifecycle, Credentials change.

- **Open the new connection before closing the old one.** Switch the tokens, identity, Web API client and socket together only once the new socket has reached `hello`, then close the old one as the manager's own close. Never close first: a failure would leave the persona with no connection. SR-3.1 allows two sockets and two Web API clients per persona only during this overlap.
- **A failure keeps the old connection.** A locally bad file or a Slack refusal discards only the new clients; the old connection, its identity and its client stay in use, one `persona-credentials-change-failed` line is logged and the change stays pending. Slack unreachable keeps the old connection too, while the new one retries on its own SR-3.2 schedule and its own episode latch.
- **Every `start()` is bounded at 10 s, the reconnect's included** (SR-3.3). Build the reconnect's clients through the same attempt code as a bring-up, never a second path without the bound.
- **Run it in the persona's serialized turn, and block no other persona.** The operation goes through `personaLifecycle.run(key, …)` and awaits only its own first attempt; one that attempt left retrying resolves then and counts as complete for step order. Its later attempts run on the manager's timer, never through the serializer. No state, timer or lock of one persona's reconnect is shared with another's.
- **The persona stays up.** A persona being reconnected is `up` throughout, so `onLeftUp` doesn't fire and its MCP session isn't dropped. Nothing is killed or launched. The one exception is a persona whose own connection Slack refused meanwhile: it is credentials-broken, and a later swap brings it back up and launches it through the collision ladder.
- **Clear what is cached per Slack identity before the swap.** The new tokens may belong to another app. Anything keyed to the old app (today the DM-destination conversation, `personaDestinations.forget`) is cleared in the reconnect's `beforeSwap` hook, which runs before the persona is reported up on the new connection, so the notifier's flush at up never uses the old app's state. A new per-identity cache is cleared there too, not after the swap.
- **Keep what is held apart from what is live.** The controller holds the content the reload tick compares (tokens and digest) and, separately, the content the persona's own connection uses (`live`). A refusal, at once or later, holds `live` again, never content captured when the change started: a later swap may have changed it since.
- **End every episode the reconnect opened.** A cancelled reconnect (a later change, `stop`, `stopAll`) ends its Slack-unreachable episode with a cleared line (`SlackEpisodeTracker.end`), so every start line gets an end.
- **A credentials-broken persona recovers only through a confirmed change.** No retry, reopen or reconnect revives it. Apply step 6's recovery bring-up clears its bring-up state, connection and DM cache and brings it up afresh. Decide credentials-broken when the step runs, never from the preview: a persona can break or recover between the two.
- **Watch every long-lived persona Web API client for auth errors** (bug b.ujn). Every long-lived Web API client the manager hands out is wrapped with `watchWebClientAuth` (`src/persona-web-api-watch.ts`), so the first call refused with `invalid_auth`, `token_revoked`, `account_inactive` or `not_authed` marks the persona credentials-broken at once. A new long-lived client, the reconnect's included, goes through the same wrap; never hand a consumer an unwatched client. The mark itself never waits for the serializer; only the detached socket's network close is submitted through it, never awaited.

### Post to a Persona's Destination Through the Hold

A persona's destination is its `permission_prompts` channel or its DM with `dm.contact`. Every post there goes through the one shared destination hold, `personaDestinationHold` in `server.ts` (`createPersonaDestinationHold` in `src/persona-destination-hold.ts`), which posts through the shared destination resolver.

- **Take the shared hold, don't build one.** The notifier and the permission poller get the same instance, so a persona's prompts and notices share one episode and one retry schedule. A new poster takes it as an injected dependency: a re-derived item asks `begin(key)` for an attempt and gets nothing while the persona is held; a one-off message is handed to `deliver`. Posting through the resolver directly bypasses the hold: the failure is then neither retried nor logged once.
- **Keep it side-effect-free and cancel it at shutdown.** `server.ts` builds it at module scope with no Slack call and no timer; timers start only when a notice is held. `shutdown()` calls `personaDestinationHold.cancelAll()`. Code that removes a persona calls `cancel(key)` beside `personaDestinations.forget(key)`, as the persona teardown in `src/persona-lifecycle.ts` does.
- **Don't log destination failures per attempt.** The hold logs one `persona-destination-failed` line when an episode starts and one when it clears; that is the diagnostic. A poster logs only a failure the hold doesn't retry: a payload error about the message itself (`MESSAGE_PAYLOAD_ERRORS`). Why: a retry every 300 s for days would otherwise flood the log, as for bring-up retries.

### Latch a New Per-Persona Notice Kind in persona-episodes.ts

A per-persona notice that posts once per episode keeps its latch in `src/persona-episodes.ts`, the server's one instance built in `main()`.

- **Add a kind there, never a flag in the site module.** Declare a `PERSONA_EPISODE_KIND_*` label, add it to `PERSONA_EPISODE_KINDS`, and have the poster call `begin`, `post` and `end` on the instance it is handed. A kind with a case (a new case begins a new episode) passes it to `begin`; a kind with two texts gives each its own mark in `post`.
- **It is not an `OutageClass`.** The classes in `src/outage-state.ts` are outage flags with their own onset and all-clear notices; a notice kind never becomes one. The `tmux-unresponsive` kind is begun and ended by its condition (`createTmuxUnresponsiveCondition`, see The tmux-unresponsive condition is not an outage above).
- **The not-connected reasons are the exception.** b.f2b's not-connected notices keep their one shared latch (`notConnectedNoticeRaised` in `src/session-manager.ts`, through `notifyPersonaNotConnected`); `persona-episodes.ts` neither reads nor writes it.
- **Post through the instance, not the notifier.** Its sink is the persona notifier, so a notice still goes through the hold above.

Why: one place begins, ends and forgets every episode, so a persona teardown forgets all of that persona's episodes in one step (`forgetNoticeEpisodes`) and shutdown closes the instance (`close()`: every episode ends and none begins again), with no latch left in a site module to go stale or post for a torn-down persona.

### Report Delivery Failures Only to the Persona's Destination

Report a message that couldn't be delivered (the lost-message notice) only to the persona's permission-prompt destination, through the notifier. Never post a server message in the conversation the message came from, channel or DM, to report a delivery failure. When that conversation is also the destination, the destination's one notice is the only post there; it goes there because it is the destination, never because the message came from there. Why: a persona may pass as a person in a shared channel, and a server message there would give it away. The rule binds future delivery or queueing work too (for example b.4vj, guaranteed inbound delivery): report saved, queued or undeliverable messages to the destination as well.

### Keep the Debugging Skill Complete

`skills/debug-slack-channel-bots/SKILL.md` is the operator's catalogue of persona failures. It ships in the npm package.

- **Update the skill in the same change.** Adding or renaming a persona diagnostic class (`PERSONA_DIAGNOSTIC_CLASSES` in `src/persona-diagnostics.ts`) or a reload diagnostic class (`RELOAD_DIAGNOSTIC_CLASSES` in `src/reload.ts`), a start refusal over the config file or the last-applied record, a `config.json` load-time rejection (`src/config.ts`) or an operator-visible persona failure mode (a refusal, skip or retry line) requires a matching entry in the skill: its meaning, cause and fix, with the class or message spelled as the code spells it. Removing one removes its entry. Why: the operator diagnoses from shipped material only (b.av2 SR-12, AC 27), and a missing entry leaves them with a log line nothing explains.
- **Never show a token value in the skill.** Describe a bad token by its key and the rule it breaks, and use obviously fake placeholders (`xoxb-…`) where a shape must be shown. A shape check may report key names and prefixes, never values.
- **Name pre-persona keys only in the SR-1.7 entry.** That entry, under its own heading, is the one place in any shipped description allowed to name the rejected pre-persona keys, and only to say they're rejected and must be rewritten as personas.

## Health-Check Poller

`health-check.ts` runs a `setInterval` loop that checks every applied persona that is up on a fixed cadence and schedules recovery for sessions that read `dead` — and, as of b.9a7, for sessions that are alive (AD live state) but MCP-disconnected — when they are not already being recovered. Both cases route through `scheduleRestart`, which then reconnects or relaunches per case. The alive-but-disconnected case requires `!connected` on two consecutive ticks before firing, to avoid poking a freshly-launched session that has not yet registered its MCP connection; the one exception is a `working` row whose idle evidence is being gathered (b.f2b, below).

### Configuration

`health_check_interval` in `config.json` sets the polling interval in seconds. Type: `number`. Default: `120`. Set to `0` to disable the poller entirely — `startHealthCheck()` returns immediately without creating an interval.

### Async Interval Pattern

Each tick fires an `async` callback. The callback iterates the persona work list sequentially to keep concurrent `client.status(...)` traffic predictable. `HealthCheckDeps.getPersonas()` supplies it as persona key → working directory; production wires the pure `buildPersonaWorkList(personaConfig, canRelaunch)`, one entry per persona that is up, however many channels it lists. Errors on a single persona are caught and logged; they do not abort the rest of the iteration. agent-director's library Client is internally safe for concurrent verb calls (see SR-0.1).

```typescript
intervalId = setInterval(async () => {
  for (const [key, cwd] of Object.entries(deps.getPersonas())) {
    try {
      // check and maybe scheduleRestart
    } catch (err) {
      console.error(`[slack] health-check: error checking persona=${key}: ${describeThrownValue(err)}`)
    }
  }
}, intervalSeconds * 1000)
```

### Coordination with restart.ts and backoff.ts

The work list already leaves out every persona that is not up (its bring-up is broken or retrying, or its Slack connection is not serving), so the tick never raises `cwd-unreachable` for, reconnects or relaunches such a persona; its bring-up retry owns it until it is up. Don't add a tick path that bypasses the work list. A persona left out of a tick's work list also loses its disconnected streak, as the pending-restart and cap skips do, so a persona that comes back up starts a fresh two-tick count instead of inheriting an observation from before it went down.

The poller's guards, all keyed by persona key, come in two kinds. The two skips, checked first and in this order, skip the persona before any read and clear its streak:

- `isRestartPendingOrActive(key)` from `restart.ts` — returns `true` if a restart timer is queued or a restart's launch is running; skip, silently, to avoid double-launching.
- `isAtCap(key, RESTART_FAILURE_CAP)` from `backoff.ts`, injected as `HealthCheckDeps.isAtCap` — returns `true` if the persona has reached the consecutive-failure cap; skip the tick for this persona, logging `[slack] health-check: persona=<key> is at cap — skipping tick (SR-25.3/25.4)`. It is checked before the in-flight guard, so a capped persona with a launch in flight logs this line too. A capped persona recovers only via a server restart (see SR-25). The tick guard only stops the *poller* from re-scheduling. The `scheduleRestart` path is itself cap-exempt, but neither message trigger in `src/persona-routing.ts` revives a capped-dead persona: the b.9cj streamless trigger reaches `scheduleRestart` only for a session that is registered yet missing its `_GET_stream` (which a capped-dead persona does not have), and both it and the b.kvq no-session trigger ("No live session for persona … — dropping message") go through `decideLostMessageState`, which checks `isAtCap(key, RESTART_FAILURE_CAP)` and declines to fire at the cap, reporting `restart-limit-reached` in the lost-message notice at the persona's destination. Both key every guard and the `scheduleRestart` call on the receiving persona's key.

Then the no-attempt guards (b.jg5 SRJ-315), decided once per persona per tick before any read (`noAttemptReason` in `src/health-check.ts`, the first that holds). Neither skips the persona: the working-directory check runs and liveness, connection and stream are read as below, so a persona that recovered on its own takes the healthy branch (ending `tmux-unresponsive` and clearing `tmux-unavailable`). Any other reading but `unknown` (`dead`, `pending`, disconnected or streamless) only clears the streak: no `scheduleRestart`, no not-connected notice, no line. `unknown` takes its usual line and skip.

- **In flight** — `HealthCheckDeps.isLaunchInFlight(key)` (b.f2b) returns `true` while anything is in flight for the persona. Production binds it to the server's one in-flight predicate (`isPersonaWorkInFlight` in `main()`), the same binding the UNAVAILABLE retry timer gets as `isInFlight`. Today that is a launch call (the session manager's `isLaunchInFlight`): a start launch parked while it waits for a `working` row (up to 10 minutes), a bring-up retry's launch or a restart's. The work in flight owns the session, and its wait reconnects it or reports it. Why shared: today one predicate serves both, so the tick never attempts over work that holds back the retry timer. The two need not stay identical: work can count as in flight for the tick without holding back a retry (b.jg5 SRJ-303, SRJ-401), so check each consumer before adding work to the predicate. Why still read: the tick must still see a persona that recovered on its own. A throw from the predicate ends the persona's work for the tick before any read (the per-persona catch logs it).
- **`tmux-unavailable` raised** — the persona's `tmux-unavailable` outage flag is set (`getOutageFlags`). Its retry timer then retries on its backoff, one per interval (b.jg5 SRJ-311), and the tick makes no attempt; a tick attempt would double the pace and could launch while tmux is unusable. The tick is not the only other trigger: a lost message or a session disconnect can still call `scheduleRestart`, but while tmux is unavailable the restart's tmux-touching steps (the reconnect keystrokes, the kill, the launch) are refused, so it launches nothing and counts nothing (b.jg5 SRJ-105, SRJ-302).

Add a new no-attempt reason as one more `NoAttemptReason` member and one more check in `noAttemptReason`, not as a new skip: a skip stops the reads, and the reads are what end the outage.

When neither skip fires, the poller checks liveness, connectedness, and stream presence via `isSessionAlive(key)`, `isSessionConnected(key)` (added in b.9a7, wrapping the same registry-`connected` adapter restart.ts uses), and `hasSessionStream(key)` (added in b.9cj). `hasSessionStream` is exported from `src/persona-routing.ts` (`getSessionByPersona` → `hasGetStreamKey(transport)`); it is the one `_GET_stream` probe shared by the dispatch path, the restart guard (`RestartDeps`) and the health check (`HealthCheckDeps`), so all three agree on whether a session can receive a message:

`isSessionAlive(key)` answers a liveness reading (`src/liveness-reading.ts`, b.jg5 SRJ-314): `live`, `pending`, `dead` or `unknown`. The tick reads it through `livenessKindOf`, so a probe that throws, or answers something that is not a reading, is `unknown`; `live` and `pending` are alive, but only `live` is ever healthy (b.jg5 SRJ-314): a `pending` row's session has not started, whatever its connection shows:

- **Unknown** → agent-director could not report on the persona. Log one line and skip the persona for this tick: nothing scheduled or posted, no episode ended, no retry timer armed (the tick runs outside every attempt). Clear its streak, as every skip does, so an `unknown` tick neither builds toward a restart nor proves the persona healthy.
- **Dead** (`dead` only) → `scheduleRestart(key, cwd)` immediately — the same function used by the reactive `onsessionclosed` path.
- **Alive but not deliverable** (`live` or `pending`, and `!connected || !hasSessionStream`; or `pending` connected with its stream) → increment a per-persona consecutive-failing streak; `scheduleRestart` fires only once the streak reaches two consecutive ticks (the freshly-launched false-positive guard). Both the MCP-disconnected (b.9a7) and connected-but-streamless (b.9cj) cases share this one branch and streak: a session between `registerSession` and its stream re-open is legitimately streamless for a moment and must not be poked mid-boot, the same hazard the disconnected case already debounced. restart.ts then hands a `pending` row to the `pending` deferral whatever its connection shows (never a reconnect or relaunch), and reconnects a disconnected `live` row or recovers a streamless one. A `working` row is deferred (`reconnectSession` returns `'transient'`) while a launch for the persona is in flight or its `slack_bot_<key>` tmux session probe fails. With the tmux session alive, the positive-idle rule decides (`checkWorkingRowPane`, b.f2b, below): the stale row is reconnected only once its pane has shown the same idle screen and its transcript has ended with a completed turn, both unchanged, across attempts spanning `STALE_WORKING_WINDOW_MS`; anything else defers. A mid-long-turn session is never poked (b.rmy invariant preserved). The `working` deferrals are bounded: once they have run for `UNPROVEN_IDLE_NOTICE_AFTER_MS` (10 min), the `unproven-idle` notice reports the persona (see [Auto-Restart](#auto-restart)). An `ask_user` or `check_permission` row is never typed into: it is deferred while its tmux session lives, escalated like a `working` row once the session is gone, and swept on each deferral once the deferrals have run for 10 min (b.jdc). A `waiting` row whose pane shows a running turn or a prompt (`checkWaitingRowPane`) is deferred too. A failed status call types nothing. Once the tmux session is gone, the row is swept and escalated instead; the same restart run probes it again and relaunches the persona only when it reads `dead` (b.d61).
  - **Two-tick exception (b.f2b).** While the reconnect adapter holds an idle run for the persona's `working` row that one more attempt can conclude (`HealthCheckDeps.hasPendingWorkingRowEvidence`, production `hasPendingWorkingRowEvidence`), the tick schedules that attempt on the first undeliverable tick, not after two. Each attempt makes one evidence read, so without it the evidence would need twice as many ticks. The freshly-launched false-positive guard isn't needed here: the run exists only for a session already read idle with its row `working`, and any launch for the persona forgets it (`spawnForPersona` calls `forgetWorkingRowEvidence`), so a booting session never has it. A prompt run doesn't count: nothing recovers that persona until someone answers the prompt.
  - **Delay 0 (b.f2b).** When the tick calls `scheduleRestart` for an alive persona and auto-restart is disabled (`HealthCheckDeps.isAutoRestartDisabled`), `scheduleRestart` only logs, so the tick also calls `HealthCheckDeps.notifyNotConnected(key, cause)` (production `notifyDisconnectedWithAutoRestartDisabled`): the `auto-restart-disabled` not-connected notice, worded by `cause` (read once per tick, from the same `isSessionConnected` answer the branch used): *Not connected* for `disconnected`, *Not receiving messages* for `streamless`. A `pending` row connected with its stream gets no notice: neither wording would be true. At most one notice per episode (see [Auto-Restart](#auto-restart)). The dead-session branch raises no such notice.
- **`live`, connected, AND stream present** → healthy; reset the streak and end the persona's not-connected episode (`HealthCheckDeps.endNotConnectedEpisode`, production `forgetNotConnectedEpisode`), so a later episode is reported again.

The capped-persona skip above covers the alive-but-not-deliverable path too: a capped persona gets no tick-driven reconnect, deliberately, so the operator contract carried by the lost-message notice's `restart-limit-reached` state (automatic restarts are suspended; restart the server to recover) is not quietly contradicted.

**Never defer on a `working` row alone.** A row stays `working` after its tmux session is killed mid-turn, until a `findMissing` sweep reconciles it. A defer keyed only on the row repeats every tick, and the persona never recovers (b.d61). Bound a defer by evidence that the turn it waits for can still end: the persona's tmux session (`hasPersonaTmuxSession`), with a failed probe counted as alive and a launch in flight (`isLaunchInFlight`) deferring without a probe.

**Nor on a prompt row alone.** A session that dies under a prompt keeps its `ask_user` or `check_permission` row: agent-director only refreshes a row at SessionEnd and leaves reaping to its sweep (b.jdc). Probe the persona's tmux session before deferring on such a row or reporting it as blocked on a prompt, as the reconnect adapter (`promptRowReconnectVerdict`) and the collision ladder (`launchOnPromptRow`) do: a gone session is swept and relaunched, never reported. A live tmux session can still hold a gone claude process, so the adapter's deferrals are bounded too: from `PROMPT_ROW_SWEEP_AFTER_MS` (10 min) each one sweeps and reads the row again (`checkPromptRowDeferral`). Never type into the row on either path (b.rmy).

**Nor on a live tmux session alone.** agent-director can leave a row `working` after the turn ended, with the session idle at its prompt, and nothing moves it back (b.f2b). Deferring on the row and a live tmux session strands such a persona for good. Bound the defer by positive evidence that the session is idle, and never by the pane alone (`classifyWorkingPane` and `foldWorkingPaneRun` in `src/session-manager.ts`, `src/session-transcript.ts`):

- **Idle needs the pane and the transcript.** Claude Code 2.1.280 can draw a live turn with no spinner: an API retry or stall holds static rows with no glyph and no timer, so a still screen proves nothing. `foldWorkingPaneRun` counts a read as idle evidence only when the pane classifies `idle` AND the session's transcript, read with it, ends with a completed turn. The row is stale only once every read across `STALE_WORKING_WINDOW_MS` (60 s) saw the same screen and the same transcript snapshot (path, device, inode, size and mtime, `sameTranscriptSnapshot`). A busy, blank or unreadable pane, a changed screen or transcript, or a transcript that is open, can't be located or can't be read ends the run: no evidence. Never shorten the window, reconnect on a single read, or drop the transcript requirement.
- **"Ended" means the last conversation entry is a completed turn** (`transcriptTailTurnState`). Scanning back from the end, entries that are not part of a turn are skipped: every type other than `user`, `assistant` and `queue-operation`, and a completed local command's three `user` lines (the `isMeta` `<local-command-caveat>`, the `<command-name>` line and its `<local-command-stdout>`/`<local-command-stderr>` line), so the `/mcp reconnect` CSCB types after a turn doesn't hide the turn's end. The first other entry decides: `ended` for an `assistant` entry whose stop reason is `end_turn`, `stop_sequence` or `refusal` and which holds no `tool_use` block, and for an interrupt marker, a `user` entry whose only content block is the text `[Request interrupted by user]` or `[Request interrupted by user for tool use]`: the user ended the turn, Claude Code fires no Stop for it, and the row stays `working`. Any other `user` entry (a prompt, a tool result, even one beside the interrupt text, Stop-hook feedback), a `queue-operation`, a sidechain entry, a line that isn't a JSON object and a last line with no newline yet are `open`. So is an `attachment` recording a Stop hook that keeps the turn going (`hook_additional_context` or `hook_blocking_error` with `hookEvent` `Stop`) after the last `assistant` entry: Claude Code writes nothing else for it (b.rmy). Other attachments, a SessionStart hook's context after a resumed session's last reply included, are skipped. A live turn, an API retry included, never ends that way.
- **Locate the transcript from the row, and read only its tail.** `locateTranscript` takes the row's (`get`) `jsonl_path` when its file name is `<claude_session_id>.jsonl`, else composes `<claude_config_dir>/projects/<cwd slug>/<claude_session_id>.jsonl` with `resolveJsonlPath` (`src/cozempic.ts`) from the row's `cwd` and the persona's effective `claude_config_dir`, so a path left from an earlier session is never read. agent-director records `jsonl_path` only at SessionStart, and only when the file exists, so a fresh session's row has none. `readTranscriptTurnState` opens the file read-only and non-blocking, `fstat`s it, reads only a regular file and only its last `TRANSCRIPT_TAIL_BYTES` (256 KiB), and never throws; a tail that doesn't start at byte 0 drops its first, possibly cut, line. Anything it can't locate, open or parse is `unreadable`, with a fixed, token-free reason for the log line.
- **Read the evidence at a bounded cadence.** The launch wait reads it every `WORKING_ROW_READ_INTERVAL_MS` (5 s), not on each status poll: every agent-director call goes through one queue shared by every persona. The restart path makes one read per attempt. Either path reads the transcript (an agent-director `get` and a file read) only when the pane shows an idle screen.
- **Never type into a prompt or dialog.** `/mcp reconnect` and Enter could confirm the dialog's default. A pane that shows one, and an `ask_user` or `check_permission` row whose tmux session lives, is deferred and reported through the `blocked-on-prompt` notice, never typed into. Probe before you report: a prompt row whose session is gone gets no notice (b.jdc). A prompt outranks a busy sign in `classifyWorkingPane`, since a dialog can sit under a running turn's spinner. Anchor dialog detection to Claude Code's layout, never to wording alone (`paneShowsDialog`): in the pane's bottom 12 lines, a numbered option list (an option `1.` and, below it, an option `2.`) with the `❯` cursor on one of its options, plus a question line ending in `?` above it, a dialog option or footer (`DIALOG_NEEDLES`) on or below it, or its options drawn inside the dialog's box (`│`). An idle reply that quotes a dialog's wording must not read as a prompt, or its stale row would be held forever.
- **Check a `waiting` row's pane before typing.** The reconnect adapter reads it once (`checkWaitingRowPane`): a running turn or a prompt defers, and a prompt raises the `blocked-on-prompt` notice. A failed read doesn't defer: the `waiting` row is agent-director's own idle signal.
- **Never type blind.** When the reconnect adapter's status call throws, nothing is known about the session, which may be mid-turn: log it, forget the persona's idle evidence and return `'transient'`. During an agent-director outage the liveness probe reads the persona `unknown` too, so nothing kills or relaunches it; it is retried on its timer (C12, below).
- **Match the spinner line only in its own shape.** On Linux, Claude Code 2.1.280 draws `●` (U+25CF), the spinner's glyph with prefersReducedMotion, at column 0 before every reply and tool call (macOS draws `⏺`), and those lines can hold an ellipsis. A pattern that reads any `●` line with an ellipsis as busy holds an idle persona back for good, a `waiting` row included. `BUSY_SPINNER_LINE_RE` takes the spinner's shape: at column 0 a glyph (`·` `✢` `✳` `✶` `✻` `✽`, or `*`), a space, a message of at most 80 characters with no ellipsis, then an ellipsis ending the line or followed by ` (` and the status. The message can be several words: a custom verb from the `spinnerVerbs` setting (an emoji and three words on a live pane) or a task's `activeForm`. A `●` line counts only as a single word and an ellipsis ending the line, or with a status that starts with an elapsed time (`12s`, `2m 42s`), a token arrow (`↓`, `↑`) or `thinking`/`thought for`. Test a new pattern against real `●` reply and tool lines with ellipses (`LINUX_IDLE_PANE`), not only against spinner lines.
- **Keep the busy and dialog patterns verified.** `BUSY_SPINNER_LINE_RE` (above), `BUSY_PANE_NEEDLES`, `BUSY_API_RETRY_ROWS`, `DIALOG_OPTION_LINE_RE` and `DIALOG_NEEDLES` match Claude Code's own screen text (verified against 2.1.280). Anchor each API retry row on Claude Code's `·` separator or fixed wording, so a reply that mentions a retry doesn't read busy. When a Claude Code release changes that text, update them and their tests in the same change. A busy screen the patterns miss is still held back by the transcript rule; a static dialog they miss reads idle, and only its open transcript keeps it from being typed into.
- **Keep one evidence store per path.** The launch wait keeps its run for the wait (`WorkingPaneWatch`); the restart path keeps one run per persona across attempts (`workingRowPaneRuns`). That run is forgotten when it ends or concludes, when an attempt reads another state or its status call fails, when a launch for the persona starts, and with the not-connected episode (`forgetNotConnectedEpisode`).
- **Bound every deferral on a `working` row.** Both paths share one run of deferrals per persona (`workingRowDeferredSince`): each hold-back that types nothing calls `noteWorkingRowDeferral`, and once the run has lasted `UNPROVEN_IDLE_NOTICE_AFTER_MS` (10 min) from its first deferral the `unproven-idle` notice is raised, at any delay, through the shared latch (see [Auto-Restart](#auto-restart)). The positive-idle rule can't prove every idle session idle, and the notice is what keeps such a persona from being held back from silently.

**Act on a reconciliation in the run that ran it.** After a sweep reconciles a row, probe it again in the same restart run and act on the answer, as `reprobeDeadAfterEscalate` does: relaunch only on `dead`; `live`, `pending` and `unknown` return with no relaunch, and `unknown` calls the arm hook. Leaving it to the next tick adds a full `health_check_interval` plus another backoff delay (b.d61). Ask the shutdown and not-up checks again after that probe, as after any await.

**A liveness `status` error is `unknown`, never dead (C12, b.jg5 SRJ-314).** Only `dead` (`ended`, `missing`, `ErrSpawnNotFound`, `ErrSystemInstallDisappeared`) leads to a kill and a launch. Every other `status` error, a state CSCB does not know and a probe that throws read `unknown`: the restart work returns with nothing reconnected, killed, launched or counted and calls the arm hook, and the tick skips the persona. Why: agent-director failing to report on a persona is no proof its session is gone, and killing a live, possibly mid-turn session on that guess loses work. Decide each error by name through `src/ad-error-class.ts` (`hasAdErrorName`, `classifyAdError`), never with a new `instanceof` ladder. The `dead` list is closed: a new error name or row state reads `unknown`.

**A refused send-keys on a row just read live is a dead session, not a failure.** A row's state can change between the read and the keystrokes: a findMissing sweep (the launch wait starts with one, b.m4r, and it covers every persona's row) can mark it `missing` in between. agent-director then refuses the keystrokes with `ErrSpawnNotInteractive`, which `reconnectMcp` answers with `'dead-session'`, no spawn-failure notice, so the caller recovers the persona: the ladder through `resumeOrFreshSpawn`, the reconnect adapter through `'escalate-dead'` and the re-probe (b.dup). Never pass `reconnectMcp` a row read `pending`: agent-director refuses that too, and it is not dead. Defer it through `deferPendingRow`: the restart work does so as soon as its liveness probe reads `pending`, before it looks at the connection, and the reconnect adapter does when its own read finds `pending`.

## Reload Detection Tick

The reload controller in `src/reload.ts` checks every 5 s whether `config.json`, or a credentials file it references, differs from what is applied, and keeps `config.json.pending` in step (b.av2 SR-8.2, SR-8.3). Its driver is `createReloadTickDriver` in `src/reload-timer.ts`.

- **Use a serialized, self-re-arming timer for new periodic work**, as `src/cron-scheduler.ts` and `src/reload-timer.ts` do: arm the next pass only after the previous one settles, so passes never overlap and one timer is pending between them. Never `setInterval` (the health check's loop above predates this rule; don't copy it) and never a file watcher: a single-file watch drops the atomic-save rename editors use, and a pass can only act at a tick anyway.
- **Start it after the start's bring-up pass returns, stop it at shutdown.** `startDetection()` is the last statement of `main()`, after `startHealthCheck`; `stopDetection()` runs in `shutdown()` after `stopHealthCheck()`. `start` itself runs no pass. Why: the tick compares credentials with the digests the bring-up pass records; before that there is nothing to compare with, and a change would go unnoticed. A start launch the pass parked on a `working` row (b.f2b) may still be in flight when the tick starts; that keeps SR-8.2's intent, since every persona's bring-up has read its credentials by then, and a teardown of that persona cancels the launch's wait and then waits for it to settle (`whenLaunchSettled`). Don't make the pass wait for parked launches.
- **Detection notices and reports, nothing else.** Detecting a change writes or removes `config.json.pending` and logs; it applies nothing, makes no lifecycle call and posts nothing to Slack. The only thing a pass applies is a confirmation (`config.json.apply`) whose fingerprint matches the candidate as it stands (b.av2 SR-8.5). Log the preview only when the pending state changes, not on every pass, and each write or remove failure once per episode. An episode ends at the next success or when the derived state changes (to nothing pending or to another pending fingerprint), so a failure that repeats within one state is logged once and each new state logs its first failure.
- **Read files only through the stat-first readers**: the config file through `readPersonaConfigBytes`, each referenced credentials file (deduplicated, none in dry run) through `readCredentialsFile`. See Configuration and Security.
- **Classify and render a change only in `src/reload-plan.ts`.** `buildChangePlan` is the one place a candidate is diffed against the applied config and each field's SR-8.6 effect (destructive, in place, next launch, server-wide at the next start) is decided; the preview, its log lines and the header counts are rendered from that plan. The apply must call `buildChangePlan` and `changePlanCounts` too; never diff the configs a second time. The apply takes each step's personas from the plan the pass built from the confirmed bytes (`applyStepInputs` in `src/reload-apply.ts`); a new apply behaviour reads its inputs from there, not from its own comparison of the old and new config. Why: the apply must do exactly what the preview said.
- **Put apply behaviour in its numbered pipeline step.** A confirmed change is applied in six steps (`src/reload-apply.ts`): 1 the record rewrite and the applied-set swap (done by the controller in `src/reload.ts`), 2 teardowns, 3 in-place updates, 4 credentials reconnects, 5 the template refresh, 6 bring-ups. Each step completes for every persona before the next starts. New apply work is a per-persona lifecycle member (`ReloadLifecycleOps` in `src/reload.ts`): implement it in `src/persona-lifecycle.ts`, bind it in `server.ts`'s `lifecycle`, and extend `lifecycleApplySlots` (`src/reload-apply.ts`) so its step's default body fans it out over the input classes it acts on (`ApplyStepInputs`; every step is bound: step 2 handles `removed` and `destructiveOld`, step 3 `inPlace`, step 4 `credentials` and `credentialsBroken` for personas not credentials-broken when it runs, step 5 calls `refreshTemplate` once, and step 6 `added` and `destructiveNew` plus a recovery bring-up of every credentials-changed persona step 4 did not reconnect). Make the member required in the type once it is bound. The controller's `applySteps` is a test override that replaces every default body; production never sets it, so don't bind production work there. `applyStepsFor` decides which steps run; never apply anything ad hoc outside a step. A failing step is logged and the later steps still run, so a step body reports its own per-persona failures and never relies on a later step being skipped. Keep `src/reload-apply.ts` pure: bodies do the I/O, it only orders and awaits them.
- **A destructive modify is the teardown, then a fresh bring-up** (b.av2 SR-8.6). A `credentials_file` path or `working_directory` change runs the persona teardown in step 2 over the old declaration (`destructiveOld`) and the apply bring-up in step 6 over the new one (`destructiveNew`). Never give it a bespoke path: a fix to either half serves removals, additions and destructive modifies alike. Its key stays applied through step 1, so the applied-set guard does not stop work queued for it; the teardown therefore cancels the persona's bring-up and restart timer when it is submitted, before its serializer turn, and drops notices held during it after its agent-director calls. Every teardown, a removal's included, also cancels its launch's wait for a `working` row at submit (b.f2b). Keep the per-apply step-4 to step-6 handoff intact when you touch `lifecycleApplySlots`. A row a failed delete leaves is met by the step-6 launch through the collision ladder, which may resume it when only the `credentials_file` path changed (an accepted limit).
- **Next-launch settings need no lifecycle call** (b.av2 SR-8.6, SR-6.2, SR-9.4). `claude_config_dir` and `stop_hook_bootstrap`, own or inherited, are in no step's input: step 1's swap is all they need. Every launch path reads them from the applied set when it runs (the spawn environment, the `config_dir` label, the trust patch, the reply-guard record and hook install, the transcript check). Never restart, re-patch or rewrite a record for a running instance because of them, and never copy them at start into a closure a later launch uses. A new next-launch consumer reads the applied persona at launch.
- **Server-wide values come from `configInEffect`** (`src/reload.ts`). After an apply, `server.ts`'s `personaConfig` is `configInEffect(startTime, applied)`: the confirmed personas over every server-wide setting the server started with. A consumer of a server-wide setting reads that holder, never the reload controller's applied config or the record, so a confirmed value takes effect only at the next start. The two inheritable defaults act only through the personas, which the loader already resolved. `stop_timeout` and `exit_timeout` are the CLI's and come from the record (see Configuration).
- **The apply-time template refresh (step 5) stays non-fatal and memory-read-only.** `refreshSlackChannelBotTemplate` (`src/agent-director-template.ts`) rewrites only the `allow` rules, derived from the applied personas, over the params the boot install wrote (`installSlackChannelBotTemplate`'s `params`, captured once at start); never rebuild `claude_args` or any other server-wide argument from the applied config. A rejection logs one line (an untyped throw only through `describeThrownValue`), records no startup error, exits nothing, is not retried and never stops step 6. It belongs to no persona, so it doesn't go through the serializer. `applyStepsFor` selects it from the plan's lexical `configDirsChanged` only.
- **Run every lifecycle operation for a persona through the shared serializer** (b.av2 SR-6.6). A new operation that launches, kills, tears down, updates in place, reconnects or retries a persona is submitted with `personaLifecycle.run(key, …)`, the one `createPersonaSerializer` instance in `server.ts`, injected as `serialize`; never build a second serializer or add a lock of your own. Put the operation's checks (applied set, up state, cancelled) inside it, so they see the state when it starts, not when it was queued. Re-entrancy rule: code running inside an operation for a key must never await `run` or `whenIdle` for the same key, since it would wait for itself forever; call the next body directly (as the bring-up controller's directory re-check calls its launch). Submitting for the same key without awaiting, or awaiting another key's operation, is fine. A launch that runs outside the serializer (the start pass, including a launch it parked in the background, b.f2b) is waited for with `whenLaunchSettled(key)` before a teardown kills anything. A wait inside a launch that can last minutes must be cancellable by the teardown, as `waitForWaitingAndReconnect` is (b.f2b): the teardown calls `cancelWorkingRowWait` (injected as `cancelLaunchWait`) when it is submitted and again right before `whenLaunchSettled`, and the wait checks the flag after every agent-director call, wakes from its poll sleep at once, types nothing and returns `cancelled`. Otherwise the teardown, and the apply that runs it, would wait up to 10 minutes (SR-8.6).
- **Read a persona's routing settings at each use** (b.av2 SR-8.6). A consumer of `channels`, `delivery`, `permission_prompts` or `dm.*` reads the persona's entry from the applied set (`personaConfig` in `server.ts`, injected as a getter such as `getPersona(key)`) each time it acts, never a copy captured at start or held in a closure. Step 1 of a confirmed apply swaps that entry, and the in-place update (step 3) pushes no values anywhere. Across an await, re-read the entry before acting on it, and skip the item when the persona is gone; the permission poller's `reResolve()` after the agent-director `get` is the pattern. Never store these fields with a held or queued item; store the key and resolve at the attempt, as the destination hold does. An item already posted stays where it was posted. Why: a copy keeps posting to, or routing by, a destination the operator removed.
- **Invalidate caches derived from routing settings in the in-place update.** A new cache derived from those fields is forgotten per key by `PersonaLifecycle.updateInPlace` (`src/persona-lifecycle.ts`) when a field it depends on changed, as the DM-conversation cache is (`personaDestinations.forget` when `permission_prompts`, `dm.enabled` or `dm.contact` changed), and by the teardown too.
- **Clear every per-persona state in the persona teardown** (b.av2 SR-6.5). The teardown in `src/persona-lifecycle.ts` is the one path that forgets a removed persona. A module that keeps anything keyed by persona exports a silent per-key forget; the teardown calls it through an injected dependency (`PersonaLifecycleDeps`), and a test shows it drops only that key. Why: a key added again must start clean.
- **Bring a persona up at apply only through the shared procedure** (b.av2 SR-6.1). Call the bring-up controller's `bringUp`, then `spawnForPersona`. Never add an apply-only credentials, directory or Slack check. The only apply-specific steps are `runPersonaStorageCheck` and the shutdown skip.
- **Every launch, restart or retry path does nothing for a key outside the applied set** (b.av2 SR-8.6). From step 1 on, a removed persona may still have a serving connection, a pending restart timer or a bring-up retry. Route every such path through the relaunch gate or `createPersonaUpPredicate` (both use `isPersonaUpGiven` in `src/persona-start.ts`, which asks `isApplied`), and read the applied set live (the bring-up controller's `appliedPersonas` getter, `isApplied(key)`), never from a copy taken at start. Don't add a launch path that bypasses the gate or checks the up state some other way. `preLaunchReplyGuard` is already a no-op for such a key.
- **Warn in the preview about what would stop a persona coming up, with the check its bring-up runs.** An added persona's causes and a changed `claude_config_dir`'s problem (own, inherited or alongside a destructive modify) come from the same checks as the bring-up and launch (`checkPersonaWorkingDirectory`, the credentials read, the injected `checkConfigDir`), asked only for the personas the change affects, and are worded as those checks word them. They are warnings on the persona's (or setting's) line, never a refusal: the plan stays valid and a confirmation applies it.
- **Keep the plan and the renderers pure and deterministic.** Gather every I/O fact in the tick (real paths, digests, the bring-up state, the added personas' local checks, a changed `claude_config_dir`'s check) and pass it in as `ChangePlanFacts`; the same inputs always give the same plan and the same text. When a fact can't be gathered, pass `FACT_UNKNOWN` so the preview says it could not be checked; never substitute a default answer.
- **Derive a persona set's config directories only through `effectiveClaudeConfigDirs`** (`src/persona-identity.ts`). The template's memory-read rules and the plan's `configDirsChanged` both use it, so the apply refreshes the template exactly when its rules would change.
- **Let the plan alone decide a credentials change.** A credentials change is pending exactly when the plan lists one; don't compare digests anywhere else in the tick.
- **A new config field needs a reload effect.** Add it to the right class in `src/reload-plan.ts` (`DESTRUCTIVE_SETTINGS`, `IN_PLACE_SETTINGS`, `NEXT_LAUNCH_SETTINGS`, or a server-wide key through `PERSONA_TOP_LEVEL_KEYS`), with a preview test. A persona field left out of every class is never reported as changed. A server-wide path key must also be in `SERVER_PATH_SETTINGS` (`src/config.ts`), or the plan compares it by string and reports a respelled path as changed.
- **Tests drive it through the injected tick driver** (`ReloadControllerDeps.tickDriver`; the reload harness in `tests/test-helpers/reload-harness.ts` has a manual one), and the driver itself through an injected clock; no real timer runs in a test.

## Avoiding Duplicated Effort with agent-director

agent-director owns spawn liveness, process management, and resume semantics. Before building CSCB-side logic that reimplements or works around any of those, figure out which case you're in:

- **agent-director already does it.** Use its verb (or its typed errors — see `src/agent-director-errors.ts`) instead of building a parallel implementation. Accidental duplication drifts out of sync with agent-director's actual behavior and doubles the maintenance surface.
- **Genuine capability gap on agent-director's side.** Build the *minimal* workaround CSCB needs, and flag it for removal: note the agent-director plan (or file one) that closes the gap, and reference it in the code comment so the workaround dies when the fix lands.

The precedent to follow is the b.4dk/b.m4r/b.93m/b.ecw chain, which shows how to split responsibilities cleanly rather than fork them. agent-director's `find-missing` had a degraded-mode guard that refused to answer liveness *reconciliation* queries right after a reboot. Once agent-director's own fix landed (plan b.93m: per-row, evidence-based `find-missing`, guard removed, shipped in ≥ 0.8.0), CSCB handed the reconcile responsibility back to agent-director: the dead-session recovery path in `src/session-manager.ts` (`resumeOrFreshSpawn`'s `reconcileMissingFirst` branch) calls `client.findMissing({})` before resume — no parallel *reconciliation* implementation on the CSCB side. Note the boundary here, and how it shrank once the gap fully closed. The `working`-branch `dead-session` verdict — the one from `waitForWaitingAndReconnect` — now keys on the *claude process* via AD's `findMissing` + `status`, not on a raw tmux probe: b.ecw retired the `_hasTmuxSession` probe from the two terminal branches of `waitForWaitingAndReconnect` (ended/missing returns `'dead-session'` directly; timeout runs a fresh `findMissing` sweep + `status`). (The other `dead-session` trigger that also falls through to `reconcileMissingFirst` — the `waiting`-branch `reconnectMcp` — still keys on the tmux session: its verdict comes from a double `ErrTmuxSendKeys` failure (`src/session-manager.ts`), untouched by b.ecw.) CSCB still keeps the narrow `tmux has-session` probe (`_hasTmuxSession`, `src/session-manager.ts`), but its remaining role is narrow and structural — the cases AD *cannot* answer: the poll-loop `ErrSpawnNotFound` branch (no AD row exists to reconcile or consult), the timeout branch's AD-outage fallback (so a `status` error can't manufacture a false `'dead-session'`, the b.rmy invariant), and the restart reconnect adapter's `working` defer (b.d61, through `hasPersonaTmuxSession`), where AD's row stays `working` until a sweep runs, and likewise its `ask_user`/`check_permission` defer and the collision ladder's prompt-row branch (b.jdc), where AD's row keeps its prompt state after SessionEnd. Those probes only decide whether to keep deferring; a gone session triggers AD's `findMissing` sweep, and the relaunch waits on AD's reconciled row, not on the probe. Only the *reconcile* (which spawns are actually missing) moved to `client.findMissing({})` first; then, once b.93m Part E made per-row verdicts evidence-based, the liveness *verdict* itself handed back too — the probe stayed only where AD structurally has nothing to say. Do the same when you own a workaround: give it a cited exit path, and when agent-director closes the gap hand back exactly the responsibility it now covers — not more, not less — rather than keeping a permanent fork.

## Raw tmux Calls

The server still calls tmux itself in four places, until the b.fmk version moves them to agent-director: the b.vub self-heal kill (`kill-session`), the dialog approver's pane read and Enter for an `ended` or `missing` row (`capture-pane`, `send-keys`), the liveness probe (`has-session`) and the reconnect's `start-server`.

- **Start tmux only through the runner** (`_runTmux` in `src/session-manager.ts`); never spawn `tmux` anywhere else. A source audit in `tests/session-manager.test.ts` fails on a second site. Why: the exact-target rule has one home, and one seam (`_setTmuxCommandRunner`) keeps every unit test off a real tmux server.
- **Address a session exactly.** Build every target with `tmuxExactSessionTarget` (`=<name>`, for `has-session` and `kill-session`) or `tmuxExactPaneTarget` (`=<name>:`, for `capture-pane` and `send-keys`); never pass a bare name. Why: tmux resolves a bare name by prefix when no session has that exact name, and persona keys can prefix one another (`dev`, `dev_2`), so a bare `slack_bot_dev` kills or types into `slack_bot_dev_2` once `slack_bot_dev` is gone (b.1ix). tmux 3.2a refuses `=<name>` as a pane target, so a pane needs the trailing `:`.
- **Give an operator the exact target too.** A tmux command in a notice, log line, skill or the README names the session `=slack_bot_<key>`: `tmux attach -t =slack_bot_<key>`, `tmux has-session -t =slack_bot_<key>`. The not-connected notices build it with `tmuxExactSessionTarget`. Why: a bare name attaches to, or reports as present, the prefix neighbour. tmux 3.2a resolves `attach -t =<name>` to that exact session and refuses it when only a neighbour exists.
- **Known gap: agent-director's own tmux calls still prefix-match.** agent-director 0.10.0's `read-pane`, `send-keys` and `kill`, and the `has-session` inside `resume`, pass a bare session name. So with keys where one prefixes another (`dev`, `dev_2`), a persona whose session is gone can still be misread (its pane read is the neighbour's), typed into or ended through agent-director, whatever the server's own calls do. Until the b.fmk version, claim exactness only for the server's own tmux calls, never for "a bot's recovery" as a whole. The configuration check (`checkPrefixRelatedKeys` in `src/config.ts`) rejects any two personas where one key starts with the other, so the case can't be configured.
- **Test a new raw call with a prefix neighbour**: a unit test through the runner seam with `slack_bot_dev_2` present and `slack_bot_dev` absent and present, and a case in the `/ci` scenario `tests/integration/test-11-exact-tmux-targets.sh`, which runs against real tmux. Try tmux behaviour only in a throwaway container, never on a host's tmux server.

## The Start Sweep

`reconcileOrphans` (`src/session-manager.ts`) runs once at every start, before any launch (see docs/architecture.md, Server-Managed Startup step 4).

- **Never delete a pre-persona row.** A row with no `persona` label is kept: it is killed only when its state is live, with one kill call per start, the kill's result is logged, and it is never deleted (`keepPrePersonaRow`, b.1ix). Why: agent-director 0.10.0's `kill` can report success while the session lives on, and a deleted row leaves that session running with nothing to find it by; at the upgrade to personas that is every bot at once. Its ID (`cscb_<name>_<channel>`) is never a persona's, so keeping the row costs nothing.
- **Reconcile after a kill.** agent-director 0.10.0's `kill` leaves the row's state as it was, so a killed row still reads live until a findMissing sweep runs; a check keyed on that state acts on it again. After the start sweep's pre-persona kills, one findMissing sweep runs (`reconcileKilledPrePersonaRows`, through the shared memoized core `sharedFindMissingSweep`), so a killed row whose session is gone reads `missing` and the next start doesn't kill it again. Don't describe such a kill as happening once: a row whose session survives it is killed again at every start. Add the same sweep after any new kill whose row a later check reads.
- **Don't add a delete.** The sweep still kills and deletes a row naming an absent persona (agent-director 0.10.0 has no reuse, and a persona added again must start fresh), a wrong instance ID and a wrong `cwd`, even after a failed kill, until the b.fmk version removes those deletes. Don't add another delete to the sweep, and don't delete after a failed kill on any new path.

## Persona Session Environment

A persona's Claude gets its environment only from `personaSpawnEnv` (`src/persona-identity.ts`). `buildSpawnParams` passes it as `extra_env` on every spawn; agent-director's resume takes only the instance ID and restores the env stored with the row at its spawn.

- **Keep prompt suggestions off.** Every persona env ends with `PROMPT_SUGGESTION_OFF_ENV` (`CLAUDE_CODE_ENABLE_PROMPT_SUGGESTION=false`). Why: Claude Code's end-of-turn suggestion fork runs the session's PreToolUse hooks and is denied, and agent-director flips the idle persona to `working` (b.svb). The stale-`working` recovery (b.f2b) stays; this only makes it rarer. Don't make it configurable or let another entry replace it.
- **Add a variable only there.** Give it a fixed name outside agent-director's reserved `AGENT_DIRECTOR_` prefix, and never put a secret in it: the spawn env is on agent-director's command line and stored in its database.

## Async Patterns

- Use `async/await` throughout — no raw Promises except where explicitly holding connections open (e.g., SSE keep-alive streams)
- SSE keep-alive pattern: hold the response open with a `Promise` that resolves on `req.signal` abort; stream events by writing to `res` directly; clean up on abort via `req.signal.addEventListener('abort', ...)`
- Always clean up on abort: `req.signal.addEventListener('abort', ...)` for held HTTP connections
- Use `settled` flag pattern to prevent double-resolution in race conditions
- Bound any Slack `start()` or call that may never settle with a timer on the injected clock (as `src/persona-connections.ts` does). On expiry, abandon it, and disconnect or catch whatever it settles to later
- Per-persona work keeps its state in that persona's own entry: no lock, queue, promise chain or timer is shared between personas

## Review Prioritization

Not all issues are equal. When writing or reviewing code, focus in this order:

1. **Security vulnerabilities** — fix immediately
2. **Logic errors** — fix immediately
3. **Missing tests** — add before merging
4. **Architecture problems** — address in current work if feasible
5. **Code quality** — address if touched, don't go hunting
6. **Style nits** — let the linter handle it

## Definition of Done — closing a bee

Before any bee closes, a change to shipped text (README, any file under `skills/`, `slack-app-manifest.yml`, `MCP_INSTRUCTIONS` in `src/registry.ts`) keeps `tests/shipped-docs.test.ts` and `tests/access-file-retired.test.ts` green. Shipped text describes personas only: no pre-persona configuration shape, token environment variable or access-control file, except the debugging skill's pre-persona rejection entry (b.av2 SR-12, SR-13.5). Don't widen the audit's exceptions to make a change pass.

A bee may be set `finished` only when one of the following holds, and the chosen justification is stated plainly in its closure note:

- **On main.** Its commits are reachable from `main` — name the commit SHAs in the note.
- **Resolved outside the repo.** The fix is ops-only or lives in another file/host, so no commit on `main` can ever land it. Carry the explicit heading `## +closed:out-of-repo <path>` in the closure note, naming the artifact that was changed — e.g. `## +closed:out-of-repo ~/startup/start-all.sh`. The operand is required (a bare `## +closed:out-of-repo` does not qualify) and is never checked on disk: the marker is a signed statement by the closer, auditable by reading the ticket, not a filesystem probe that would give different verdicts on different machines. Prose alone does not qualify — describing a `~/` path near fix language used to pass the audit and let a ticket that said the out-of-repo change was *declined* read as closed.
- **Documents-only, outside any git repo.** The ticket's product is markdown/docs whose files live outside any git repository (e.g. Apiary ticket markdown under the non-repo project root), so no commit on `main` can ever land it. Carry the explicit heading `## +closed:docs-only` in the closure note — a deliberate, greppable marker, not loose prose. Phrases like "documents only" in body text do not qualify; only the heading does.
- **Closed without a code change.** It is explicitly no-repro, won't-fix, not-a-bug, superseded, abandoned, or satisfied by other work — say which, and point at where the real work lives (or why none is needed). A bare, reasonless `## Closed` heading does **not** count — a closure needs a stated reason.

The audit recognizes these closure phrasings (case-insensitive, matched as whole words anywhere in the body):

| Verdict | Accepted phrasings |
| --- | --- |
| Could not be observed | `no-repro`, `no repro`, `not reproducible`, `cannot reproduce` |
| Observed, fix declined | `won't fix`, `won't-fix`, `wont fix`, `wont-fix` (straight `'` or typographic `’`, any case) |
| Observed, behavior is correct | `not a bug`, `not-a-bug`, `by design`, `works as intended` |
| Covered elsewhere | `closed as superseded`, `closed as abandoned`, `superseded by`, `fully satisfied by`, `already satisfied` |

Pick the verdict that is true. The first three rows are distinct claims — no-repro means the behavior could not be observed, won't-fix means it was observed and a fix was declined, not-a-bug/by-design/works-as-intended mean it was observed and is correct — and the audit accepts all of them, so a closure note never has to misstate what was decided to satisfy the gate.

**"Pending merge/release" is NOT a valid finished state.** A fix that only exists on an unmerged branch is stranded, not done — `main` still carries the bug. Those exact words were in b.qps's closure note while its fix sat on an unmerged branch for months and the root cause stayed live on `main`; the fix was nearly re-implemented from scratch before the stranded branch was noticed. If work is on a branch and not yet on `main`, the bee stays open.

`scripts/audit-finished-tickets.sh` enforces this. It is read-only: for every `finished` bee in the Bugs hive, the Plans hive (`Ideas/Plans/`), and the Ideas hive's top-level bees (`Ideas/<id>/`, excluding the `Plans/` subdirectory so nothing is double-reported) it flags tickets whose work is neither reachable from `main` nor covered by a recognized closure marker, branches referencing finished tickets whose heads are not ancestors of `main`, and any unmerged branch that references no known ticket at all. Recognized closure markers are: the explicit `## +closed:out-of-repo <path>` heading naming the artifact changed outside this repo, an explicit reasoned closure note drawn from the closure vocabulary table above (each matched only as a word-bounded phrase, so a bare `## Closed` heading with no stated reason does not qualify), and the explicit `## +closed:docs-only` heading for documents-only work outside any git repo. Both `+closed:` headings are deliberate, greppable tokens that cannot be produced by accident; the closure vocabulary is prose-level by design, so it will also match the phrase used incidentally in body text — the anti-marker check and the main-commit requirement, not the vocabulary, are what guard a wrongly-finished ticket. A closure note that says "pending merge/release" or "fixed on branch X" is treated as an anti-marker and forces a flag — disqualifying every closure marker above. It exits non-zero when stranded work exists and runs at release preflight as gate SR-2.6 (see below), so a release cannot ship while finished work is silently stranded. Idea-hive top-level bees are held to the same standard as bugs and plans: an idea can legitimately be `finished` by being absorbed into an Epic/plan that landed, but that must be stated explicitly with the same closure vocabulary (a "fully satisfied by \<plan\>" / "superseded by \<id\>" note pointing at where the work went), not left implicit.

## Releasing CSCB

Releases are cut with the `/publish` skill from a Claude Code session whose CWD is any checkout of the `claude-slack-channel-bots` repo on `main`. The skill is **invocation-location-neutral** for its npm-publishing steps — those run identically from the primary checkout of the main clone, from any feature worktree (so long as that worktree's HEAD is `main` and in sync with `origin/main`), or from a throwaway `git clone` under `/tmp` or anywhere else. The one exception is the SR-2.6 stranded-work audit: it needs the hives locatable one level above the repo checkout (`<project>/Bugs`, `<project>/Ideas/Plans`, `<project>/Ideas`, `<project>/<repo-checkout>/`). A throwaway `/tmp` clone with no hives beside it cannot run the audit — it fails the setup-failure diagnostic (SR-2.6 exit 17, see below) rather than passing. Run `/publish` from the canonical checkout that sits beside the hives.

> **SR-2.6 is green today.** The stranded-work audit exits zero with no findings in either class — no stranded finished tickets, no stranded branches. There is no known expected debt, so a non-zero SR-2.6 now means genuinely new stranded work: fix it, do not wave past it. Resolving a stranded branch is push-class (publish an `archive/<name>` tag **first**, then delete the remote ref, then `git fetch --prune`) and is reserved for the repo owner. Do not re-list findings here — the audit's own output is the inventory, and the tracking ticket for a given finding is the source of truth for expected vs new.

### Release notes

Release notes live in `CHANGELOG.md` at the repo root, under an "Unreleased" heading until the release is cut. Record a user-visible or breaking change there in the change that makes it; an upgrade step that the README must not carry (such as removing a leftover retired file) goes only there. `CHANGELOG.md` is not in `package.json`'s `files`, so it is not in the npm tarball, and `/publish` does not read or edit it: the release commit and tag stay `Release v<version>` (see `docs/registry-install-runbook.md`).

### Preconditions

Before invoking `/publish`, confirm:

- Working tree is clean and HEAD is `main`, exactly equal to `origin/main` (run `git fetch origin && git status` and `git log origin/main..HEAD` to verify).
- `bun install --frozen-lockfile`, `bun test`, and `bun run typecheck` all pass locally.
- Docker daemon is running (required by the `/ci` gate).
- `ANTHROPIC_API_KEY` is exported in the environment (required by `/ci`). A raw `sk-ant-api…` key suffices; a gateway credential (e.g. NVIDIA InferenceHub) also requires `ANTHROPIC_BASE_URL` and `ANTHROPIC_MODEL` to be exported so the bot Claudes spawned inside the test container hit the gateway rather than `api.anthropic.com`. `/ci` forwards all three into the container when set.
- `npm whoami` returns a `claude-slack-channel-bots` maintainer account (`npm login` if not).

If any precondition fails, `/publish` will abort at the corresponding preflight gate with an `SR-2.x` diagnostic — you do not need to pre-check by hand, but knowing the list helps diagnose a failure quickly.

### Invocation

```
/publish <patch|minor|major>
```

The bump kind is **required** — there is no default. The skill exits with `SR-1.2 (argument)` if the argument is missing or not one of the three keywords.

### Phases of execution

`/publish` runs four phases in order. Each phase has a well-defined abort behavior:

1. **Phase 1 — Local preflight (SR-2.1–SR-2.6).** Clean tree on `main` in sync with origin; frozen-lockfile install; at least one `*.test.ts` file under `tests/`; `bun test` and `bun run typecheck` pass; `npm whoami` succeeds; the next version is not already on npm; the host's `agent-director` binary is at or above the installed agent-director client's own minimum, compared in the client's own version order (SR-2.5 — `scripts/ad-version-check.ts`; `package.json` is not read; a binary at or above that minimum but below CSCB's Phase 1 floor passes with an `SR-2.5 (preflight) NOTE` block on stderr naming the README section "Switching over to agent-director Phase 1"); no stranded finished work (SR-2.6 — `scripts/audit-finished-tickets.sh` exits zero; audit exit 1 → stranded work, preflight exit 16; audit exit 2 → setup failure such as unlocatable hives/repo/main, preflight exit 17). **Abort behavior:** the skill exits before any side-effecting step. The working tree is untouched.
2. **Phase 2 — `/ci` integration gate (SR-2.7).** The `/ci` skill runs the full Docker-based integration suite. It must report PASS. **Abort behavior:** identical to Phase 1 — no side-effecting step has run yet.
3. **Phase 3a — Bump and smoke test (SR-3.1, SR-4.1–SR-4.3).** `npm version <bump> --no-git-tag-version` applies the bump; `bun pm pack` produces the release tarball; the tarball is scratch-installed into a temp `BUN_INSTALL`; the installed bin is invoked with no args and must exit non-zero with `Usage:` in stderr. **Abort behavior:** the working tree is rolled back (`git checkout -- package.json bun.lock`). Nothing is committed, pushed, or published.
4. **Phase 3b — Real release (SR-5.1–SR-5.4, SR-6.1, SR-7.0–SR-7.5).** Commit `Release v<version>`, create the annotated `v<version>` tag locally, push the commit to `origin/main`, publish the smoke-tested tarball with `npm publish <tarball-path>` (the byte-identical artifact, not a repack), push the tag to `origin`, poll the npm registry until the version is visible (5s cadence, 10-minute window, progress line every ~30s), sanitize the global `package.json` of the bun-1.3.13 empty-string-dependency-key poison, check for a shadowing install in another bun prefix (SR-7.0), remove any pre-existing global install, run `bun install -g claude-slack-channel-bots@<version>`, verify the install resolves under `${BUN_INSTALL:-$HOME/.bun}/install/global/` at the published version (SR-7.4), and ensure the postinstall actually ran (SR-7.4b).

The SR-5.1 → SR-5.4 ordering is load-bearing: the tag is pushed only after `npm publish` succeeds, so the git remote and npm never disagree about whether `v<version>` exists.

#### Phase 7's two prefix assumptions

`${BUN_INSTALL:-$HOME/.bun}/install/global` is the **correct** expansion of bun's global prefix (with `BUN_INSTALL` unset, `~/.bun` is bun's default) — it is not a bug and must not be "fixed". What Phase 7 cannot assume is that it is the *only* prefix on the host: an install performed with `BUN_INSTALL` pointed elsewhere leaves a second global prefix, and a PATH shim (e.g. `~/.local/bin/claude-slack-channel-bots`) can make that stale copy win `command -v` even after a correct install here.

- **SR-7.0 (pre-install shadow check)** resolves `command -v claude-slack-channel-bots` plus `readlink -f` *before* the remove/install, and warns when the result is outside `${GLOBAL_DIR}/`. It **warns and continues** — aborting before the install would leave the host with the stale copy and no new install, which is strictly worse.
- **SR-7.4** fails with exit 72 if the shadow still wins after the install, printing the same shadow report: the path on PATH, the hop-by-hop symlink chain, the expected prefix, the derived stale prefix, and the exact manual remediation.
- Both share one report builder so the pre- and post-install diagnostics cannot drift.
- Promote **reports, never deletes**, an install in another prefix. It does not own other prefixes on the host, and a wrong `rm -rf` there is unrecoverable. Two rules the emitted remediation always carries: never touch any `install/cache` directory (bun's shared download cache, used by every package on the box), and **repoint** the PATH shim with `ln -sfn` rather than deleting it — `~/.bun/bin` is often not on the interactive PATH, so deleting the shim makes the command unresolvable.
- **SR-7.4b (postinstall trust)** closes the fresh-prefix trust gap: a brand-new global prefix has no `trustedDependencies` entry, so bun silently blocks `src/postinstall.ts` and the failure surfaces much later as `start` dying with `missing prerequisite: config.json`. It runs `bun pm -g trust claude-slack-channel-bots` when the global manifest lacks the entry, then verifies the two scaffolded artifacts exist (`${SLACK_STATE_DIR:-~/.claude/channels/slack}/config.json` and `~/.claude/slack-mcp.json`). The `debug-slack-channel-bots` skill link postinstall also creates is a convenience that neither the server nor its persona sessions need, so the check leaves it out. Missing artifacts are a loud warning with one consequence sentence per missing file (`config.json`: `start` fails with `missing prerequisite: config.json`; `slack-mcp.json`: persona sessions launched with the default `mcp_config_path` cannot reach the server's MCP endpoint), **non-fatal** — the release is published, tagged and verified by then, so failing here would misreport a delivered release as broken.
- `scripts/sanitize-global.sh` is deliberately scoped to the canonical prefix only and carries a comment saying so. It is best-effort and always exits 0, so it must not mutate state outside the one directory it owns; shadow detection is publish-promote's job.

### Diagnostic contract in the release scripts

Every non-zero exit from a release script must carry an `SR-X.Y` diagnostic on stderr naming the failing step and the operator's recovery action. The driving LLM relays that stderr verbatim and stops, so the stderr is the whole artifact the human gets — it must be unambiguous.

Two mechanisms enforce this in `publish-prepare.sh`, `publish-promote.sh`, `preflight.sh`, `smoke-check.sh`, and `install-local.sh`; new code in those scripts must honor both:

- **Guarded exits.** Print the `SR-X.Y` line, then exit via `sr_exit <code>` rather than a bare `exit <code>`. `sr_exit` raises a one-way `SR_GUARDED_EXIT` flag before exiting, which tells the backstop this failure is already described.
- **The SR-99.0 backstop.** Each script installs an EXIT trap that prints `SR-99.0 (uncaught)` when it exits non-zero *with the flag unset* — i.e. a `set -e` death at a site nobody wrapped. It preserves the failing command's exit code and reports the command text, so the unguarded site can be found and wrapped.

Consequences worth knowing before editing these scripts:

- Do not use an exit-code allowlist instead of the flag. An allowlist silently rots the moment a new SR code is added; the flag needs no bookkeeping.
- `sr_exit` must run in the script's own shell. Inside a subshell or command substitution the flag would be set in the child only, and the backstop would fire anyway. A helper that must fail from a subshell should `return 1` and let its call site do `|| sr_exit <code>`.
- A correct run therefore produces exactly one SR block. Seeing `SR-99.0` alongside a per-step `SR-X.Y` means the guard was bypassed, not that two things failed.

`scripts/sanitize-global.sh` is exempt: all of its deliberate exits are 0 (it is belt-and-suspenders by design), so it has nothing to guard. `scripts/install-local.sh` is a developer helper outside the release path, so its one guarded failure prints an `[install-local]` diagnostic rather than an `SR-X.Y` one — but it still routes that exit through `sr_exit`, for the same reason.

### Post-publish

`/publish` ends with a success summary listing the published version, npm URL, GitHub tag URL, the resolved local install path, and a final instruction. Run that final instruction to swap the running CSCB daemon onto the new binary:

```sh
claude-slack-channel-bots clean_restart
```

This gracefully exits the managed Claude Code sessions, stops and restarts the server on the new binary, and brings each session back up. See `clean_restart` in the README for behavior details.
