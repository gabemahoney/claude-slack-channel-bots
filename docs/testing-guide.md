# Test Writing Guide

## Framework

- Bun Test (`bun:test`) — `describe`, `test`, `expect`, `beforeEach`
- Run all tests: `bun test`
- Run one file: `bun test <file>`
- When stdout is not a TTY (piped, or run by an agent), Bun prints only failing test titles. To see the passing titles, such as a `test.each` matrix's rows, run it in a TTY or add `--reporter=junit --reporter-outfile=<path>`

## Isolation (SR-13.2)

Tests never touch the real home or a real install. A dev-tree test once ran against the real home and caused a production outage.

- **Temp directories only.** Every file a test reads or writes (config, credentials, state directory, crontable, logs, working directories, agent-director store) sits under the test's own `mkdtempSync` directory, passed explicitly, and removed in `afterEach`.
- **Never the real home.** No test reads or writes `~/.claude`, `~/.claude/channels/slack`, `~/.agent-director` or `~/.npm`, and no path in a fixture resolves to them. Code that falls back to `os.homedir()` is tested through `runInFakeHome` (see Credentials Fixtures and Leak Checks); code that takes a home or `SLACK_STATE_DIR` gets a temp one.
- **No real server or CLI.** No test calls `main()`, runs `src/server.ts` or `src/cli.ts` as an entry point, or starts a real daemon in-process. The one exception is the usage-text test in `tests/cli.test.ts` (`unknown subcommand`), which runs `src/cli.ts` in a child `bun` process with a temp HOME and a built env (`PATH`, `HOME`, `SLACK_STATE_DIR` and nothing else) and never reaches a subcommand. The CLI is otherwise tested through `createCli` with injected `CliDeps`; `server.ts` through its importable modules (see Importing server.ts).
- **CLI log seams.** `openLogAppend`, `closeFd` and `initLogging` are `CliDeps`, so CLI tests inject fakes: no real descriptor is opened and `console` is never taken over. To see which lines reach the log and which the terminal, inject an `initLogging` that swaps `console.error` for a recorder and restore it afterwards. The agent-director calls are built by the exported `createDirectorOps(getClient)`; test it by passing a stub client, not by installing a Client singleton.
- **Fake tokens only.** See the rules under Credentials Fixtures and Leak Checks.

### Integration scripts run only in docker CI

The integration scripts (`tests/integration/*.sh`), their driver (`tests/integration/fixtures/driver.ts`) and `tests/runner.sh` install the packed package, write a persona config, start the server and spawn bots. They run only inside the `cscb-ci` docker container, started by the `ci` skill (`/ci`), which runs `tests/runner.sh` and reports `PASS` or `FAIL`.

- Never run them on a dev box or on any host without container support, and never against the real home. If docker is not available, report the integration run as not done; don't run the scripts directly.
- Their config and credentials files are written inside the container; the scripts never read a config from the host.
- `bun test` does not run them. `tests/integration/session-leader.test.ts` is the one `bun test` file under `tests/integration/`: it spawns only a throwaway child and touches no CSCB state.

## Fixture Patterns

### Factory Functions

Every test file defines factory functions that create fixtures with sensible defaults and optional overrides:

```
makePersonaConfig(overrides?, baseDir?) — a resolved PersonaConfig with one default persona
makeMultiPersonaConfig(specs, baseDir, overrides?) — a resolved PersonaConfig with one persona per spec
makeTransport() — minimal transport stub
makeServer() — minimal MCP server stub
```

Always use factory functions instead of hardcoding fixture values in individual tests. When a new field is added to a type, update the factory function — all tests automatically pick up the default.

Reload-controller tests build their configuration directory, personas and runs with `makeReloadHarness` (see Reload Tests), not by hand.

Persona-loader tests, and tests of persona-keyed code such as `spawnForPersona`, `startupSessionManager` and `launchSession` in `src/session-manager.ts`, use the shared persona-config helper, `tests/test-helpers/persona-config.ts`. It is the only config fixture; a route-keyed config appears only as raw JSON in a pre-persona rejection case. The CLI's `loadConfig` dependency returns a resolved `PersonaConfig`, so CLI tests build it with these helpers too. The persona-config helper provides:

```
makePersona(overrides?, baseDir?) — one PersonaInput entry in file form; default paths sit under baseDir
makePersonaConfigInput(overrides?, baseDir?) — a PersonaConfigInput file-form config with one default persona
makePersonaConfig(overrides?, baseDir?) — a resolved PersonaConfig, as loadPersonaConfig returns it, except mcp_config_path (see below)
makeMultiPersonaConfig(specs, baseDir, overrides?) — a resolved PersonaConfig with one persona per PersonaSpec, in order
makeStandInPersonaConfig(personas, baseDir, overrides?) — makeMultiPersonaConfig for stand-in personas keyed and named by one channel ID each
writeConfigFile(dir, input) — writes input as JSON to <dir>/config.json and returns the path
```

Use `makeMultiPersonaConfig` when a test needs several personas. Each `PersonaSpec` is any resolved `Persona` field except `index`; `overrides` sets the server-wide fields as for `makePersonaConfig`.

- It runs no validation, so a stand-in persona can set `key` to a channel ID directly.
- Each persona defaults to its own `all` channel, with prompts to that channel and DMs off. A spec with no channels gets `permission_prompts: 'dm'` but DMs still off, a pair the loader rejects; set `dm` in that spec yourself.
- It throws when two personas share a name or a key.
- `baseDir` is required; pass the test's `mkdtempSync` directory.

`makeStandInPersonaConfig` is kept for older suites whose fixtures key personas by channel ID; new tests use `makeMultiPersonaConfig` with real persona names. Each record key is a channel ID that becomes the persona's `name` and `key`, its one `all` channel and its `permission_prompts` target; the record value sets further fields such as `working_directory`. Personas keep record order, and everything else, including the required `baseDir`, is as for `makeMultiPersonaConfig`.

For the other helpers, `baseDir` defaults to the OS temp directory; pass the test's own `mkdtempSync` directory when paths must exist or be unique to the test. `writeConfigFile` writes only into the caller-supplied temp directory and has no default location. Pass `loadPersonaConfig` a temp home as well, so `~` never expands to the real home. Remove both the temp directory and the temp home in `afterEach`.

Build agent-director rows in tests with the canned-row helpers in `tests/test-helpers/agent-director-stub.ts` (`cannedListRow`, `cannedGetResult`, `cannedGetResultPlural`), never by hand. Every row they build is persona-labelled (b.av2 SR-13.4):

- **Default form** — `cannedListRow({ claude_instance_id })`: the row stands for the persona whose key is the instance ID without its `cscb_` prefix. Labels are exactly `service=cscb` and `persona=<key>` (no `config_dir`, no `channel`), tmux `slack_bot_<key>`, and `cwd` is `defaultCannedRowCwd()`, the working directory of the default persona fixture (`makePersona()`, `<tmpdir>/personas/test_bot/work`; nothing creates it). The stub client's default `get` row uses this form. Use it for permission-poller and click-handler rows, and pair it with a `getPersona` stub that knows that key.
- **Persona form** — `cannedListRow(overrides, persona, home)`, likewise `cannedGetResult` and `cannedGetResultPlural`.

A `channel` label appears only in explicit negative rows that test the rejection of pre-persona rows (the poller skipping a row with no `persona` label, the start sweep removing one): override `labels` to carry only the old `channel` label.

For the persona form, pass a resolved persona (e.g. from `makePersonaConfig`). The row then carries what a spawn of that persona writes: `cwd` = its working directory, `cscb_<key>`, `slack_bot_<key>`, and the `service`, `persona` and `config_dir` labels. The collision ladder and the start sweep replace a row whose `cwd` or `config_dir` label doesn't match (b.av2 SR-6.2, SR-6.3), so a fixture meant to reach a resume, reconnect or wait path must use this form. `home` is required and the persona form throws without it; there is no OS-home fallback. The `config_dir` label must be computed under the same home the session manager's `_setSpawnHomeDir` seam uses, or it won't match the one the code computes, so pass that home. To test a guard, override `cwd` or `labels` explicitly. `spawnForPersona` joins a launch already in flight for the same key, so a suite that can leave a launch unsettled calls `_resetInFlightLaunches()` in `afterEach`.

To test that only one launch per persona is in flight, wrap the stub with `holdSpawns(stub, shouldHold?)` from the same file. Each `spawn` whose instance ID passes `shouldHold` (all by default) stays open until the test settles it; other spawns go to the stub's original `spawn`. The handle exposes `calls` (every spawn received), `held()` (instance IDs still open), `entered(id)` (resolves once a spawn for `id` is issued), `release(id)` and `fail(id, err)` (settle the oldest held spawn for `id`), and `releaseAll()` for teardown.

To assert which agent-director calls a case made (for example, none for a persona that is not up), use the shared stub call-log helper in the same file rather than a hand-rolled recorder, so every suite reads the stub's calls the same way.

`makePersonaConfig` puts `mcp_config_path` under `baseDir`, but the loader defaults it to `~/.claude/slack-mcp.json` under the home you pass. When comparing against loader output, override `mcp_config_path` with the loader's value (e.g. `join(home, '.claude', 'slack-mcp.json')`).

### Credentials Fixtures and Leak Checks

Any test that touches Slack tokens or a persona credentials file uses the shared helper `tests/test-helpers/credentials.ts`. It builds fake tokens that all carry one marker, `LEAK_SENTINEL`, and checks captured output for that marker or any token-like value. A leak then fails a test instead of reaching a log.

| Export | Use it for |
|--------|------------|
| `LEAK_SENTINEL` | The marker every fake token embeds. It uses identifier characters only, so an error that quotes an identifier quotes the whole sentinel. Refer to the constant; never copy its value into a test. |
| `BOT_TOKEN_PREFIX`, `APP_TOKEN_PREFIX` | The Slack token prefixes, for building fakes and for asserting on rule text. A bare prefix is not a token. |
| `fakeToken(prefix, suffix?)` | One fake token built at runtime: the prefix, then the sentinel, then an optional suffix. Use distinct suffixes to tell two fakes apart; pass a wrong prefix or none for bad-prefix cases. |
| `makeCredentials(overrides?)` | A credentials object. By default it is valid (exactly `bot_token` and `app_token`, distinct fakes); an override set to `undefined` removes that key, and any other override adds or replaces one. |
| `writeCredentialsFile(dir, name?, overrides?)` | Writes a credentials file with mode 0600 inside `dir` and returns its path. An object override merges over the valid defaults; a string override is the whole file content, for non-JSON or non-object cases. `dir` is required and `name` must stay inside it. |
| `writtenFile(path)` | Marks a file or directory the code under test wrote, so `assertNoLeak` checks its content. This is the only way to check a file: a plain string is always checked as text, never read as a path. |
| `assertNoLeak(captured, label?)` | Fails if the sentinel (any case) or a token-like value appears anywhere in `captured`. Strings, errors (message, stack, properties, `cause`, aggregated errors), arrays, objects, maps, sets, buffers and `writtenFile` marks are all checked, recursively. |

Rules:

- **Fakes only.** Tests use only tokens from `fakeToken`, `makeCredentials` or `writeCredentialsFile`, so every token embeds `LEAK_SENTINEL`. No test file contains a token literal, not even a fake one; build it at runtime from the prefix constants.
- **Check everything captured.** Every test that handles credentials runs `assertNoLeak` over its captured log lines, errors and results, including rejected calls and failure paths. Pass them together as one object so a failure names the leaking item (for example `captured.lines[2]`). Wrap any file the code wrote in `writtenFile`.
- **Override the token environment.** Nothing in `src/` reads `SLACK_BOT_TOKEN` or `SLACK_APP_TOKEN`, so tests normally leave them alone. A suite that sets either (for example to show that `start` or the connection manager ignores them) sets both to fakes for its whole run and restores the previous values afterwards, so an ambient real token can never reach a failure message.
- **Why the failure is safe.** `assertNoLeak` reports which item leaked and whether it held the sentinel or a token-like value, never the leaked text. Rule text such as "must start with" a bare prefix passes.

Isolation (SR-13.2) applies to credentials files, crontables, cron logs and working-directory fixtures exactly as it does to config files:

- Create them only under the test's own `mkdtempSync` directory, pass every path explicitly, and remove the directory in `afterEach`. `writeCredentialsFile` has no default location and refuses a name that escapes `dir`.
- Never read or write `~/.claude/channels/slack` or `~/.agent-director`, and never point a credentials path at the real home.
- To test code that falls back to `os.homedir()`, use `runInFakeHome` from `tests/test-helpers/fake-home-subprocess.ts`. Setting `process.env.HOME` in a test doesn't work: Bun reads HOME only at startup. The helper runs the module call in a child `bun` process launched with HOME and `SLACK_STATE_DIR` set to the test's temp directories. The child gets only those two, PATH and the JSON input, so no token reaches it. Assert `observedHomedir` equals the fake home before checking anything else. The helper refuses the real home, and a child that hangs past its timeout (30 s by default) or dies from a signal throws. `tests/trust-bootstrap.test.ts` and `tests/stop-hook-bootstrap.test.ts` are the references.
- Code that can call `recordStartupError` writes `startup-errors.log` under `SLACK_STATE_DIR`, which defaults to a path under the home. Point `SLACK_STATE_DIR` at a temp directory for the whole file in `beforeEach` and restore the environment in `afterEach`, as `tests/stop-hook-bootstrap.test.ts` does. A test that reads the log points it at its own directory.
- A test that needs a per-persona reply-guard record (`reply-guard/<key>`) builds it with `makeReplyGuardRecordDir` from `tests/test-helpers/reply-guard-record.ts`. It creates a `mkdtempSync` state directory (under the OS temp directory or the test's own `parentDir`) with its `reply-guard/` record directory, writes records byte-for-byte, and removes what it created with `cleanup()`. It never reads `SLACK_STATE_DIR` or HOME.
- When a test compares real paths (for example a symlinked credentials file shared with another persona), resolve the temp directory with `realpathSync` first; the OS temp directory may itself be a symlink.

Permission cases (an unreadable credentials file, an unreadable or unsearchable working directory) inject a failing operation through the check's file-system seam, so they pass under root in docker CI. The credentials seam is `openFile`, `fstatFile`, `readFileFd`, `closeFile` and `realpath`; the working-directory seam is `stat`, `access` and `realpath`, and the combined `PersonaBringUpFs` carries both. For an unreadable credentials file, make `openFile` or `readFileFd` throw an errno-style error (`EACCES`, `EPERM`, `EIO`). To test a credentials path that is not a regular file (a FIFO or a device), make `fstatFile` report `isFile()` false, assert `readFileFd` is never called and `closeFile` is called for the opened descriptor. Because the real open is non-blocking, a real FIFO, directory or `/dev/zero` is also safe to use as a control. The config reader (`readPersonaConfigBytes`, used for `config.json` and the last-applied record) has the same seam, `PersonaConfigFs`, and the same rule, reached through `configFs` on the reload controller and `readAppliedPersonaConfig`. A durable write whose directory open or fsync fails after the rename (`DurableWriteUnsyncedError`), or a durable delete whose directory open or fsync fails after the unlink (`DurableUnlinkUnsyncedError`), is driven through the `DurableWriteFs` seam. The reload detection tick's credentials reads take the same `CredentialsFs` seam, through `opts.credentialsFs` on a reload harness run. A variant that uses real permission bits is marked `test.skipIf(isRoot)`, with the reason in the test name. Restore any mode a test changed before `afterEach` removes the directory.

A test that could hang on a blocking open or read (a real FIFO with no writer) runs the risky call in a child `bun` process (`spawnSync` with a `timeout`, 10 s in the references) and asserts the child was not killed (`child.signal` is null), with a per-test timeout above that bound. A test timeout can't interrupt a blocking synchronous call, so in-process a regression would hang the whole suite instead of failing one test. Skip it where `mkfifo` is missing (`test.skipIf(!hasMkfifo)`, the reason in the test name). The real-FIFO cases in `tests/config.test.ts` and `tests/reload.test.ts` are the references.

### Slack Stub

New persona and connection suites fake Slack with the shared helper `tests/test-helpers/slack-stub.ts`, not with hand-rolled WebClient or SocketModeClient stubs. `makeStubSlack(opts?)` builds one independent fake Slack for one persona. It has no module-scope state, network, file system, environment access or timers, and its error shapes follow the installed `@slack/web-api` and `@slack/socket-mode` libraries.

| Member | What it gives a test |
|--------|----------------------|
| `identity` | The bot user ID, bot ID and team ID a successful `auth.test` returns. The bot user ID and bot ID default to random values, distinct per stub; the team ID defaults to a fixed value. Override them through `botUserId`, `botId` and `teamId`. |
| `script` | Outcome queues `authTest`, `connect` (socket `start()`), `post` (`chat.postMessage`), `update` (`chat.update`), `upload` (`filesUploadV2`), `history` (`conversations.history`), `replies` (`conversations.replies`), `info` (`conversations.info`) and `open` (`conversations.open`). Seed them through the options of the same names (every queue but `open`), or push onto them at any time; a test scripts `conversations.open` by pushing onto `script.open`. Each call takes the next outcome; an empty queue means success. |
| `calls` | Capture arrays of call arguments: `authTest`, `postMessage`, `update`, `reactionsAdd`, `reactionsRemove`, `conversationsOpen`, `usersInfo`, `filesUploadV2`, `conversationsHistory`, `conversationsReplies`, `conversationsInfo`. Every Web API client of the stub shares them. |
| `callLog` | Every Web API call in call order, as `StubWebCall` entries (`method`, a `StubWebMethod` such as `'conversations.open'`, and `args` exactly as passed). A call is logged when it is made, so a failed call is logged too. The stub's `callLog` holds the calls of all its Web API clients; each client's `callLog` holds only its own. Assert an order with `callLog.map((c) => c.method)`, for example `['conversations.open', 'chat.postMessage']`, and no call at all with `toEqual([])`. |
| `web` | A ready Web API client with default options, for direct calls. Its bot token is the `token` option; the default is a sentinel-bearing fake token with a random suffix, distinct per stub. |
| `createWebClient(token?, options?)` | Builds a Web API client as the real constructor would; recorded in `options.web`. Without `token` it uses a fixed sentinel-bearing fake token, the same for every stub. |
| `createSocketClient(options?)` | Builds a socket client; recorded in `options.socket` and `sockets`. Throws on an empty app token, as the real constructor does. |
| `token`, `hasToken(expected)` | Every Web API client carries the bot token it was built with as `token`, like `WebClient.token`. It is not enumerable, so printing or comparing a client never shows it; assert with `hasToken(expected)`, which prints no token on failure. |
| `options` | The options every client was built with, in build order (`web`, `socket`). |
| `sockets`, `socket` | Every socket client built, and the latest one (`socket` throws if none was built). |

**Opening a DM.** An unscripted `conversations.open` succeeds with a `D…` ID derived from the requested `users`: `stubOpenedDmId(users)` returns `D0OPN` followed by the user IDs without their `U`/`W` prefix (`U0BOB` gives `D0OPN0BOB`), so each user gets its own ID and none equals the event factories' default DM (`D0STUB0001`). Use `stubOpenedDmId` to compute the ID a test expects the post to go to. To choose the ID, push `openedDm(id)` onto `script.open`; to fail the open, push a `platform` outcome such as `missing_scope`, `user_not_found` or `cannot_dm_bot`.

**Passing a stub client as a `WebClient`.** `WebClient` is a class with private members, so no plain object satisfies it. Where code under test takes a `WebClient` (a persona's client in the registry's `SessionToolDeps.clientFor`, the connection manager's factory), pass `asWebClient(client)`, the helper's one cast, rather than casting in the test file. `makeStubSlackFactory()` already uses it.

The socket stub behaves like `SocketModeClient` with auto-reconnect off:

- `start()` takes the next `connect` outcome and first runs the connect leg (`apps.connections.open`). A failure there (the Web API kinds, `no-url` or `reject`) rejects `start()` with no lifecycle event.
- Otherwise `start()` emits `authenticated` and `connecting`, and the WebSocket phase settles on a later microtask according to the outcome. `startCalls` counts calls, and `start()` can be called again after a drop, so a test can drive a reopen.
- `drop()` is Slack closing the connection, the case the connection manager reopens: it emits `close` and `disconnected`, and a `start()` still waiting for `hello` rejects with no value. `disconnect()` is the client's own close, which is not reopened: it is counted in `disconnectCalls` and emits `disconnecting`, then `close` (if a WebSocket phase ever began) and `disconnected`.
- `deliver(event)` sends an Events API event and `deliverInteractive(payload)` an interactive payload, in the shape `server.ts` consumes. Both need a connected socket and resolve once every listener settles.
- `acks` records each ack in order; `lifecycle` records every lifecycle event emitted, in order.

**Scripted outcomes.** Each queue entry is one outcome kind:

| Kind | Result |
|------|--------|
| `ok` | Success. On `auth.test`, `post`, `update`, `upload`, `history`, `replies`, `info` and `open`, an optional `result` is merged over the default response; a key set to `undefined` is removed. |
| `platform` | A named Slack error (an `ok: false` answer) with that `error`, and an optional `retryAfter` in the response metadata. |
| `network`, `dns`, `timeout`, `http`, `rate-limited` | Slack unreachable: a request error, an HTTP error with a status, or a rate-limited error with `retryAfter` in seconds. |
| `no-url` | Connect only: `apps.connections.open` answered without a URL. `start()` rejects with a plain error on the connect leg, with no lifecycle event. |
| `closed-before-hello`, `websocket-error` | Connect only: the WebSocket closes before `hello`. `start()` rejects with no value after `close` and `disconnected`; `websocket-error` emits `error` first. |
| `never` | Connect: `apps.connections.open` answers, `authenticated` and `connecting` are emitted, and the WebSocket phase never reaches `hello`; `start()` ends only on `drop()` or `disconnect()`. Web API calls: the call never settles. |
| `open-never-answers` | Connect only: `apps.connections.open` never answers. `start()` stays pending for good with no lifecycle event; `disconnect()` does not end it. |
| `deferred` | Connect: built with `makeDeferredConnect()`. `start()` waits at the connect leg until the test calls `settle(outcome?)` (default `ok`), then proceeds as that outcome. Settling after the manager abandoned the `start()` drives a late settlement. Web API calls: built with `makeDeferredWebApiCall()`; push its `outcome` onto any Web API queue (`script.open`, `script.post`, …) and each call that takes it waits until `settle(outcome?)` (default `ok`, any kind but `deferred`), then answers as that outcome. Use it to hold an open or post in flight, for example to show concurrent posts share one open or that an attempt settling after `cancel` changes nothing. `settled` says whether it was settled; a second `settle` throws. |
| `reject` | The call rejects with the given value exactly as given (a plain error, a string, `undefined` and so on). |

Set `leakMarker` to `LEAK_SENTINEL` and every error the stub builds carries the marker wherever a real error can hold secrets: the message, the wrapped `original` error and its headers, HTTP headers and body, fields of `data`, and the error the socket's `error` event carries. `data.error` stays exactly as scripted, so classification still sees the real Slack error code.

Not every failure carries the marker. A rejection with no value carries nothing: `closed-before-hello`, and the `start()` rejection after `websocket-error`. `reject` passes its value unchanged, so plant the sentinel in the value if the row needs it. Run `assertNoLeak` over what the code under test produced (see Credentials Fixtures and Leak Checks).

**Event factories.** `makeChannelMessage`, `makeDm`, `makeBotMessage`, `makeWebhookPost` and `makeAppMention` build Slack events with defaults and overrides (a key set to `undefined` is removed). Text builders for message bodies:

- `mentionText(userId, label?)`: a user mention, `<@U…>`, or `<@U…|label>` with a label. Pass the stub's `identity.botUserId` to mention that stub's bot.
- `broadcastText(kind?, label?)`: `<!here>` (the default), `<!channel>` or `<!everyone>`, or the labelled form such as `<!here|here>`.
- `userGroupMentionText(groupId?, label?)`: a user-group mention, `<!subteam^S…>`, or the labelled form, with a fixed default group ID. It mentions no persona; use it to prove that a user-group mention does not deliver.

**Reference example.** The `Slack validation classification (both legs, sentinel-bearing errors)` describe block in `tests/persona-connections.test.ts` is a table test. Each row scripts one outcome and runs it against a fresh sentinel-bearing stub on each leg it applies to: `auth.test`, `socket-mode` or both. It checks the class, the reason fields and `assertNoLeak` on everything captured.

### Fake Clock

Persona suites that need virtual time use the shared helper `tests/test-helpers/fake-clock.ts`, not hand-rolled single-shot timer fakes. The connection manager takes its clock and timers by injection, so tests pass it a clock from `createFakeClock` rather than using Bun's global fake timers. The helper also flushes pending promise continuations after each timer it fires and lets a test list the pending timers, which is what driving the backoff, the 10 s bounds on an `auth.test` or `start()` that never settles, and the bring-up and reopen retry timers without sleeping needs.

`createFakeClock({ start?, flushTurns? })` builds one independent clock. Its `now`, `setTimeout` and `clearTimeout` satisfy the connection manager's `PersonaConnectionClock`, so a test passes the clock with no cast. Virtual time moves only when the test moves it.

| Member | What it gives a test |
|--------|----------------------|
| `now()` | The current virtual time in ms (default start 0). |
| `advance(ms)`, `advanceTo(time)` | Move virtual time forward, firing every due timer in due-time order, including timers that callbacks schedule during the move. Resolves with the number fired. |
| `runNext()` | Jump to the earliest pending timer and fire every timer due then. |
| `flush()` | Let pending promise continuations run without moving time. The clock does the same before, between and after firings, so a stub's settled promise chain finishes before the next timer fires. |
| `pending()`, `pendingCount()`, `firedCount()` | Introspection: each pending timer's requested `delayMs`, `dueAt` and `scheduledAt`, earliest first; the pending count; callbacks fired so far. |

Code that only reads the time takes a plain `() => number` clock (the inbound dedupe store, the routing harness's `dedupeClock`); pass the fake clock's `now` and move time with `advance`, never `Date.now` or a hand-written counter.

A zero, negative or overlong delay fires after 1 ms, as in Bun, but `pending()` still reports the requested `delayMs`. Assert on the requested delay to check what the code asked for.

### Backoff and Retry Tests

Backoff, retry and timeout tests never wait in real time.

- **Pure schedules are called, not timed.** `createPersonaRetrySchedule` holds no timer and reads no clock: it returns the next wait. Tests drive it by calling `nextDelayMs` and asserting on the returned sequence, as the `backoff schedule` describe block does.
- **Timers and clocks are injected.** Code that schedules a wait, or abandons a call that never settles, takes its clock and timers as parameters. Tests pass the shared fake clock (see Fake Clock) and advance it; they never sleep past a real delay.
- **Never-settling cases.** A `never` outcome stays pending for good, so the test ends it through the stub (`drop()`, `disconnect()`) or through the injected clock, never by waiting for it.
- **`retryAfter` rows.** Script `retryAfter` values above and below the current step, and assert that the wait is never shorter than `retryAfter`. The outcome carries `retryAfter` in seconds and the schedule returns milliseconds, so convert before comparing. The `retryAfter` describe block is the reference.
- **One exception: the real spawn path.** A case that launches through the real `spawnForPersona` polls in real time for the spawn only (see Connection Wiring and Bring-Up Tests); its backoff and retry waits stay on the fake clock.
- **Leak checks still apply.** Every captured log line and error passes through `assertNoLeak`.

### Destination Failure Tests

A post to a persona's destination that fails is held and retried by the destination hold (`src/persona-destination-hold.ts`), shared by the permission poller and the notifier. Test it on a fake clock, never in real time.

- **Always inject a fake-clock hold.** Any test that can hold a notice or prompt passes a `destinationHold` built with `createPersonaDestinationHold({ destinations, getPersona, clientFor, clock: createFakeClock(), log })`. The notifier's and the poller's default hold uses the real clock, so a held notice would start a real timer. To build the resolver, the fake-clock hold and the notifier together, as `server.ts` wires them, call `makeNotifierStack({ getPersona, clientFor, log, clock?, isDryRun? })` from `tests/test-helpers/persona-notifier.ts`; it returns `notifier`, `hold`, `destinations` and `clock`. `makeNotifierHarness` (`h.clock`, `h.hold`), `makeRoutingHarness` (`h.holdClock`, `h.hold`) and `makeManagedRouting` are built on it; `makeHold` in `tests/permission-poller.test.ts` does it for the poller.
- **Make the failure sticky.** One scripted failure is used up by the first attempt, so the first retry would succeed. To keep the cause in place across retries, fill the queue: `stub.script.open.push(...Array<WebApiOutcome>(1000).fill({ kind: 'platform', error: 'missing_scope' }))` (or `script.post` with `not_in_channel`).
- **Clear the cause.** `stub.script.open.length = 0` empties the queue, so the next call succeeds; push `openedDm(id)` after it to choose the DM.
- **Drive the retries.** `clock.pending()[0].delayMs` is the wait the hold asked for (5 000, then 10 000, doubling to 300 000); `clock.runNext()` fires the next retry and `clock.advance(ms)` moves time, for example to show nothing is attempted 1 ms before the due time. A poller prompt has no timer of its own: advance the clock past the due time, then `tick()`.
- **Assert the episode, not the attempts.** One `persona-destination-failed` start line per episode and one `cleared:` line after the cause clears, no line per failed retry, each held item posted exactly once after it clears, and `hold.view(key)` (`held`, `heldNotices`, `nextDueAt`). For a notice, `onPostFailure` runs once, at its first failed attempt.
- **Clean up.** A hold that can hold notices sets retry timers: call `hold.cancelAll()` in `afterEach`, and assert `clock.pendingCount()` is 0 once a case's held items are delivered. A hold used only by the poller sets no timer.

`tests/persona-destination-hold.test.ts` is the reference for the hold alone; the `destination failures are held and retried` describe block in `tests/persona-notifier.test.ts` and the `a destination failure holds the persona's prompts` block in `tests/permission-poller.test.ts` for the two callers.

### Connection Manager Tests

Connection manager tests build `createPersonaConnectionManager` from injected fakes only: the `factory` from `makeStubSlackFactory()` (in `tests/test-helpers/slack-stub.ts`) and the `clock` from `createFakeClock()`, which supplies both the clock and the timers. Always pass both: an omitted `factory` falls back to `PRODUCTION_SLACK_CLIENT_FACTORY` (real Slack clients) and an omitted `clock` to `SYSTEM_PERSONA_CONNECTION_CLOCK` (real timers). A test never builds a real Slack client.

| `makeStubSlackFactory()` member | What it gives a test |
|--------|----------------------|
| `factory` | The `PersonaSlackClientFactory` to pass to the manager, uncast. It routes each build to the persona whose token it received: the app token for a socket client, the bot token for the validation and long-lived Web API clients. |
| `addPersona(key, tokens, opts?)` | Registers a persona with its own `makeStubSlack(opts)` stub. No identity, script queue, capture or socket is shared with another persona. |
| `persona(key)` | That persona's stub. `socket` is its latest socket client and `sockets` every one built, abandoned ones included. |
| `builds`, `buildsOf(key, kind?)` | Every client built, in build order, each with its `kind` (`socket`, `validation` or `web`), `persona` and `options` exactly as received. |
| `hasToken(expected)` | On each build record: whether the client got exactly that token. The token itself is not enumerable, so a failing assertion never prints it. |

Rules:

- **Check client options through the build records.** Assert on `options` in `builds` or `buildsOf`, per client kind. A socket build's options hold the app token, so drop that field before comparing. Check tokens with `hasToken`, never by reading or printing the token.
- **Use the file-level harness.** `makeHarness()` in `tests/persona-connections.test.ts` builds personas A and B, their credentials files and stubs (leak marker on), the manager, the fake clock and the captured lines, statuses and events. Its `afterEach` stops every harness manager with `stopAll()` and runs `assertNoLeak` over everything captured. A new connection test uses it rather than building a second harness.
- **Isolation tests check both personas.** Whenever one persona fails, drops, is rejected or hangs, the test also delivers on the healthy persona (`expectDelivers`) and checks its events still arrive, tagged with that persona. Asserting only on the failing persona does not show isolation.

**Reference example.** The `AC 5: per-persona isolation walk-through (fake clock)` describe block in `tests/persona-connections.test.ts` is the model. Each case is named "AC 5: …". A's socket drops and reopens at once while B keeps delivering. A rejected reopen waits 5 s, then 10 s, and B keeps delivering throughout. A reopen whose `start()` never settles is abandoned at 10 s on the fake clock and retried. The case `AC 5: no agent-director call is made for A across a drop, a rejected reopen, an abandoned reopen and a refused reopen` counts calls on an agent-director recorder built with `makeStubClient` and asserts zero.

### Connection Wiring and Bring-Up Tests

The server's per-persona wiring lives in importable modules, so test it there, never through `main()`:

- **Connection seams and the event router.** Build personas on the real connection manager with `makeConnectionHarness(specs, baseDir, opts?)` from `tests/test-helpers/persona-connection-harness.ts`. It uses the shared stub factory and a fake clock, and builds `clientFor` and the identity lookup with the same `persona-start.ts` factories `server.ts` uses. Its `onEvent` and `onStatus` are late-bound, so a test can build the real `createPersonaEventRouter` or `createPersonaUpFlushListener` over the harness and plug it in. With `files: true` it writes each persona's credentials file and working directory under `baseDir`, so the real start procedure passes steps 1–2. The `tokens` option (by persona name, each built with `fakeToken`) registers a given token set (and, with `files: true`, writes it) instead of the default fakes, for example a rotated one. `h.connections` has only `bringUp`: it records each call in `h.bringUpCalls` and appends `slack:<key>` to `h.order`, a shared step log the test may add its own markers to. Call `h.manager.stopAll()` after each test. `tests/persona-connection-wiring.test.ts` is the reference.
- **Real routing over the harness.** To drive the real `createPersonaRouting` with the manager's identities and clients, build it with `makeManagedRouting(h, baseDir, { archive? })` from `tests/test-helpers/persona-routing-managed.ts`, which wires it as `server.ts` does and registers a session per persona. Its `notify` is the real persona notifier (from `makeNotifierStack`) over the harness's persona and client lookups, with its hold on its own fake clock, and its user-name lookup is `users.info` on the persona's own client (the user ID when it has none). It returns only `routing`, `logs` and `notifications`; for a test that asserts notices or the hold, use `makeRoutingHarness` (see Inbound delivery below). Don't hand-wire the routing deps. The caller owns `initRestart`, `resetRoutingState()` and `h.manager.stopAll()`.
- **The start procedure.** Drive the real bring-up controller, `createPersonaBringUpController`, alone (`controller.bringUp(persona, applied)`) or as `startupSessionManager`'s `bringUp`. Build it over a harness with `files: true`: `{ bringUp: h.connections.bringUp, status: (key) => h.manager.status(key) }` (or the manager itself) as `connections`, since the controller needs `status` as well as `bringUp`, `h.clock` as `clock`, the `fs` seam for credentials and directory failures, and a recording `launch` (or one that calls the real `spawnForPersona`, as `server.ts` does). Compose `controller.onConnectionStatus` into `h.onStatus` with `composePersonaStatusListeners`, so a persona that reaches `up` through a retry is launched. Assert the step order, each persona's outcome (`up`, `broken` or `retrying`) through `controller.state(key)` or the start pass's `perPersona`, that a broken or retrying persona launches nothing, and, in dry run, that no credentials file is read. `tests/persona-bringup.test.ts` is the reference for the order; `makeBringUpFixture` in `tests/persona-connections.test.ts` (`bring-up outcomes (E5)`) for outcomes and retry timers. Its `dropSessions` option wires the controller's `onLeftUp` as `server.ts` does (`createNotUpSessionDropper` over the real `dropPersonaSession`), for cases where a persona that stops being up must lose its MCP session.
- **MCP admission of a not-up persona.** `server.ts`'s initialized handler can't be imported, so decide a session through the real `decideSessionAdmission` with the production up check (`createPersonaUpPredicate` over the manager and the controller) and have the test promote an admitted session or close a refused one, as that handler does. `registry.test.ts` (`not-up personas: MCP session admission and drop`) and the surviving-instance cases in `persona-connections.test.ts` are the references; a source audit in `server-startup-wiring.test.ts` pins what the handler itself does with a refusal.
- **Retry timers.** Directory re-checks and Slack retries run on the harness's fake clock: advance it through the backoff steps and assert on the requested delays and the stat times, never sleep. In `afterEach`, call `controller.cancelAll()` and `h.manager.stopAll()`, then assert `h.clock.pendingCount()` is 0, so no retry timer leaks into the next test.
- **The real spawn path uses real timers.** `spawnForPersona` (its dialog polling and tmux probes) does not take the fake clock, so a case that launches through it waits for the spawn by polling in real time, in 1 ms steps with a 2 s cap, then asserts. Shorten the spawn path's own waits first (`_setDialogPollIntervalMs(1)`, `_setDialogReadyTimeoutMs(200)`, the tmux fakes). Keep every Slack and retry wait on the fake clock.
- **The start pool.** Drive `startupSessionManager` with the controller as `bringUp` and launches held open, so the test can show every persona's Slack bring-up happens before any launch settles, that no more than `concurrency` launches run at once, in readiness order, that a broken or retrying persona uses no slot, and that a retrying persona that comes up later is launched outside the pool. The `startupSessionManager` bring-up cases in `tests/session-manager.test.ts` are the reference.
- **Isolation still applies.** Every persona path sits under the test's `mkdtempSync` directory, and a persona failing its bring-up is checked alongside a healthy one (see Connection Manager Tests).

A test that needs the persona key an action ID was built for uses `personaKeyFromActionId` from `tests/test-helpers/action-id-key.ts`; production takes the key from the receiving connection instead.

### Serialization and Teardown Tests

Every lifecycle operation for a persona runs through the per-persona serializer (`src/persona-serializer.ts`), and the teardown in `src/persona-lifecycle.ts` is the one path that clears a persona's state.

- **Controllable promises, never delays.** Serializer tests settle each operation from the test (a `Promise.withResolvers` gate) and check order after flushing continuations; no timer and no real delay. Elsewhere, hold a persona's turn by submitting a gated operation to the same serializer the code under test uses (`f.serializer.run(key, …)` in `makeBringUpFixture`, the fixture's serializer in `tests/persona-lifecycle.test.ts`), never a stand-in lock.
- **The accepted real-timer exceptions.** `initRestart` (`src/restart.ts`) takes no clock, so its timer is real wherever the restart module runs. The restart-module cases in `tests/persona-lifecycle.test.ts` set `getRestartDelay` to 0.001 s (a real 1 ms `setTimeout`) and wait for it with a 1 ms-step poll capped at 2 s; only those cases poll in real time, and every other case there flushes continuations or uses the fake clock. `tests/restart.test.ts` waits for its short restart timers with `Bun.sleep(WAIT_MS)` (50 ms) throughout, as it always has, and its `RestartDeps.serialize` cases follow that pattern. Don't add a real timer anywhere else.
- **Teardown tests check every piece of state.** Assert the teardown's full ordered trail for the removed key (bring-up cancel, restart timer, launch in flight, connection, routing, destinations and hold, notifier, poller prompts, session drop, kill and delete, outage state, failure counts, disconnected streak, reply guard and launch pass) and that no step ran for another persona. A new per-persona state gets its forget in that trail and a test in its module's suite that drops only the removed key.
- **Hold notices on a fake clock.** A teardown or apply test that can hold a notice uses a destination hold on `createFakeClock()` (see Destination Failure Tests), and asserts a held notice for the removed persona is cancelled, its timer gone.

Rules for reload tests:

- **Use the harness.** Build every SR-8.1 path through the harness (`h.paths`, `h.persona`, `h.write…`), never by joining `config.json.pending`, `.apply` or `.last-applied` onto a directory by hand. The harness keeps each path under its temp root and refuses one outside it.
- **Manual ticks only.** Drive detection with `run.ticks.tick()` / `ticks(n)`. Never use real timers, `sleep` or a timer-backed tick driver; bring-up retries run on `run.clock`, and advance only when the test moves it, so they never mix into a stretch of ticks. One exception: the test that shows the first check comes 5 s after `startDetection` passes the production driver on the run's fake clock through `opts.tickDriver` (a factory returning `createReloadTickDriver` over the `clock` and `log` it is given) and moves `run.clock`; it never uses a real timer. Every other reload test drives ticks by hand.
- **Assert effects through the recorder.** Which personas were brought up, launched, torn down, reconnected or updated in place, and with what outcome and class, is read from `run.lifecycle`, and file effects from `run.writes`, `run.removes`, `h.readRecord()`, `h.readConfig()` and `h.configDirEntries()`. Don't stub `ReloadLifecycleOps` by hand.
- **Detection applies nothing.** A detection test takes a checkpoint before the edit and asserts `run.since(cp)` in full: `NO_RUN_ACTIVITY` when nothing should happen, or `NO_RUN_ACTIVITY` spread with only the expected pending-file write or delete and log lines. At the least, `run.since(cp).lifecycle` is `[]`, which is how a test shows a tick made no lifecycle call (AC 55).
- **Held states come from the harness.** Put a persona in `retrying` or `broken` with `SLACK_UNREACHABLE`, `SLACK_AUTH_REJECTED` or a credentials or directory fixture, and revert a credentials edit with the function `h.saveCredentials` returned. Compare held content through `h.credentialsDigestOf` and `run.bringUps.credentialsDigest`, never by printing a digest or reading a token.
- **Fake tokens only.** Credentials files come from `h.writeCredentials` (sentinel-bearing fakes, rotated on each call) or `h.writeCredentialsContent`; a hand-shaped file that holds a token builds it with `fakeToken`.
- **Paths explicit, temp dirs only (b.av2 SR-13.2).** Pass every path explicitly and keep every file under the harness's `mkdtempSync` root. Never read or write `~/.claude/channels/slack` or `~/.agent-director`, never let a path resolve to the real home, and never start a server or run the CLI against the real HOME.
- **Leak-check every run and assert no Slack post.** Call `assertNoLeak(run.captured())` for each run in every test, failure paths included, so the logs and reload files carry no token. Every detection test also asserts that `run.slackPosts()` is empty for each run, so no reload output reached Slack (b.av2 SR-7.2); `tests/reload.test.ts` wraps both in `expectNoPostNoLeak(...runs)`. `captured()` includes only files the run's writer wrote that still exist, so to check the pending file's content, call it while the file is there. A test-written file holding `LEAK_SENTINEL` (a malformed config with a pasted fake token) is left out of `captured()` on purpose; a test that checks what the code wrote passes it through `writtenFile` itself.
- **Clean up.** Call `await h.cleanup()` in `afterEach`; it stops every run (detection included) and removes the root. A test that must show no timer is left calls `await run.stop()` and asserts `run.clock.pendingCount()` is 0.
- **Permission cases use seams.** Record and pending-file write failures go through `h.failWrites`, pending-file delete failures through `h.failRemoves`, an unreadable file through `h.replaceWithDirectory`, `h.makeCredentialsUnreadable`, `opts.configFs`, `opts.credentialsFs` or `opts.bringUpFs`, never through file modes, so the suite passes as root.
- **Real FIFOs run in a child process.** A case that puts a real FIFO at the config or a credentials path (`h.makeFifo`) builds its harness inside a child `bun` process with a 10 s bound and asserts the child was not killed (see Credentials Fixtures and Leak Checks). In `tests/reload.test.ts` every such case goes through `runHarnessInChild(body)`, which runs `body` over a harness under the test's root, bounds the child, asserts it exited cleanly and returns the one JSON line it printed with its stderr; the case then checks from that result that nothing reached Slack (no Slack call, or no lifecycle record or write on a refused start) and runs `assertNoLeak` over it.
- **Use the reference file's helpers.** In `tests/reload.test.ts`, `running(names, opts?)` is a server running `names` from a byte-equal record and config file with detection started and its first check run (`opts` goes to `h.startDetecting`). `pendingWritten(logs?)` and `pendingRemoved(logs?)` are the `run.since(cp)` of a stretch that wrote or removed the pending file once with its log lines; by default `pendingWritten` builds the expected log from the pending file itself (`loggedPreview()`: each body line classed `reload-preview`, the header ending with the pending-file suffix), so the logged preview must be the file's body line for line. `previewHeader(counts)`, `NO_EFFECTIVE_CHANGE_PREVIEW`, `invalidPreview(error)` and `invalidLogged(error, written?, pendingFile?)` are the expected header, no-effect preview, INVALID body and `reload-invalid` line; `loggedPreview(lines?, written?, pendingFile?)` and `invalidLogged` point at `h.paths.pending` unless given another pending path (a child harness's, which the FIFO cases' child prints). `personaRef(name)` is how every preview line names a persona, and `removedLine(name)`, `destructiveLine(name, setting, path)` and `addedLine(name, causes?)` are a removal's, a destructive path change's and an addition's line; `credentialsChangedLine(persona, effect?, cause?)` is a credentials line by persona and path, with `effect` one of `reconnect` (the default), `kept`, `retry`, `bring-up`, `stays-broken` or `unchecked` (the bring-up state could not be checked); a `cause` gives the "but it cannot be used (<cause>)" form, required for `kept` and `stays-broken` and refused for `reconnect` and `bring-up`; and `credentialsChangeLines()` the pending preview's credentials lines. A line these helpers don't cover (an in-place change, say) is asserted on the tick path by the header's counts, its wording left to the pure tests. Pin a pending-file write or delete failure line with `fileFailureLine(code)`, which matches the `[slack] reload:` prefix, the pending path and the errno code, not the sentence; a line whose wording another task owns is matched by its prefix or its class only.
- **Confirm through the harness.** Make the operator's gesture with `h.confirm()` and any other apply-path content with `h.writeApplyBytes`; never rename or write `config.json.apply` by hand. Make a confirmation undeletable with `h.failRemoves`, a record write fail with `h.failWrites`, and an oversized file with `h.writeOversized`.
- **An apply test shows the untouched persona is untouched.** Assert that a persona the confirmed change does not touch gets no lifecycle record (`run.lifecycle`), Slack client or Slack call from the apply. Assert the apply's step order and effects through recording `opts.applySteps` bodies and `run.appliedConfigs` / `run.appliedKeys()`, not by stubbing the controller's internals.
- **Step order through the default fan-out uses the timeline.** A test of what a confirmed change does to the personas runs without `opts.applySteps` and asserts step order through `run.lifecycle.timeline`, holding a call with `run.lifecycle.hold(op, key)` to show the next step waits for it. Record `opts.applySteps` bodies only when testing the step runner itself (step inputs, failures, order of the six slots). Assert the exact lifecycle records for the changed personas and none for any other, and use `opts.realLifecycle` when the case is about the teardown or bring-up body (agent-director calls, dependency order).
- **The token environment is poisoned, not read.** To show an added persona's tokens come from its file, call `h.poisonTokenEnvironment()` and assert no read is added to its `reads` over the apply and no Slack client got its values; never set the variables by hand.
- **Preview wording is pinned in the pure tests.** Every sentence of the preview is pinned in `tests/reload-preview.test.ts`, against `src/reload-plan.ts` with facts injected as data. A tick-path test in `tests/reload.test.ts` asserts the pending file's lines and compares the logged preview with the pending file (`pendingWritten()`, `run.lastPreviewText()`), rather than re-pinning every sentence.
- **Assert each preview line kind exactly.** A preview test asserts each SR-8.4 line kind by its exact line or its exact prefix or keyword: the counted header (`previewHeader`), `DESTRUCTIVE:` (`h.pendingDestructiveLines()`), `INVALID:`, `no effective change`, the credentials line by persona and path, and an added persona's causes. Showing only that some text exists, or that the file is non-empty, is not enough.
- **Assert the log carries the same preview once.** Compare the whole emission, not a line count: `run.since(cp)` equal to `pendingWritten()`, one emission per pending-state change (`run.previewEmissionCount()`), and none for a rewrite caused only by a changed fact. An INVALID candidate logs exactly one `reload-invalid` line and no `reload-preview` line.
- **Leak-check previews that involve credentials.** Whenever a credentials file is involved (a rotation, a held state, an added persona's credentials cause), run `assertNoLeak(run.captured())` while the pending file still exists, so both the file and the log are checked. In the pure tests, `render()` does this for every rendered form.
- **A new config field fails the coverage test until it is classified.** `tests/reload-plan-coverage.test.ts` holds the loader's key lists in `src/config.ts` against the plan's setting classes. A key added to the loader fails it until the key is in exactly one class in `src/reload-plan.ts` (a new server-wide key also needs a row in `CHANGED_VALUES`, a new channel-entry key an entry in `CHANNEL_FIELD_SETTING`) and has a preview line in `tests/reload-preview.test.ts`. Put a field in `UNCOMPARED_PERSONA_FIELDS` only when its change genuinely has no effect; never loosen the test to make it pass.
- **No lifecycle call before confirmation.** A preview test shows the tick applied nothing: `run.since(cp)` in full, or at least `run.since(cp).lifecycle` empty, so there is no reconnect, bring-up or teardown before confirmation (AC 67), and a broken persona stays broken (AC 65, preview half).

Test `durableWriteFileSync` and `durableUnlinkSync` themselves in `tests/atomic-write.test.ts` through their `DurableWriteFs` seam, the production tick driver in `tests/reload-timer.test.ts` on `createFakeClock()`, the fingerprint and pending-file layout in `tests/reload-fingerprint.test.ts`, the change plan and the preview's wording in `tests/reload-preview.test.ts`, which class each config key lands in in `tests/reload-plan-coverage.test.ts`, and parsing and validation of the config bytes in `tests/config.test.ts`; `reload.test.ts` asserts what a start and a detection tick do with them. Where `server.ts` starts and stops detection is a source audit in `tests/reload-wiring.test.ts`, since `main()` can't run in a test.

### Process-Level Listeners

`bun test` runs every file in one process, so a listener added to `process` is process-global state, with the same hazard as `mock.module` (see Module Mocks). A leaked `unhandledRejection` listener would change how every later file handles a stray rejection.

- **Call the handler, don't install it.** Tests call the exported `createUnhandledRejectionHandler(log)` result directly with each rejection reason. The `unhandledRejection handler (SR-3.3)` describe block is the reference. `bun test` already fails on an unhandled rejection, so no test needs a handler of its own.
- **Run code that rejects unhandled in a child process.** When the case under test is itself an unhandled rejection (a throw inside a fire-and-forget tick), run it in a child `bun` process through `runInFakeHome` and have the child count rejections with its own listener and print the result, as the `a throw while a persona's retry is due leaves it retrying` describe block in `tests/permission-poller.test.ts` does.
- **Remove what you add.** A test that must register a process-level listener removes it in `afterEach`. No test leaves one installed. A spy on `process.exit` is restored in `finally`.
- **Check import side effects by count.** To show a module installs no listener at import, compare `process.listenerCount('unhandledRejection')` before and after a fresh import, as the `connection manager: no module-scope effects (SR-13.1)` describe block does.
- **Leak checks still apply.** Every log line the handler produced passes through `assertNoLeak`.

### Parametrization

When 3+ tests follow the same structure with different inputs, collapse them with `test.each`:

```typescript
test.each([
  ['', 'empty string'],
  ['no-prefix', 'missing type prefix'],
])('rejects invalid id %s (%s)', (id) => {
  expect(() => validateId(id)).toThrow()
})
```

Don't wrap simple domain strings in constants (`const STATUS_OPEN = 'open'`) — inline them. Constants earn their keep only for complex formats or values used in 5+ places.

### State Reset

Use `beforeEach` to reset module-scoped state between tests:

- Registry: `_resetRegistry()` (exported from registry.ts)

### Module Mocks (mock.module)

**The hazard.** `bun test` runs every test file in a single process. `mock.module(...)` patches the module registry at the process level — it is process-global state. A top-level `mock.module(...)` call fires at import time and is never cleaned up, so the patched module leaks into every subsequent test file that imports the same module. If the mock factory omits an export that a later file imports, the later file crashes at runtime.

**The b.b8s incident.** A top-level mock in one file replaced `child_process` with only `{ spawn: fakeSpawn }`. A later file did `import { spawnSync } from 'child_process'` and failed with:

```text
SyntaxError: Export named 'spawnSync' not found in module 'node:child_process'
```

The root cause and class-of-bug fix are tracked in bugs b.b8s and b.5wd.

**The rule.** Every `mock.module(...)` call must live inside a `beforeEach` or `beforeAll` block, paired with a matching `afterEach` or `afterAll` that calls `mock.restore()`. Never call `mock.module(...)` or `mock.restore()` at file top-level. This includes calls inside a `describe(...)` body but outside hooks — those run at import/registration time and leak the same way.

**Don't:**

```typescript
// BAD — top-level, leaks into all subsequent test files
mock.module('child_process', () => ({ spawn: fakeSpawn }))

describe('MyTest', () => { ... })
```

**Do:**

```typescript
import { mock } from 'bun:test'

describe('MyTest', () => {
  beforeEach(async () => {
    // Spread the real module so later imports get all original exports unchanged
    const real = await import('node:child_process')
    mock.module('node:child_process', () => ({ ...real, spawn: fakeSpawn }))
  })

  afterEach(() => {
    mock.restore()
  })

  test('uses fakeSpawn', () => { ... })
})
```

**Fake children must behave like real ones.** Under Bun 1.4, `mock.restore()` does not undo `mock.module`, so a `child_process` fake stays installed for later files. A fake `spawn` must return an EventEmitter-like child (`on`/`once`, `stdout`/`stderr` streams, `unref`, `kill`, `pid`) that emits `exit` and `close`. Prefer injection over a module mock: the CLI's daemon spawn is a `CliDeps` seam (`spawnDaemon`), so CLI tests pass a fake child there and need no `child_process` mock.

**Enforcement.** `scripts/check-no-toplevel-mock-module.ts` runs as part of `pretest`. It scans all files under `tests/` and fails the test run if any line at column 0 (zero leading whitespace) contains `mock.module(` or `mock.restore(`.

### Throwaway Git Repos

Fixtures that create a throwaway git repo and commit in it use one canonical setup: declare a repo-local `identity.account` plus a neutral `user.name`/`user.email`, and wrap each commit in a retry-once. Reference implementation: `tests/publish-promote-bun-g-cwd.test.ts`.

```typescript
git('config', 'user.name', 'Test')
git('config', 'commit.gpgsign', 'false')
git('config', 'identity.account', 'work')
git('config', 'user.email', 'fixture@example.com')
...
try { git('commit', '-q', '-m', 'init') } catch { git('commit', '-q', '-m', 'init') }
```

**Why the retry.** The host's git identity hook blocks a config-sourced `user.email` mismatch exactly once: it rewrites the repo-local `user.email` to the resolved identity and tells you to re-run. The second attempt passes. On hosts without enforcement the first commit succeeds and the `catch` is dead code — harmless either way.

**Do not bypass enforcement.** No `core.hooksPath` redirects, no `--no-verify`, no `GIT_AUTHOR_*`/`GIT_COMMITTER_*` overrides. The hook staying active in fixtures is deliberate — these commits are the suite's only incidental exercise of the identity hook, so they double as its canary. Disabling it there would make the suite demonstrate the very technique b.q53 was told not to use, and would hide any future change in the hook's behavior.

### Self-Contained Test Servers

Test an HTTP endpoint through its real handler module, not a copy of its logic. `/interject` is the reference: `tests/interject.test.ts` imports `handleInterject` from `src/interject.ts` and injects its dependencies (a persona config from `makeMultiPersonaConfig`, stub sessions keyed by persona key, a fixed clock, a capturing logger). When a case needs a real HTTP request, (the 32 KB cap and a loopback delivery), it serves the real handler from a port-0 `Bun.serve()`. When logic still lives in `server.ts`, move it into an importable module. Its exported helpers can be imported directly (see Importing server.ts above), but the `/mcp` fetch handler is built inside `main()` with `Bun.serve`, which no test may run, so a stand-in server remains the way to test that branch until it moves (`sse-timeout.test.ts` mirrors the MCP GET/POST branch this way). Prove `server.ts` delegates to the handler with a source-text audit (see server.ts wiring above).

A stand-in `/interject` server is still the right tool when the code under test is an HTTP client of the endpoint: `cron-dispatch.test.ts` records the dispatcher's POSTs and scripts its responses. `cron-scheduler-interject.test.ts` instead serves the real `handleInterject` on port 0, so a scheduler fire is checked end to end through the real handler. For any `Bun.serve()` in a test:

- Bind to port 0 (random available port) to avoid conflicts
- Share Maps between test code and server handler via closure
- Stop the server in afterAll()

## Assertions

- Use `expect(x).toBe(y)` for primitives
- Use `expect(x).toEqual(y)` for objects/arrays
- Use `expect(x).toBeUndefined()` / `toBeDefined()` for presence checks
- Avoid `.toBeTruthy()` / `.toBeFalsy()` — be specific about expected values
- When testing async behavior through closures, use non-null assertions (`resolved!`) if TypeScript narrows incorrectly

## What to Test

- Happy path for each public function
- Error cases (invalid input, missing data, API failures)
- Edge cases from the SRD/PRD
- Concurrent operations (e.g., multiple pending requests)
- Cleanup on abort/disconnect
- State isolation between tests (no leaking via module-scoped Maps)

## What NOT to Test

- Internal implementation details (private helper functions)
- Exact log output (test behavior, not logging)
- Timing-dependent behavior with real delays — inject the clock and timers (see Backoff and Retry Tests); older suites use short configurable timeouts
- Test infrastructure itself (factories, stubs, reset helpers) — if a fixture breaks, the real tests that use it will fail anyway

## Keeping the Suite Lean

The goal is good coverage with as few lines of test code as possible. Apply the 80/20 rule: strong coverage of behavior does not require testing every input permutation — don't gold-plate.

- Test behavior, not implementation: assert on what a function produces (return values, state changes, captured calls), not on how it got there. A test needing 3+ stubs to run is usually testing implementation details and will break on harmless refactors.
- Prefer removing a redundant test over keeping it "just in case"
- Prefer `test.each` over copy-pasted test functions
- Prefer factory functions over repeated inline setup blocks
